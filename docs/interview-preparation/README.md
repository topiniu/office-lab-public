## 一句话：这个项目到底是什么

**office-lab（「望子成龙小学」）是一个把「一支有职责分工的 AI 数字员工团队」跑成真实软件交付流水线的自研编排工作台。** 六个角色 agent（PM / 全栈开发 / QA / 教导主任 / DevOps / 巡视员）在同一个真实企业代码库上工作，靠**仓库里的 Markdown 文件**做状态总线，靠**收工汇报里的机器标记**做交接，由一个 8770 行的 Node 引擎负责会话生命周期、自动接棒、健壮性自愈、权限三名单、质量硬门禁、以及企微/飞书渠道。

它**不是** MetaGPT/ChatDev 那类「一句话生成一个 demo app」的一次性生成器，也不是 LangGraph 那样的通用编排框架。它的独特点是：**持久任务档案 + 人在环门禁 + 面向真实生产仓库的交付**，而这三样的组合在开源界没有成熟对标。

## 项目事实分层（讲解时必须区分）

| 层次 | 含义 | 表达方式 |
|---|---|---|
| **已实现** | 代码 + 单测 + 真机跑过，可指到文件行 | 「当前实现了……」 |
| **半实现 / 有入口** | 有协议或局部能力，闭环不完整（常因外部依赖未上线而 fail-closed 降级） | 「已经有……基础，仍缺……」 |
| **规划中 / 提案** | 只在设计文档或路线里出现，明确标注未落地 | 「下一步会……」 |

### 典型边界（已按 0.10.0 核对）

**已实现**：
- 引擎：Agent SDK 常驻流式 `query()` 多轮热推（对齐 5 分钟 prompt 缓存 TTL）、watchdog judged-dead 自愈、空转熔断（双判据：SDK 自催次数 + 零产出轮次）、后台任务可观测与自动接棒、跨线程「待处理队列」、只读咨询窗（零写能力并发窗）、会议室（一次性隔离 query）。
- 编排：`【下一棒】/【交回】/【等你拍板】/【教训】` 四标记 + `cc_colleague` 抄送原语（fire-and-continue）+ 服务端强制守卫（深度/自环/回发/扇出/线程预算）。
- 门禁：QA 覆盖率硬闸（facet 为一等可追溯单元，五态语义，`COVERED_GREEN` 禁手填、只能由引擎从真 summary 机读签发，证据绑 runId/testHash/summaryHash/commit）、有效性 linter（DB_FISHING / NO_ACTION / PRESENCE_ONLY）、facet_doc 生命周期 fail-closed 门禁、发布四件交付物机器核对、收工即校验（缺标记当场拒收）。
- 守航（无人值守）：契约签发、三红灯台账（越权/超预算/假绿，含 `unverified` 第三态）、门禁矩阵（机器定级压过人填 risk_class）、发布链七环对账、park 台账分家、版本级晨检验收单。
- 渠道：企微 Python sidecar 长连接 + 主人格端点（防抖攒批 / 读图 / zip 批量投喂 / KB 按人限额）、飞书多维表格直连客户端（自动翻页 + 双向对账 + 降级熔断）、企微智能表格只读镜像（自适应二分批量写）、Bark 手机推送 + Windows 托盘原生通知与悬浮窗。
- 工程：`app/paths.js` 三层路径语义（monorepo 嵌套 / 独立 clone 双形态）、跨平台一条命令首启 `scripts/bootstrap.mjs`（含仓库完整性自检）、449 条单测（纯函数 + 依赖注入，不启 server）。

**半实现 / 降级态**：
- 猪猪（vision-e2e）v1.5 的四个新接口（`verify_evidence` / `report-card` / `preflight` / `get_env_fingerprint`）**lab 侧消费点已写好并有单测**，但**接口本体尚未全部上线** → 全部走 fail-closed，结论写「未验证」而不是「通过」。因此 `guard.fake_green` 只算了引擎自己能算的那一半。
- RED 校准判据：有 `failureClass` 走结构判据，拿不到时**仍退回标题正则**并标 `redBasis=title-regex`（降级留痕，不是已完成）。
- 需求巡航（A1）：`pool_scan` 工具 + 聊天窗一键按钮已有，**没有「闲时自动跑」的调度器**。
- worktree 隔离：只做了 `worktreePlan`（算出该开哪些树），**没做自动 `git worktree add`**。
- 企微智能表格当主表：代码全通、表已建出、写入实测成功，**因「搜索与获取文档内容」能力授权未批下来而降级搁置**，需求表仍以飞书为准。

**规划中 / 提案（勿说成已实现）**：
- 「全时双态协作」的完整状态机（14 状态）、快车道任务分级、薄派发器/工作胶囊、条目级 worktree 真并行、跨机调度、macOS 常驻（launchd + 菜单栏）、多用户/权限/数据库化归档。

> **讲并发时务必说清并发单位**：跨员工的 run 可以真并发（`liveRuns` 是 Map，`busyRunFor` 只挡「同一员工开第二条可写会话」）；同员工**不并发**，跨线程来消息走「待处理队列」串行排空。这是**刻意的**——所有 run 共用一个工作树、没有 worktree 隔离，同员工两条可写会话必然互相踩写。只读咨询窗因零写能力而豁免这道闸。

## 这个项目最值得讲的五条主线

按「技术含量 × 别人讲不出来」排序：

1. **「把布尔判断托付给模型的措辞」是一族根本性缺陷，并且复发了四次。**
   `【等你拍板】` 一写就买断三道防线（§3.84）；写了 `【交回】` 标记就被巡视当合法收尾放行而实际从没投递（§3.81）；空转闸的判据挂在「SDK 恰好会说的一句话」上、上游改成静默重发后整条静默失效（§3.101）；巡视员的升级因只写白话被降噪守卫吞掉、还顺手盖上「已裁决」封存签名（§3.101 坑二）。**结论沉淀为一条设计原则：判据要挂在本层能直接观测到的事实上（这一轮有没有产出 text/tool_use），而不是别人给的信号；凡把布尔判断托付给措辞的地方，引擎侧必须留一条不依赖措辞的旁路。**

2. **QA 可信度经历了四代范式转移，最后一代是「放弃让 AI 审 AI」。**
   加红线（无效）→ 新建一个同质 QA（它给假绿盖了章）→ 建对抗审计员菲斯拉（她太会讲道理，接受了自洽说辞）→ **把判定移出 LLM，变成确定性 if/else**（覆盖率闸门 + 有效性 linter + 机器证据血缘 + 取消 LLM 最终放行权）。老板那句「菲斯拉改成机器门禁，那不就是 if/else 吗？」正是要点——最可信的质检（编译器/类型检查/CI/断言）全是 if/else，正因它蠢、确定、不讲道理，才不可能被说辞绕过。v2 上线当天把 v5.17 的历史矩阵重算成 34/34 gap、`qa_passed=false`：**宁可诚实全红，不兼容历史假绿。**

3. **「SOP 是软约束、工具与门禁才是硬约束」，并且有十四轮 A/B 对照数据。**
   §3.106 把迷糊的十四轮增强史列成表：凡改成机器判定/工具契约的（覆盖闸门 / linter / 硬闸 v2 / facet 门禁 / `run_e2e_batch`）都稳住了；凡写进 SOP / 加红线 / 改派工文案的都会被下一轮压力压穿。**更狠的一层**：最后一轮发现连「软约束失效」都不是——她**够不到**那些能力（zhuzhu base 存成已死端口 → 18 个 MCP 工具静默全缺），而系统还在骗她说「平台没做」（我方猜错端点路径，404 被记成「对方没实现」，假事实沉淀两周）。由此得出**加规则前的三问**：机器答案存不存在？够不够得到？够不到时会不会如实说「我不知道」？

4. **性能与可靠性问题几乎全是「只治了看得见的那半边」。**
   §3.47 治静态资源压缩/缓存/缩图，半年后 §3.83 发现 API 走的是另一个出口 `json()`、一律不压缩（`/api/runs` 3586KB 明文），同一类浪费原样复现；`REPLAY_TAIL` 只截行数、被「行少但每行 606KB base64」绕过；`env(safe-area-inset-bottom)` 在浏览器态常报 0，于是用 `100lvh - 100svh` 自校准悬浮底栏高度。**沉淀的方法论：横切策略（压缩/缓存/限流/轮询）的落点必须是唯一出口，不能是「当前看到的那几个分支」；隧道/弱网是放大镜，内网无感 ≠ 没问题。**

5. **对第三方集成，「方言」比「接口签名」更容易致命。**
   企微镜像四修才通：限流（45009）→ 批量 → 一行坏拖垮整批（40058）→ 顶层键 `records`→`add_records` → **最终真根因是整个请求体用错了方言**（webhook「接收外部数据」用 FIELD_ID + 无 `key_type` + 纯文本值；access_token API 用字段标题 + `key_type` + 类型数组）。而这期间还叠了一个更荒诞的事实：**修好的代码从没重启生效**，老板对着旧进程点了好几天。由此两条铁律：**「改了代码 ≠ 代码在跑」，验证第一步是翻日志看真实请求体属于哪一版**；**权限模型比接口签名更值得先问清**（企微 wecom-cli 那次撞的是「能力按项授权」，`create` 通而 `list` 不通）。

## 回答质量自检

- 是否先讲**协作问题**，再讲技术方案？（这个项目的技术都是被协作事故逼出来的）
- 是否能指出一个真实代码入口或产物，而不是只讲概念？
- 是否说明了**取舍**和**残留面**？（每条对策都要能说出「它救不到什么」）
- 是否把「写进 SOP」和「做成门禁」区分开？
- 是否把「机器 GREEN」和「真的没有缺陷」区分开？（v5.19 17/17 全绿，两个真缺陷都是老板手工用出来的）
- 是否把「未验证」和「通过」区分开？（fail-closed 第三态是 0.10.0 最重要的一条设计决定）
- 是否避免把「提案/设计文档」说成已落地？（全时双态的完整状态机仍是提案）
- 是否能说清自己的决策路径，包括**判断错过的地方**？（testid 契约门禁那一刀砍在只占 3% 的靶子上，是自己撤回的）
