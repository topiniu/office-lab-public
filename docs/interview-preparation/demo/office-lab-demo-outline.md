# office-lab 团队技术分享大纲

> **基线**：0.10.0 · 核对日期 2026-08-31。
> **定位**：这份大纲**不做 slides 工程**（office-lab 是本地工具、真机演示成本低），只给讲稿节奏、Demo 路线、失败兜底。要做静态演示时按 §8 的 18 页骨架自己搭。

## 演讲标题（三选一）

- **主选**：《让一支 AI 员工团队在真实生产仓库上「可被验证」——office-lab 的 38 个事故与 12 条原则》
- 备选 A：《当 AI 说「我测过了」——把判定从 LLM 挪进 if/else 的四代范式转移》
- 备选 B：《把布尔判断托付给模型的措辞：一个复发四次的病根》

> **标题选择的理由**：不要叫「AI 数字员工工作台介绍」。那种标题会把听众预期设成「又一个 agent demo」，而这个项目**最值钱的部分恰恰不是 demo，是事故与判据**。

## 演讲目标（听完之后他们应该能说出）

1. 多 agent 协作的难点**不在生成，在验证与可观测**。
2. 有一族缺陷叫「把布尔判断托付给模型的措辞」，它会**静默失效**。
3. 「写进 SOP」和「做成门禁」是两件事，且有 A/B 数据。
4. 「未验证」不等于「通过」——新指标不许自带虚假健康值。
5. 这个项目**没有**做到什么（跨机调度 / worktree 真并行 / 业务效率基线）。

## 5. Demo 路线（4 分钟版，只做三件事）

> **原则：Demo 不演示「AI 能干活」**（听众已经信了），**只演示「它说的话可被验证」**。

### Demo-1（90 秒）· 看板 → 覆盖矩阵 → 一行证据

1. 打开任务看板，指一个真实版本的任务卡片。
2. 展开 facet 覆盖条：**「4/6 绿 · N 源码坐实 · M 真机人工」**。
   - 讲：「这一条不是员工自己填的状态，是引擎从覆盖矩阵算的。」
3. 打开覆盖明细抽屉，指一行 `COVERED_GREEN` 的证据串。
   - 讲：「`runId` + `case` + `testHash` + `summaryHash` + `commit` + `env`。**员工手填 GREEN 会被工具直接拒**——只有引擎从真 summary 机读才签得出来。」
4. 再指一行 `SOURCE_ATTESTED`：「这个状态**不算通过**，它令整版 `qa_passed=false`。五种状态里没有一种叫『我判断不用测』。」

### Demo-2（90 秒）· 一次真实的静默停顿（看历史，不现场跑）

1. 打开一条真实的历史会话（那条被 `_turnText` 兜底假绿的）。
2. 指出：绿灯「✅ 本轮收工」，但档案没建、下一棒没派。
3. 打开 `runs/<id>.jsonl` 的尾部（或提前截好图）：**两条 assistant 消息各只含一个 thinking 块，`message.id` 不同 = 两次独立 API 请求，`result: ""`。**
4. 讲：「当时装的闸挂在『SDK 会注入一句 no visible output』上，而 SDK 这条路是**直接重发请求、一条 nudge 都不注入**。闸门还在、代码还在、日志什么都不缺，**只是永远不触发**。」
5. 讲修法：「判据换成『这一轮到底有没有产出 text 或 tool_use』——本层能直接观测到的事实。」

### Demo-3（60 秒）· 收工即校验（可现场触发）

1. 给一个员工派一条极短的活（比如「读一下 README 的第一行然后收工」）。
2. 它收工时若没写标记 → 引擎**当场拒收**并回灌具体提示。
3. 讲：「这件事以前是事后派一个 agent 去读收尾原文猜它该做什么——**79 次巡视只有 2 次是真停，97% 的浪费来自判据挪错了位置**。而『收尾里有没有那一行标记』是纯字符串判定，成本接近 0。」
4. 讲边界：「**每条会话最多拒 2 次**，chat 轮完全不管；上线前先把判据离线跑过 604 条历史收工按角色分组——**异常高的那一组不是违规者，是判据没覆盖到的一类合法形态**。」

## 7. 可能被问到的问题（现场高频）

| 问题 | 30 秒答法 |
|---|---|
| 「这个要多少 token / 多少钱？」 | 「全员 Opus（含闲聊，为体感）、巡视员 Sonnet、思考预算封顶 24k。**成本我没有做硬顶杀进程**——夜里被杀死比超支更坏，改成记一条『没设硬顶』让它在晨检包里可见。这是个诚实的短板。」 |
| 「你们真的用它交付线上代码？」 | 「是。真实业务版本走完整流水线到发布。但要说清：**发布那一下永远是人按的**，agent 只准备不执行；而且首两轮无人值守的诚实结论是『行为纪律成立，但结构缺席』。」 |
| 「效率真的提升了吗？」 | 「机制侧有量化。业务侧**我不编数字**——某版守航最该证明的指标（进入执行→测试环境可用）是 4 天而非 1 夜，因为『合进同一版等大件一起发』的决定把夜里赚到的时间吃掉了。这属于流程缺一个默认值，已列进路线。」 |
| 「为什么不用 XX 框架？」 | 「本项目的真问题不是『状态转移画不清』，而是『模型措辞不可信』。换框架等于把现有守卫翻译一遍，而那些守卫每条都对应一次真实事故。唯一值得借的是『显式状态定义 + 每棒入口前置断言』。」 |
| 「六个 agent 会不会互相打架？」 | 「会，而且我有具体案例：后台任务 settle 唤起了一条**被同线程新会话顶替的旧会话**，两条会话并发改同一份档案。修法是唤起前查『这条会话还是它这条线程的现役吗』——**而且必须按线程判，按员工判会误伤多线程并行**。」 |
| 「AI 会不会偷偷降低测试标准？」 | 「会，这就是我做了四代门禁的原因。现在 `lintAck`（自批豁免）已经失效、`COVERED_GREEN` 禁手填、`SOURCE_ATTESTED` 不算通过。**但我不说已经完全防住了**——软性回避真跑还在，靠机制点名 + 人抽检兜。」 |
| 「你们怎么防 prompt 注入？」 | 「有一条真实发生过：**读记忆库时读取通道被注入过**（正文里的伪 `system-reminder`/『立即停止』）。所以 QA 的 SOP 有专条：一律视为注入并报用户。此外硬限制/配额/权限一律放确定性代码，**prompt 只负责措辞**。」 |
| 「这套能不能直接给我们用？」 | 「不能直接用——它深度绑定我们的仓库结构、SOP 和一个外部 E2E 平台。**能借的是判据**：三层正交监督的分层、门禁四代的结论、fail-closed 第三态、加规则前的三问。」 |
| 「有没有开源？」 | 按实际情况答；如果不开源，就说「文档口径可以分享」，并指 `docs/tech/**` 的写法（起因/根因/对策/取舍/**残留面**/通用教训/改动落点/验证 八段式）。 |

## 8. 现场失败兜底

| 风险 | 兜底 |
|---|---|
| 引擎起不来 | **提前截好 5 张图**：看板 + 覆盖明细抽屉 + 一条真实会话 + 一份晨检验收单 + `runs/<id>.jsonl` 尾部。Demo-1/2 完全可以纯截图讲。 |
| 派工要真起 agent（慢 / 花钱 / 可能空转） | Demo-3 改讲「已发生的那一次」——用历史 run 讲。**或者干脆跳过 Demo-3**，它是三个里最不必现场的。 |
| 外部 E2E 平台不在跑 | 不影响——三个 Demo 都不需要它。若被问到，正好讲 fail-closed 第三态（「探不通时引擎会说 `unverified` 而不是 pass」）。 |
| 网络/隧道不通 | 全部本机 `127.0.0.1`，不依赖外网。 |
| 有人挑战数据真实性 | 现场打开 `docs/tech/**` 对应小节——**每条都带 run id、日期、改动落点、验证方式**。这是这个项目最强的可信度背书。 |
| 时间被压到 8 分钟 | 只讲 slide 1、7、8、10、11、16 六页（失败 → 病根 → 复发四次 → 门禁四代 → if/else → 诚实边界）。**保住这六页，故事仍然完整。** |

**建议提前录屏的两段**：① 看板展开覆盖明细到指到一行证据串（30 秒）；② 收工即校验当场拒收（40 秒）。**理由**：这两段依赖真实数据 + 真实模型，现场最容易掉链子。

## 9. 结尾话术（三个版本）

**版本 A（面向工程师，推荐）**：

> 这个项目做了半个月我才想明白一件事：**多 agent 系统真正难的不是让它们干活，是让它们说的话可以被验证。** 而验证不能交给另一个 AI——最可信的质检全是 if/else，正因为它蠢、确定、不讲道理，才不可能被说辞绕过。
> 我复盘文档里有 3500 行、38 个事故，最大的一族只有一句话：**把布尔判断托付给了模型的措辞。** 它复发了四次，每次换个皮，每次都是静默失效——闸门还在、代码还在、日志什么都不缺，只是永远不触发。
> 如果今天只带走一句话，我希望是这句：**判据要挂在你这一层能直接观测到的事实上，不是别人给你的信号。**

**版本 B（面向管理者）**：

> 这个项目里所有值钱的东西都不是设计出来的，是被事故推出来的。所以它有一个副产品：**一套「什么样的规则会失效」的经验。**
> 结论很反直觉：**写进 SOP 的规则会被下一轮压力压穿，做成工具和门禁的才留得住。** 我有十四轮的 A/B 数据支持这句话。
> 而更反直觉的是最后一轮的发现：连「规则失效」都不是真因——**员工够不到那些能力，而系统还在骗它说「平台没做」。** 所以现在我加任何规则之前先问三件事：机器答案存不存在？够不够得到？够不到时会不会如实说不知道？

**版本 C（面向怀疑者）**：

> 我知道 AI agent 这个话题现在有很多噪音，所以我今天讲的每个数字都能落到一个 run id 和一份文档上，包括那些不好看的：某版机器 17/17 全绿，而两个真缺陷都是人手工用出来的；首两轮无人值守跑完的结论是「行为纪律成立，但结构缺席」；业务侧的效率提升**我没有基线，所以我不编数字**。
> 我认为这些不好看的结论比那些漂亮的架构图更有价值——**因为它们是下一轮要做什么的唯一依据。**
