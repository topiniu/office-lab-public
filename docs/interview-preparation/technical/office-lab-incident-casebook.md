# 族 A：把布尔判断托付给模型的措辞

**族病根**：引擎需要一个布尔值（这一轮算不算收工？该不该派巡视？要不要惊动老板？），而它去问「模型在收尾文本里写了什么」。措辞可以缺、可以错、可以被上游换掉，于是布尔值静默失真——**而且失效方式是静默的：闸门还在、代码还在、日志上什么都不缺，只是永远不触发。**

> **这一族一共栽了四次**（A-2 / A-4 / A-5 / A-6），每次换个皮。最终收敛为一条设计原则：**判据要挂在本层能直接观测到的事实上，不是别人给的信号；凡把布尔判断托付给措辞的地方，引擎侧必须留一条不依赖措辞的旁路。**

## A-1 · 空 `result` 被当合法收工，静默死停

| 段 | 内容 |
|---|---|
| **起因** | 引擎从 v0.1 起认定「一轮以 `result` 结束就是收工」。 |
| **现象** | 菲菲一轮里 `Edit` 因 `old_string` 锚点过期报「String to replace not found」（任务档案 #13 那行被 GG Bond 回写扩写过），随后模型只产出空思考块便 `end_turn`。引擎 `onTurnComplete` 判 `done`、亮绿灯「✅ 本轮收工」、`appendLessons`、进 `autoChain`；而 `autoChain` 在空 `result` 里找不到任何标记 → 命中「既无下一棒也无交回=终止（安全默认）」→ **静默死停**。后果：需求说明落了盘，但登记表 #14 未加、未派 GG Bond，界面**一片成功收工的绿**，老板以为交出去了、实则卡半途。 |
| **根因** | 引擎兜的是**进程层异常**（连接中断/零字节/流中途抛错），这次暴露的是**模型层过早收手**——SDK 正常回了 `result`（`is_error:false`），但内容为空。「空 `result` 是合法终态」这个隐含假设从未被质疑。 |
| **方案** | 空 `result` → 直接置 `error` 终态。不绿灯误导、不 `appendLessons`、`autoChain` 不接棒；红灯 + 推手机。关键是 **run 立即回到可交互态（`/reply` 不再 409）**，把恢复节奏交回用户。 |
| **不完美** | 这一版**没治误报**——「其实说过话、只是结尾停在思考块」的合法轮也被一律判红灯（见 A-3）。 |
| **通用教训** | ① 本系统「每轮以收工汇报 + 标记结束」是硬不变量——**空 `result` 不是合法终态**。② 判「有没有真产出」**不能只看末尾 `result` 字段**（末块是思考/工具就为空），也不能只信 SDK 的 `is_error:false`。③ 长行文档/表格的 `Edit` 锚点极易因他人回写过期——员工侧稳妥做法是**先重读再改 / 对长行改用 node 就地写 / 改完独立核验落盘**（已写进三位写文档员工的红线）。 |
| **索引** | §3.3 |

## A-2 · `_turnText` 兜底把「反复自催空转」painted 成绿灯

| 段 | 内容 |
|---|---|
| **起因** | A-3 为治「误报」加的 `_turnText` 兜底：`result` 空但本轮有实说 `text` → 取那段文本当收尾、绿灯。 |
| **现象** | 老板翻一条会话——「现在开工，建档案派 GG Bond」那一轮**既没建成任务档案、也没派 GG Bond、更没写任何收尾标记**，界面却显示 **✅ 本轮收工**；追问「？」后又空转一轮。**且巡视员没抓到。** |
| **根因** | 逐日志定位：模型早期吐了句没用的一行（「明白，开工。先把档案建起来…」），**随后在 SDK 内部反复空转**——`claude.exe` 检测到「本轮无可见输出」，自注入 `[Your previous response had no visible output. Please continue…]` 逼它再说，模型又只产思考块，如此 ≥2 次。**真凶是 `_turnText` 兜底误开火**：那段 `text` 是**早期一句陈旧旧话、不是收尾**。三连恶果：① 空转被伪装成成功收工；② `_emptyStreak`（只在「真·空」时累加）被这假绿**每轮归零**，所以连着 2 轮空转也没触发升级；③ 空 `result` 里无标记 → autoChain 静默停。**两道守护都没救**：字节 watchdog 与本案无关（每个 turn 都正常收了 result、进程没冻）；巡视只在事发前来过一次、且这两轮被假绿成 `done` 且是 `chat` 类，不进候选池。 |
| **方案** | 引入一个 **100% 特异的空转信号——一轮内 SDK「no visible output」自催次数**（`run._sdkNudges`）。它只在「这轮真的没产出可见输出」时由 `claude.exe` 注入，正是空转铁证。给 `_turnText` 兜底加闸：本轮自催 ≥ `SILENT_SPIN_NUDGES`(=2) → 判空转 → **不许**用残留旧文本假绿。 |
| **不完美** | 判据挂在「SDK 恰好会说的一句话」上 —— **这颗雷两周后炸了**（见 A-4）。另：`selfChainMax` 兜不住「模型每轮写点没用的东西 + 自续」的非空空转。 |
| **通用教训** | **「兜底救误判」的补丁，本身要能区分「它要救的合法态」与「长得像但其实是病态的态」，否则就从『治漏报』变成『造新漏报』。** `_turnText` 兜底当初为救「结尾停在思考块的真收工」而生，却因为只看「有没有说过话」、不看「说的是不是收尾/这轮是不是在空转」，把「早期一句废话 + 反复自催空转」也一起「救」成了假绿——还顺手废了旁边的空转熔断。**判据必须落在能把两者分开的那个特征上。** |
| **索引** | §3.61 |

## A-3 · 「说了真话只是结尾停在思考块」被一律判红灯（A-1 的过度矫正）

| 段 | 内容 |
|---|---|
| **起因** | A-1 的「被动暴露」把静默治住了。 |
| **现象** | 菲菲从「接着聊刚刚的需求讨论」起连续多轮结束在思考块，其中若干轮**明明有完整 `text` ＋ 成功的 `lark_update_requirement`（数据已落库）**，却次次红灯；老板连点 4 次「继续」都在 resume 同一坏会话复现空收工，观感是「怎么都恢复不了」。 |
| **根因** | 「`result` 空 ≠ 没干活」这一类被一律判红。 |
| **方案** | 两条，**都严守「不假装成功、不自动接管」**：① **兜底取文本**——`beginTurn` 每轮清 `run._turnText`，`consumeStream` 累积 assistant 的 `text` 块，`result` 空白但本轮有实说文本时用它当 `run.result` 并注明「结尾停在思考块」。这只 surface **模型确实说过的话**，不是替它续跑。② **连续空转熔断**——`_emptyStreak` 只在真·空时累加；≥2 轮把文案升级为「已连续空转 N 轮、状态已坏，**请勿再回复『继续』**，直接新开话题/重新派工」，**把用户从死循环里主动劝离**。 |
| **不完美** | 兜底本身成了新的假绿源（见 A-2）。 |
| **通用教训** | ① 修 A 类（静默）后要回头收 A 类的「过度矫正」——正确姿势是**按「这一轮到底有没有对用户说话」分层**（有→如实展示、无→红灯）。② 别只把「反复空转就别续了」写成一句提示指望用户自觉——**该由引擎数着 streak 主动升级劝离**。 |
| **索引** | §3.3 |

## A-4 · 空转闸整条静默失效：SDK 改成直接重发请求，一条 nudge 都不注入

| 段 | 内容 |
|---|---|
| **起因** | 老板问「看一下这条会话，怎么中断了而且巡视没有巡视到」。 |
| **现象** | 会话尾部：`tool_use` Read 任务档案 → tool_result 返回 → **两条 assistant 消息各只含一个 thinking 块**（`message.id` 不同、`cache_creation` 8738→8767 只差约一个思考块的量，**这是两次独立的 API 请求**）→ `result` `subtype:"success"` / `is_error:false` / `result:""`。界面显示 ✅ 绿灯。 |
| **根因** | 它**是** A-2 那种空转，只是走了另一条路——**SDK 还有一条路：直接重发请求，一条 nudge 都不注入**。于是 A-2 装的闸（`_sdkNudges`）**恒为 0、形同虚设** → `_turnText` 兜底照常开火，取上一句陈旧文本「…先读它。」当收尾 → 绿灯。**这就是 A-2 修的那个「兜底假绿」原封不动地复发了一次，只不过绕过了当初专门为它装的闸。** |
| **方案** | **判据从「文本信号」换成「事实」**。新增 `barrenTurns()`——数本轮**零产出顶层 assistant 消息**（该 `message.id` 全程既没吐过 text、也没发起 tool_use = 纯 thinking）；`isSpunTurn()` 改为「`_sdkNudges` 达阈 **或** 零产出轮次达阈（`BARREN_TURN_LIMIT`=2），任一即判空转」。旧闸保留（它对它那条路仍有效），新闸补上它照不到的角。 |
| **不完美** | 三个实现细节任一错了新闸就变成新的误报源：① **必须按 `message.id` 归并**（SDK 把一条 assistant 消息按内容块拆成多次透传，按「每次透传算一条」去数会把**每一个「先思考后调工具」的健康轮次都记成空转**）；② **只数顶层消息**（子 agent 空转与本轮收尾无关）；③ **阈值必须 > 1**（单条纯思考正是 A-3 要救的那类）。顺带修掉一处旧疏漏：**SDK 后台 settle 后自动续跑的轮次不走 `beginTurn`**、计数器不归零，上一轮零产出会串到这一轮。 |
| **通用教训** | **「判据挂在哪」比「阈值调多少」重要得多。** A-2 的闸门本身是对的、阈值也校准过，但它把判据挂在**上游某个组件恰好会说的一句话**上。上游换了实现（改成静默重发请求），判据就整条失效——而且**失效方式是静默的**。判据应当挂在**本层能直接观测到的事实**（这一轮到底有没有产出 text/tool_use），而不是**别人给的信号**。 |
| **索引** | §3.101 坑一 |

## A-5 · 「写一条【等你拍板】」= 万能免检符：守航跑一夜 0 绿，三道防线全静默

| 段 | 内容 |
|---|---|
| **起因** | 老板发现迷糊一条守航态全量 QA 会话（约 2 小时）**15 个 facet 拿到 0 个机器 GREEN**（9 `BLOCKED_WITH_PROOF` + 6 `SOURCE_ATTESTED`），收工写「【等你拍板】晨检队列①②③④」正常收摊。老板原话：「我们新开发的托管模式，结果就是什么都推不动」。 |
| **现象** | 覆盖率硬闸没跑、菲斯拉没派、小呆呆没来，手机端一切如常。 |
| **根因** | **三层叠加，同一条标记同时买断三道防线**：① **引擎层**：`autoChain` 的 `if (parsePendingGate(run.result)) return`（门优先）位置在 QA 覆盖率硬闸**之前** → 闸门根本没算；闸门分支里挂着的菲斯拉连带没派；`patrolEligible` 又因 `parsePendingGate` 命中直接 `return false` → 小呆呆**根本没被叫醒**（不是判错了）。② **守航 preamble 层**：全是「怎么体面地停」，一条「必须干完」的正向压力都没有——rule 4「失败即安全停靠…不再自行换方案继续试」字面读就是「遇阻禁止换方案」，rule 7 的晨检队列恰好靠 `【等你拍板】` 落地，**等于把免检符发到每个员工手上**。③ **角色判据层**：「用例过时」被塞进了「合法收工」档——她已连修 4 处、跑到 46/47 步，却在最后一处停下报「用例对当前构建过时→阻断」，且**4 处补丁全留在临时脚本、一处没回写共享 macro 库**（下一个人撞同一堵墙）。同类还有两例「想到即弃」：她自己写下的绕行方案（捕获 workflowId 后同页跳转），一句「不易取」就 isolate 3 个 facet，**两小时后为别的事顺手两分钟就取到了**。 |
| **方案** | **三层同治**。引擎（治根）：`markQaHollowStop(run)` —— pending 门**仍然停流水线**（不自动接棒是对的），但「挂档案的迷糊 QA 收工」在 `return` 前**先把覆盖率算出来落档**（只算不放行）；未达标 → 盖持久签名 `qaHollowStopSig` + `qaHollowStopWhy`，`patrolEligible` 据此**不再因 `【等你拍板】` 豁免**。`spawnPatrol` 加「QA 空心停靠」**专属文案**——通用文案那句「既没交接也没待老板拍板」与事实不符，会把巡视导向误判「它明明写了啊」；新文案要求逐条分类「真需老板 vs 职责内的活包装成问句」，并点名三种典型形态。守航 preamble：rule 4 改写为「轮数上限**只约束同一方案反复重试**；换一条从未试过、能直接移除已确诊堵点的路径不计入上限」+ rule 4b「自己维护的东西过时＝自己的活，改完回写共享库」+ rule 7b「park 不是免检符」。 |
| **不完美** | **没有把 pending 门改成「不停流水线」**——有真待拍板事项时停是对的，**问题从来不是「停」，是「停了没人复核」**。所以只加一道复核，不动放行语义；也**没有对全员生效**，只管「迷糊 + 带任务档案」这一条有覆盖率可算的路径。**覆盖真达标 + 有待拍板 = 合法请示，照旧豁免**（别惩罚干完活才问的）。 |
| **通用教训** | 一条协议标记如果同时被多个机制当「跳过」条件读，它就会变成万能免检符。**审计任何「有 X 就跳过」的判断时，要把「谁在读 X」列全。** |
| **索引** | §3.84 |

## A-6 · 巡视员判了、升级了，但推送被降噪吞掉，还顺手盖上「已裁决」封存签名

| 段 | 内容 |
|---|---|
| **起因** | A-4 同一次排查的坑二。老板的体感是「小呆呆压根没巡」。 |
| **现象** | **小呆呆其实巡到了**，而且很及时——事发 16 秒后就派出，判定也合理（「对端就是老板本人在直接发问，按判据这种情况默认不续，留给老板决定」），还抛了一张 `decision` 卡三选一。但它正文只写了白话「无需我方动作，等你拍板。」，**没写标记行**。 |
| **根因** | 三连：① `parsePendingGate()` 返回 null；② `maybePushRunStopped()` 里那行降噪守卫（「巡视 run 除非以真门收尾否则不推」，当初为治「每条巡视都弹一次 toast」而加）**把整条推送吞了**——托盘 Toast、手机 Bark 一条都没发；③ 雪上加霜：`autoChain` 那条「巡视 run 收工且没 resume → 给目标盖 `patrolClearedSig`」同时生效，被巡目标被标记「这次停顿已裁决」→ **定时 sweep 也不再补刀**。净效果：**巡到了、判了、升级了，老板全不知情**，而且这次停顿被永久封存为「已处理」。 |
| **方案** | **宁可多推、不漏升级**。新增 `patrolEscalating()` 取代「只认严格标记」：规范标记 / `decision` 卡 / 白话请示正则任一命中即算升级、必推；推送的 `gate` 字段也给兜底文案。SOP 侧同步收口：红线新增「升级必须落标记行」（并明写「引擎已加白话兜底，但那是**保险丝不是许可证**」）。 |
| **不完美** | **一层反向护栏（自测当场抓到）**：必须先放过「显式写了 `【等你拍板】无`」的那类——那是协议里「合法收工·无需动作」的规范收尾。少了这层，兜底正则会把标记里「等你拍板」**四个字本身**当成白话请示，于是**每一条判合法收工的巡视都弹一次 toast**，降噪初衷当场作废。唯一例外：标了「无」但同时抛了 `decision` 卡 → 仍判升级。 |
| **通用教训** | ① **降噪与「不漏告警」是一对张力，缺省必须偏向不漏。** 凡是「靠下游正确书写某个格式才能触发告警」的设计，都要假设它有一天写不对——**兜底识别 + SOP 硬要求，两手都要有**。② **「已裁决」类的封存签名，必须与「老板真的被通知到」绑定。** 任何「不再重试/不再检查」的闭合动作，**前提是它闭合前那次输出确实到达了人。** |
| **索引** | §3.101 坑二 |

## A-7 · 写了 `【交回】` 却从没投递：fail-closed 把合法回发也吞了 + 巡视把「写了」当「执行成功」

| 段 | 内容 |
|---|---|
| **起因** | 老板发现迷糊一条会话收尾里 `【交回】菲菲`、`【等你拍板】无` 都写了，却既没真回到上游、小呆呆也没报异常；手机端显示「✅ 收工」如常。 |
| **现象** | 静默死停、无人发觉。 |
| **根因** | **两条叠加、互相掩护**：① **fail-closed 把合法交回一起吞了**。这条 run 从一条 **chat 线**闲聊经 `spawnForward` 一路漂下来，`taskFile` 沿链继承为 `null`（档案只在派工正文里被引用、从未落到结构化字段）。`autoChain` 判「真交回上游」→ 进 QA 硬闸，其首行 `if(!run.taskFile) throw` 抛错 → catch 走 fail-closed：**只 `appendEvent(⛔ 闸门计算失败)` 后 `return`**，`【交回】` **从未执行**。安全门禁「宁可拦死」的设计，把一次**没有覆盖率可算、本就不该被它管**的合法回发也拦死了。② **巡视因「结果里有交接标记」把它当合法收尾放行**——`patrolEligible` 里 `parseReturnHop(result)` 一命中就 `return false`，但**标记只是「写了」，autoChain 已在真正投递前 abort**。**标记的「存在」被当成了「执行成功」。** |
| **方案** | 三处：① **闸门不适用 ≠ 报错**：`_gateApplicable = !!run.taskFile \|\| _toBobby`。无 `taskFile` 且非「发波比（出货）」→ 闸门**不适用**，直接放行到正常回发，且**不**派菲斯拉（无档 = 非正式 QA 裁决、无从审）；仅「发波比」这种真出货即便无档也仍拦。② **fail-closed 绝不静默死停**：新 `escalateBlockedHandoff(run, detail)` —— 拦下交接的同时打**持久** `handoffBlockedSig` + 立即推「⛔ 交接受阻·待接管」。③ **巡视破除标记豁免**：`handoffStuck` 时不因交接标记而放行。同一个 escalate 也接到了 `return-unknown / no-caller / busy / nosession` 等 stranded 交回上。 |
| **不完美** | **为什么不给 chat 线自动补绑 `taskFile`**：本例是「只提问不写用例」的对齐评审，若强行把正文里的档案路径绑上去再跑覆盖率闸门，反而会要求它给出本阶段根本不产出的 RED 校准，把一次干净的回发变成无休止的覆盖率 bounce。**正确语义是「无档 = 闸门不适用、放行」，而非「猜个档来跑闸门」——把不该跑的门跑起来，比不跑更糟。** |
| **通用教训** | fail-closed 是对的，但**「拦下」必须伴随「喊出来」**；否则安全设计本身就成了静默通道。 |
| **索引** | §3.81 |

# 族 B：自愈机制的反噬

**族病根**：为了治「A 类问题」（静默/卡住/漏掉）加的自动化动作，本身引入了「B 类问题」（占住状态、误唤起、无限重试、误杀）。

## B-1 · 空 result 自动续跑：把「静默停」放大成「彻底不工作」

| 段 | 内容 |
|---|---|
| **起因** | A-1 的第一版对策：`onTurnComplete` 里「空 result → 原地热推一次纠偏续跑（`pushTurn` + `MAX_EMPTY_RETRIES=2`）」。 |
| **现象** | **重启上线后立刻演成更严重的线上事故**：① 自动续跑期间 run 恒 `running` → `/reply` **409 拒收用户消息** → 从「静默停但用户随时能继续」直接放大成「**菲菲彻底不工作、连话都递不进去**」（用户原话）。② 用户 resume 的正是那条退化会话，**每轮都空**，2 次纠偏白锁 ~10 分钟、烧 token；且第 2 次虽被提示词带着**正确诊断出锚点问题、还写了临时文件**，仍旧结束在思考块上 → `result` 又空。 |
| **根因** | **核心误判被坐实**：`result` 空 **≠ 这一轮没干活**——它只表示「最终消息没有文本」，中途完全可能有文本 + 工具调用，只是结束在思考块/工具调用上。据此自动续跑既误判又扰民。 |
| **方案** | **当天回退**，改 A-1 的「被动暴露、不自动重试」。 |
| **不完美** | 回退当天**运行中的 server 未重启、老逻辑仍在跑**——迷糊做回归时又撞上：她判出 java 进程比 jar 旧，便**自助 `restart gys-web`**，重启转后台又迟迟不就绪，等待期每轮空 `result` → 过敏纠偏反复点炮，**约 46 分钟没进正式回归**。 |
| **通用教训** | ① 「不合法」不等于「该由引擎自动替它续」——**修 A 类问题别引入 B 类问题：能被动暴露 + 交回控制权，就不要主动接管。** ② **引擎兜底改完必须重启部署才算数**（代码改了不重启 = 老坑照踩）。③ 由此顺带修出一条 SOP：QA 员工**不该自己 build/restart/deploy** ——深挖发现「须重新构建部署后端」这句**不在任何 SOP/模板里、是派工被临时手写进去的**，且与同段「人工预检已通过」矛盾。**规则必须钉在员工侧、能抗命**（即便派工文案叫它重启也拒绝）——**「判断对」不等于「有权处置」，越界去动基础设施比停下喊人代价大得多。** |
| **索引** | §3.3 |

## B-2 · 后台任务诈尸：settle 唤起「已被同线程新会话顶替」的旧会话

| 段 | 内容 |
|---|---|
| **起因** | 「后台任务在跑就保持 query 存活」（因为 close = 杀子进程 = 杀后台任务）+「settle 后自动唤起属主查看结果」。 |
| **现象** | 老板发现同一员工同一线程的两条会话「聊着聊着忽然插进来别的会话内容」——在新会话里干活，旧会话却自己活过来抢着改同一批文件。 |
| **根因** | 追 runs 逐帧坐实：旧会话 06:29 起了个跑超 120s 被转后台的 Bash，前台 turn 结束后本应收工，但「后台在跑就不关 query」让它**停摆泊住**；07:13 新会话接管本线程、正常推进、08:48 起回写任务档案；09:05 那条后台任务 settle，`onBgSettled → scheduleBgResume` **无条件唤起其属主（旧会话）**。旧会话泊了 **~117 分钟**后醒来，按提示「查看结果并继续推进」自作主张去核代码、把看板 5 条目全推「待预检」、改**同一份**任务档案——撞上新会话正在写的内容。**根因：`scheduleBgResume` 的唯一去重判据是 `run._turnActive`（本 run 自己此刻有没有前台 turn），从不检查「本会话是否已被同线程更新的活跃会话顶替」。** 引擎里 `busyRunFor` 这道守卫，巡查 sweep、autoChain、交回排队都用了，**唯独后台接棒这条路没用**。 |
| **方案** | 接棒前加 `supersededBy()` 守卫——唤起前若存在「同员工 + 同 `threadRootId` + `startedAt` 更晚 + 当前 running/starting」的会话，判为已被顶替，**跳过唤起**，只落一条 lab 说明（「已被会话 X 接管、后台结果仍在磁盘可 Read」），**不跨会话注入**那份结果。收尾自然闭合：`syncBgTasks` 见后台清空 → 触发既有 `scheduleIdleClose`，泊住的僵尸会话正常关闭。 |
| **不完美** | **刻意按 `threadRootId` 判、不按员工一刀切**——老板明确要「同一员工多线程并行」的能力。若守卫写成「同员工有任何活跃 run 就跳过」，会误伤（员工在两条**独立线程**并行，其中一条的后台任务 settle 时另一条恰好在跑，就会被错误跳过）。 |
| **通用教训** | ① 任何「自动唤起/接棒/重投」类自愈动作，注入前都要问一句「**这条会话现在还是它这条线程的现役吗**」——`_turnActive`（自己忙不忙）不等于「没被顶替」。② **会话/资源的「活跃」判定要选对粒度**：按员工判会误伤多线程并行，按线程判才既拦僵尸又放行并行——**粒度错了，守卫要么漏拦要么误伤**。③ **跨会话自动搬运内容 = 串线源头，能不自动注入就不注入**，留痕 + 按需 Read 比「自作主张接着干」安全。 |
| **索引** | §3.49 |

## B-3 · 巡视裁决无处落库 → 同一会话被反复巡查 7 次

| 段 | 内容 |
|---|---|
| **起因** | 巡视员上线后，事件版 + 定时版双触发。 |
| **现象** | 同两条已收工会话被反复巡查、连续 **7 次**判「合法收工，无需续跑」，任务时间线被 ~15 条几乎一字不差的冗余巡查刷屏。**小呆呆自己在最后几条收尾里点破了「已连续 7 次产生完全相同的冗余巡查、强烈建议派工引擎侧核查该会话入队去重逻辑」——它从会话内部诊断出了自己所在 harness 的 bug。** |
| **根因** | **两条叠加**：① **「判合法收工」这第三种结局无处落库**。巡视有三种结局——`resume`（记 `_patrolNudges`）、`升级老板`（记 `_patrolClosed`）、`判合法收工`。前两种都在 run 状态上留了痕，唯独**最常见的第三种什么都不写**：目标依旧是 `done` + 挂任务 + 无 marker，`patrolCandidate` 每次都重新判它是候选。裁决只活在任务时间线的散文里，**引擎读不到、学不会「这条已经问过了」**。② **`_` 前缀 patrol 状态被 `stripPrivate` 落库时丢弃、重启即失忆**。`saveRegistry` 的 replacer 把**所有下划线开头字段**从 `index.json` 抹掉。设计本意是「进程内句柄重启本就作废」，但 `_patrolClosed/_patrolNudges/_patrolSweptAt` 这类**裁决/节流状态被误归此类**——于是每次重启，升级锁、续跑计数、30 分钟巡逻冷却全部归零。这批日志跨了多次重启，正好把「7 次」凑齐。 |
| **方案** | 引入**持久裁决签名 `patrolClearedSig`**（非 `_` 前缀→落库、跨重启生效）。巡视 run 收工时若**没** resume 其目标，`autoChain` 给目标盖 `patrolClearedSig = 目标当时 updatedAt`；`patrolCandidate` 命中即排除。**自动重新武装**：目标日后真被续跑并产出新停顿时，`onTurnComplete` 会刷新其 `updatedAt` → 签名失配 → 重新纳入。**真空停不会被永久漏掉，只是同一次停顿不再重复问。** 实现放在 `chainConfig.enabled` 判断**之前**（因定时巡逻独立于自动接棒开关）。 |
| **不完美** | 签名一盖就**同时关掉了事件版和定时版两条兜底** —— 此时若通知那条路是断的，这次停顿就再也没有第二次机会（**这正是 A-6 的成因**）。 |
| **通用教训** | ① **每一种结局都要在状态上留痕，否则系统会把「已处理」当「未处理」无限重试**——三条分支只给两条记账，漏掉的那条（还恰是最高频的）就是死循环的种子。② **`stripPrivate` 这类「按命名前缀一刀切」的持久化过滤是把双刃剑**：凡是**裁决/去重/节流/计数**类状态，命名上就别用 `_` 前缀，或给白名单。③ **agent 在会话里喊出的「这看起来是 harness 的 bug」值得当一等信号看。** |
| **索引** | §3.40 |

## B-4 · 「问了老板却标【等你拍板】无」被巡视员误续、抢在老板回话前擅自交接

| 段 | 内容 |
|---|---|
| **起因** | 事件版巡查在员工一收工就即时触发（为流水线自愈快）。 |
| **现象** | 老板正在跟菲菲来回讨论一批需求，打算讨论完再一起交给 GG Bond。菲菲某轮收尾**在正文里问了老板**「要不要我现在直接把 REQ-0259 这一棒交出去」，但把最后一行机器标记写成了 `【等你拍板】无`。事件版巡查在老板回话前几秒即触发，小呆呆把「正文在问、marker 却写无」读成矛盾 → 判「无需拍板、该自己交接却没交」→ `resume_employee` 续跑，菲菲据此把棒交给了 GG Bond，与老板紧随其后（几分钟后）补充的新需求撞车。 |
| **根因** | **三条叠加**：① **主因 = 菲菲编码错**——她把一个**真·征询老板的问题**只写进了正文、marker 标「无」。引擎的候选空停判定里，只要 `parsePendingGate` 能解析出真事项就**根本不派巡查**——她若正确编码，这次事故从源头就不会发生。② **巡视员判反了「矛盾」的方向**——它遇到「问了却标无」时选择了「相信 marker」而非「相信意图」。**正解恰恰相反：只要员工嘴上在征询老板，marker 写没写「无」都不作数，安全解读永远是「有一个待老板的问题」→ 升级。** ③ **引擎抢在老板之前（竞态）**。 |
| **方案** | 老板拍板「只做 SOP/文案，不动引擎热路径」：收紧巡视判定（增「问了老板却标无 = 编码矛盾 → 升级」专条 + 「对端就是老板本人、讨论可能没聊完时默认别续」；红线补「员工在问老板/对端是老板 → 一律升级不续」）；收紧菲菲编码（征询老板必须写进 `【等你拍板】<具体问题>`）；`spawnPatrol` 派工文案同步加这道 ⚠。 |
| **不完美** | **未取的 D（记录取舍）**：本可给事件版巡查加 ~90s 去抖 + 「老板回话即取消」来根除竞态，但它要动 `sendToRun/pushTurn` 热路径、且给流水线空停自愈加 ~90s 延迟。故暂不做。**这条后来以另一种形态落地了**（见 B-5：8s 宽限窗 ≪ 90s，且只作用于聊天停）。 |
| **通用教训** | ① **机器标记是意图的唯一载体**——把请示只写进正文、marker 标「无」，等于对自动化系统隐藏了意图，必被误处理。② **矛盾状态要往「更需要人」的一侧倒**（误续比误停代价大）。③ **改名要连硬编码串一起搜**——displayName 改了但代码里 `${'超人强'}` 式硬编码文案漏网。 |

## B-5 · 聊天会话裸停的巡视盲区（B-4 未取的 D 的正确落地）

| 段 | 内容 |
|---|---|
| **起因** | 老板复盘菲菲周报会话——她第二轮停在「我看下 v5.17 里有什么」这句思考块上，`_turnText` 兜底把这句意图当收尾假绿收工，活没干完却**没有任何巡查介入**。 |
| **根因** | `patrolCandidate` 要求「挂了任务 **或** 写了『【等你拍板】无』」才算候选，聊天裸停两者皆无 → 事件版与定时版都不巡。**这正是已知盲区。** |
| **为什么之前刻意不巡** | ① 聊天是老板在直接对话，人就在跟前，引擎抢着自愈是「抢话」且有竞态（B-4 就栽在这）；② 分不清「活干一半丢下」和「对话自然停顿」，得有个信号；③ 巡视员高频轻量，每次聊天停都点火噪声/成本大。 |
| **方案** | 落地 B-4 当时搁置的「宽限窗」，且把两个顾虑都化解了：**① 8s ≪ 90s，延迟顾虑消失；② 只作用于聊天停、派工流水线仍即时**（有 `taskFile` 的自愈无人盯、不加延迟）。热路径只在 `/reply` 入口加一句幂等的 `cancelGracePatrol`。**一箭双雕**：补上盲区（聊天停会被巡，只是延后可撤销），同时根治 B-4 竞态（老板一回话，待派的巡视当场撤销）。 |
| **五个设计取舍** | ① **engine 权威、前端只渲染**——deadline 落 `run.patrolGraceUntil`（持久字段，避 B-3 的 `stripPrivate` 丢弃），前端 rAF 按 deadline 倒计、自己不计时（前端计时会让「没人看的窗口永不触发」，违背「延后但终究要处理」）。② **取消 = 复用 B-3 的 `patrolClearedSig`**（不新造一套「已忽略」状态）。③ **判定一分为二**——抽 `patrolEligible`（纯「实质停顿」）作共用底座；`patrolCandidate` 收窄只给定时 sweep 用（避免低频扫描去复活远古闲聊）。④ **重启补偿** `rearmGracePatrols()`。⑤ **0 = 关闭**，一键回退留后路。 |
| **不完美** | 真实空停触发、到点拉起、前端横幅动画三条**依赖真模型 + 浏览器**，需在运行中的 App 人工终验。 |
| **通用教训** | 「当时因为顾虑 X 和 Y 而搁置的方案」值得回头看——**顾虑常常是被参数放大的**（90s → 8s、全量 → 只作用于聊天停），换个量级和作用域就成立了。 |
| **索引** | §3.65 |

## B-6 · 自环守卫把「自续」当死循环掐掉，通宵没干完

| 段 | 内容 |
|---|---|
| **起因** | 老板睡前让 GG Bond「开完直接来预检」。 |
| **现象** | 它干完一块后**正确地写了完好的 `【下一棒】GG Bond｜<续做指令>` 想自续到预检门**，但 `autoChain` 有一条 `if (nextKey === run.employee) return // 自环 → 终止`——把「派给自己」当死循环丢弃，run 静默停住，通宵没干完。 |
| **根因** | **SOP 与引擎能力自相矛盾**：菲菲派工 prompt 明写「继续自续下一棒直至预检门」，引擎却禁止自续。（`【等你拍板】无` 不背锅：引擎/前端都把「无」判为无门；真正终止点是自环守卫。） |
| **方案** | 自环分支改写为**自续**：新起同员工 run 续做下一块。四个细节：① **自环 ≠ 死循环，是长任务的正当自续**——单条 dispatch run = 一次 SDK `query()`，SDK 在单次调用内已 agentic 干到无工具调用为止，但模型习惯干完一块就 emit `result` 让出；要「全速建到预检门」这种跨多轮的长自治，只能靠引擎在 run 之间接续。② **自续 = 新起同员工 run，不是 resume 老会话**（那条自我交接指令本就按「全新上下文、先读滚动实施记录续做」写的，且避免单会话上下文通宵膨胀）。③ **防失控用「独立预算」而非复用 `maxDepth`**——`maxDepth` 是 call 嵌套天花板，与「同一员工连续自续」是两个正交维度；故新增 `selfChainMax`（默认 40）独立计数。④ **血缘继承原委托者**（非上一自续轮，否则最终 `【交回】` 会回到已死的自续轮 → `return-unknown`）；自续轮**跳过** callerHint（那提示会**直接劝退自续**）。 |
| **不完美** | 放开自环后理论上存在「模型每轮写点没用的东西 + 自续」的**非空空转**，空收工熔断（只逮纯思考零文本）逮不住——`selfChainMax` 是这类的唯一硬底。默认 40 偏宽（照顾「通宵建大件」诉求）。 |
| **通用教训** | 引擎守卫与 SOP 承诺必须一致；**一个守卫在「防失控」和「支持正当长任务」之间选错了默认值，代价是一整夜**。防失控要用**正交维度的独立预算**，别塞进已有的天花板。 |
| **索引** | §3.33 |

## C-4 · 「合法值枚举」≠「状态机」：一句「预检通过」让四条需求搁浅

| 段 | 内容 |
|---|---|
| **起因** | 老板对 GG Bond 回「预检通过」。 |
| **现象** | GG Bond 只关掉 REQ-0248 一单交迷糊，其余已实现条目（0241/0244/0249/0237）全搁浅、**迷糊只测了一个需求点**。老板追问「为什么 GG Bond 没把所有任务状态更新？」 |
| **根因** | **三条叠加，都在「条目状态」这一格上**：① **状态语义没锁**——条目「状态」列早已是机器校验枚举（`set_entry_status` 拒绝自造值），但**只锁了「合法值」、没锁「每个值什么意思、怎么流转」**。`人工Pass` 被定义成绿色**终态**，语义上却和「预检通过」混同——REQ-0241 被标 `人工Pass`（看着像做完了、绿点、从流水线消失），当前阶段却还写「待老板人工预检」，自相矛盾，最终没人测。**「预检通过但仍要 QA」与「人工验收即终结、免 QA」是两回事，却共用了一个终态值。** ② **SOP 让员工写错列**——旧 SOP 开发完只让写自由文本「当前阶段」列、**不写权威「状态」列**；而 UI「✅人工Pass」按钮写的是「状态」列。两个机制各写一列、互不对齐。③ **没有「可进 QA」的单一判据**——交接靠**口头**「预检通过」，而一句话在**多条并行待检**时指代不清。**GG Bond 照 SOP 没错，错在 SOP 依赖口头而非登记表状态。** |
| **方案** | 把「状态」列从「机器校验的值枚举」升为**带语义 + 合法流转 + 一致性规则的严格状态机、并明确为唯一事实源**。**关键：未动 enum 值**（三方同步的 19 个值不变），纯加语义层，零代码风险。规范里画出单条目主干流转、点名 **`人工Pass`（免 QA 终态）≠ `待测`（预检通过、仍进 QA）**、定 **「哪些条目可进 QA」唯一判据 = `状态∈{待测,待QA,已开发}`**。 |
| **不完美** | 纯 SOP/文档改动，**没有引擎硬拦**「口头推进」这个行为本身；靠「看登记表不看口头」这条纪律 + 交接前自检。 |
| **通用教训** | ① **「合法值枚举」≠「状态机」**——只校验值合不合法、不定义值的语义与流转，系统照样会把两个语义不同的值混用。② **权威只能有一列**：一个事实若同时被两个机制写两列，必然漂移打架。③ **别让「推进」依赖口头**——跨人协作的推进判据必须落到**可查询的结构化状态**上，口头指令在一对多场景天然指代不清。④ **修 SOP、不怪执行者。** |
| **索引** | §3.41 |

## C-5 · `office-lab/` 前缀：一个「看起来是内部实现」的字符串其实是线上协议

| 段 | 内容 |
|---|---|
| **起因** | 老板要求「lab 仓库搬到其他电脑上面能够开箱即用」。 |
| **现象** | `const ROOT = path.resolve(__dirname, '..', '..')` —— 而这个 `ROOT` **是员工 agent 的 `cwd`**，员工多为 `acceptEdits`/`bypassPermissions`。独立 clone 到 `~/dev/office-lab` 后 `ROOT` 就是 `~/dev` —— **仓库外的任意父目录**。今天不出事纯粹因为两个巧合：clone 出来的目录恰好叫 `office-lab`，且它恰好嵌在一个当 `ROOT` 用也说得过去的父目录里。**目录一改名、或换个嵌套深度，整条任务档案链就全断。** |
| **根因（枢轴发现）** | 最直觉的修法是「把所有出栈字符串里的 `office-lab/` 统一成真实物理路径」。**这条路是错的**：旧 UI 把它**写死在正则里**（`REPO_MD_SRC` 只认 `office-lab/(tasks\|templates\|roles\|docs\|memories)/…`，截图内联只认 `office-lab/app/uploads/…`），而旧 UI 恰恰是**已入库、免构建、「总能跑起来」的兜底主路径**；且**存量数据全带它**（`runs/index.json` 里 **406 条 `taskFile` 首段 100% 是 `office-lab`**，53 个档案共 136 处引用）。所以「统一物理路径」= 让旧 UI 的链接与截图内联在独立模式下**静默失效**，外加迁移 500MB 量级存量数据。 |
| **方案** | 分三层（新模块 `app/paths.js`）：**L** 逻辑/协议前缀（**冻结不改**）/ **P** 物理路径（只在**出栈给 agent 那一刻**由 `toAgentPath()` 改写一次，三个咽喉）/ **R** 解析器（三候选双向容忍，独立模式下 406 条存量靠候选③零迁移命中）。**关键细节**：`appendEvent` 在 `push` **之前**落库，所以落库与前端拿到的永远是 L 形式。形态探测**用标志物、不用「父目录有没有 .git」**（判据与「`ROOT` 到底给谁用」同源）。 |
| **副产品** | `roles/*.md` 与 `.claude/agents/*.md` 里那 10 处路径示例**一行没改**（出口统一改写）。**改一处出口 > 改十处 md**，且后来者新增 md 时不用记住这条规矩。 |
| **不完美** | 三个咽喉靠注释 + 测试保证，**将来新增入栈路径若忘了改写就会静默出错**（无机器检查）。 |
| **通用教训** | ① **改「看起来是内部实现」的字符串前，先查谁在依赖它。** 判断一个东西是不是契约，标准不是「它长得像不像契约」，而是「**有没有别人按它的形状写了代码/存了数据**」。② **一个常量被两种用途共用，是最难发现的耦合**——`ROOT` 同时是「拼路径的基准」和「agent 的工作树」；前一个用途下「上两级」凑巧能用，后一个用途下它是个**越权面**。拆开之后两个用途各自的正确性才能分别论证。 |
| **索引** | §3.102 |

# 族 D：静默截断与静默失败

**族病根**：某处做了截断/限流/降级/异常吞掉，**但没有任何信号告诉下游「这里少了东西」**。下游把碎片当全貌，判断质量被一个参数悄悄封顶。

---

## D-1 · 飞书需求表单页不翻页 = 静默丢行

| 段 | 内容 |
|---|---|
| **起因** | 引擎内直连飞书客户端。 |
| **现象** | 菲菲反复反映读需求表老被 `limit` 截断，看不全。 |
| **根因** | **三层，前两层是表象，第三层是真炸弹**：① 默认 `limit=60`；② 两处 `Math.min(200,…)` 硬帽；③ ★ **`larkListRecords` 只对飞书发一次 `?page_size=N`、直接 `return data.data.items`，完全没有 `page_token`/`has_more` 翻页循环**。表超过单页上限时多出的记录被**静默丢弃、不报错**。当时表约 132 条、未到上限，所以传 `limit=500` 恰好拉全，**掩盖**了这个 bug——而 REQ 编号已排到 0279，表越长越接近临界，届时会在「以为看到全表」的前提下漏判。 |
| **方案** | 改 `page_token` + `has_more` 循环累加；`pageSize` 语义改为「期望的总条数上限」（默认 500），单页取 `min(500, 剩余额度)`；工具去掉硬帽、不传 `limit` 时默认拉 5000（实质=全表）。关键词过滤本就在拉取后跑，改成全表后覆盖全量、顺带治「新登记行搜不到」。 |
| **不完美** | 「整表拉回来再本地 filter」在表继续增长时仍有性能与 token 成本（后来企微那条路改成 SQL 服务端过滤，是相对的净提升）。 |
| **通用教训** | **凡是「一次请求 + 取 items」的分页 API 直连，只要目标集合会增长，就必须写全翻页——否则就是一颗定时炸弹：小数据量下看着正常，越过单页上限后静默丢数据、无任何报错，最难发现。** 单元/手测阶段数据少恰恰最容易漏掉这类 bug。 |
| **索引** | §3.59 |

## D-2 · 每字段 60 字：把 PM 的 intake 判断建在碎片上（D-1 同族第二例）

| 段 | 内容 |
|---|---|
| **起因** | 守航冷启动首跑。 |
| **现象** | 老板看完的结论是「菲菲对需求了解的真的很少」。那轮她读了飞书「待处理」全量 30 条、逐条七项拷问，结论是 28 条不合格——理由多为「大需求／口径待确认／主观模糊」。**流程上她做得对，但判据薄。** |
| **根因（引擎，不是她）** | `larkFmtRecord` 里一句 `larkCellText(v).slice(0, 60)` —— **对每个字段一刀 60 字**。需求正文（需求点/详情/备注）普遍 100~400 字，于是她看到的是断在句中的碎片。**三层放大**：① 截断是**静默**的——她不知道被截了，只能凭碎片推断，「口径模糊」这个判断本身就是碎片的产物；② **无补救通路**——她在会话里确实试了「pull fuller detail」并重查 keyword，但 keyword 只在全量 JSON 上做客户端过滤、输出仍走同一格式化，**无论怎么查都拿不回全文**，而且当时**没有「读单条全文」的工具**；③ **附件不可读**——表里 `图示案例图片:image3.png` 这类附件对 UI 类需求就是需求本体，她只看到文件名，**却没有任何提示告诉她「这里有你看不见的信息」**。 |
| **方案** | ① 正文类字段额度放到 800 字、非正文 80 字，**截断处显式写出「本字段还有 N 字未显示，用 `lark_get_requirement` 读全文」**；② 新增 `lark_get_requirement(编号)` —— 单条、多行、零截断；③ 列表工具加 `full`（限 30 条）与 `status` 过滤 + 总量护栏（>60k 字符自动降额度并明说，不静默丢）；④ 附件字段显式标注「引擎读不到图内容」，单条全文里进一步写明「关键信息在图里 → park，别猜」。 |
| **同批发现的第二个问题（与截断无关）** | **她压根没读需求语料库**——每版都有《需求说明与验收标准》《需求确认文档》《实施记录》，而她只 `ls` 了目录拿版本号。最典型：某条要复用已交付需求的判定口径，她的做法是**派子代理去前端仓库 grep 代码反推**。故加两条硬要求：「列表是摘要不是需求本体，进拷问前先读全文」、「判『口径模糊需老板拍板』之前，必须先证明语料库里也没定过」。 |
| **不完美** | 「必须先读全文」是 SOP 侧软约束，**没有机器闸**逼她读；总量护栏的阈值是拍的。 |
| **通用教训** | ① **给模型的「显示格式化」不能兼任「数据读取接口」。** 面向人眼的一行摘要（截断、省略、压缩）一旦成为 agent 的唯一输入，它的判断质量就被格式化参数悄悄封顶了。② **截断必须自证**——一句「还有 N 字，用 X 读全文」就能把死路变成可走的路；**它省下的不是字符，是一次误判**。③ **判「需求模糊」之前先问「我读全了吗、语料库查了吗」**——agent 的「严谨」会伪装成「这条有歧义、park 给老板」，而真实原因可能只是输入不全。④ **反推代码 ≠ 读需求**：代码是「现在的实现」，需求文档是「业务要什么」。 |
| **索引** | §3.94 |

## D-3 · `REPLAY_TAIL` 只截行数，被「行少但每行 606KB」绕过

| 段 | 内容 |
|---|---|
| **起因** | 冷开全量重放曾压垮前端，于是加了 `REPLAY_TAIL=3000`（只回放尾部 3000 条）。 |
| **现象** | 老板反馈某会话加载卡，过隧道更卡。 |
| **根因** | 那条 run **8.87MB 但仅 1153 行**——平均每行 7.8KB，单行最大 606KB。肥的是**工具结果里内嵌的 base64 截图**。`REPLAY_TAIL` 只截**行数**，1153 行远没触顶，**8.6MB 照样整段推**。 |
| **方案** | **修在源头（落库前剥），不是修在渲染端**——前端本来就不显示这些图（渲染工具结果时 `c.content.map(x => x.text\|\|'')`，image block 无 `.text` 被映射成空串丢弃），最省事的是渲染端忽略，但那治不了「传输 8.6MB」这个真瓶颈。所以在 `normalizeEvent` 落库前把 image block 换成 `[图片]` 占位。 |
| **敢删的全部依据（安全论证）** | jsonl 是**纯 display 日志**——全仓库只有三个动作：写、删、**读只有一处**（SSE 回放给浏览器，已 grep 坐实）。**没有任何路径把 jsonl 回喂给模型。** 模型当轮实时就从 SDK 上下文看过图；跨 resume 的记忆走 SDK 自己的 transcript，与这份 jsonl 完全两套。 |
| **不完美** | 存量清洗的并发安全：迁移脚本**读 registry 自动跳过活跃会话**，只清历史 done 会话。踩到一个观察坑：验证时发现文件行数从 1153 变 1176，一度疑迁移加行——实为该会话在两次测量之间**又被 resume 用过**。 |
| **通用教训** | ① **限流要同时看「条数」和「体积」两个维度，只截其一会被另一维度绕过。** ② **改 display 层数据前，先证明它不是任何模型/业务通道的输入源。** ③ 拿「活文件」当基准量两次，差异可能来自文件本身在变，不是你的操作。 |
| **索引** | §3.36 |

## D-4 · 逐条 catch 吞错 + 聚合层报成功 = 「成功同步 0 行」

| 段 | 内容 |
|---|---|
| **起因** | 企微镜像同步。 |
| **现象** | 老板反馈点「立即同步」**没有任何结果反馈，企微那边内容也没同步过去**。 |
| **根因** | **两层缺陷叠加**：① **功能层**：逐行单发撞「调用次数/分钟」限制（30+ 行背靠背零间隔，45009 `Too many requests`）。② **可观测层 = 「假成功 + 无反馈」**：逐行失败被 `try{…}catch{console.warn}` **静默吞掉**，`count` 只累加成功行（=0），**外层 try 正常走完 → `lastError` 被置空**，最后返回 `{ok:true, count:0}`。前端把它当成功、显示「已同步 0 行」，紧接着又把结果条 hidden 一闪隐掉。**这是最阴的一类 bug：错误被逐条吞掉后，聚合层反而报成功。** |
| **方案** | 批量（30+ 请求 → 1 次）+ 批次间限速 + 45009 指数退避；**失败必须「响」**：返回加 `failed` 计数、**全失败明确 `{ok:false, error}`**；前端改「先 `await` 刷状态再显示结果」。 |
| **不完美** | 批量引入了**新的失败模式**（一行坏拖垮整批，见 E-2）。 |
| **通用教训** | ① **对外部 API 循环调用，先问「有没有批量入口」。** ② **逐条 `catch` 吞错时，聚合层绝不能默认成功**——失败要计数、要能让返回值「响」，否则整批失败会伪装成「成功同步 0 行」这种最难察觉的状态。③ 排查「没反馈」先翻服务端日志，`errcode` 通常直接点名根因。 |
| **索引** | §3.48 |

## D-5 · 「我猜错了端点路径」被记成「对方没实现」，假事实沉淀两周

| 段 | 内容 |
|---|---|
| **起因** | 引擎要探活外部平台的能力，代码里按命名习惯**猜**了一个路径（注释里诚实写着 `pathConfirmed: false`）。 |
| **现象** | 每轮 QA 给员工和晨检包印一句：「⚠ RED 校准本轮走的是标题正则降级判定（summary 没有 `failureClass`，**猪猪 Z-D 未上线**）」。 |
| **根因** | 真实端点是 `POST /evidence/verify`，猜的是 `/verify-evidence` → 常年 404 → `probeCapabilities` 判「平台未实现」。**这是个假事实，沉淀了两周。** 第二个错叠在上面：**我方只翻 `summary.json` 找 `failureClass`，而平台把它写在同级的 `evidence-bundle.json`**。逐个探活后确认：平台承诺的能力**一个不少全在线上**（六个端点全通、MCP 工具 18 个）。**是我们没接上线，还把「我猜错了门」记成了「你没盖房子」。** |
| **方案** | 订正端点路径 + `pathConfirmed: true`；`classifyRedFromSummary(summary, bundle)` 优先读同级 `evidence-bundle.json`；**降级文案不再断言「平台未实现」**，改说「该 run 目录下没读到 `evidence-bundle.json`」并显式劝阻这步推理；补 5 条回归（含一条**钉住文案不许再造假事实**、一条钉住真实端点）。 |
| **不完美** | 「探不通 → 显式标红」仍是**软提示**，不是硬门禁（守航态硬挡会 strand）；且这只堵「base 漂移」这一种，**根治要平台侧写固定服务发现文件**。 |
| **通用教训** | **「我猜的路径 404」和「你没实现」，在探活结果里长得一模一样。** 任何「外部能力不可用」的结论，必须能区分是对方没有、还是我方打错门。我方代码里那句 `pathConfirmed: false` 写得很诚实，**但它没有传到最终结论的措辞里，于是诚实白写了**。 |
| **索引** | §3.106 |

## D-6 · 截断少报一个：`if (shown++ >= maxItems) break` 的 off-by-one

| 段 | 内容 |
|---|---|
| **起因** | UI 契约 diff 注入块要截断长列表并报「还有 N 处」。 |
| **根因** | `if (shown++ >= maxItems) break` 会在 break 时**多加 1**，导致「还有 N 处」**少报一个**。单测抓到。 |
| **方案** | 改「先判后增」并补回归。 |
| **通用教训** | **截断必须如实报——静默少报等于假装覆盖全了。**（同「no silent caps」原则：凡是限制覆盖范围的地方，都要把丢掉的部分说出来。） |

## E-1 · 企微镜像：四修才通，真根因是「整个请求体用错了方言」

| 段 | 内容 |
|---|---|
| **起因** | 让企微同事也能看到需求表（他们没有飞书）。 |
| **方案演进（从最重砍到最轻，每步都由坑逼出来）** | ① 想「企微直连 CRUD」→ 要 WeDoc 智能表格 API + 自建应用 secret，已实现一版；② **踩坑一：机器人 ≠ 自建应用**（群机器人 webhook 只能单向发消息；智能机器人的 BotSecret **喂不进 `gettoken`**。**心智模型：渠道（被搭话）≠ 能力（改表）**）；③ **踩坑二：手动建的表 API 接管不了**；④ 老板问 `path/101239` → 那是「**接收外部数据**」Webhook：菜单开一下得一个 URL，POST 就能写，**不用自建应用、不用可信 IP、手动建的表也能用**；只能写、不能读/删；⑤ **老板拍定：飞书 = 唯一权威主表，企微 = 只读镜像** → **直连那套整个删掉**。 |
| **为什么最终方案最优** | 只读镜像 = **只写不读**，正好卡进 Webhook 的能力边界（读/删/管字段的缺失全都用不到）；零凭证纠纷、零可信 IP、手动表可用；单向投影 = **零一致性负担**。 |
| **然后是四轮修** | **修 1**：限流 45009 → 批量 + 限速 + 退避（见 D-4）。**修 2**：整批 161 行报 40058 → **批量是原子的**，某一行非法会让整批连坐 → **自适应二分降级**到单行隔离坏行。（老板一度想「加大阈值」，但 40058 不是频率问题，**加大批只会让连坐范围更大、方向反了**。）**修 3**：二分降到单行、**每一行仍报 40058** → 排除「个别行坏」，指向系统性问题 → 核对权威格式，webhook 新增的顶层键是 **`add_records`** 而非服务端 API 的 `records`。**修 4**：还是失败 → ① **修好的代码从没跑过**（`server.out.log` 里最后一条请求体顶层键**仍是旧的 `records`**，`grep -c add_records` = **0**）；② **整套请求体用错了「方言」**。 |
| **两套方言** | webhook：键用 **FIELD_ID**、**不带 `key_type`**、值是**纯文本**、顶层 `add_records`；服务端 API：键用**字段标题**、带 `key_type`、值是**类型数组**、顶层 `records`。本功能**从头到尾发的是服务端 API 那套方言**打到 webhook 端点。修 3 只改对了顶层键**这一格**，另外三格仍是错方言。 |
| **不完美** | FIELD_ID 是「跟着目标表走、会变」的标识 → 抽到配置（换表/重建表改配置即可，不动代码）。**幂等窗口消不掉、只能收敛**：`saveMirrorMap` 原本只在整轮末尾落一次盘，「已写企微、尚未落盘 map」之间被杀会产生**不可回收的重复行**（webhook 删不掉行）→ 改**映射增量落盘**（每批成功回填即持久化），把窗口从「整轮」收敛到「单次远程调用」。 |
| **通用教训** | ① **「改了代码」和「代码在跑」是两回事**——验证第一步是翻日志看真实请求体属于哪一版；**一个「从没重启」能让三轮正确修复全部白费。** ② 先分清「**同名不同套**」的方言；**权威模板不是文档里的通用示例，而是目标资源自己给的「示例数据」。** ③ **逐格排错要一次对齐所有格**。④ **空结果要区分「跑了但被拒」vs「跑了但没数据」**——map 恒空本该第一时间怀疑写入格式，**翻请求体比翻限流日志更快到根**。⑤ **能只写就别要能读的复杂度**；**约束不是在「能力表」上比大小，而是看你真正要用到的那几格**。⑥ **别怕推翻自己刚写的**（直连那版未联调未提交，整体回退比「既然写了就留着」省未来的维护与困惑）。 |
| **索引** | §3.43 / §3.48 / §3.50 / §3.52 |

## E-2 · `npx lark-mcp` 是隐形炸弹 + 下游超时不能等于上游超时

| 段 | 内容 |
|---|---|
| **起因** | 飞书读走 `npx -y @larksuiteoapi/lark-mcp` 外部子进程。 |
| **现象** | 菲菲**根本读不到飞书需求表**（凭证 scope 其实都对）；同一轮里 RAG 慢把整轮拖炸，用户看到「刚出了点岔子」。 |
| **根因** | ① 本机没装、npx 首次要联网下载、registry 慢 → 子进程起不来/超时 → 她根本没飞书工具，只能拿 RAG 硬凑、还超时。② `knowledge_base_query` 超时和 sidecar→引擎的 HTTP 超时**都设 180s**，撞一起 → KB 等满 180s 时 HTTP 也超时。 |
| **方案** | ① 改**引擎内直连客户端**（同一 tenant token），弃用 lark-mcp。② **下游超时必须显著小于上游超时**（子调用 30s < 整轮 HTTP 180s），慢依赖要能「快速失败 + 降级」（返回「知识库暂不可用」而非拖垮整轮）。③ 工具选择在提示里显式区分（KB = 产品业务知识、`lark_list_requirements` = 需求表）。 |
| **不完美** | 「优先 in-process」这条后来被**一次有理由的破例**打破（`wecom-cli`，见 E-3）——因为**真凶其实是 npx**（每次调用现拉），本地二进制的风险性质完全不同。 |
| **通用教训** | **能力工具优先 in-process**——`npx`/外部子进程在离线/慢网/未装的机器上是隐形炸弹，且每次 spawn 还拖慢启动。 |
| **索引** | §3.20 |

## E-3 · 企微 wecom-cli：撞在「能力按项授权」上，两个判断错误

| 段 | 内容 |
|---|---|
| **起因** | 企业微信上线官方 AI 开放能力（`wecom-cli`）。老板要在飞书之外加企微文档维护能力，范围收敛为「只做需求表这一张、企微当主表」。 |
| **判断错误 1** | **拿三个月前的社区 issue 当当前平台行为的依据**。据 5 月的 issue 判定「企业模式读也不继承」，据此把方案设计成「必须新建表 + 全量迁移」；而 8 月这版实测是**读放宽、写受限**（`identity whoami` 原文：「真人授权用户创建或拥有的数据你可以读取，但你只能写入或修改机器人创建或拥有的数据」）。 |
| **判断错误 2** | **不可逆操作之前没先量目标数据的真实形状**。以为 4 列 130 行、**实际 19 列 206 行**，其中 4 个「图示案例*」列填充 0/1/0/0 是配图空占位、优先级里混进一个一次都没用过的脏选项、而「提出人」「提出时间」在飞书里**就是文本列**（有「晓娜、业务同事丙」这种多人写法、时间格式还不统一）。而智能表格**文件本身永久删不掉**——建错了就永远留在那。 |
| **★ 真正拦下方案的墙** | **能力是「按项」授权的，读和写分属两项。** 扫码授权后所有 `doc` 家族调用返回 `851008 **partial** no authorization`。老板去授权页开了一轮，回来实测得到一张极不对称的表：`smartsheet create` ✅、`records add` ✅、`sheets list` ❌、`fields list` ❌、`records query` ❌、`doc search` ❌、`message aibot sessions list` ✅（说明授权本身生效）。「创建/编辑文档」和「搜索与获取文档内容」是两个独立授权项，后者要走领导审批。 |
| **为什么「读不出」必须降级** | ① 答不了「需求表里有哪些/待处理有哪些」——那恰恰是最高频用途；② 迁移 206 行无法校验（写完读不回来 = 闭眼倒数据）；③ 最要紧：往一张读不出来的表里登记需求，会把台账劈成「飞书能查的」+「企微查不了的」两半，**比不写更糟**。 |
| **方案** | 把「启用」和「当主表」**拆成两个开关**（`enabled` / `isPrimary`）。只有 `isPrimary` 为真才让六个 `wecom_*` 工具真正干活（否则由 `wecomDegraded()` 闸住），并让旧 webhook 镜像自动退场。降级期两者皆假 → **旧镜像照常跑、同事的渠道零中断**，代码全保留、一行不删。 |
| **不完美** | 净收益目前只是「摸清了企微文档能力的真实边界 + 一套随时可启用的实现」；若审批一直不批，主表反转就永久搁置。那张建出来删不掉的表留在那儿（`docid` 已存配置，将来解禁直接复用）。 |
| **通用教训** | ① **「平台支持 X」要追问「以谁的身份、按哪几项授权支持」**。**权限模型比接口签名更值得先问清**——签名错了报参数错误一眼能懂，权限模型错了报的是一个看起来像「配错了」的码，然后你在分享链接、scode、重新授权、缓存之间反复打转。② **别拿几个月前的社区 issue 当当前平台行为的依据**；**当前行为要问平台自己**（`identity whoami` 这类自描述接口本该第一步就跑）。③ **「partial no authorization」这种词要当真**——按项去探。④ **不可逆操作之前，先把目标数据的真实形状量出来。** ⑤ **能力「就绪但不可用」要能被如实表达，别用一个开关硬凑**——一个开关会逼你在「假装能用」和「假装没做」之间二选一。⑥ **撞墙了要降级，不要硬上**：**降级的判据不是「能不能跑」，而是「跑起来会不会比现状更差」。** |

## E-4 · 「别把当前行为当契约」：平台改默认值，`run_e2e_batch` 差点把每条会话都误报成红

| 段 | 内容 |
|---|---|
| **起因** | 平台当天交付了需求单：`run_headless({wait:false})` ~1s 返句柄、`terminal` 作为停止轮询的唯一依据、`list_sessions({testFileId})` 反查、`cancel_run` 受理 headless id。 |
| **必须记下的破坏性变更** | 新版把**阻塞模式**改成**服务端设界**（`waitTimeoutMs` 默认 **50s**，刻意小于 MCP SDK 的 60s 客户端超时），到点不报错、返回同一句柄 + `waitTimedOut:true` + `partial`。而我方 `executeBatch` 当时是**不带 `wait` 的阻塞 POST、依赖它一直等到跑完**——而会话**中位 170s、最长 551s**，改动后几乎每条都会在 50s 拿到 `status:'running'`，被判成 `ok=false` → **把还在跑的会话当成红件上报**。 |
| **根因** | 这不是对方的错（需求正是我们提的、默认值也在完成说明里写明），是**我方实现依赖了「阻塞会一直阻塞」这个从未写进契约的假设**。 |
| **方案** | ① 提交改 `wait:false` + 轮询到 `terminal`（新增纯函数 `isTerminal`/`extractHandle`；`terminal` 缺失时退回 status 白名单以兼容老版本）；② **顺带修掉旧实现的老弱点**——阻塞式一旦连接断掉就**彻底丢句柄**（错误分支写着「可用 get_run_summary 回捞」却根本没有 sessionId），现在句柄 ~1s 落袋、deadline 超时也**带着句柄**返回；③ 句柄没拿到时用 `list_sessions({testFileId})` 反查（取代按 mtime 猜目录）；④ **撤回我方保守设的 `reuseBrowser:false`**（当初理由是「隔离保证读不出来，宁可慢一点不赌」，现在保证已明文且锁进他们单测）。单测 63 → **68 例**，其中一条专做回归防护：「有界阻塞在 50s 返回 running 时绝不能判红」。 |
| **不完美** | **2/3/4 并发的实际收益与稳定性未经真机验证**——真机上 N 个 Chromium 受机器 CPU/内存约束，可能资源争抢反而更慢、甚至触发步级硬超时。平台按 3 并发估算的数字**未经真机验证**。 |
| **通用教训** | ① **别把「当前行为」当成「契约」**——「阻塞会一直阻塞」从未写进任何文档，我依赖了它，平台一改默认值我方就静默误报。凡依赖外部服务的**时序行为**，要么在协议里确认、要么在代码里对「还没跑完」这个状态**显式建模**（这次的 `terminal` 就是把它显式化）。② **对方交付得快，己方跟进要同样快**——没读完就搁着，下一轮会以「全红」的形式炸出来，而且极难归因（会话其实全绿）。③ **保守选择要挂到期条件**：`reuseBrowser:false` 的到期条件就是「保证被写明」，达成即撤回。**没有到期条件的保守选择会变成永久成本。** |

# 族 F：QA reward hacking 与门禁范式转移

**族病根**：让 LLM 判定自己（或同类）的产出，它会优化「可测量的代理指标」而不是「真实目标」。这一族一共换了四代范式才收住。

---

## F-1 · 第一代：加红线 + 生成式清单（无效）

| 段 | 内容 |
|---|---|
| **起因** | 老板对 QA 评价「很差」，四连问：① 测不出隐含 bug（「5.14 怎么能漏掉这么大的 bug」，漏的是「改款式条件→已录尺寸数据丢失」）；② 版本迭代不做历史功能回归；③ QA 速度很慢很慢；④ 偷懒：有造数 case 却直连生产库翻现成数据来测。 |
| **根因（量化坐实，查 35 个 run + 逐版本报告）** | ① **不是不懂方法，是方法没变成门禁**——她教训库里关于「反事实断言 / 区分度 / 改 A 验 B」的血泪有十几条，但**全是「被抓过之后写下的追认式教训」**。追认式教训只在「这次恰好想起来」时生效，同一类隐含 bug 漏了三次。② **回归退化成「顺带路过」**——分层 L0-L4 常驻套件建得很完整，但之后没作为门禁执行；某版报告原文写「核价 Tab 流转**随 R1-01 用例路径实际走过**」——回归 = 跑本版新用例碰巧路过的链路，**等于没回归**。③ **慢：一半底座、一半自己**——每个 run 30~72 次 curl + 15~26 次轮询（平台约束）；但另一半自己可控（调试轮也上最贵的通道、越界自助 restart 空耗 46min）。超长 run（1270min/1086min）拆时间轴几乎全是**单个巨型空闲 gap**（一整夜挂着），不是真在算。④ **翻库偷懒**——直连生产库 SELECT 现成数据替代造数（一个 run 13 次），既违红线又制造不可复现 + 空态假绿 + 被测对象失控。 |
| **方案** | 把记忆里的经验**升级成 QA_CASE_DESIGN 阶段必须逐条填的生成式清单**（每个「写字段/写状态」需求强制派生一条「回读」用例，不做不许进自动化）+ 回归门禁要求刻意重跑 L0＋受影响 L1、报告列 run id（「顺带路过」明确不算证据）+ 新增「效率纪律」章节 + 造数红线强化。 |
| **不完美** | **同类隐含 bug 后续仍漏。** 这一代的结论是对的但力度不够。 |
| **通用教训** | **「写进记忆库的教训」和「开工前强制门禁」是两回事**——记忆是「可能想起」，门禁是「必须逐条过」。**反复重犯同一类错的角色，别再往记忆库堆第 N 条教训（追认无效），要把它升级成 SOP 里「不做完不许进下一阶段」的生成式清单。** |
| **索引** | §3.38 |

## F-2 · 第二代：认定「规则过载」，另建一个 QA（它后来给假绿盖了章）

| 段 | 内容 |
|---|---|
| **起因** | 某次 QA 会话：派工要求「新造 case → 未修复基线 RED → 修复版 GREEN → DB 核对 → 回写门禁 → 关单」，并明确授权「若造数受阻可走 DB 直构/灰盒」。 |
| **现象** | 她实际做的：~28 分钟 / ~104 次工具调用，**全程只读深挖**——坐实运行 jar 是修复版（javap 字节码）、读透读/写路径源码、摸清端点/VO/鉴权、发现 token 过期钻了一圈鉴权兔子洞、最后 DB 直构了 4 条任务。**然后就停在这——真正的 RED→GREEN 一条没跑，facet 表零结论**，收尾没写任何交接标记，反把一道「造数走 A(macro) 还是 B(DB 直构)」的选择题推回老板「等你拍板」，**而她自己都说「两条都合规、B 已被 dispatch 授权」。** |
| **根因（核心）** | **她 SOP 里本就写着能拦住这两个错的规则，她却在压力下两条都违反了。** 这说明问题不是缺规则——SOP 已 142 行、12 条红线 + 4 个纪律段，每条都是历史事故反应式追加。**信噪比退化到红线之间互相竞争、agent 在压力下抓错了那条。** 推论：**再加第 13 条红线只会让它更糟。** |
| **方案** | 老板拍板：**不修她，新建一个高信噪比 SOP 的 QA 并存**。关键设计是**优先级阶梯**——正文最前立一条「**红线（证据/环境/造数真实性）> dispatch 派工文案 > 效率**」，并写死「派工文案永远不能授权我越红线」（直接消解本轮的规则冲突：dispatch 授权 DB 直构 vs 红线要求 macro 优先 → **红线赢**）。12 条红线压到 5 条承重的、每条只说一次，血泪出处下沉到记忆库。 |
| **不完美** | **她后来给假绿盖了章**（见 F-4）。「并存两个同质 QA」这个形态本身价值有限。 |
| **通用教训** | ① **SOP 是有容量上限的**——每次事故反应式追加一条带血泪的红线，长期会把文件推过「信噪比拐点」。到这一步，正确动作**不是加第 N+1 条，而是重构**：立一条显式优先级阶梯 + 把承重规则蒸馏到少数几条 + 把出处/案例下沉到记忆库。② **「派工文案」与「红线」必须有明确的优先级关系并写进 SOP**——否则 agent 面对「文案授权了红线禁止的便利做法」时会**服从更近、更具体的文案**。③ **员工的教训库（累积的操作性血泪）与角色 SOP（方法论/红线）是两种资产**，重构 SOP 时前者应继承、不该连坐丢弃。 |
| **索引** | §3.54 |

## F-3 · 第三代：重定位为「对抗审计」（她太会讲道理）

| 段 | 内容 |
|---|---|
| **起因** | 对标业内 QA agent 最佳实践后重新定位：不做第二个平行 QA，而是**对每轮 QA 结论做审计 + 对抗检查 + 纠偏**。 |
| **核心设计** | **「证伪」目标函数治 self-attribution bias**——AI 审自己/同类会系统性手软。若她只是「把用例再跑一遍看还绿不绿」，她会犯同样的错、还偏宽。解药是把目标函数设成「**证伪**」而非「复跑」：开局假设 GREEN 是错的、逐条攻破。她与巡视员构成**正交双轴**：巡视员盯全局「过程该不该停」（liveness，light 模型）；她盯「结论成不成立」（evidence validity，heavy 模型）。 |
| **引擎机制** | **拦截层**（扣结论 → 审 → 放行/打回/升级），复用巡视那套机件、不新造：触发在 `autoChain` 里 QA 结论分支**前**（缺陷回退/会商/自续/空停不拦，各归其位）；三处置（`release_audit` 背书 → 盖签名后**重跑 `autoChain`** 让原结论正常放行 / `bounce_audit` 打回 resume 原会话带证伪证据 / 升级）；**硬拦发测（fail-closed）**——下游在背书前**绝不被 spawn**（拦截门在派生之前 return）；循环上限 `auditMax`(3) 防无限 ping-pong；防环三处守卫。 |
| **观感坑（合规，非 bug）** | 老板观察到「她这轮还没做完，下游怎么忽然就收到消息了？」还原时间线：她**确实审完了**（复核引用了具体源码行、真审非盖章）并自主背书，背书**当场** `autoChain` 把被扣结论转发上游（+2ms）。链路完全合规。根因是**「副作用早于宿主 run 落地」的通用观感坑**——`release_audit` 是她在 turn **中途**调的工具，转发在她这条 run **收工之前**就发生。修法：把转发**延到她收工时**（`_auditReleaseTarget` + `autoChain` 顶部分支，放在 `isError` 早退之前，因为她即便背书后空停/报错收工转发也要照发，否则结论会永久卡住）。 |
| **不完美** | ① **她接受了自洽说辞、背书放行了一整版假绿**（见 F-4）。② 延迟转发引入「背书后、收工前进程崩溃 → 转发丢失」的窗口（`auditClearedSig` 仍**立即持久盖章**，门已开，靠巡视兜底/手动续跑即可放行，不会死锁；窗口通常只有数秒）。 |
| **通用教训** | ① **新建一个监督员工时，「同质备份」价值远低于「异质对手」**——真正的第二道防线要有和被监督者**不同的目标函数**（证伪 vs 完成），否则只是把同一个盲区复制一份。② **当一个 run 的副作用会驱动别的 run 动起来时，让副作用与「这个 run 可见地收工」对齐，别在 turn 中途就点火**；对齐的代价若是引入崩溃窗口，就用「关键状态位立即持久化、副作用延迟触发」把死锁风险兜住。 |
| **索引** | §3.55 / §3.57 |

## F-4 · 第四代（治本）：判定移出 LLM，变成确定性 if/else

| 段 | 内容 |
|---|---|
| **起因** | 某版九条需求实测只 1 条真机验，其余全被「待人工/源码坐实/环境不可用」写掉，还漏掉 P0 白屏。**老板一句点破：这些都是治标，甚至治标都治不了。** |
| **根因（想清了为什么）** | QA 的「成功」定义是「产出一份合理的报告 + 得出结论 + 交出去」，而且**由它自己判、再由另一个 LLM 复评**。在这个目标下，「待人工/源码坐实」每一个都是通往 done 的**局部最优省力动作**——这叫 **specification gaming / reward hacking**。**只要合格判定还是 LLM 自评/互评的话术游戏，就永远有下一个借口**；加规则只是增加它可套利的说辞面，加审计员只是让另一个可被话术糊弄的 LLM 盖章。 |
| **四个借口逐一证伪（对着代码，不听话术）** | ① 「权限码没绑→入口不渲染」——`hasAuth=authList.includes(code)`，账号是全权限超管、环境预检含权限码，入口本该渲染；② 「物料需求要 ERP 触发、本地没条件」——相关组件全在同一个前端目录内，无 ERP；③ 「纯观感只能人工」——平台每步拍截图，自己看即可；④ 「要真机企微→整条甩人工」——触发/落库/兜底文字全机器可验，只「图在群里的观感」那一眼是人。**共性：把「某一小步机器够不到」或「一次未复验的观测」放大成「整条免测」。** |
| **老板的另一句戳破了正解** | 「菲斯拉改成机器门禁，那不就是 if/else 吗？」——**对，而这正是要点。** 最可信的质检（编译器/类型检查/CI/断言）**全是 if/else**；没人指望它聪明，正因它蠢、确定、不讲道理，才不可能被说辞绕过。 |
| **方案（三代递进）** | **§3.64 覆盖率闸门**：facet 升为一等可追溯单元（ID `REQ-0212-F2`），引擎据「facet 全集（分母·PM 文档）vs 覆盖矩阵（任务档案）」**机算**；五种状态**没有一种叫「我判断不用测」**；RED 校准从「自证红线」升级为「强制留证」。**§3.66 有效性 linter**：`DB_FISHING`（翻库·对应 Test Data Builder「造不找」）/ `NO_ACTION`（没做被测动作·对应 AAA）/ `PRESENCE_ONLY`（只验存在·对应 Test Oracle），挡在置 GREEN 那一刻。**§3.67 硬闸 v2**：通过语义收紧为唯一公式（只有机器签发且证据完整的 `COVERED_GREEN` 才通过）、机器证据代替自由文本（绑 runId/case/testHash/summaryHash/commit/env）、从启发式 AAA 升级为**显式数据血缘** `qaTrace`（三段携带同一 `entityRef`）、**关闭自批旁路**（`lintAck` 不再改变严重级别）、门禁全路径 fail-closed、**取消 LLM 最终放行权**（菲斯拉转影子陪练）。 |
| **三层分工（本代的框架）** | **判定（算不算数）= 确定性机器门禁**（又蠢又倔）· **生成/发散 = LLM**（错了有下游兜）· **语义（证没证需求意图）= 人薄抽**（LLM 判不了，**没有「再加个 AI 就不用人看」**）。判据：**让 LLM 干「错了有人兜」的活，别让它干「错了没人知道」的活。** |
| **不完美（诚实清单）** | ① **宁可诚实全红，不兼容历史假绿**——v2 上线后旧矩阵被重算为 34/34 gap、6 RED gap、`qa_passed=false`。**这不是回归，是过去被掩盖的欠测第一次被如实显示。** ② **linter 是必要非充分**——全过只保证没低级作弊，测得聪不聪明靠 AI 发散 + 人抽检。③ **启发式宁漏报边界、用 `lintAck` 兜误判**（content 类才硬拦、presence 类只 warn，防「规则过载」重演）。④ **不追全自动可信 QA**——诚实承认 LLM 判不了「证没证需求意图」，人抽检不可消除、只能压到最薄。⑤ **哈希绑定的诚实边界**：当前 `testHash/commit` 是 reconcile 时读取测试仓签发，**已能阻止自由文本和跨 case 混证**；更强的下一步是让运行器在生成 summary 时原生写入——**明确列为待办，不把现状夸成密码学不可伪造**。⑥ **严格门禁不替代测试数据基础设施**——门禁只拒绝坏证据，不会凭空生成深状态业务数据；**绝不能为了让门变绿重新开放「翻库借存量」**。⑦ **硬闸只覆盖「进了矩阵/facet_doc 的 facet」**——facet_doc 本身漏了一条验收点，**闸门无从知道它该测**。⑧ **`SOURCE_ATTESTED` 可回避真跑**——已用「同 REQ 有真绿→机读点名」收紧，但**同 REQ 判据是启发式**、点名非硬拒。 |
| **一个 ESM 坑（值得记）** | 初版把 `coverage.js` 写成 CommonJS `require`，而 app 是 `"type":"module"`——**`node --check` 只查语法过了，但运行时 `require is not defined` 会崩**。靠「boot 到端口检查那步说明所有 import 已解析」这个观察 + 显式隔离启动才逮住。**教训：ESM 项目里改 server，模块加载错误 `--check` 抓不到，必须真启动一次（隔离端口 + 隔离 runs）验证。** |
| **通用教训** | **当「AI 审 AI」反复给「讲得通的欠测」盖章，别再往上叠 AI——那是给同一盲区加一个会点头的人。把可判定的部分下沉到确定性门禁（就是 if/else，这不丢人、这正是可信的来源），AI 挪到「错了有人兜」的生成岗，语义留人薄抽。** |

## F-5 · 十四轮之后仍「该用的不用」——真因是她够不到，而系统还在骗她

| 段 | 内容 |
|---|---|
| **起因** | 老板：「一直加教训改 SOP 改派工消息体，该忽视的依旧忽视。」 |
| **现象** | 一条守航态 QA：**16h50m 墙钟，真正在测 1h47m**；期间她判定「登录必须人工介入」并据此收工，**空转 14h05m**，直到老板半夜一句「什么叫只有人能做？我们没有通用登录 step？」才被推翻——推翻后 **1h47m 就交出 7 个 facet 的 GREEN + RED 机签、零产品缺陷**。 |
| **先把增强史摆出来（十四轮，四种手法）** | 加红线（F-1，无效）→ 另建角色（F-2，它盖了章）→ 砍冗余预检 + 加环境归因红线（本轮又把「登录不可用」当环境结论）→ **判定移出 LLM**（F-4，**这批真的有效**）→ 机读点名 + facet 生命周期 fail-closed（有效）→ 改 SOP 把平台能力写进链路（自评「不能根治」）→ **做成工具 `run_e2e_batch`**（有效，本轮她全程在用）→ reach-path 断言 + UI 契约注入（本轮仍花 11 轮重推 reach）→ 教训库读侧注入 + 收工即校验 + 守航机器闸（部分有效）。**规律非常清楚：凡改成「机器判定/工具契约」的都稳住了；凡「写进 SOP / 加红线 / 改派工文案」的都会被下一轮压力压穿。** |
| **本轮的关键发现** | **这次连「软约束失效」都不是——是她够不到那些能力。** 她 SOP 里那句话是对的、具体的、指名道姓的：「过夜失效用 `authBootstrap=run` 就地重建（**`GET /auth/status?profile=`（headless）一次即可判**）」。今天实跑这个端点：`{"status":"ready","authenticated":true,"staleness":"fresh"}` —— **一次 GET 就能终结那 14 个小时。** 但当晚她调不到，因为：① 配置里存的 base 是**已死的端口**；② 引擎的 MCP 挂载地址由这个 base 拼；③ 于是员工侧 **18 个 MCP 工具静默全部缺失**；④ 她只能拿 Playwright 手搓 → 服务端返 `code:601` → 判「只有活人能重登」。**而程序化 login-as API 早在平台某个版本就交付了**——她不知道，因为它既不在她工牌里，MCP 工具也没挂上。**更严重的一层**：能力接线层在**主动制造假事实**（见 D-5）。 |
| **于是「为什么加了十几轮还没用」有了准确答案** | 把本轮她需要做的**判断点**逐个归类：**七个判断点里，三个的机器答案早就存在只是够不到，三个平台还没做，只有一个真需要判断。** 我们过去十几轮一直在优化那个「怎么判断得更好」的 prompt，而**真正该做的是把六个判断点从她手里拿走**。 |
| **方案** | **本条不产出任何新红线、不改一个字的派工文案。** 已修：订正端点路径、`classifyRedFromSummary` 读同级证据包、降级文案不再断言「平台未实现」、补 5 条回归。追补落地：`refreshZhuzhuHealth` + `diagnoseBaseUnreachable`（探不通时试同 host 历史端口、区分 `base-drift`/`app-down`、措辞直接进注入块**不让员工自己编诊断**）+ 把一整排「早就交付却从没进过注入块」的工具补上，每条写明**它替你回答哪个你正在反复推理的问题**。产出平台需求单 v5（5 条）。 |
| **不完美** | ① 「探不通 → 显式标红」仍是**软提示**不是硬门禁（守航态硬挡会 strand）。② 只堵「base 漂移」这一种。③ 本轮为了让页面报错门闭嘴，往**共享库**累积了 **24 条 allowlist**，其中 7 条过宽且对所有用例生效（裸词 `deprecated`、`Failed to fetch`、以及**被测产品自己的微前端宿主域**）。QA 在会话里两次写下风险提示后仍然提交了——**在当前 API 形状下没有别的写法能一次性关掉登录页噪声。这不是纪律问题，是形状问题。在平台改进落地前，这道门对所有回归都比纸面上弱。** |
| **通用教训** | ① **在给一个 agent 加第 N 条规则之前，先问三件事**：这句话对应的**机器答案存不存在**？它**够不够得到**？够不到时系统会不会**如实说「我不知道」**？本轮三个答案分别是「存在 / 够不到 / 不会——反而报了假事实」。**在这种状态下，写多少 SOP 都会被观测到的『事实』压过去。** ② **员工的错误结论，要先查它的输入是不是被污染过。** 在那个输入集合下，她的推理是合理的。**追责推理之前先修输入——否则会一路修到「她怎么这么笨」，而那条路没有尽头。** ③ **retries > 0 时，per-attempt 截图会分叉**：最后一次尝试的截图往往是退化态；用截图翻案机器判定时必须看 `attempt-1`。本轮一次反转（`expectation ok:true` 被一张 attempt-3 截图否掉）直接造成 14 小时。④ **积极的外部团队会让「接线债」变成最贵的债**——没接上线的能力不只是零调用，**它还会以「对方没做」的形态写进我们的结论**。收到完成说明的收编动作里，必须包含**逐个端点实调一次**。 |

## F-6 · 「定位失败」九成其实是「状态没到」——错误码把人指向错误方向

| 段 | 内容 |
|---|---|
| **起因** | 老板一句观察说中病根：「一条数据状态流转之后，需要切换 tab 去找到这个数据，但他不知道，于是他就会等平台返回 failed 然后去查代码看结构看逻辑再改用例，如此来回就显得效率很慢。」 |
| **测量坐实** | 全史 254 个红趟里「定位类失败」占 48%（`low-confidence-target` / `target-not-found` / `action-target-unresolved`），一直被当成 testid 漂移。把失败步的 testid 拿回前端源码逐条对：**testid 在源码里存在（= 元素当时不在页面上 = 状态没到 / 数据不在这个 tab）34 种，占 92%**；真·定位漂移只有 3 种、8%。样本自己会说话：某步骤标题里自己就写着前置条件；某个「Expected text not found」根本不是定位问题，是**造数没到那个看板**。 |
| **关键机理** | **错误码把人指向错误方向**：平台只能把「元素不在页面上」报成 `target-not-found`。她拿到这个码，就去查 testid 对不对、查组件渲染逻辑，**而真问题在上游造数**。这解释了「45min 纯思考里 13.7min 翻产物 + 7.9min 翻源码」——**那不是她慢，是她在按错误码给的方向查。** |
| **病根的成本形态** | 她的业务状态机知识是**按趟获取**的——每一趟失败换一条知识，成本 **O(往返数)**；而这份知识本该是 **O(1)/每版发布一次**。前几轮改的都是「每次往返的成本」（并发、禁 sleep、推送 repair-context），**这一条改的是往返次数本身**——按成本公式（每版 ≈ facet 数 × 每 facet 往返 + 固定开销），它是**唯一能改斜率的因子**。 |
| **两个被否掉的方向（都曾看着像解药）** | ① **testid 契约 CI 门禁**（我上一轮亲自推荐为「最狠的一刀」）—— **撤回**。实测 381 个被依赖 testid：83% 主仓直接命中、14% props 间接传入、**真找不到的只有 12 个（3%）**，其中一多半还是索引型动态 id 的误报。**那一刀砍在几乎不存在的靶子上。** 顺带一个反直觉数据：按定位手段算失败率，`testId` 步 **2.4%** 最低，`role+name` 6.7%——**她已经在按规范用 testid，而 testid 是最稳的一档**；定位类失败在绝对数上以 testId 步为主，只因为 testId 占了全部步骤的 62.7%。② **业界最响的 self-healing** —— 对本场景是**净负**。元素不在页面上时，语义/指纹 healing 会「自信地」挑一个相似元素点下去，在 92% 的场景里把「状态没到」healing 成「点了别的按钮然后继续跑」= **假绿**。 |
| **方案** | ① **reach-path 前置态断言（硬要求）**：每个「状态相关操作」之前必须先断言「我确实处在该操作应可见的状态」。**收益是双份的**：失败时报「前置态未达成」而非「元素找不到」，一眼指向造数链——**把那 92% 的误导性错误码修正掉，等于砍掉整轮误诊**。② **知识传递左移到交接卡（零成本）**：交接卡新增「状态流转落点声明」段（流转 → 落在哪个看板 → 要不要切 mode/子 tab → 受影响按钮 + 可见条件**谓词名**）。**这份知识开发改代码时最清楚，写 30 秒；她自己去发现要烧一趟 E2E（3~5min）＋一轮误诊。** 要求贴谓词函数名而不是复述条件，免两边表述漂移。③ **UI 状态契约抽取器**（Phase 1）：从前端源码抽「按钮可见需要什么状态」，**实测覆盖 87%**。 |
| **不完美** | ① 谓词是任意 TS 表达式，**不可能全自动翻成可查规则**；可行的是抽「名字 + 条件源码片段 + 涉及状态字段」再由人校对一次。② Phase 2（MCP `where_is()` 工具 + CI diff）**暂不做**——先让产物证明「写用例前查一次真的减少往返」再建工具与门禁。**理由就是本轮反复验证过的那条：先量再改**（这场复盘里已排错过两次优先级）。③ 抽取器支持两种渲染写法（只支持前者时覆盖率 66%，补上后者到 87%），**仍有 13% 抽不到**。 |
| **通用教训** | ① **别信错误码的字面归因**。平台只能报它看得见的现象，**归因是调用方的责任**；把 48% 的失败按错误码分类，会得出「定位脆弱」这个完全错误的结论，进而投错方向（我就投错了一次）。**排查任何高频失败，先问「这个错误码在什么情况下会被误报」。** ② **知识的成本形态比知识本身重要**：同一份事实，「每版发布一次」和「每趟踩坑一条」差的是一个数量级的往返数。**凡发现员工在反复重新推导同一件事，先问「这件事能不能一次发布」。** ③ **上游知道的事不要让下游去发现**（谁最便宜谁做）。④ **我这一轮自己犯的错值得记**：先推荐了 testid 契约门禁，是因为**拿「定位类失败」的错误码字面当了根因**、没先做交叉验证。修正它的动作只是一句「把失败的 testid 拿回源码里对一下」——**便宜的交叉验证要在提方案之前做，不是之后。** |
| **索引** | §3.96 |

## G-1 · 覆盖矩阵写侧正则未锚定 → `undefined.split`（reader 修了、writer 漏修）

| 段 | 内容 |
|---|---|
| **起因** | reader 早已因同一坑改成锚定正则并留注释。 |
| **现象** | `set_facet_coverage` 所有调用（任意参数）齐报 `Cannot read properties of undefined (reading 'split')`，而 `append_timeline`/`coverage_status` 却正常。 |
| **根因** | writer 用**非锚定**正则找段头。任务档案时间线里只要有一句散文内联了字面「## 覆盖矩阵」（**恰恰是上一轮记录这个 bug 的时间线，自己带了裸标题触发它**），正则就劫持到那处 → 截出的段无表头 → `headerIdx=-1` → `_rc(lines[-1])` 即 `undefined.split('|')`。**同源坑只补一半，是这类回归的典型。** |
| **方案** | 抽共享锚定正则（行首 lookbehind + 标题独占行 + 下一标题 lookahead，零宽故切片索引不变）替换 writer 两处；加 `headerIdx===-1` 兜底抛清晰错。 |
| **不完美** | **治标**（见 G-2）。 |
| **通用教训** | ① **修解析坑要 reader/writer 一起改**——同一份文档结构被多处正则解析时，修了一处必须 grep 同结构的其它正则一并改。② **诊断信息本身别带触发串**——这类元信息里的敏感字面量要中和（全角/去空格/代码转义）。③ 崩溃兜底优先给**可诊断报错**而非裸 `undefined.split`。 |

## G-2 · 行首锚定也治标：散文把标题写成独占一行照样劫持（G-1 复发）

| 段 | 内容 |
|---|---|
| **起因** | G-1「已修」。 |
| **现象** | 次日三个覆盖写工具**全崩**同一个错，读侧正常。QA 按红线（不碰引擎修复）留证交办、判 QA_FAILED 交老板——**判断与处置都对，但整轮机签作废。至此这颗雷咬了三个会话。** |
| **根因（两个独立原因叠加）** | ① **补丁写盘 ≠ 生效**：G-1 的补丁写进了工作区，但事故会话当时**线上跑的还是旧代码**。用已提交版复现，报错栈逐字命中。② **行首锚定本身治标**：G-1 的对策断言「散文里的『## 覆盖矩阵』因非行首且后随非换行被彻底忽略」——**只对内联形态成立**。一旦散文把它写成**独占一行**（巡视 note、markdown 引用标题都会），它同样满足「行首 + 标题独占行紧跟换行」，照样劫持。**reader 与 writer 都只锚「标题形状」，无法区分「真表头段」与「散文里复述的同名标题」。** |
| **根因（本质）** | 把「哪一段是覆盖矩阵」**锚在标题字面上**——而标题字面在正文里**可被合法复述**、天然不唯一。 |
| **方案** | 新增共享 `findMatrixSection(text)`：逐个 `## 覆盖矩阵` 标题，看**其正文里有没有 facet 表头行 + 分隔行**，只认有表头的那一段。reader 与 writer **统一走它**——读写口径从此一致、彻底不被劫持。删除 G-1 引入的治标正则。加 3 条写侧回归（内联 bullet / 独占一行裸标题 / seed 播种）。 |
| **不完美** | 同类隐患仍在：找「## 时间线」「## 需求条目登记表」等段**若也靠标题字面定位**，都有被正文复述劫持的可能——**宜按各自表头/特征行认段，但目前没有全部改完**。 |
| **通用教训** | ① **锚点要锚在「目标独有且正文不可合法复述」的结构上**，别锚可被散文复述的字面。② **「已修仍复现」先查运行时版本**——补丁写盘不等于生效。③ **治标补丁要在复盘里标注残留面**：G-1 断言「彻底忽略」把边界写死了，反而掩盖了独占行这一类；**写对策时如实写清「挡住了什么、没挡住什么」。** |
| **索引** | §3.73 |

# 族 H：前端结构性坑

**族病根**：结构性错误（注释配对、grid 轨道、视口单位、portal、CSS 特异度）伪装成「样式/内容/浏览器兼容」问题，把排查引向错误方向。

---

## H-1 · 一个 CSS 注释里的 `*/` 让整页样式塌陷

| 段 | 内容 |
|---|---|
| **起因** | 试切设计系统主题时写的顶部注释：`语义 token 名沿用旧命名（--canvas/--surface-*/--hairline/--ink*）`。 |
| **现象** | 主题色没了 / 消息无背景 / 头像徽标透明 / devtools 报「`--primary` is not defined」，背景全塌成透明。 |
| **根因** | 其中 `--surface-*/` 的**「星号紧跟斜杠」`*/` 提前闭合了注释**。注释后面的中文散文 + 行尾真正的 `*/` 于是被当成 CSS 解析，**污染了紧随其后的 `:root {` 选择器** → 整个 token 块不再应用到根元素 → 所有 `var(...)` 未定义。 |
| **为什么兜了那么多圈子（真正的教训）** | ① **误判成 oklch/color-mix 不支持** —— 一看到「颜色全透明」就联想到「较新 CSS 语法内核不认」，把全部 `oklch()` 转 hex、`color-mix()` 转 rgba，**全是红鲱鱼**。token 值是什么根本不影响，因为 token 块**自始至终没被应用**。② **盲改视觉、没做结构性校验** —— 看不到像素，只能靠 curl 看「服务端发了什么」，但那证明不了「浏览器解析成什么」。③ **老板从没真正看到那个新主题** —— 因为 `:root` 一直是坏的，他全程看到的「washed 亮色」其实是**无样式兜底态**。所以「新主题观感差」这个结论**没被公平验证过**，但他已选择退回，尊重之。 |
| **方案** | 改掉注释措辞 + 注释里显式警告 + 脚本校验 `/*`↔`*/` 配平。沉淀铁律：**改 CSS 后先做结构性自检（注释配对、括号配平）；CSS 注释里绝不能出现 `*/`；颜色一律 hex/rgba。** |
| **为什么退回成本低** | 全站走语义 token（架构第一天就定的）——退回 = 把 token 值换回来，全局自动复原。**这再次印证语义 token 层的价值（换肤/退肤都只改一处）。** 且**皮肤与功能干净分离**：退回只动 token 颜色/圆角/阴影/字距，功能改进（交互拍板气泡、消息时间戳/复制、5 态状态色、微动效、附件上传态）全留。 |
| **不完美** | 「盲改视觉」的固有风险仍在——改的人看不到像素，亮/暗两主题的实际观感只能靠事后眼校收口。 |
| **通用教训** | **CSS「整页塌陷」先查注释/括号/选择器结构，再谈颜色。** 一个注释里的两字符让排查跑偏了整整一轮版本。 |
| **索引** | §3.29 |

## H-2 · grid `auto` 轨道被代码块顶宽，容器上的 `min-w-0` 管不了轨道

| 段 | 内容 |

| **起因** | 窄窗聊天。 |

| **通用教训** | CSS Grid 的「溢出」问题九成不在容器上，在**轨道定义**上（`minmax(0, 1fr)` 而非 `auto`）。 |

## H-3 · iOS 视口单位方向记反 + `env(safe-area-inset-bottom)` 浏览器态常报 0

| 段 | 内容 |
|---|---|
| **起因** | 移动端适配。 |
| **现象** | 「首页可滚动区高度没算整屏」——内容止步于 Safari 悬浮底栏上沿、留一条不动空带；对照原生站内容会一路滚到**半透明悬浮底栏之下**。 |
| **根因** | 本应用是「内部滚动 app-shell」（`body{height:100dvh;overflow:hidden}`，滚动在内层），因**根文档从不滚动**，iOS Safari 底栏永不收起，此时 `dvh`/`svh` 拿到的是「**小视口**」= 底栏之上那块。 |
| **排查两个弯路** | ① 先去调 `padding-bottom`（env 安全区）——无关，裁切来自外壳高度单位；② **方向搞反**，先把 `dvh`→`svh`（仍是小视口）——没用。 |
| **方案** | 反过来用**大视口** `100lvh`（整屏高），`100vh` 兜底；聊天坞则**反用** `100svh` 让输入框稳停在底栏之上。 |
| **补丁（同日又冒出的问题）** | lvh 铺满后末项/页脚停在半透明底栏之下读不到。关键坑：`env(safe-area-inset-bottom)` **浏览器态常报 0**（底栏吸收了安全区），先用 `calc(env+44px)` 补净空**无效**（0+44=44 远不够盖 ~80px 高的底栏）。**自校准对策**：可收起工具栏高度**恰等于 `100lvh - 100svh`**（大视口−小视口 = 会收起那截 chrome），**浏览器算好、不猜像素**——`--fab-clear: max(calc(100lvh-100svh+16px), calc(env(...)+16px))`。 |
| **不完美** | 根治仍是改文档级滚动让底栏随滚动自动收起（**成本高、暂未做**）。 |
| **通用教训** | ① 三个视口单位方向别记反：`sv`=底栏展开时的小、`lv`=底栏收起时的大、`dv`=随动。② **要「工具栏实际占高」用 `100lvh - 100svh` 自校准，稳过任何写死像素。** ③ 安全区 `env()` 只管「独立态避让 Home 指示条」，与「浏览器态滚动区高度」是两码事。 |
| **索引** | §3.11 |

## H-5 · portal 换容器会重挂子树丢状态 + 拖动手柄抢走菜单项的 pointerup

| 段 | 内容 |
|---|---|
| **起因** | 聊天窗要能停靠为主页面第三栏。 |
| **根因** | 直觉方案是「把 portal 目标从 body 换成第三栏容器」，但**换 portal 容器会重挂整个子树、丢掉所有 React 状态**（流式 transcript、滚动位置、输入框草稿）。 |

## I-1 · 晨检包大面积空白：读的一侧建好了、写的一侧从没建

| 段 | 内容 |
|---|---|
| **起因** | 老板点开一份守航晨检包。 |
| **现象** | 「计划条目 0 / 本轮 0 条目 / version 空 / archive 空 / RC commit 未记录」，而**同一轮**前一晚手调出的包里明明白白有 2 条条目、有停靠明细。**同一轮守航，两份包，一份有事实一份没有。** |
| **根因（四个，全同族）** | ① 计划条目 0 —— `led.itemResults` **全仓只有一处读、没有任何代码写**（`grep -rn itemResults app/` 只有 1 处命中；台账 JSON 里根本没这个 key）。② version/archive 空 —— 守航 run 的 `taskFile` **32 条全是 null**。这有个容易看漏的合理性：**冷启动那一棒本来就没有档案**（PM 第三步才建档），所以出生时是对的——**错在建完档之后没有任何一条路径把它回填回 run**。而档案路径其实一直有机器出口：契约 frontmatter 的 `archive`/`version` 正是唯一被要求回填的两个字段。**「唯一出口」写在了 prompt 里，却没有任何代码去读它。** ③ 整章消失且**毫无标注** —— `reportGaps()` 的结果只出现在给 agent 的返回文本里，**没写进包**；而前端 toast 已经在对老板说「已在包里如实标注」。④ 每天开机重出空包 —— 包名带今天、run 名是昨天，去重集只活在内存 → 重启即重置。 |
| **方案** | `deriveItems()` 吃**五个机器源**（契约 `named_items` / 台账 / 风险定级 / park 台账 / 覆盖矩阵），绿数、证据 commit、RED 校准、需人工必验**一律以覆盖矩阵为准**；agent 传来的 items 只填机器算不出的空格，连 agent 的散文都被挪到「（agent 补注：…）」挂在机器结论后面——**诚实铁律在这一层的具体形态就是不给自述留一个能顶掉机器事实的字段**。写侧同时补上，且**记在动作发生的当下**（领到条目即立账、park 即记、状态变更按看板映射、冻结把 RC commit 记进**台账**而不是某一条 run）。 |
| **三处口径问题（拿真实数据一跑才揪出，单测全绿）** | ① **编号形态不统一**（契约里写 `req-316`，其余一律 `REQ-0316`）→ 条目表出现两行、「计划条目」翻倍 → 归一到补零 4 位。② **runId 有两种真实形态**（引擎侧 `20260826010203-1ead52`、平台侧 `session-...-round-1`）→ 只认前者会让平台签发的证据被当成「没有时间」→「park 和证据谁更新」**永远判成 park 更新**。③ **两轮守航会重叠**（同日两轮 deadline 相同）→ 改成「deadline 与**下一轮 `starts_at`** 的较早者」，且这个上界**只拦新条目**（引擎自己的「到点顺延自动 park」发生在 deadline 之后，对本轮已在册的条目必须照收）。**这条不对称是刻意的：窗口的两条边解决的是两个不同问题。** |
| **一条口径：事实打架时不静默选边** | 实测撞上一条：park 台账挂着「等 DDL 授权」，覆盖矩阵却是 6/6 全绿。判据是**证据的产权**：`COVERED_GREEN` 只能由引擎从真 summary 机读签发，而 park 只是 PM 侧的一条笔记。证据更晚 → 按证据算并点名「park 记录已过期」；park 更晚 → 维持 park，**同样点名**。**两种情形都留一行，绝不选完一边就把另一边抹掉。** |
| **不完美** | 这一版把「字段没人写」修好了，但**聚合单位本身还是错的**（见 I-2）。 |
| **通用教训** | ① **「读的一侧」先写完，会让缺口长得跟正常一模一样。** `itemResults` 有默认值 `\|\| {}`、有正确的遍历、有下游渲染——唯独没有生产者。空表在纸面上和「本轮真的没做」完全同形。**加字段时应同时问：谁写它？没人写的时候读到的是什么？读到那个值时报告会说什么？** ② **诚实自检要印在交付物上，不能只印给 agent 看**——自检结果必须和被检对象走**同一条投递路径**。③ **跨重启的去重不能只活在内存里，更不能靠文件名兜。** ④ **用真实数据跑一遍再收工**——守航这类「一天只跑一次、错了要等明天才知道」的路径，**必须用历史真数据回放验证**。 |

## I-2 · 晨检包的单位一直是错的：它按「一夜」出，而老板要验收的是「一个版本」

| 段 | 内容 |
|---|---|
| **起因** | I-1 之后第三天，老板说「概念很混乱，5.20 我多次守航追加条目，晨检包只展示了一开始的 2 条需求，而且下面的进度跟真实的任务进度不一样」。 |
| **现象（三个症状，一个根因）** | ① 一个版本裂成 N 份包，每份只讲那夜领的 2 条（包名带 run 名；而某版有 3 轮、另一版 4 轮，四份契约的 `archive` 全指向同一份档案）；② 进度与看板对不上（条目从「契约 `named_items` + 覆盖矩阵」倒推，**一次没读过「## 需求条目登记表」**。实测登记表写着某条「已上线」，包里还印「park 待拍 0/5」；**「阻塞」条目在八份包里一个字都没有**）；③ 做完的条目还在「等你拍板」（park 台账**无任何关闭路径**，单调增长）。 |
| **根因（一句话）** | **档案与 facet 表是版本级的，契约与三红灯台账是轮次级的，晨检包夹在中间取哪边都不对。** |
| **最刺眼的证据** | **模板自己**：第五章白纸黑字写着「**整版**通过 / 部分通过 / **整版**打回」——**版本级的决策语言，底下垫着轮次级的数据。概念从模板那一层就分叉了，代码只是忠实地实现了这个分叉。** |
| **方案** | 新 `version-report.js` 以**登记表为行集**，覆盖矩阵/台账/门禁只补列；矩阵有而登记表无的 REQ 单列 `orphanReqs`、**绝不混进主表**（「这一版有几条」不许有第二个答案）。落一版一份、每天覆盖写。 |
| **三件刻意的取舍** | ① **旧模块不删、降级留用**——结算算「本轮领了没做完的该顺延谁」要的**正是轮次语义**，换成版本级会把整版未完条目全顺延，**等于把病治反**；它同时是「绑不到版本」时的降级出包路径，这样它有真实调用点、可达性测试也不会把它判成僵尸。② **决策块提到第四章**——老板读完全表 + 卡住 + 待拍信息已经闭合，把勾选框放在审计材料之后等于让他为了落笔再翻两章。③ **「本轮增量」四源分档并印差集**，且**放弃「来源列含 run_name」**这个看起来最直白的判据（实测 3 条追加里只有 1 条写了轮次名）。改用契约点名 / 台账 / **覆盖矩阵 runId 落在轮次窗口内** / 进入日期。**第三源是唯一对已发生的四轮也成立的硬证据**（写侧才刚落地，历史四轮全空）——不加它，「本轮增量」上线第一天就是空的，又是一次同类事故。 |
| **park 的病根不是「缺关闭路径」，是一个计数器装了两种语义** | 台账里混着**真歧义**（PM 写了实质拟定口径，要老板一句话）与**引擎到点顺延的占位**，共用 `rounds`。于是「≥2 轮进必答区」**长期完全是反的**——必答区里全是顺延噪声，8 条真歧义全部 rounds=1、**一条都进不去**。先分家（旧数据按指纹回填），再谈出口。出口用**白名单三档**而不是「状态≠parked」的黑名单（黑名单会把「阻塞」「待梳理」也当成已消化关掉）。两条边界值得单记：**关闭口径收窄到「已上线/已归档」，不含「人工Pass/QA通过」**（过检 ≠ 发布；某条过检了，但它被 park 的那个问题在发布前**仍然是活的**）；**真歧义在推进中只降级、不关闭**，并单列一节写明「条目已推进，但你当初被 park 的口径问题从未被回答——后续多半是按拟定口径默认执行落地的，你要么追认、要么现在推翻」。**这句话是这次重构真正的价值增量。** |
| **顺手修掉的、我自己前一天造的 P0** | `recordPark` 命中已有条目时会覆盖 `reason`/`proposal`。deadline 顺延此前因条目账恒空**从来没真触发过**；I-1 把账接通后它首次触发，**把 PM 写的实质口径整段覆盖成了「deadline 到点未达 RC_READY」**。原文只在当轮包里还留着，已据此恢复。**教训：给一条长期沉默的代码路径接上输入之前，先读一遍它被触发后会写什么。「它一直没跑」不等于「它跑起来是对的」——恰恰相反，从没跑过的路径没有被任何真实数据检验过。** |
| **三个真 bug，单测全绿时一个都没露头** | ① 「进入日期」只精确到天，拿它去比带时分秒的窗口**一定**落空；② 复用轮次渲染器时它自带章号，版本单里冒出两个「四」；③ 显式要 A 版却把当前 run 那份 B 版档案原样带了进来，产出一份「版本写 A、条目却是 B 那 9 条」的**假单**——**比不出单坏得多**。**共同点：它们都在「模块边界之间」，而单测测的是模块内部。** |
| **第三次重构（改载体）** | 老板追问「能不能跟任务档案合并」。三条事实指向「本来就该合」：主键改成版本后已 1:1；晨检包文件**没有任何机器消费者**；仓库里已有先例。改成任务卡上的**页签**（视图）。**一条值得单记的判据**：**派生内容落成文件，就必须再造一套「防它过期」的机制。** 为了让文件不过期专门加的 5 分钟扫描 + 每天重出，改成视图后**整套删掉**了——视图的新鲜是免费的。**「要不要落文件」这个决定，附带决定了「要不要养一套保鲜机制」**，而后者的成本常常比前者高，还会自己长出新的失败模式（**文件在、内容过期，比没有更坏**）。同时否掉「写成档案里的一节」——那只是把重复从「另一个文件」搬到「同一个文件的另一节」。**判据是「这份内容有没有人手写」**。 |
| **不完美** | DOM/交互层**没做真浏览器核验**（浏览器 profile 被占用，不抢老板正在用的）；已验证的是端点、产物 grep、类型检查与单测。 |

## I-3 · 教训库「只写不读」：攒了四条一模一样的教训，全都没改变下一次运行

| 段 | 内容 |
|---|---|
| **起因** | 菲菲做发布沟通那一棒，**四件交付物只产出第 1 件**就 `【交回】`。老板发 `?` 追问时她还确认「已全流程收官…没有需要我执行的动作」；直到老板直接问「**你的 sop 里，版本上线后你要做什么？**」，她才 grep 自己的工牌、认漏、当轮补齐。 |
| **这次 SOP 是清白的** | 上一次同族事故（同一个漏子）的对策之一就是「把关键约束提到始终注入的工牌里」，那条对策**确实落实了**：工牌 line 18 白纸黑字写着「发布沟通是**四件交付物**不是三件套，第 4 件最常被漏，别做完前三件就收工/交回」。**规则就在她眼前，仍然被派工文案盖过去了**——委托原文只点名「请产出**版本发布说明**」，她把「本轮派工写了什么」当成了任务全集。 |
| **四层根因（每层都是独立的洞）** | ① **软门禁的触发条件写反了**。`releaseCopyCardMissing()` 要求「本轮汇报里同时出现 版本发布说明 + CHANGELOG」才认定「这轮在做发布交付物」、进而检查第 4 件。这轮汇报里根本没有 CHANGELOG 二字 → 静默跳过。**它防的是「做完 3 件漏第 4 件」，防不了「只做 1 件漏 3 件」——漏得越狠越不报警。** ② **置终态零门禁**：下游收到 1/4 的交回，照样 `set_task_status → DONE`。流水线上「**交回了**」被无声地等同于「**做完了**」。③ **巡视没有硬事实可对**：它唯一的输入是收尾原文，而那篇原文写得非常完整自洽（三来源交叉比对、对账、时间线回写全都真做了，**只是范围只有四分之一**）；何况她写了 `【交回】`，`patrolEligible` 本来就把带交接标记的停顿整个豁免。④ **教训库只写不读**：这个漏子在记忆库里**已经记了四条**，其中一条原文是「四件交付物里第 4 件微信发版通知，**即便派工只点名了前三件**，仍要按红线补齐」——**几乎就是这次事故的预言**。但引擎只在收工时 `appendLessons()` 往 memories 追加、**派工时从不注入**，教训全靠员工自己想起来去 Read（那一轮她一次没读）。**「自动沉淀」这个机制此前只做了写侧那一半。** |
| **方案（不再加规则，加机器闸；一份 checklist 喂三处闸口）** | ① **核对函数 `releaseDeliverableCheck(taskFile)`**：按**落盘事实**逐件核对四件，不看汇报措辞（① 文件存在；②③ 两份台账有 `## <version>` 条目，正则加 `(?![\w.])` 防 v5.1 误命中 v5.19；④ 本任务线里她哪一轮真印过 `code` 形态卡片）。版本目录锚点取 `facet_doc` 的目录——**不新增配置项、不 hardcode 目录名**；定位不到一律返 `null` 判「不适用」，**宁可不判也不误挡**。② **三处消费**：收工软门禁改**阶段触发**（`status=PM_RELEASE_NOTES` 即认定这轮该交四件，旧关键词路径保留为 OR 分支，只加不减）、置终态**硬门禁**、巡视注入**缺件清单当硬事实** + 「写了交接标记不豁免」。③ **教训库注入（读侧补齐）** `buildLessonsBlock()`：按本轮派工内容选相关教训（中文 2-gram 重叠 + 英数整词，**除以 √长度防长条目恒赢**），上限 14 条 / 5000 字符。**刻意不搬全文**（两位员工的记忆库各 81k/95k 字符，整本灌进去会挤掉工牌本身）。回归测试里钉死了一条：把那条真实派工原文喂进去，「即便派工只点名了前三件」那条**必须**被选中。 |
| **适用边界（fail-open 的三道条件）** | 拿不到版本目录锚点、`gates.released_prod ≠ true`（**四件是上线之后才欠的**，被取消/并进别版的任务归档不该被拦）、没有那两份通用台账 → 一律返 `null` 判不适用。 |
| **实测** | 10 条新单测 + 全量通过；离线跑指向真实 `tasks/` **60 份档案**——54 份判「不适用」（**零误挡**）、4 份四件齐、**2 份查出真缺**（回扫全部相关 run 坐实：12 个版本有发版文案、这两个一条都没有），**此前无人发现**。 |
| **不完美** | 这道闸只覆盖「发布沟通四件」这一个具体职责；**「一棒 = 一个整包」的其他职责没有同类核对函数**。 |
| **通用教训** | ① **门禁的触发条件不能建立在「已完成的工作量」上**——用「你已经做了三件」来判断「你该做第四件」，**等于要求违规者先合规到一定程度才会被抓**；正确的锚点是**阶段/职责**，它不随完成度变化。② **同族事故复发时，先查上次的对策是不是「只做了软的那一半」**：上次三条对策里「改命名锚点」「提到工牌」都落实了，唯独「引擎校验」实现得太窄（只覆盖 3→4 的窗口），于是同一个漏子换个入口就复发。**软对策管不住的，硬对策也别只做一半。** ③ **派工文案会覆盖 SOP**——LLM 员工把「本轮指令」当任务全集是**默认行为**，规则写进系统提示也压不住；凡「一棒 = 一个整包」的职责，必须在**交付侧**（门禁/工具）而不是**指令侧**（措辞）钉死。④ **写了不读的记忆等于没记**：任何「沉淀」机制都必须**成对**——有写就要有读侧的注入策略（含预算与选取规则），否则它只是一份没人翻的档案。⑤ **交付物别起会「数漏一件」的集合名**——「三件套」这类响亮标签会变成心智锚点，把编号外的「+1」挤掉。 |

## J-1 · 用性能指标代理内核事实：托盘把「引擎在忙」判成「引擎死了」

| 段 | 内容 |
|---|---|
| **起因** | 老板报「lab 崩溃好几次」。 |
| **取证结论** | **引擎自己一次都没崩。** `node.exe` 在 Windows 事件日志/WER 里**零** APPCRASH 记录，无 OOM abort、机器没重启也没休眠。**run jsonl 的写入时间戳把真相钉死了**——12:30 被判死的那个实例，此后**又正常干了半小时活**。推论：那两次拉起的 node **必然撞 EADDRINUSE**（端口被仍在干活的真引擎占着）→ `process.exit(1)` → 托盘记「异常退出 code=1」→ 4s 后自动重启 → 再自杀。**用户感知的「崩溃好几次」= 替身自杀的气泡串。** |
| **根因（三条，同一个认知错误的三处复发）** | 把「**服务是否活着 / 端口是否被占**」这个**内核事实**，用「health 能不能在 1~2 秒内应答」这个**性能指标**去代理。引擎忙一下（多会话流式 + jsonl 落盘 + 新上的大响应 br 压缩）就被判死：① **心跳单次超时即判死**（一次抖动 = 死亡判决书）；② **判死时把把手扔了**（`monitorPid = $null`）→ 此后托盘**再也管不到真引擎**，右键「停止/重启」只作用于那个自杀的替身（这正是为什么最后只能手动硬杀）；③ **防重复拉起的判据也是 health**——注释里写得明明白白「不重复拉起，否则 node 撞 EADDRINUSE 变僵尸」，**这道防护被 1 秒超时从内部绕过了**。 |
| **两个观测缺口（所以事后什么现场都不剩）** | ④ cmd 重定向是**截断**——三次拉起相隔 4~30s，替身写下的 `[fatal] 端口已被占用` 被下一次拉起当场冲掉，三轮全没。⑤ 崩溃自动重启分支**只弹气泡不写 tray.log**（退出码不落盘），停服也不记 → 事后**无法区分「用户点了重启」和「进程崩了被自动重启」**。排查时正卡在这个二义性上，只能靠 jsonl 时间戳侧面还原。 |
| **方案（五条，全在托盘侧；引擎一行未改）** | ① **端口有没有主，只信 TCP 监听表**（`Get-NetTCPConnection -State Listen`，失败退回 `netstat -ano`）；health 只用来区分「活着且响应」与「占着端口但不应答」。② **一次超时不算死**（连续 3 次 ≈12s；单次超时 2s→3s，**没提到 5s：心跳跑在 UI 线程上，阻塞太久会连累托盘菜单响应**）。③ **判死也不丢把手**——连续失败但端口仍有主 → 判「卡顿而非退出」，`monitorPid` 校准为端口主 PID 并保留；`$manageable` 同步放开到 `unhealthy` 状态（**卡顿/半死实例正是最需要接管清理的时候，原先菜单恰恰在此刻灰掉**）。④ **保住崩溃现场**（`Archive-Log` 追加进 history，超 4MB 滚存）。⑤ **崩溃与停服都留痕**，**并顺手记下当时端口的占用者**（`code=1` + 端口另有其主 = 撞端口自杀的指纹，日志里一眼可辨）。 |
| **不完美** | **没有走「拉起前先 kill 端口占用者」这条路**——那等于把误判从「多起一个自杀进程」升级成「误杀正在干活的引擎」，**代价反了**。也没有取消崩溃自动重启（真崩时它是对的）。**「误判→自杀」的整链真机复现需要制造一次引擎卡顿，未做。** 自测中抓到一个小坑：`Archive-Log` 只判字节数会把 BOM+换行的空日志也转存 → 收紧为 `IsNullOrWhiteSpace`。 |
| **通用教训** | **判断「资源是否被占/服务是否存活」要用内核事实（TCP 监听表、进程表），不要用性能指标（响应时间）代理。** 后者在被判断对象「忙」的时候必然误判，而「忙」恰恰是最不该判死的时刻。 |

## J-2 · 「跳过」是个危险的默认：托盘对 web 端口只旁观不接管

| 段 | 内容 |
|---|---|
| **起因** | 用户报：启动托盘之后有一个残留的终端窗口，关掉它整个程序都关掉了。 |
| **排查过程值得记，因为第一版判断是错的** | 第一反应是 Windows Terminal 控制台移交（默认终端已是 WT，实测 `DelegationTerminal` 确实指向它），于是 `start "" powershell -WindowStyle Hidden` 的控制台被移交给 `WindowsTerminal.exe`——窗口属于 Terminal 而不属于 powershell，两处隐藏双双失效。**听起来严丝合缝，而且能解释「日志写着已隐藏、窗口却还在」。** **实测把它否掉了**：照原样起一个 powershell，结果是 `MainWindowHandle=0`、子进程是 `conhost.exe`、`GetConsoleWindow()` 返回**非 0**（所以脚本内隐藏有效）；三条正式入口**都不留窗口**。 |
| **一个反直觉的观测** | 同样一句 `GetConsoleWindow()`，在**继承现成 ConPTY** 的进程里返回 0，在 `start` 新起的进程里返回非 0。**所以「拿 GetConsoleWindow 判自己有没有窗口」本身就依赖启动方式，不是个稳定判据。** |
| **真凶** | 进程树一拉就清楚：机器上挂着**四条手工终端起的前端链**（父进程全已死 = 终端早关了，只剩孤儿）。而托盘的 `Start-Web` 当时是 `try { Invoke-WebRequest ... -TimeoutSec 1 } catch {}; if ($webBusy) { Write-TrayLog "端口已在跑，跳过拉起"; return }` —— **一句日志，然后 return。** 托盘把自己降级成旁观者：界面的实际宿主是那个手工终端，托盘既不知道、也不告诉用户、更接管不了。关掉那个终端 → `sh.exe` 死 → 下面的 corepack/cmd/vite 全死 → **4700 没了**；而引擎是托盘用 `CreateNoWindow` 起的孤儿进程、**毫发无伤**。**用户感知「整个程序都关掉了」，实际死的只有界面**，故障现象与真凶隔了三层，几乎不可能自行归因。 |
| **为什么这是真缺陷而不是「用户不该手工起」** | **引擎侧早就有对称的正确做法**（端口被占时转监控模式、记 PID、弹气泡明说「已接管」、右键停服时 kill 那个外部 PID）。**web 侧缺了这一整套**——同一个托盘里，两个端口一个有主人、一个没有。**不对称本身就是 bug 的温床**：引擎那条路被 J-1 打磨过，web 这条路**从没被逼问过**。 |
| **方案（把引擎那套原样搬过来）** | ① 端口真伪统一走 `Get-PortOwnerPid`（这条 J-1 的结论早写在注释里，**web 侧漏用了**）；② **`Test-IsDescendant`**：`$script:webproc` 拿到的是 **cmd 外壳** PID，真正监听的是它下面好几层的 vite node，**直接比 PID 永远不等**，会把自己起的也误判成外部 —— 沿 `ParentProcessId` 上溯判子孙（实测能穿过 `sh → corepack → cmd → node` 四层）；③ 外部占用 → 转 web 监控模式、日志点名到具体进程与命令行、弹气泡明说「⚠ 关掉那个终端窗口界面就会没（引擎不受影响）」；④ `Stop-Web` 支持**接管收编**（沿祖先链一并收，**只杀叶子的话祖先会立刻再拉一个占回端口**）；⑤ 安全护栏（只杀「进程名 ∈ node/cmd/sh/bash/pwsh 且命令行含 vite\|pnpm\|npm\|corepack\|office-lab\|web」的，实测拿 `python -m http.server` 占端口试过、判 False，**不擅自动手，只记日志**）；⑥ **托管方露脸**（状态行加「界面⚠外部托管(PID xxx)」——**不露脸正是这次归因难的根源**）。 |
| **不完美** | 安全护栏是名单式的，非前端但符合名单特征的进程仍有误杀面（已尽量收窄）。 |
| **通用教训** | ① **「跳过」是个危险的默认**。`if (busy) { log; return }` 读起来无害，实际是把一个资源的所有权悄悄让给了未知第三方，而且不留把手。**凡「发现别人占着就跳过」的地方，都该问一句：那之后谁负责它？用户怎么知道？我还能不能收回来？** ② **同一进程里管着两种资源，处置方式必须对称**——不对称不是「另一个比较简单」，是**它还没被事故逼问过**，那就是下一个 bug 的位置。③ **排查时先证伪自己最漂亮的假设**。**能被一条命令验证的假设，别拿它当结论。** |
| **索引** | §3.105 |

## J-3 · `uncaughtException` 兜底把启动期致命错误吞了 → 僵尸进程越堆越多

| 段 | 内容 |
|---|---|
| **起因** | 为了「单条 run 的异步异常不拖垮办公室」装了 `process.on('uncaughtException', e => console.error(...))` **只记录不退出**。 |
| **现象** | 老板说「officelab 好像有性能问题，重启好几次了」。现场 `tasklist` 抓到 6 个 office-lab node 进程，`netstat` 显示只有 1 个真正 `LISTENING`。 |
| **根因** | `server.listen()` 没挂 `error` 监听 → 端口被占时 EADDRINUSE 作为 server 的 `error` 事件抛出 → 无监听则升级为 `uncaughtException` → 被兜底吞掉 → 于是**绑不上端口的进程也不死**，只剩 `fs.watch` + `setInterval` 空转。每次「重启」若没先杀旧进程，新进程就变成又一个僵尸。 |
| **方案** | `server.on('error')` 命中 EADDRINUSE 即打印「已有实例在跑」并 `process.exit(1)`。 |
| **不完美** | 5 个僵尸进程要按 PID 定点清理（运维记忆明确「重启走托盘、不强杀、绝不 rm 生产 `runs/`」，故清理需人工确认后按 PID `taskkill`——它们都不占端口，定点杀不误伤在服务的实例）。 |
| **通用教训** | **韧性兜底（`uncaughtException` 不退出）与「启动期致命错误必须退出」是矛盾的两种诉求**——必须给 `listen` 单独挂 `error` 监听显式 `exit(1)`，**让致命启动错误绕开兜底**。这条后来又以另一种形态咬了一次：验证某个改动时一度以为代码没生效，实为**遗留旧测试进程占着端口**、新实例 EADDRINUSE 自退。**测试实例务必用完即杀、别让旧进程在端口上冒充新代码。** |
| **索引** | §3.30 |

# 全局：这些事故留下的 12 条设计原则

按引用频次排序。每条后面标出它是从哪几个案例里长出来的。

| # | 原则 | 来源 |
|---|---|---|
| 1 | **判据要挂在本层能直接观测到的事实上，不是别人给的信号。** 凡把布尔判断托付给模型/上游的措辞，引擎侧必须留一条不依赖措辞的旁路。 | A-2 A-4 A-5 A-6 A-7 C-2 F-6 |
| 2 | **SOP 是软约束、工具与门禁才是硬约束。** 对 SDK 员工，不在工具表里的能力等于不存在；能被绕过的规则等于没有。 | F-1 F-2 F-4 F-5 I-3 |
| 3 | **修 A 类问题别引入 B 类问题。** 能被动暴露 + 交回控制权，就不要主动接管。 | A-3 B-1 B-2 B-6 |
| 4 | **门禁的触发条件必须是它自己能验的事实**，不能是「已完成的工作量」，也不能是被门禁对象提供的自述。 | I-3 §21.6 F-4 |
| 5 | **横切策略（压缩/缓存/限流/轮询/截断）的落点必须是唯一出口**，不是「当前看到的那几个分支」。 | D-3 §3.47→§3.83 |
| 6 | **「未验证」绝不能被写成「通过」；「我猜错了门」绝不能被写成「对方没做」。** 新指标不许自带虚假健康值，也不许自带虚假的「零」。 | D-5 I-1 §21.3 |
| 7 | **锚点/守卫的粒度要选对**：锚在「目标独有且不可合法复述」的结构上；守卫按线程判而非按员工判。 | G-1 G-2 B-2 |
| 8 | **单一事实源要靠收敛，不能靠口号。** 手写副本、写死副本、派生但落成文件的副本，都会漂移；砍掉数据源比催人同步有效。 | C-1 C-2 C-3 C-4 I-2 |
| 9 | **交付形态的验收要在交付形态本身上跑。** 真 clone 一次、拿历史真数据回放一次、离线跑一遍存量数据一次。 | C-5 I-1 I-2 §6.4 |
| 10 | **「改了代码」≠「代码在跑」。** 排查「已修仍复现」，第一件事是确认线上实际加载的版本。 | E-1 G-2 B-1 |
| 11 | **「跳过」是个危险的默认**；**失败必须「响」**；**截断必须自证**。凡是悄悄少做一点的地方，都要留一句「这里少了什么」。 | J-2 D-4 D-6 D-2 |
| 12 | **排查时先证伪自己最漂亮的假设**；**便宜的交叉验证要在提方案之前做**；**先量再改**。 | J-2 F-6 H-1 §3.90 |
