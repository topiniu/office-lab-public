# office-lab 后续优化路线与差距分析

> **基线**：0.10.0（`[Unreleased]`）· 单测 449/449 · 核对日期 **2026-08-31**。
> **用途**：回答「如果重构你会怎么做」「怎么产品化」「技术债怎么排优先级」。**每条都写清「不做会怎样」和「做了要付什么代价」**——只列方向不列代价的路线图没有价值。

---

## 1. 当前成熟度评级

| 维度 | 评级 | 依据 | 距离下一级差什么 |
|---|---|---|---|
| **编排骨架** | **生产可用（单人）** | 四标记协议 + 服务端守卫 + 抄送原语 + 跨线程队列 + 三种非流水线会话，449 条单测 | 同员工真并行（需 worktree）；显式路由表 |
| **健壮性** | **生产可用** | 三层正交监督（进程/模型/协作）+ 收工即校验 + 持久裁决签名 + 跨重启补偿 | 巡视判断准头无量化基线；`liveRuns` 在内存，重启丢审批挂起态 |
| **质量门禁** | **机制成熟，覆盖不全** | 机器证据血缘 + 五态语义 + 三个 linter + 全路径 fail-closed；假绿式偷懒已基本堵死 | facet 全集本身的盲区（横向 facet）；`SOURCE_ATTESTED` 软性回避真跑；平台 console/pageerror 缺失 |
| **无人值守（守航）** | **L0 陪跑** | 契约 + 三红灯 + 门禁矩阵 + 发布链对账 + 版本级验收单已跑通 | 平台方案给的 L1 判据是「晨检包自动产出 + 三红灯连续 3 轮全 0 + 证据全部 verify 通过」——**第一项具备，第二项要跑起来才有数，第三项卡在外部接口** |
| **可移植性** | **可交付（Windows）** | 三层路径语义 + 双形态探测 + 跨平台首启 + 仓库完整性自检；真 clone 两份验过 | **macOS 真机首启未验**；macOS 常驻未实现 |
| **安全** | **仅适合单人内网** | 三名单 + `DANGER_DENY` + code-lock + 只读窗零挂载 + 凭据脱敏 | **本地 HTTP 无鉴权且默认绑所有网卡**——这是唯一的实质口子 |
| **可观测性** | **够用** | 30+ SSE 事件 + 手机推送 + 托盘 Toast + 台账/审计 jsonl | 无统一 traceId、无指标面板、无跨 run 聚合 |
| **产物治理** | **不足** | 剥图 + 列表投影 + 分页缓解了症状 | **无 retention policy**（唯一必然恶化的债） |
| **团队化** | **未开始** | — | 多用户 / 权限 / 数据库化归档 / 共享报告 |

**一句话定位**：**机制自洽的单人/小团队本地编排平台**，在「让 AI 的结论可被机器验证」这一点上做得比多数同类深，但在「多人可用、产物可治理、外部依赖闭环」上还没开始。

## 2. P0（不做这五条，其它都是在往上叠）

### P0-1 · 本地 HTTP 鉴权

- **现状**：默认绑 `0.0.0.0`（局域网/Tailscale 可访问），**无任何鉴权**。`OFFICE_LAB_HOST=127.0.0.1` 可锁回本机，但那砸掉「手机走隧道访问」这个真实用法。
- **不做会怎样**：同网段任何进程可**触发派工**（起真实 agent 改代码）、**读写仓库文件**、读取会话历史与凭据脱敏前的部分信息。
- **做法**：随机 token（首跑生成、落 `runs/`，设置页可看）+ Origin 校验 + `X-OL-Token` 头；SSE 走 query param（EventSource 不能带自定义头）；旧 UI 的 fetch 包装一处注入（已有 `installNetBar` 包裹 `window.fetch` 的先例）。
- **代价**：手机/隧道访问要带一次 token；托盘悬浮窗与 `/approve` 页要跟着改。**约半天。**
- **为什么排 P0-1**：它是唯一「别人能主动伤害你」的口子；其它债都是「自己越来越难受」。

### P0-2 · `runs/` 保留策略（retention）

- **现状**：曾达 291MB / `index.json` 626KB。已做剥图（-24.7MB）与列表投影（3586KB→320KB），但**没有任何清理机制**。
- **不做会怎样**：**这是唯一必然恶化的债。** 磁盘线性增长；`index.json` 全量序列化的成本随 run 数线性上涨；`/history` 与 SSE 冷开仍是「整文件读进内存再切片」。
- **做法**：分三档——① 活跃（近 N 天 / 未终态）原样；② 归档（终态且超 N 天）压缩 jsonl（`.jsonl.br`，读时按需解压）；③ 过期（超 M 天且非里程碑）只留 `index.json` 里的摘要行 + 删 jsonl。里程碑（被任务档案引用为证据的 runId）**永不删**——这条要先建一份「哪些 runId 被引用」的反向索引。
- **代价**：需要「被引用 runId」反向索引（从覆盖矩阵证据串 + 任务档案时间线抽），否则会删掉正在被当证据的 run。**约 1-2 天。**

### P0-3 · QA 只测不可变 commit（治「移动靶」）

- **现状**：QA 测的是 **working tree**，证据绑的是 `git commit`（reconcile 时读取）而非**运行产物指纹**。某版至少 8 次「QA 后又改码」→ 旧证据作废 → 至少重跑 3 轮。
- **不做会怎样**：机器 GREEN 的可信度有一个天花板——**它证明的是「某次跑过了」，不是「当前这份代码过了」**。
- **做法**：三步递进——① 守航态交接前**强制 commit**（哪怕 WIP，`freeze_handoff` 已有雏形，未 commit/未 push 直接拒）；② 证据同时绑 **commit + 运行产物指纹**（前端 bundle 编译时间戳/构建指纹 + 后端 `target/classes` 指纹）；③ **改码即自动作废受影响 facet 证据回 `UNCOVERED`**（`impact_radar` 已有雏形）。
- **代价**：③ 需要「改动文件 → 受影响 facet」的映射，目前靠 `impact_radar` 的启发式；误判会把好证据打回（**代价可接受：多跑一轮 vs 放过一个假绿**）。**约 2-3 天，且需要平台侧配合出产物指纹。**

### P0-4 · 环境新鲜度探针

- **现状**：曾有一次前端 dev server 缓存崩掉 → watcher 卡死 → **长时间发陈旧 bundle**，是「故意改坏两次都不红」才被发现。**跑前没有任何新鲜度校验。**
- **不做会怎样**：假绿的最后一条大通道——**证据全齐、哈希全对，但测的是三小时前的代码**。
- **做法**：跑前校验前端 bundle 编译时间戳/构建指纹与后端 class 指纹，写进 summary；**不新鲜判 `blocked` 而不是继续跑绿**。`fakeGreenHunt` 里已有对应判据（「环境指纹整体陈旧 → 可信度直接判 0，不是逐条打折」），只缺指纹来源。
- **代价**：需要一个「怎么算指纹」的约定（前端 `dist/index-*.js` 的 mtime + hash；后端 `target/classes` 最新 mtime）。**约半天，且依赖 P0-3 的产物指纹。**

### P0-5 · `console` / `pageerror` 纳入自动化默认门

- **现状**：**平台 headless 不采集 `console` / `pageerror`，也没有任何「无 JS 报错」断言类型**。
- **不做会怎样**：**一整类前端崩溃在自动化里不可能变红**——「点一下就抛 TypeError、整页白屏」这种 P0 只能靠人手工用出来（v5.19 那两个逃逸缺陷之一正是这样）。
- **做法**：任一 page error / console error 级即判红（可 allowlist）。**这条在平台侧，不在 lab 侧**——lab 侧要做的是消费端准备好（已有 `visual_acceptance` / `preflight_gates` 的消费点，走 fail-closed 降级等接口）。
- **代价与风险**：allowlist 会成为新的逃生舱（**已实证**：为让报错门闭嘴，某轮往共享库累积了 24 条 allowlist，其中 7 条过宽、对所有用例生效，包括**被测产品自己的微前端宿主域**）。**所以这条必须和「allowlist 作用域 + 阶段 + 过宽告警」一起做**，否则治好一个病造出另一个。

## 3. P1（消除结构性风险与重复成本）

### P1-1 · `server.js` 分层（8770 行单文件）

**问题**：路由是 if 链、**顺序是隐式契约**；`autoChain` 一个函数塞了背书延迟转发、QA 闸门、发布核对、四种标记分支、巡视分流；`import` 即 `listen` 导致纯函数**不能直接 import 单测**（现有回归只能「按名从源码抠出定义再 eval」）。

**做法（按风险从低到高）**：
1. **`listen` 挪进 `main()`**（`if (import.meta.url === ...) main()`）→ 立刻让纯函数可 import，测试从「抠源码 eval」升级为真 import。**这一步风险最低、收益最大。**
2. **显式路由表**替代 if 链（`[method, pattern, handler]` 数组 + 首个匹配）→ 消除「顺序是隐式契约」。
3. **`autoChain` 拆三段**：`parseMarkers(result)` → `runGateChain(run, markers)` → `dispatchAction(verdict)`。三段各自可单测。
4. 把已抽出去的 16 个模块的调用点收进薄 facade，减少 `server.js` 直接依赖数。

**代价**：`autoChain` 是全仓最 delicate 的函数之一（它承载了族 A 的全部修复），拆的时候**必须先把现有行为钉成测试**（`spin-and-patrol.test.js` 的回放法可复用）。**约 3-5 天，建议分四次提交、每次一小步。**

### P1-2 · 协议 schema 单一事实源

**问题**：run 形状 / 标记协议 / 覆盖矩阵列契约 / 条目状态枚举，全靠约定 + 三处同步注释（`server.js` 校验 = 前端渲染 = 规范文档，靠脚本核对键集一致）。

**做法**：不上 TypeScript（引擎的「无构建」是刻意的），而是：
- 抽 **JSON Schema** 放 `app/schema/`，`zod` 已是生产依赖 → 可直接用 zod 定义 + `z.toJSONSchema()` 导出；
- 前端 `web/src/lib/types.ts` 从 JSON Schema **生成**而非手写；
- `文档格式规范.md` 里的枚举表从 schema **生成**一段（或至少加 CI 式的一致性脚本，现有的键集核对脚本升级）。

**代价**：`web/` 已是 TS，生成类型是净收益；引擎侧要接受 zod schema 的运行时开销（极小，已在用）。**约 2 天。** **注意别过度**：只给「跨模块/跨端/跨人」的四个协议做，run 内部字段不必。

### P1-3 · `parseFrontmatter` 换成健壮解析

**问题**：自研 YAML 子集只覆盖标量/布尔/一层嵌套/字符串数组。**档案格式一旦超出子集会静默解析错，而看板据此渲染 → 错得无声。**

**做法**：两条路。① 引入一个极小的 YAML 解析器（但违「零依赖」）；② **保持自研，但把「超出子集」变成显式错误而不是静默降级**——遇到不认识的结构就抛 + 在看板上显示「档案 frontmatter 有本解析器不支持的结构：<行号>」。

**推荐 ②**：它守住了零依赖，且把「无声的错」变成「有声的错」，符合本项目一贯口径。**约半天。**

### P1-4 · 共享环境的产权边界

**问题**：一个库同时是开发库和测试库；QA 造数直写全局主数据（自建测试品类进共享表，收工靠手工清理；还撞见预置数据被并发置停用，**至今只能靠「我没碰过」互相排除**）。**这不是纪律问题，是缺租户/前缀/独立 schema 的结构问题**——Anthropic 红队报告点名的正是这条。

**做法**：① dev 与测试库分离（基建层，不在 lab 侧）；② QA 造数走**专用租户/前缀**（如所有测试数据名带 `__QA_<runId>__`）；③ 收工自动核**预置数据完整性**（`residue_report` 工具已有雏形）。

**代价**：② 需要被测系统支持前缀过滤，可能要改产品代码。**这条是 lab 侧推不动的，要作为「向基建提的需求」列出来。**

### P1-5 · 把「一棒 = 一个整包」做成通用核对，不只发布四件

**问题**：`releaseDeliverableCheck` 只覆盖「发布沟通四件」这一个具体职责。**「派工文案会覆盖 SOP」是 LLM 员工的默认行为**，凡「一棒 = 一个整包」的职责都有同一个漏子。

**做法**：抽一个通用形态——`stageDeliverableCheck(stage, taskFile)`，每个阶段声明「本阶段的整包是哪几件 + 每件怎么按落盘事实核对 + 不适用的三道 fail-open 条件」。已知需要的：PM_INTAKE（需求说明 + facet 表 + 七项拷问打标）、DEV_HANDOFF（交接卡 + 实施记录 + 人工预检单 + 状态流转落点声明）、QA（测试用例 + 结果报告 + 覆盖矩阵 + 缺陷单）。

**代价**：每个阶段的「怎么按落盘事实核对」都要单独想清楚，且必须遵守「宁可不判也不误挡」（上次实测 60 份档案零误挡）。**每个阶段约半天，共约 2 天。**

### P1-6 · 两套 UI 的定位收窄

**问题**：能力对齐靠人工清单，有过整轮「逐文件比对新旧 UI 按清单修 bug」。

**做法**：明确把旧 UI 降级为**「兜底只读 + 配置面板」**——保留任务看板查看、运行列表、会话回看、5 个配置面板；**不再跟进新功能**（facet 抽屉、晨检验收页签、快捷动作、GSAP 动效等一律只在新 UI）。在旧 UI 顶部加一条「这是兜底界面，完整功能请用 4700」。

**代价**：`office-lab/` 前缀这个协议常量仍由旧 UI 的正则依赖着，**所以旧 UI 不能删、只能冻**。**约半天（主要是决策 + 一条提示 + 文档口径）。**

## 4. P2（提效与降本，先量后改）

### P2-1 · ★ 快车道任务分级（唯一能改「手感」的一条）

**这是效率复盘十轮之后唯一被认定为「提速主路」的改动。**

```
现状：每个任务（不分大小）
  PM[冷启动:全量SOP+227KB档案] ─卡→ 开发[冷启动] ─卡→ QA[冷启动] ─卡→ DevOps[冷启动]
  厚SOP全量常驻 · 任务档案只增不减 · 每跳一次全量冷启动+序列化/反序列化

改造：intake → 判血缘半径
  ├─ 小/低风险 ─▶ 【快车道】单 agent 一个热上下文做完 fix+verify+publish
  │               （轻量审计存根 · 不走全套门禁四件套 · 塌回近似裸 CC 手感）
  └─ 大/多角色/高风险 ─▶ 【全套】PM→开发→QA→DevOps
                        （仪式随血缘半径伸缩，而不是恒定）
```

**为什么它是最大杠杆（有量化）**：小任务 4 跳塌 1 跳 = 省掉整整 3 个 agent「启动到跑完」的循环（分钟~十分钟级/个），**量级碾压「省几 k token」**（后者对墙钟 <0.1%）。

**代价与风险**：
- 「血缘半径」怎么判是核心难点。**别用 LLM 判**（那又是一个可被合理化绕过的判定）——用机器信号：改动仓数 / 是否触碰 DDL·权限·主数据 / facet 数 / 是否需要真机。`gate-matrix.js` 的 `classifyRisk` 已经是这个形状，**可直接复用**。
- **快车道必须有「升级回全套」的出口**：跑到一半发现半径超了（比如碰到 DDL），要能停下转全套，而不是硬跑完。
- **审计存根不能省**：快车道也要留 commit + 一句改动摘要 + 一条时间线，否则「小任务」会变成审计黑洞。

**先量再改**：动手前先量「当前一版真实冷启动次数 × 每次墙钟」。**这条纪律来自两次自己排错优先级的经历。**

### P2-2 · 砍断 append-only 棘轮

**问题**：**系统被设计成越用越慢。** 任务档案版本内越滚越大（曾 227KB / 462 行）、红线/SOP 每出一次事故加一条、连「每个优化都要留记录」都是硬门槛。

**做法两条**：
1. **任务档案拆「当前态头 + 时间线日志」**：小而新的「当前态头」（状态 + 未决项 + 条目表 + 覆盖矩阵，每回合只读它）+ 按需才读的时间线日志（另存 `tasks/<name>.timeline.md`）。
2. **红线/SOP 加退役纪律**：**已被机器门禁覆盖的红线就下架。** 现在至少有这些可以退役——「必须回写看板」（已有 `set_entry_status` 工具 + 收工即校验）、「不许手填 GREEN」（工具已拒）、「造数不许翻库」（linter 已拦）。
3. （可选）借**薄派发器**把「厚 SOP 全量注入」改成「按任务类型只加载相关片段」。

**诚实定位**：**这条是成本 + 质量杠杆，不是提速杠杆**（缩注入体积对墙钟收益 <0.1%）。它的真价值是「稳定前缀利于缓存 + 降误判」以及**阻止税无上限增长**。**别把它排在 P2-1 前面**（这是一次自我订正的结论）。

### P2-3 · 共享环境事实卡

**问题**：每个 agent 每回合各探一遍服务活性、git 枚举、平台 base、仓库清单。

**做法**：做成 **fleet 级、每任务刷一次**的事实卡（引擎持有、随派工注入）。这是「状态层常驻 · 推理层惰性」的落地形态之一。**`refreshZhuzhuHealth` 与 `refreshUiContract` 已经是这个模式**，只是没推广到 git/服务活性。

**代价**：小。**约 1 天。** 收益 modest（分钟级/次）。

### P2-4 · 按条目流水线（开发↔QA 重叠）

**问题**：「一次性交 8 条」→ QA 在开发写全 8 条的整段时间**干坐**、然后被 8 条一起砸。

**做法**：「写完一条就交这一条、自己继续写下一条」→ **QA 早条目与开发晚条目重叠**。这是目前能拿到的**最大真并行**。

**代价（不免费，要试点）**：① 回归面变大（QA 测 A 时开发改共享码可能搅乱已测、需重测）；② 撞人工预检门（每批老板过一眼 → 按条目交要么更碎、要么放宽此门）；③ **开发是单 agent、码串行写**——「并行」不是他分身，是**两角色重叠**。
**先在「条目彼此独立、共享码少」的版本上试点并量一次**（攒批 vs 流水 各自 dev+QA 总墙钟 + 重测次数）用数据决定。

### P2-5 · 知会 ping 与文书解耦

**问题**：引擎推送/接棒靠收工 marker 触发，故「消息」天然是最后一步 → 老板感到「非得全弄完才发消息」。

**做法**：拆三件——① **给老板的「知会 ping」（code done）能拆早，零风险纯赚**（老板多数时候只要知道码完）；② **只服务下游的文书（RELEASE_CHECKLIST / CHANGELOG）能移出关键路径**；③ **给 QA 的交接拆不得**（交接卡 + 档案当前态**就是她冷启动要读的接口**，抢在写完前叫她 = 她冷读到过期档案）。

**代价**：需要一条「中途知会」通道（现推送只在收工 marker 触发）。**约 1 天。**

## 5. P3（产品化方向，不做也不恶化）

| 方向 | 内容 | 前置 |
|---|---|---|
| **macOS 完整体验** | launchd LaunchAgent（**`KeepAlive` 天然替代 health 轮询重启，刻意不把「忙 vs 死」的启发式判断第二次实现**）+ LSUIElement `.app` + JXA 菜单栏（零编译）。**两个要先认的能力差距**：悬浮窗做不到真置顶（降级为 `--app=` 无地址栏独立窗口）、系统通知没有按钮（降级为无按钮通知 + 点击开 UI） | 无（清单已列好） |
| **归档索引数据库化** | `runs/index.json` + 文件扫描 → SQLite 索引（run 列表、会话检索、跨 run 指标聚合） | P0-2 retention 先做，否则索引一份必然恶化的数据 |

| **统一日志 traceId** | 跨 IPC/HTTP/runtime 的 `traceId + runId + threadRootId` + 脱敏规则 | 无 |
| **worktree 泳道（真并行）** | 每条目独立 worktree，同员工可并发；`worktreePlan` 已能算出该开哪些树 | 要先解决：共享 dev 库、端口单例、归并锁。**且自动建树要处理「树里有未提交改动」——误判代价是丢代码** |
| **多用户 / 权限** | 账号体系 + 项目空间 + 数据权限 | P0-1 鉴权 |
| **CI 集成** | **注意：本项目明确决定不做 CI**（理由见下）。若将来要做，定位应是「跑单测 + 类型检查」，而不是「契约漂移告警」 | — |
| **前端 E2E** | 新 UI 目前只有 `tsc -b` + oxlint | 无 |

### 关于「为什么不做 CI」——这是个明确决定，不是遗漏

抽取器实测 ~650ms/次，够便宜挂在流水线上。选引擎而非 CI 的理由：

> **CI 只会告诉前端开发「契约变了」——而他本来就知道，他就是改的人。真正需要这条信息的是下游写用例的 QA。引擎算 diff 并注入她的系统提示，是把信息送到消费者面前。CI 在这里是对着错误的人喊。**

**触发点也选得刻意**：选在「开发收工」而不是「派工 QA」——① 他是唯一会改前端的员工，且流水线顺序是开发 → 人工预检 → QA，所以她开工时契约必然已是最新；② 这样**不必在任何派工路径上 await**（`createDispatchRun` 有十余处同步调用点，改成异步是大动）。兜底再加两处：开机一次 + 巡视 sweep 顺带（5min 防抖）。

**fail-soft 三层**：前端仓不在本机 → 静默跳过；抽取器报错 → 块里如实写「本次刷新失败(原因)，下方基于磁盘旧产物」；产物读不出 → 只给错误块。**绝不挡派工、绝不静默假装成功。**

## 7. 如果重构，我会怎么做

**不会做的事**（先说清，因为这几条最容易被误当成「显然该做」）：

1. **不把状态总线换成数据库。** Markdown 是这个项目的第一性取舍，它换来「产物永远在仓库文件里、删掉 app/ 不丢数据、人和 agent 都能直接读写、可 diff 可审计」。它的代价（YAML 子集脆弱、长表格 Edit 锚点、并发写要串行化）**都已经有对策了**。换数据库要重写协作协议、失去 git diff 与可审计性，而且 agent 对 Markdown 的原生亲和度是真实优势。
2. **不迁旧 UI 到 React。** 它的定位是「已入库、免构建、总能跑起来的兜底」，而且 `office-lab/` 协议前缀正被它的正则依赖着。**应该做的是收窄它的定位（P1-6），不是迁它。**
3. **不引入通用编排框架（LangGraph 等）。** 现在的编排是「四标记 + autoChain + 服务端守卫」，它的每一条守卫都对应一次真实事故。换框架等于把这些守卫翻译一遍，而框架的 typed-state 图**解不了本项目的真问题**（本项目的问题从来不是「状态转移画不清」，而是「模型措辞不可信」）。**唯一值得借的是它的显式状态定义 + 每棒入口前置断言**，这可以在现有骨架上加。
4. **不给「守航态」加更多规则。** 十四轮 A/B 数据已经说明：**凡是「写进 SOP / 加红线 / 改派工文案」的都会被下一轮压力压穿。** 要加就加工具/门禁。

**会做的事（按顺序）**：

```
第一阶段（安全与治理，约 1 周）
  P0-1 鉴权 → P0-2 retention → P1-3 frontmatter 显式报错
  判据：跑完之后「别人不能伤害你」「磁盘不再必然增长」「解析错不再无声」

第二阶段（结构可测，约 1 周）
  P1-1 第 1 步（listen 挪进 main）→ P1-2 协议 schema → P1-1 第 2-3 步（路由表 + autoChain 三段拆）
  判据：纯函数可真 import 单测；改枚举只改一处；autoChain 三段各自可单测
  ★ 顺序很重要：先让它可测，再动它

第三阶段（证据可信，约 1-2 周，部分依赖外部）
  P0-3 不可变 commit → P0-4 环境新鲜度 → P0-5 console 门（平台侧）
  判据：机器 GREEN 从「某次跑过了」升级为「当前这份代码在新鲜环境里过了」

第四阶段（提效，先量后改，约 1-2 周）
  量「当前一版真实冷启动次数 × 每次墙钟」→ P2-1 快车道分级 → P2-4 按条目流水试点
  判据：小任务的手感塌回近似裸 CC；用数据（不是感觉）确认

第五阶段（产品化，视需要）
  macOS 常驻 → 数据库化索引 → 指标面板 → 多用户
```

**这个顺序的依据**（不是拍的）：
- **安全先于一切**——它是唯一「别人能伤害你」的维度。
- **「让它可测」先于「改它」**——`autoChain` 承载了族 A 的全部修复，不先钉住行为就动它，等于把那些事故的修复押上去赌。
- **「证据可信」先于「提效」**——提效会让流程跑得更快，如果证据不可信，那只是更快地产出假绿。
- **「先量再改」贯穿全程**——这条纪律来自两次自己排错优先级的经历（静态门禁天花板实测仅 3~5%、testid 契约门禁靶子实测仅 3%）。

## 8. 结论

office-lab 已经把「一支 AI 员工团队跑真实交付流水线」这件事从「能跑」推到了「机制自洽」：交接不会静默丢失、停顿不会无人知晓、结论必须过确定性门禁、外部能力缺位时如实说「未验证」。**这套东西在开源界没有成熟对标**——MetaGPT/ChatDev 有组织结构但是一次性生成器；LangGraph 有编排但不管「模型说的话可不可信」；Superpowers 有纪律层但是单上下文。

它现在的短板不在「想错了」，而在三处：

1. **结构缺席** —— 契约没有机器闸（已在补）、证据绑的是可变工作区、共享环境没有产权边界。这一条有外部佐证：*失败的形状更取决于环境结构而非模型性格。*
2. **外部依赖未闭环** —— 四个验证接口未全部上线，于是「守航可信」目前只有一半是机器算的；而这一半的**诚实表达（`unverified` 第三态）本身是 0.10.0 最重要的一条设计决定**。
3. **效率税的架构固有性** —— 冷启动 + append-only 棘轮 + 齐平仪式。诊断和杠杆排序都已完成（**减跳数 ＞ 减停顿 ＞ 减返工 ＞ 不重探环境 ＞ 缩体积**），快车道分级仍是提案。

**下一步最该做的三件事，如果只能做三件**：本地鉴权（关掉唯一的实质安全口子）、`runs/` retention（止住唯一必然恶化的债）、`listen` 挪进 `main()`（让 8770 行那坨变成可测的）。**这三件加起来不到两天，但它们决定后面所有事能不能安全地做。**
