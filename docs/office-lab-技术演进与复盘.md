## 1. 起源与目标

- **不先做系统**：起点不是先写办公室 UI、也不是先选技术栈，而是先把一个真实小需求跑成「办公室格式」的完整闭环样本（`tasks/2026-07-08-cost-report-style.md` 是 0 号原型；构思见 `temp.md`）。目标是先得到一个**可复用的标准样本**：一个任务 → 开发 → 测试 → 上线准备 → 形成完整任务档案。
- **蓝本**：`docs/示例项目需求/` 从 v1 到 v5.10 的完整迭代史。逆向复盘（`复盘-示例项目v1到v5.10流程提纯.md`）把散落在开发/DevOps 身上的职责提纯成独立 agent，切出开发（GG Bond）、QA（迷糊老师）、DevOps（波比）三角色，后补产品经理（菲菲）。
- **核心信条**：**产物永远在仓库文件里，Lab 只做调度与观测**——删掉整个 `app/` 不丢任何数据。任务档案 / 交接卡 / 教训库都是纯 Markdown，人和 agent 都能直接读写。

## 2. 架构总览

### 进程与技术栈
- 后端 `app/server.js`：Node 18+ 原生 `http`，**零第三方 HTTP 依赖**（npm 依赖只有 `@anthropic-ai/claude-agent-sdk` 与 `zod`）。默认绑 `0.0.0.0:4800`（`OFFICE_LAB_PORT`/`OFFICE_LAB_HOST` 可覆盖；新 shadcn UI 另在 4700）。路径根（monorepo 嵌套 / 独立 clone 双形态）由 `app/paths.js` 统一探测，见 §3.102。
- 前端 `app/public/`：纯静态（`index.html` + `app.js` + `cards.js` + `style.css` + `vendor/marked.min.js`），无构建步骤。`index.html` 由服务端按资源 mtime 注入 `?v=` 缓存版本号，改文件即自动刷缓存。
- 员工引擎：`@anthropic-ai/claude-agent-sdk` 的 `query()`，工牌全文 append 到 `claude_code` preset 系统提示。
- 企微渠道（可选）：server 按需 spawn 并看护一个 **Python sidecar** `app/wecom_sidecar`（官方 `wecom-aibot-python-sdk` 长连接，纯 I/O 哑管道）；企微消息经 sidecar 转 office-lab 主人格端点作答。自带 venv，未装依赖时不影响引擎其余功能（详见 §3.13）。

### 数据流（一句话）
用户在 UI 派工 → server `createDispatchRun` 建 run 并 `startRun` 拉起 query → SDK 消息流经 `normalizeEvent` 落 `runs/<id>.jsonl` 并经 SSE 推前端 → 员工按 SOP 回写仓库里的任务档案 `.md` → `fs.watch` 广播 `tasks-changed` 刷看板 → 收工汇报里的标记驱动 `autoChain`（接棒/回发）、`appendLessons`（沉淀教训）、`maybePushRunStopped`（手机推送）。

### 持久化文件（都在 `app/runs/`，已 gitignore）
| 文件 | 内容 |
|------|------|
| `index.json` | 运行注册表（run 形状；重启后可回看/续聊；私有句柄经 `stripPrivate` 不落库） |
| `<runId>.jsonl` | 每条 run 的事件流（SSE 断点续传按行号做 id） |

## 5. 与业界的差距 / 升级方向

> 来源：`生产级员工Agent方案调研-2026年中.md`（27 源 / 124 主张 / 25 核查 / 23 通过 2 证伪）。

### 定位（office-lab 踩在主流上，不是异类）
- 业界无「无人值守自主上线」，共识是 **supervised autonomy（受监督自主）**：agent 起草/测试/解释/升级，人类保留架构与合并决策权——这与波比「只准备不执行、逐项等放行」天然一致。
- 自研编排在生产份额排第二（~28%，仅次 LangGraph ~38%）；MetaGPT(ICLR 2024) 是 office-lab 的「直系骨架」但仅学术原型；「深度绑定真实企业代码库 + 私有规范 + 自动接棒」这类私有内部方案市面无现成成品，精英组织都是自己长出来的。
- **头号敌人是误差复合**：流水线成功率乘法衰减（95%×10 步→59%，85%→20%；真实 E2E 生产流水线普遍 20-40%，「不是 bug，是算术」）。MAST 失败三分类：规约 41.77% / 协调 36.94% / 验证 21.30%。

### 3 个可对标升级点
1. **⭐ 规范从 prompt「下沉」到 CI 硬闸（最重要）**：Salesforce 经验「Generation 不再是瓶颈，Verification 才是」。把可机检硬规则（禁手写 SQL、Controller 不含业务逻辑、Java 8 语法、data-testid 规范）做成 CI lint / ArchUnit 构建期红灯，而非只靠 agent 读 `agents.md`/`CLAUDE.md` 散文自觉。
2. **接棒编排显式化为状态机**：现在 `【下一棒】` 是隐式状态机（轻但状态/交接错乱难追）；给每个版本流程一份显式状态定义 + 每棒入口前置断言（对标 LangGraph typed-state 图）。
3. **提高验证闸密度 + 克制棒数膨胀**：把「每棒交接后一次验证回路」制度化（迷糊的 validate→headless→RED→App-run 已是雏形；每次工具调用后加验证回路可把完成率 81%→94%），同时控制流水线步数以对冲误差复合。

## 6. 已知短板与复盘切入点（技术判断，供讨论）

- **版本号未随 v0.2.1 bump**：权限从 auto 分类器切到三名单是实打实的行为变更，但 `package.json` 仍 `0.2.0`、也无对应 commit——版本流水与代码事实脱节，复盘时需对齐。
- **无自动化测试**：引擎（标记解析、YAML 抽取、autoChain 守卫、权限名单）全靠人肉验证；标记解析已两轮踩坑，正是最该有回归测试的地方。
- **自研 YAML 子集解析脆弱**：`parseFrontmatter` 只覆盖标量/布尔/一层嵌套/字符串数组；档案格式一旦超出子集会静默解析错，看板据此渲染 → 错得无声。
- **消息卡片依赖 agent 自觉产出**：协议 + SOP 指引到位，但没有强制/校验机制；员工不产出卡片就退回纯文字，效果不保证。可考虑在 server 侧对特定环节的收工汇报做卡片补全或校验。
- **动作卡对已收工会话不可操作**：reply-based 写回依赖当前有在跑会话；历史已收工 run 点动作卡只提示「重新开聊」。若要闭环需接「对已收工会话自动 resume 续跑」。
- **卡片「已处理」态存 localStorage**：跨设备/清缓存不同步，多人/多端场景会各看各的。真要可靠需落服务端。
- **全员 Opus 成本**：闲聊也走 Opus 是为体感，但成本显著；是否按 kind/复杂度智能分档可再评估。
- **单机单进程**：liveRuns/pendingPerms 全在内存，重启丢活跃 query（run 置 interrupted 可续跑兜底，但审批挂起态会丢）。
- **权限 glob 依赖实测经验**：`./x/**` vs `//abs/**` 的匹配规则是踩出来的、写在注释里，SDK 升级可能变——脆弱耦合点。
- **（QA 复盘 backlog · 基础设施类，待排查）夜间无人值守 run 的两类失效**（来源：§3.38 迷糊复盘，2026-07-31）：① **进程崩溃**——`Claude Code process exited with code 3221226505`（Windows 崩溃码 0xC0000409，派工那一刻即崩、一步没跑），需查崩溃根因（SDK/内存/超大上下文？）＋崩溃后自动 resume；② **超长空闲挂起**——run 卡在单个巨型空闲 gap（一整夜），需查是 App-run 同步阻塞死等还是自动接棒漏触发。夜间排活＋无人盯＋无断点续跑＝崩/挂一次整晚白费，是「早上回来发现中止」的机械根因（非 QA 能力问题）。
- **（v5.14 复盘 backlog · 基础设施类，暂记不做）** ① **dev 环境无后端编译校验**：GG Bond 本机无 JDK/Maven，后端仅静态逐层核，大件全栈改动靠"拆专注轮"规避裸建返工（v5.14 REQ-0091 后端单拆一轮）——接入容器化 JDK+Maven / CI 预检可消掉一整类"跑旧 jar 被误判成缺功能"风险。② **交接标记/任务档案缺「分支 owner」字段**：v5.14 父仓动不动、谁切哪些仓靠用户口头兜（"父仓不要动"）；可把 repos 表 + 分支归属固化进档案，别每次口头。③ **多 mode 守卫矩阵靠人工逐条抄**：v5.14 交接卡手抄 9 行"同文件多 mode 目标 present/其余 absent"守卫表——可基于 testid 注册表对"同组件多 mode"自动生成 checklist。（来源：v5.14 沟通记录复盘，2026-07-24）
