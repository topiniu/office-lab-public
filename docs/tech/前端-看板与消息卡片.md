### 3.11 前端要点
- SSE 渲染管线 `renderEvent`：assistant 文本→气泡（marked）/ 卡片（OLCards）；tool_use→折叠工具组并回填结果+耗时；result→状态签。
- iMessage 式头像成组、进行时活动标签（"正在写 X"）、打字指示器、DOM 节点上限裁剪防长会话内存爆。
- Linear 设计系统：近黑画布 `#010102` + 四级 surface + hairline + 单强调色 `#5e6ad2` + 语义色；明暗双主题（首帧前定妥防刘海闪黑）。
- 移动端：侧边栏离屏抽屉、聊天坞全屏、`env(safe-area-inset-*)` 全面屏安全区、`visualViewport` 软键盘避让、聊天坞桌面可拖拽调宽（localStorage 持久化）。
- 移动端顶栏收纳（2026-07-24）：顶栏原平铺 6 个低频设置图标 + 刷新 + 派工，手机窄屏放不下 → 「派工」被切出右缘。修复用 `#topbar-tools` 包住 6 图标，桌面 `display:contents`（透明包裹、布局与从前一致），手机由 `syncToolsPlacement`（matchMedia≤640）**物理搬进左侧抽屉「设置」区** —— 物理搬家（单一事实源）而非复制，因复制会撞 `#theme-toggle` 等 id、JS 换图标 `$('theme-icon-dark')` 只命中第一个。
- **CSS 特异度坑（事故根因）**：`#chat-expand{display:none}`（特异度 1,0,0）本想在窄屏隐藏「全屏放大」，却被更早的 `#run-head .btn.ghost{display:inline-flex}`（1,2,0）盖过 → 手机上放大按钮一直没隐藏成功。修复：隐藏规则加 `#run-head` 前缀（`#run-head #chat-expand`，2,0,0）。教训：给某元素定 `display:none` 时，先确认没有「祖先+类」组合选择器以更高特异度设了 display；单 id 选择器并不天然最高。
- **iPhone 滚动区没算整屏 = 外壳高度单位坑（事故根因，2026-07-25）**：现象是「首页可滚动区高度没算整屏」——内容止步于 Safari 悬浮底栏上沿、留一条不动空带；对照原生站（古文岛）内容会一路滚到**半透明悬浮底栏之下**、整屏可用。本应用是「内部滚动 app-shell」（`body{height:100dvh;overflow:hidden}`，滚动在内层 `#content`），因**根文档从不滚动**，iOS Safari 底栏永不收起，此时 `dvh`/`svh` 拿到的是「**小视口**」= 底栏之上那块，外壳高度只到底栏上沿 → 滚动区够不到整屏。**排查两个弯路**：① 先去调 `#content` 的 `padding-bottom`（env 安全区）——无关，裁切来自外壳高度单位；② 方向搞反，先把 `dvh`→`svh`（仍是小视口）——没用。**正确解**：反过来用**大视口** `100lvh`（整屏高），外壳铺满整屏、内容滚到悬浮底栏之下，对齐原生站；`100vh` 兜底。聊天坞则**反用** `100svh`（小视口）让输入框稳停在底栏之上、别也钻到底栏下。**教训**：想要「内容滚到悬浮底栏之下、整屏铺满」用**大视口**（`lvh`/`100vh`）；`svh`/`dvh`（小视口）会把你钉在底栏之上。三个视口单位方向别记反：`sv`=底栏展开时的小、`lv`=底栏收起时的大、`dv`=随动。安全区 `env()` 只管「独立态避让 Home 指示条」，与「浏览器态滚动区高度」是两码事。
  - **补丁：悬浮底栏净空 `--fab-clear`（同日）**：lvh 铺满整屏后又冒出「末项/侧边栏页脚停在半透明悬浮底栏之下读不到」。因原生站是**文档级滚动**、底栏随滚动自动收起才能露出底部内容；本应用内部滚动、底栏永不收起，故末项须**主动抬出**底栏。关键坑：`env(safe-area-inset-bottom)` **浏览器态常报 0**（底栏吸收了安全区），先用 `calc(env+44px)` 补净空**无效**（0+44=44 远不够盖 ~80px 高的悬浮底栏）。**自校准对策**：可收起工具栏高度**恰等于 `100lvh - 100svh`**（大视口−小视口=会收起那截 chrome），浏览器算好、不猜像素——`:root{--fab-clear:max(calc(100lvh-100svh+16px), calc(env(safe-area-inset-bottom)+16px))}` 作 `#content`/`#sidebar` 的 `padding-bottom`：正好把末项从 lvh 底沿(底栏下)抬到 svh 底沿(底栏上)+16px 呼吸位；`max` 里兜一次 env 防个别机型 lvh==svh。滚到底时末项/页脚露在底栏之上，中途滚动仍整屏铺满钻到底栏下（净空只影响滚动上限、不产生中途空带）。独立态无底栏 lvh==svh → 净空≈16px。**教训**：① 别用 `env(safe-area-inset-bottom)` 当「悬浮底栏高度」——浏览器态它常是 0；② 要「工具栏实际占高」用 `100lvh - 100svh` 自校准，稳过任何写死像素；③ 根治仍是改文档级滚动让底栏随滚动自动收起（成本高、暂未做）。


### 3.24 托盘悬浮窗（全局置顶小窗，WebView2 + WinForms，2026-07-25）

需求：让 office-lab 有个「全局悬浮、钉在最前」的窗口，看别的东西时不用来回切窗口。落在**托盘侧**（`tray/office-lab-tray.ps1`，本就是 WinForms），新开一个 `TopMost` Form 内嵌 WebView2 加载 `127.0.0.1:4700`，右键菜单「悬浮窗」子菜单管显示/隐藏、重载、置顶、半透明、重置几何；关窗=隐藏（可再召唤），位置/大小/置顶/透明度持久化进 `tray-config.json`。内容直接用完整 UI，靠既有响应式窄屏布局适配小窗（零前端改动，440px 宽实测自动切手机版：汉堡侧栏 + 任务卡片清晰可读）。

**机制取舍（为什么 WebView2）**：
- **PiP（Document Picture-in-Picture）**——纯前端、零原生代码、系统级置顶，最轻。但只支持 Chromium 内核、窗口跟着开启它的标签页走（关页即消失）。用户要的是**不依赖浏览器的常驻置顶**，PiP 的「随标签页生死」不满足。
- **legacy `System.Windows.Forms.WebBrowser`（IE/Trident）**——.NET 自带、零额外 DLL。但渲染的是 IE11，跑不了现代 SPA（`EventSource`/`URLSearchParams`/CSS grid/ES2020+），直接出局。
- **`--app` 浏览器窗 + `SetWindowPos` 强行置顶**——太 hacky（找 HWND、焦点变化要反复补置顶、浏览器可能多开窗口），弃。
- **WebView2（选定）**——真·全局置顶、不依赖浏览器、渲染现代 Edge 内核，契合「托盘托管的桌面应用」方向。运行时（Evergreen Runtime）Win11 自带（实测 150.0.4078.83）。

**踩坑与根因（都记着，供复盘）**：
- **托管 SDK DLL 不随系统预装**：WebView2「运行时」Win11 有，但 PowerShell/WinForms 要嵌入还需一套**托管 SDK DLL**（`Microsoft.Web.WebView2.Core/.WinForms.dll` + 原生 `WebView2Loader.dll`），这套不预装。对策：从 NuGet 取微软可再分发 DLL（`net462` 版，配 PS5.1 的 .NET 4.8）**vendored 进 `tray/vendor/webview2/`**（约 1MB）。构建号 4078 与运行时对齐。
- **原生 loader 的 P/Invoke 搜索路径坑（`0x8007007E`）**：`Core.dll` 按**无限定名** `WebView2Loader.dll` P/Invoke，而 P/Invoke 按「进程 exe 目录 + PATH」搜、**不看托管程序集所在目录**——放在 vendor 旁默认找不到。对策：`SetDllDirectory(vendor)` + 按**全路径** `LoadLibrary` 预加载（`kernel32` P/Invoke），之后按名解析即命中已加载模块。原生 loader 按进程位数（`[IntPtr]::Size`）从 `WebView2Loader.<arch>.dll` 复制成 `WebView2Loader.dll`（后者运行期生成、已 gitignore）。
- **异步初始化不能在 UI 回调里同步等（死锁）**：`EnsureCoreWebView2Async` / `CreateAsync` 会 post 回 UI 线程；在菜单点击回调（UI 线程）里 `.GetResult()` 同步阻塞会与消息循环互锁。对策：设 `CreationProperties.UserDataFolder` 后 `EnsureCoreWebView2Async($null)` 即返回，导航放进 `CoreWebView2InitializationCompleted` 事件里做，全程不阻塞。（去风险原型阶段用 `DoEvents` 泵消息验证过一次可行，正式接入改纯事件驱动。）
- **PowerShell 不提升函数（差点开机即崩）**：把 `Sync-FloatMenu` 的初始调用**内联**写在菜单构建段（第 443 行），但函数定义在更靠后（665 行）——PS 顺序执行、不 hoist，启动到 443 行时函数尚未定义会 `Stop` 报错。核实行号后把初始调用挪到文件末尾启动区（所有函数已定义之后）。教训：托盘脚本里「菜单点击回调」是延迟执行（不受定义顺序影响），但**顶层内联调用**受严格先定义后调用约束，别混。
- **无 BOM 的 `.ps1` 被按 ANSI(GBK) 解码**：临时测试脚本用 Write 写成**无 BOM UTF-8**，PS5.1 无 BOM 时按系统 ANSI 解码，中文串字节被误当引号/反斜杠破坏词法。主文件 `office-lab-tray.ps1` **本就带 UTF-8 BOM**（已严格解码校验，我加的中文全有效）；教训仅针对「新建给 PS5.1 跑的脚本要带 BOM 或纯 ASCII」。

与 §「Start-Server 改 CreateNoWindow」同期：两者都在收敛「托盘与它托管/新开的窗口之间的关系」——服务进程要**无窗不可关**（CreateNoWindow），而悬浮窗要**有窗且置顶可交互**（WinForms TopMost）。验证：解析通过 + 去风险原型（CoreWebView2 初始化/导航成功）+ 集成实测（加载真实 UI、`document.title=望子成龙小学`、`TopMost=True`、截图确认窄屏渲染），均用隔离用户数据目录、只读加载生产页面，未触碰 `runs/`。菜单点击链路待用户重启托盘真机走一遍。


### 3.27 交互式「等你拍板」气泡 + 卡片输出硬约束（2026-07-28）

承 §3.10（OLCards 首版）。首版把「决策点变一键」的能力做出来了，但两个短板在实战里暴露：

**事故驱动的缘起**：查会话 `ead5e4fb`（波比 v5.14 发布收尾）——整场**零 `olcard`**，用一大段散文 + 裸 `【等你拍板】是否放行生产上线…` + 正文里贴裸 MR 链接收工。这里同时踩了两类卡的空：`approval`（列合并/部署动作 + 批准/暂缓按钮）和 `link`（MR 一键开 tab）都被写成了纯文本。根因：各角色 SOP 只把卡片列为「常用」——**软提示对 LLM 无强制力**，模型在长回合末尾图省事就退化回散文。**范围教训**：老板追问时点出「不止拍板卡，连 MR link 这类展示卡也全没用上」——所以硬约束不能只覆盖决策点，得覆盖**高频交付物**。

**三处机制取舍**：

- **硬约束的落点选「引擎统一注入」而非「改四份 SOP 了事」**：把《消息卡片 · 硬格式》做成 `server.js` 的 `CARD_OUTPUT_MANDATE` 常量，在 `buildRolePrompt` 尾部对**每张工牌统一 append**（四人拉起都带）。理由：① 单一事实源，杜绝四份 SOP 各写一套、日久漂移；② 规则钉在**引擎侧注入**比散在角色文件里更难被「临时手写派工」稀释（同 §3.3 迷糊红线 10「规则要能抗命」的思路）。角色 SOP 只保留「点名映射」，不重复全文。

- **约束分档：A/B 硬门槛、C 强引导（避免过度强制误伤）**：不是所有卡型都适合「无卡=不合格」。**A 拍板点**（decision/approval/toggle/gate）与 **B 高频交付物**（MR/URL→`link`、代码/SQL/DDL/文案→`code`）定为硬性——它们**判据无歧义**（一个 MR 永远该是 link 卡、一段 SQL 永远该是 code 卡），且是老板亲点的痛点；**C 其余展示卡**（table/stepper/fields/gallery/checklist）定为「默认用卡」强引导，因为「这段内容该不该做成表格卡」有判断成分，硬性化容易逼出为凑格式而生的空壳卡。**判据升级**：A/B 从「建议用卡」变「无卡=收工不合格」，把 LLM 的自由裁量收成硬门槛；C 保留弹性。

- **仍是提示层、不做程序化拦截（诚实边界）**：引擎**不**校验「该出卡没出卡」、**不**改写员工输出把裸链接自动转成 link 卡。理由：收工文本是自由文本，可靠地判「这个 URL 是不是一个该成卡的 MR」「这段是不是该成 code 卡的 SQL」需要语义判断，误杀/漏判都有代价，且改写员工产物会破坏「员工输出即事实」。所以走与红线一致的**提示层强约束**路线，效果靠模型遵从——真机是否照办需持续观察，若仍频繁漏卡，再考虑「收工后轻量正则体检 + 提示补卡」这类不改写、只提醒的兜底。

- **gate 从「被动按钮」升级为「可内嵌回复」，且加抑制规则防重复**：老板观察到拍板内容大多是「选项」或「补充文本/图片」。`R.gate` 因此二合一——可选快捷选项按钮（点了 `ctx.reply` 回发）+ 恒有的内联输入（文本 + 贴图/选附件，复用现成 `uploadFile` + `/api/runs/:id/reply`，零新增服务端接口）。关键取舍是**抑制逻辑**：gate 由 marker 自动合成，但若员工已产 `decision`/`approval`/`toggle`/显式 `gate` 任一动作卡，那张卡本身就是交互面——此时**不再补合成 gate**，避免「一条消息两张拍板卡」。心智模型收敛为：**放行/选项/封板→员工产对应动作卡（自带按钮）；只需补充自由文本/图片→裸 marker 走可输入 gate 兜底**（波比那种散文收尾也能就地打字/贴图回，不必滚到底部）。gate 仍**不做 acted 持久化**——`【等你拍板】` marker 始终是引擎唯一事实源（autoChain 门 / 状态徽标只认它），gate 只是显示层增强。

**顺带优化**：多附件消息气泡从 `flex-wrap`+`object-fit:contain`（混合宽高比→高度参差换行乱）改为 84px 定高缩略图网格（`object-fit:cover`），单图 `:only-child` 保留原比例；纯 CSS。

**改动落点**：`app/public/cards.js`（`R.gate` 重写 + DEMO）、`app/public/app.js`（`cardCtx.uploadFile`、`renderEmpText` 抑制逻辑 + `ACTION_CARD_TYPES`）、`app/public/style.css`（`.olc-gate-*` + `.bubble-imgs` 网格）、`app/server.js`（`CARD_OUTPUT_MANDATE`：A 拍板点 / B MR·SQL 硬性 / C 其余展示卡强引导）、`消息卡片协议.md`、四份 `roles/*.md`。**已知短板**：`:only-child`/`:has()` 依赖较新浏览器（office-lab 面向现代 Chrome 内核，可接受）；gate 内联输入未做拖拽（只有点选/粘贴），composer 那套拖拽未复用进卡片。真机视觉/交互终验交老板走一遍。


### 3.28 前端 UI 栈取舍：为什么不迁 React / Base UI / shadcn（2026-07-28）

老板两次问到要不要把 office-lab 工作台 UI 切到 **Base UI**、以及 shadcn/ui 新出的 **`Message` 聊天组件**。核查后**明确不迁**，理由沉淀于此，免得将来反复问：

- **这些都是 React 库**：Base UI 是 headless 行为原语（Radix 同门），shadcn `Message`（`/base/` 变体）建在 Base UI + Tailwind 上、是复制粘贴的 React 组件。采用任一 = 引入 **React + 构建管线（Vite）+ 依赖树**，直接推翻 office-lab app 的两条立身之本：`除 SDK 外零依赖` 与 `纯静态无构建`（`server.js` 按 mtime 注 `?v=` 的缓存方案也随之作废），并要**重写** 2000+ 行 vanilla 流式渲染管线。对一个能跑的内部单人工具，成本高、风险大、且 AI 员工将无法再直接编辑静态文件。
- **关键澄清：Base UI/headless 库不改「好不好看」**——它们零视觉，样式仍要自己写。老板真实诉求是「UX/UI 不够美观」，那是**设计打磨活、不是迁移活**。切框架对美观零贡献。
- **正解：借解剖学、不搬代码**。shadcn 精心抽象的聊天五件套（MessageScroller / Message / Bubble / Attachment / Marker）与我们 vanilla 实现**一一对应**（`scrollChatToBottom` / `msg-row`+`applyGrouping` / `.bubble`+OLCards / `.bubble-imgs·files` / `sysChip`+工具行）——印证结构没走偏。于是把它当**设计参照**，用纯 CSS/vanilla 精修既有件：batch-1（运动令牌统一、补齐过渡、焦点环、入场动效、reduced-motion）+ batch-2（可见时间戳页脚、hover 复制、日期/系统 Marker、附件上传态）。全部无构建无依赖，见 CHANGELOG 两条。
- **诚实边界**：若将来 office-lab 要当**正式多人前端平台**、与 docs-portal（已 React19+Base UI+Tailwind）共享组件，那才是「有意识地上构建+React」值得重谈的唯一场景——但那是**另立项目**的决定，不是给现在这个 127.0.0.1 单人工具顺手加的。长气泡内折叠也**暂未落**（流式期间气泡在增长，测高折叠会与流式打架）。


### 3.29 设计系统：试切 shadcn/ui → 踩坑退回 Linear（2026-07-28，事故复盘）

**结局先写**：这次「Linear → shadcn Zinc 重皮」**失败并已整体退回**。留作教训，别再重蹈。

**真凶：一个 CSS 注释 `*/` 打字坑（不是 oklch！）**
重皮时写的顶部注释里有一句 `语义 token 名沿用旧命名（--canvas/--surface-*/--hairline/--ink*）`——其中 `--surface-*/` 的**「星号紧跟斜杠」`*/` 提前闭合了注释**。注释后面的中文散文 + 行尾真正的 `*/` 于是被当成 CSS 解析，**污染了紧随其后的 `:root {` 选择器** → 整个 token 块不再应用到根元素 → 所有 `var(--primary/--canvas/…)` 未定义 → 背景全塌成透明。现象：主题色没了 / 消息无背景 / 头像徽标透明 / devtools 报「`--primary` is not defined」。**修复**：把注释里的 `*/` 措辞改掉 + 注释里显式警告；脚本校验 `/*`↔`*/` 配平。

**为什么兜了那么多圈子（真正的教训）**：
1. **误判成 oklch/color-mix 不支持**：一看到「颜色全透明」就联想到「较新 CSS 语法内核不认」，把全部 `oklch()` 转 hex、`color-mix()` 转 rgba——**全是红鲱鱼**。token 值是什么根本不影响，因为 token 块**自始至终没被应用**（注释坏了、选择器废了）。改完当然「没有回来」。
2. **盲改视觉、没做结构性校验**：我看不到像素，只能靠 curl 看「服务端发了什么」——但那证明不了「浏览器解析成什么」。**正确的第一步应是对 CSS 做结构性校验（注释配对 `/*↔*/`、括号配平、选择器完整），而不是从颜色值开始猜。** 一个注释里的两字符 `*/` 让我和老板来回折腾了整整一轮版本。**铁律：CSS「整页塌陷」先查注释/括号/选择器结构，再谈颜色。**
3. **老板从没真正看到 shadcn Zinc**：因为 `:root` 一直是坏的，老板全程看到的「washed 亮色」其实是**无样式兜底态**，不是真的 Zinc 主题。所以「shadcn 观感差」这个结论其实**没被公平验证过**——但老板已选择退回 Linear，尊重之。

**为什么退回成本低**：全站走语义 token（§2 就定的 `--canvas/--surface-*/--ink*/--primary`）——退回 = 把 token 值换回 Linear，全局自动复原。这再次印证语义 token 层的价值（换肤/退肤都只改一处）。

**保住的东西**：退回只动「皮肤」（token 颜色、圆角、阴影、字距、气泡底），**功能改进全留**：交互拍板气泡、消息时间戳/复制/日期 Marker、看板 5 态状态色、微动效、附件上传态、头像徽标修复。皮肤与功能能干净分离，也是因为它们落在不同的 CSS 规则/JS 逻辑上。

**若将来还想要 shadcn 观感**：先确认运行环境内核版本支持 `oklch/color-mix`（或全程 hex/rgba 手写等价色），并且**能真机看像素地迭代**，别再盲改。


### 3.32 看板为中心：数据契约 + 回写纪律（用「枚举工具」根治格式漂移，2026-07-29）

问题：看板（任务档案卡）是 office-lab 的**双重命脉**——① 员工协作的状态总线（条目流水线/下一棒/待拍板都靠它流转），② **真人用户最直接的可观测入口**（老板一眼看进度）。但员工**经常忘记回写**（卡片停在旧态，老板看到过期数据、同事接棒判断失真），且**不知道确切格式**（手搓「需求条目登记表」长表格易写错列、自造状态词落到前端灰色启发式、`Edit` 长行锚点失配静默失败——§3.3 坐实过）。

**机制取舍（复盘核心）：**
- **「记得写」与「写得对」是两个正交问题，各用一手根治**：忘记回写 → **硬门槛**（`BOARD_UPDATE_MANDATE` 注入每张工牌，与 `CARD_OUTPUT_MANDATE` 同级：开工先读、每步即时回写、收工没写=不合格）；写错格式 → **工具兜底**（新增 `set_entry_status`，串行原子写 + 按列名定位 + 枚举校验，员工一行调用即对，压根不碰长表格文本）。只写纪律不给工具＝员工照样手搓照样错；只给工具不设门槛＝员工照样忘。两手都要。
- **为什么工具而非让员工手 Edit**：条目登记表是四员工共写的长表，Edit 读-改-写有锚点失配（长行）+ 并发覆盖（cc 并行）两类顽疾（§3.3）。`set_entry_status` 走引擎单写者串行队列（`withArchiveLock`）+ 原子 temp→rename + 按表头列名定位（复用 `extractEntries` 口径、泛化自 `passEntry`），无「锚点」概念、并发安全、格式必对。这是把 §3.3 治 frontmatter/时间线的同一招（`set_task_status`/`append_timeline`）推广到条目表。
- **枚举做成「拒非法」而非「容错映射」**：条目「状态」列驱动看板圆点色 + 接棒目标（`ENTRY_STATUS`）。自造状态词会落到文字启发式、常变灰——治本不是把启发式做得更聪明（那是无底洞），而是**在工具入口就拒收非枚举值并回列合法值**，逼员工用固定词表。代价：员工要记 19 个枚举——但工具的报错信息里直接列出，且工牌 mandate 也列，学习成本低。
- **枚举单一事实源、三处锁同步**：`server.js:ENTRY_STATUS_ENUM`（校验）= `app/public/app.js:ENTRY_STATUS`（渲染 → 圆点色/下一棒）= `文档格式规范.md §3.4`（人读契约）。三处各加交叉引用注释「改一处必须同步另两处」；脚本核对键集一致（19=19）。这是「同一份枚举散落多处会腐烂」的一贯防腐做法。
- **强制但轻负担**：回写靠三个原子工具（`set_entry_status`/`set_task_status`/`append_timeline`），员工一行调用；开工定位靠已注入的 `【任务快照】`（§3.7），读负担低。硬门槛措辞与卡片硬格式同处注入、同级严厉。

**改动落点**：`server.js`（`ENTRY_STATUS_ENUM` + `engineSetEntryRow` + `set_entry_status` 工具挂进 `makeCollabTools` + `BOARD_UPDATE_MANDATE` 注入 `buildRolePrompt`）、`app/public/app.js`（`ENTRY_STATUS` 加同步注释）、`文档格式规范.md`（§3.4 枚举表补全 19 值 + §3.6 回写纪律）、四份 `roles/*.md`（各加「看板即时回写」红线 + 角色分工）。验证：`node --check` 通过 + 枚举三处一致（脚本核对）；端到端（`set_entry_status` 正确写/拒非法/追加行/并发安全、mandate 注入、看板刷新）需**重启 server**。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.34 消息卡片视觉现代化：去侧栏色条/渐变 + 表格卡加宽（2026-07-30，用户反馈驱动）

问题：老板截图 GG Bond v5.15 收工卡，指「设计不够现代化——别用带颜色的侧边栏、渐变色这种过时手法」，并且表格卡（改动文件清单/影响面）被挤在文本卡的 560px 窄栏里横向截断、第二列内容看不全。

**机制取舍（复盘核心）：**
- **颜色从「装饰性色块」退到「小而有目的」处**：原卡靠左侧 3px 语义色条（`.ol-card::before`）+ 顶边 `linear-gradient` 高光（`.ol-card::after`）做层次与强调，这正是被诟病「过时」的手法（类 Bootstrap alert 的彩色左边框 + 渐变描边）。现代扁平的共识是**层次靠留白·字重·发丝线，颜色克制、只在有信息价值处出现**。故删两个伪元素，语义色只保留在：图标 chip 的淡色底、状态徽标（`待你处理`/`已处理`）、清单/表格里的状态点与上色单元格。`olc-done` 从「绿色条」退化为「降透明度」——同样传达「已处理」，但不靠色块。
- **表格宽度用 `:has()` 按卡型分流，而非一刀切放宽所有卡**：文本类卡（link/code/checklist…）窄栏（560px）有利阅读行长，不该动；唯独 table 是用来「对比」的，多列被挤到横滚/截断反而失去表格的意义。用 `.olc-wrap:has(.olc-type-table)` 只把含表格的卡放宽到 min(840px,96%)（展开态 960px），其余不变。`:has()` 现代内核（WebView2/现代 Chrome）已稳定支持，与本项目「纯 CSS 无构建」取向一致。
- **表格长文换行取代 nowrap 截断**：原 `white-space:nowrap` 让长中文被横向截断（配合窄栏尤其糟）。改为允许换行（`word-break:break-word` + `vertical-align:top`），加大内边距、表头改小号大写弱色、行 hover 高亮；仅横向发丝线、无竖分隔（竖线会让表格显拥挤，数据表规范也建议省略）。
- **诚实短板**：这是「盲改视觉」——改的人看不到像素，亮/暗两主题的实际观感（尤其去掉色条后动作卡是否仍够醒目、表格加宽后在窄聊天面板里的换行表现）需老板真机各扫一遍再微调。动作卡的「待你处理」闪烁徽标仍在头部，是去掉色条后主要的「需注意」信号。

**改动落点**：`app/public/style.css`（`.ol-card` 去 `::before/::after` + `.olc-wrap:has(.olc-type-table)` 加宽 + `.olc-table` 换行/内边距/表头/行 hover）——**纯 CSS，`cards.js` 渲染逻辑未动**（加宽选择器锚点 `olc-type-table` class 本就由 `renderCard` 输出）。CSS 结构自检（注释 `/* */` 配对、`{}` 配平、注释内无 `*/`）通过。端到端观感需**刷新前端**（mtime 自动 bump `?v=`）后真机眼校。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.42 看板改造：从「手工同步的落后镜像」到「数据可信 + 自动跟手 + 好看好用的待办工作面」（2026-08-01，用户复盘驱动）

问题：老板复盘看板「经常不更新、落后、员工都不关心、没有操作指示与入口，UI 也 AI 味重（emoji 按钮、无优雅 popover）」。

**根因（结构性，不是员工懒）：**
- **看板是「事后要手工同步的副产物」而非「工作发生的主界面」**：员工在 chat/档案正文里干活，干完还得**额外记得**调 `set_entry_status` 才同步看板——忘了就落后。业界看板「移动卡片=动作本身」（拖拽 / CI 驱动），这里的更新是一道独立的、易漏的家务。
- **模板压根没有「状态」列**：`templates/task-archive.md` 的登记表只有自由文本「当前阶段」，而 `engineSetEntryRow`（server.js）**无「状态」列即抛错** → 员工要么报错要么退回手 Edit → 机器落到「文字启发式、常落灰」。新任务生而落后。
- **六处状态存储互不绑定**（frontmatter status / gates / 条目状态列 / 当前阶段 / 流程状态勾选 / 时间线），靠人手同步，「唯一事实源」名不副实、自相矛盾（v5.15 REQ-0241）。
- **描述性而非行动性**：只显状态，不显「下一动作/球在谁手里/是否落后」，员工与老板都缺一眼可操作的抓手。

**四条线修复（老板全选，分批交付）：**
- **B 模板/规范对齐**：登记表补「状态」列（§3.4 枚举）+ 注释改指状态机。**治「新任务生而落灰」的最直接坑。**
- **C UI Linear 化**：去 emoji 换 SVG 图标（复用 cards.js 的 Lucide `ICON`/`svg` 口径，不引库）；`title=` 原生提示换**富 hover popover**（条目：状态/阶段/下一棒带头像/来源；门禁：N/M + 明细清单）；卡片加**停滞龄期** chip（`updated` ≥2 天染琥珀）让落后可见。
- **A 状态自动化**：由「条目接棒」派起的 run 带 `run.entryNo`，收工交 QA 时 `autoChain` **自动**把该单条目置「待测」（复用 `withArchiveLock`+`engineSetEntryRow` 同一写路径）；多条目/口头审批场景交 QA 却无条目「待测」→ 一致性 ⚠ 软提醒。**把「更新看板」从家务变副产物。** 诚实边界：交接标记 run 级无条目 id、一条 run 常覆盖多条目，故自动只兜无歧义的单条目档，不猜多条目、其余靠提醒。
- **D 收敛状态存储**：卡片显「派生态=最落后条目状态」（frontmatter status 退为里程碑）；规范 §3.7 定「谁权威/谁派生/谁只读」分层，一处权威、其余派生或只读。

**通用教训**：① **要让人持续维护一个东西，就别让维护它成为「额外的家务」——把状态更新做成工作流的副产物**（交接即改状态），而非收工后要记得的独立动作。这是「看板没人更新」的通用解，比「再加一条『必须回写』的红线」有效得多（红线已经有了，还是漏）。② **模板是隐形的默认值**：模板缺一列，全量新任务都带着这个缺陷生出来——改默认值（模板/脚手架）比改一百个实例便宜。③ **「唯一事实源」要靠收敛、不能靠口号**：六处各写一份必漂移；指定一处权威、其余显式声明为它的派生视图或只读补充。④ **UI 是不是「AI 味」，看它用 emoji 当控件还是用图标系统**——emoji 当按钮 = 廉价感，换成一套 currentColor 的线性图标 + 语义 token popover 立刻「产品化」。

**改动落点**：`app/server.js`（A：`run.entryNo`/`autoAdvanceEntry`/`nudgeBoardConsistency`）、`app/public/{app.js,style.css}`（C 全部 + D 派生 pill）、`templates/task-archive.md`（B）、`文档格式规范.md`（B §3.4 注释 + D §3.7）。引擎（A/B 模板/D 规范）需重启 server；前端（C/D pill）按 mtime 刷 `?v=`。未改 HTTP 端点/SSE 事件/run 形状对外契约（仅加 `run.entryNo` 持久字段 + `entry-auto`/`board-stale` 广播）；未改 `ENTRY_STATUS_ENUM` 值集。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.58 看板「版本级下一棒」手写清单漂移：真状态在工具托管的条目表/gates，手写副本没人同步（2026-08-07，用户提问驱动）

**现象**：老板看任务卡「下一棒（版本级）」——REQ-0276 已 dev+QA 全闭环，本该提示「交波比发测/发线上」，卡上却显示过期的「菲菲：预检分诊」，老板只能手动找波比。质疑「这块是不是过时设计、一点用没有」。进一步核对同卡「等你拍板/待办」块，发现里面的项也过期（如「文案最终确认」实际已定却没翻牌）。

### 3.69 进度卡(stepper) 横排 → 竖排时间线：多步 + 长说明下横排 flex-wrap 换行错乱（2026-08-11，用户反馈截图驱动）

**现象**：老板截图报「样式全乱掉了」。定位后并非整页塌陷（§3.29 那类 CSS 结构事故），而是**单个 stepper 进度卡布局崩坏**——REQ-0261 一张 7 步、每步都带一段长说明(hint)的进度卡，节点被撑到高低错落、连接条(bar)悬空乱飘、整卡糊成一团。用 headless Chrome 加载真 `style.css` + 复刻该 7 步卡实测，1:1 复现了截图。

**根因**：老 stepper 是**横排 flex 行**——`.olc-stepper{display:flex;flex-wrap:wrap}`，节点 `.olc-step`（`min-width:60px`）之间夹 `.olc-step-bar{flex:1}` 连接条（`flex:1` 会吃掉整行剩余宽度）。两个致命点：① `.olc-step-hint` **没有宽度上限**，长说明把单个 step 撑得很宽 → 一行放不下就 `flex-wrap` 折行；② 折行后每行末的 `flex:1` bar 仍抢占该行所有余量 → 连接条变成一条条悬空长线，配合各 step 因 hint 长短不一而高度参差 → 视觉全乱。本批次又把 `.olc-type-stepper` 加进了「表格卡加宽」规则（`max-width:min(840px,96%); flex:1 1 auto`，见 §3.34），**强制把 stepper 撑到填满行宽**，令折行错乱更严重（本是想「给进度看全流程」，narrow dock 下适得其反）。

**机制取舍（为什么改竖排、放弃横排）**：横排 stepper 只适合「少量短标签、无描述」（如两段式发布 3 步、猪猪 E2E 4 步）；一旦步数多或每步带描述，横排在**可变宽度的聊天卡片**里天然脆弱——`flex-wrap` 对「节点+连接条」这种交替结构没有优雅的折行姿态。业界对「带描述的步骤列表」标准解就是**竖排时间线**（Ant Design `<Steps direction="vertical">`、Linear/GitHub 时间线）。故直接改为竖排：节点在左、标题+说明在右，连接线连成一条竖轴且**按该步状态染色**（已完成绿 / 进行中薰衣草 / 失败红 / 未开始发丝线灰），进度轴一眼可读。竖排对步数与说明长度**无上限敏感**，这类布局 bug 从根上消除。

**改动落点**：`app/public/cards.js`（`R.stepper` 改出竖排 DOM：`.olc-step > .olc-step-rail(.olc-step-node) + .olc-step-main(.olc-step-label + .olc-step-hint)`）；`app/public/style.css`（重写 `.olc-stepper` 为纵向 flex、连接线用 `.olc-step-rail::after` 撑满轨道高度并按状态染色、去掉 `.olc-step-bar`/`label max-width:76px` 横排残留；并把 stepper 从「表格卡加宽」规则移除、退回常规卡宽）。置顶进度卡（`#pinned-card`）复用同一 `OLCards.renderCard`，一并受益。纯前端、无 HTTP/SSE/run 契约变更；`?v=` 随 mtime 自动刷。

**验证**：headless Chrome 截图对比——修复前 1:1 复现错乱；修复后 7步·长说明 / 3步 / 4步三种卡在 880px 与 480px 两档宽度均整齐（连接轴 绿→薰衣草→灰、说明自然折行、标题与节点对齐）。CSS 过 §3.29 结构自检；`node --check` 通过。

**通用教训**：**横排「节点+连接条」结构在可变宽度容器里不要指望 `flex-wrap` 兜底**——折行后 `flex:1` 连接条会制造悬空长线、参差高度。步骤带描述就上竖排时间线，一次性消除对「步数/说明长度/容器宽度」三者的敏感。另：排查「样式乱」先分清是**整页塌陷**（查 §3.29 注释/括号结构）还是**单组件布局崩**（复刻该组件 headless 截图定位），别一上来就怀疑全局 CSS。

**现象**：老板截图——v0.8.0 的「列式台账」卡片（§3.42 健康条 + 8 轨对齐行 + facet 按需展开）在**三栏工作台**里被压垮。截图现场：把右侧聊天坞拖到 ~1030px，中栏 `main` 只剩 ~640px，条目行的名字被挤成十几像素、省略成读不懂，facet 展开的 源码坐标/GREEN/run 明细换行成一团。

### 3.74 移动端三连修：预检条竖排 / 触屏 hover 卡浮屏 / 待办长文越界（2026-08-12，用户 iPhone 截图驱动）

**现象**：老板 iPhone 截图三个问题——① 底部批量预检条整条按钮**逐字竖排**糊成一团；② 点条目行时一张信息卡浮在半屏、盖住内容且不消失；③ 待办项长状态文案顶出屏幕右缘被裁。

**根因①（最值得记：固定态 shrink-to-fit 宽度被夹 → CJK min-content 竖排）**：`.precheck-bar` 是 `position:fixed; left:50%; transform:translateX(-50%)`、**无显式宽度**。桌面上固定盒 shrink-to-fit 到内容宽（内容不宽、够放，不溢出）；但手机窄视口下，**固定定位盒的 shrink-to-fit 可用宽 = 包含块宽 − left**，`left:50%` 即只剩约半个视口（~195px），条被夹到这个宽度。条是 `display:flex` 无 `flex-wrap`，子项按默认 `flex-shrink:1` 收缩，收到各自 `min-content`——而**CJK 文本的 min-content = 单个汉字宽**（汉字间处处可断行），于是每个按钮被压成一字一行的竖排。**通用坑**：`position:fixed + left:50% + translateX(-50%)` 的「居中浮条」在窄屏会被夹到半屏宽；容器一旦窄于内容，CJK 会竖排（不像西文有 `nowrap` 默认那么显眼）。两道防线：给按钮 `white-space:nowrap`（任何窄容器都不再逐字竖排）＋窄屏把浮条改成贴两侧全宽（`left/right` 双钉、`transform:none`、`flex-wrap`），别再靠 `left:50%` 居中。

**根因②（hover 交互在触屏的老问题）**：`#olpop` 富 popover 绑在 document `mouseover`/`mouseout`。触屏点按会触发**合成 mouseover** → 卡按锚点坐标浮出（常在半屏中央），而触屏没有真正的 `mouseout`（手指抬起不等于移出）→ 卡不收、盖住内容。修：`mouseover` 处理器首行加 `if (window.matchMedia('(hover: none)').matches) return`——**hover 类交互一律用 `(hover:none)` 守卫，触屏不启用**。信息不丢：阶段/下一棒/球在谁在两行状态行（§3.72）+ facet 展开面板里都可达。

**根因③**：`.pending-item .st` 状态文案 `white-space:nowrap`，长文在窄屏顶出右缘；因 `body{overflow:hidden}` 不产生横向滚动、直接被裁。修：窄屏 `.pending-item{flex-wrap:wrap}` + `.st{white-space:normal}`。

**配套安全区**：`.precheck-bar` 移动端 `bottom:var(--fab-clear)`（抬到 Safari 悬浮底栏之上，复用既有净空变量，见 §3 那批 lvh/svh 安全区）；`.toast-host` 顶部 `calc(52px + env(safe-area-inset-top) + 8px)` 避让刘海+悬浮顶栏。

**改动落点**：`app/public/style.css`（`.precheck-bar .btn{nowrap}`、`@media(max-width:640px)` 内预检条全宽/待办换行/toast 避让）；`app/public/app.js`（olpop `mouseover` 加 hover 守卫）。纯前端、无契约变更；`?v=` 随 mtime 自动刷。

**验证**：隔离 server + Playwright 390×844——预检条修复前 214px·按钮竖排（1:1 复现），修复后 366px 全宽·按钮单行（按钮高 ~22px 而非竖排的 ~100px）；hover 卡桌面(hover:hover)显示、触屏(stub hover:none)抑制；横向无越界元素（docW==vw==390）；console 0 error。⚠ `env(safe-area-inset-*)` 部分 Playwright 无法模拟刘海，按既有安全区口径静态核对。

### 3.75 facet 呈现收敛：进度条弹层列全 facet，替代「行 hover 卡 + 折叠面板」两套（2026-08-12，用户指定）

**改法**：
- **进度条＝触发器**：`.cov-cell`（覆盖堆叠条 + GREEN/总）挂 `data-pop="facet{ti}_{ei}"`，`POP_REG` 里注册该需求的 `facet-rows`（逐 facet：状态徽标 + 编号 + 验收标准 + GREEN 证据链接），**无 `olpop-h` 标题**。去掉覆盖格 chevron（不再是展开开关）。

**关键取舍——hover 卡承载「可点内容」的三个坑**（facet 弹层里有证据链接 `用例`/`用例文件`，要能点）：
1. **`pointer-events`**：`.olpop` 基类是 `pointer-events:none`（纯信息 hover 卡，不挡下层）。facet 弹层要可点，故加 `.olpop.facets{pointer-events:auto}`——**只给需要交互的那类弹层开**，其余（门禁点/覆盖 chip）仍 none。
2. **hover 持久**：`pointer-events:auto` 后，光标从锚点移进弹层本体会触发锚点 `mouseout` → 若立即收起，用户永远够不到弹层里的链接。改成**延时收起（120ms）+ 弹层 `mouseenter` 取消收起 / `mouseleave` 再排收起**，并在锚点 `mouseout` 里判 `relatedTarget` 落在 `#olpop` 内就不收——这样「锚点→弹层」的空档不闪断。标准 hover-intent 模式。
3. **触屏**：hover 一律 `(hover:none)` 守卫不弹（§3.74 教训）；触屏改 `onclick` 走 `toggleOlpopClick`（再点收起）+ 文档 `click` 点弹层外收起（点弹层内/另一锚点不收）。桌面 hover、移动 click，同一份 `POP_REG` 内容。

**配套（需求点编号是重要索引）**：`.entry-id` 加大加粗（11→12.5px/700）并 **REQ/缺陷分色**——`.entry-id.req` 信息蓝 / `.entry-id.bug` 危险红（按 `en.no` 前缀 `BUG` 判定）；弹层内 `.facet-fid` 同口径加大加粗（11→12px/700）。`.facet-rows` 因现仅用于弹层，去掉自身底/框/内距做干净列表（olpop 已提供容器）。

**改动落点**：`app/public/app.js`（`ensureOlpop`/`showOlpop`/`hideOlpop` 加持久+facets 类+触屏开关；`facetParts` 改产出 `{cell(data-pop+onclick), popHtml}`；entry 渲染删行 hover 卡与折叠面板、编号加 req/bug 类；删 `toggleFacetPanel` 等）；`app/public/style.css`（`.olpop.facets`、`.facet-rows` 清容器化、`.entry-id`/`.facet-fid` 加粗分色、删 `.facet-panel*`/`.cov-cell-chev`）。纯前端、无契约变更；`?v=` 随 mtime 自动刷。

**通用教训**：**hover 弹层一旦要承载「可点内容」，就从「纯提示」升级成「hover-intent 面板」**——三件套缺一不可：给这类弹层单开 `pointer-events:auto`（别动纯提示类）、锚点↔弹层空档用延时收起 + `relatedTarget` 判定不闪断、触屏改 click 开关。把同一份内容用 `data-pop`(hover) + `onclick`(touch) 双通道喂给同一个弹层，桌面/移动一套内容两种触发。

**补丁（2026-08-12，同日）——内容过多时弹层盖住锚点/鼠标**：facet 弹层内容可能很高（9 条 facet + 长验收标准）。原 `showOlpop` 定位是「优先放下方，放不下翻上方」，但**没限高**：内容超高时翻上方后 `top` 变负、被 `Math.max(12, top)` 钳到 `top:12`，弹层从视口顶一直画到底、把锚点（进度条）连同鼠标一起盖住——`.olpop.facets` 又是 `pointer-events:auto`，于是鼠标被弹层截走、够不到下层。**修法两条**：① 宽度加大（`min(460→580px,94vw)`），条目多单行、弹层自然更矮；② 定位改为「**选锚点上/下可用空间较大的一侧**放，并把 `max-height` 限在该侧可用空间内、`overflow-y:auto` 内部滚动」——弹层高度天然 ≤ 该侧净空，故**永不越到锚点那一侧、永不盖锚点/鼠标、永不超视口**，内容再多就内部滚。**通用规则**：**贴锚点的浮层（popover/tooltip/下拉）必须限高在「所选一侧的可用空间」内并内部滚动，绝不能让它靠钳位硬塞进视口**——钳位=覆盖锚点。选边用「上下净空谁大放谁」，高度上限就取那一侧净空。

> **演进（2026-08-12）**：本节的 facet「浮层弹层」最终被**居中弹窗（模态）**取代（先试过右侧抽屉，同日又按老板要求定为居中弹窗——宽 880、高 88vh、body 内部滚动）。`.facet-drawer`（函数/元素名沿用，实为居中模态：`translate(-50%,-50%) + opacity/scale` 淡入 + scrim）由点进度条 `openFacetDrawer(key)` 打开，头部 `#编号+全名+关闭`、`.fd-body` 内部滚动、Esc/scrim 关。教训升级：**内容成规模的「明细/清单」别用贴锚点浮层，直接上弹窗/面板**——浮层的定位/限高/hover-intent/滚动这一串坑（§3.74/§3.75 上文）本质是「把面板级内容塞进 tooltip 级容器」；清单量一大就该换承载物。浮层留给「一眼信息卡」（门禁点、覆盖 chip 仍用 `#olpop` hover）。见 CHANGELOG 同日「facet 居中弹窗」条。

### 3.77 移动端交还「文档滚动」：恢复 iOS 点状态栏回顶 / 原生惯性回弹（2026-08-13，用户反馈）

**症状**：手机上碰屏幕顶部（状态栏区）不触发系统级「滚动到最顶」；页面惯性回弹也不像原生站（截图，`localhost`）。

**根因＝滚动器放错层了**。桌面刻意采用「内部滚动 app-shell」：`body{display:flex;overflow:hidden;height:100lvh}`（body 不滚），滚动关进 `#content{overflow-y:auto}`——换来两样好处：① 侧栏固定不随内容滚；② Safari 悬浮底栏永不收起（body 不滚就没有滚动手势去收 chrome，见 body 处 `100lvh` 注释）。**代价**：iOS「点状态栏滚到顶」只认**文档(window)滚动器**（`document.scrollingElement`），对任意嵌套 `overflow:auto` 的 DIV **不生效**；惯性回弹、URL 栏随滚动收起同理只发生在文档滚动器上。我们把滚动关进 `#content`，等于把这些原生手势全让掉了。**这正是与业内优秀移动站的结构差异**：新闻/文档/社交移动站都让 `<body>`/文档自身滚、顶栏 `sticky`/`fixed`、底部导航 `fixed`；「app-shell 内部滚动」是 SPA 仪表盘为固定 chrome 换来的取舍，不是移动 web 的默认，且要付这份代价。

**修法——只在 ≤640px 把外壳拆平，交还文档滚动**。关键观察：移动断点下侧栏（离屏抽屉）、聊天坞（全屏覆盖）、顶栏、scrim **全是 `position:fixed` 浮层**，`<main>` 里只剩 `#content` 一个在流元素——即 `#content` 是**唯一**的在流滚动区。既然只有它，就能安全地把它交还给文档：

```css
@media (max-width: 640px) {
  html, body { height: auto; }
  body { display: block; overflow: visible; height: auto; min-height: 100svh; }
  main { display: block; min-width: 0; }
  #content { flex: none; height: auto; overflow: visible; }
}
```

`body` 恢复普通块、高由内容撑开、文档自身滚动 → 点状态栏回顶、惯性回弹、Safari URL 栏随滚动收起（多给一屏内容）全部回归原生。顶栏仍 `fixed` 悬浮、内容从其下滚过（`#content{padding-top}` 兜底 52px+刘海净空）；底部净空仍交给 `--fab-clear`（文档滚动后 URL 栏会收起，`100lvh-100svh` 项自然退化到 ≈16px，不再堆多余空带）。`min-height:100svh` 保短页面时画布仍铺满、不露系统灰。

**为什么不改桌面**：桌面固定侧栏 + 侧靠聊天坞（`width:min(480px,42vw)` 在流）都依赖 flex app-shell，且桌面没有「点状态栏回顶」这类诉求；拆桌面得而无用、失而伤筋。故按断点分治——桌面维持内部滚动，移动端交还文档滚动。

**注意的坑**：① 别在 `body` 上加 `overflow-x:hidden` 想防横向溢出——按 CSS 规范 `overflow-x:hidden` 会把 `overflow-y` 从 `visible` 隐式提升为 `auto`，body 又变回滚动容器、前功尽弃；横向溢出应改肇事子元素（`min-width:0`/`max-width:100%`）解决。② 顶栏 `fixed` 覆盖在文档滚动内容之上没问题（这正是要的效果），但 `#content` 必须留出「等于顶栏高度」的 `padding-top`，否则首屏内容被顶栏压住。

**验证**：Playwright 双视口——390×844：`body{display:block;overflow:visible}`、`document.scrollingElement` **可滚**（scrollHeight 15547 > 视口 844）、`#content` 不再自成滚动器（`overflowY:visible`、`scrollHeight==clientHeight`）、无横向溢出（382<390）、`fixed` 顶栏 66px 净空不压内容、`scrollTo(bottom)` 到底末项可读；1440×900：`body` 仍 `flex+overflow:hidden`、文档不滚、`#content` 内部滚动器如旧（桌面零回归）。CSS 过 §3.29 结构自检（注释配对 / 括号配平）。**通用规则**：**要原生「点状态栏回顶 / 惯性回弹 / URL 栏收起」，滚动就必须发生在文档(window)滚动器上，别把主滚动区关进嵌套 `overflow` 容器**；确需 app-shell 内部滚动时，要清楚这是拿这些原生手势换固定 chrome 的取舍。

**同批修复——移动端抽屉（侧栏）几何：`top:0;bottom:0` / `inset:0` 会钻到 iOS URL 栏后**。老板同轮反馈抽屉展开时「设置块没钉在最底 + 底部露黑遮罩 + 侧栏不满高」，收起后「黑遮罩不消失、影响全站」。根因与上文同源、只是换了个受害者：**iOS 上 `position:fixed` 的 `bottom:0` 锚的是布局视口(lvh)底，落在可收起 URL 栏之后**。旧抽屉 `top:0;bottom:0;height:auto` + `padding-bottom:var(--fab-clear)`：盒子被拉到 lvh 底（栏后），`.side-controls`（`margin-top:auto` 钉盒底）随之沉到栏后，再靠 `--fab-clear` 往上撑 → 于是 settings 下留一段白 padding、白底又够不到真正的可视底沿、露出底下的灰 scrim；scrim 本身 `inset:0`（bottom:0=lvh 底）把半透明暗层也画进 URL 栏区，读起来就是「底部一条黑遮罩收不起来、像糊住整页」。

**修法（一）——覆盖层一律用「动态视口」`100dvh` 贴合可见区**：抽屉与 scrim 都改成 `top:0` 起、`height:100vh`（兜底）→ `height:100dvh`——`dvh` 精确等于「用户此刻看得见的那块」，URL 栏收/放都刚好铺满，既不留灰带也不钻栏后。抽屉再加 `overflow:hidden auto`（员工多时抽屉内部竖向滚、`overflow-x:hidden` clip 掉巡检涟漪的横溢且不产横向滚动条——注意这半条正是上文「hidden 会把另一轴提升为 auto」的**反向利用**：我要的就是竖向 auto），`padding-bottom` 由 `--fab-clear` 收敛为只避让 Home 指示条；settings 仍由 `.side-controls{margin-top:auto}` 稳钉——内容不超高时钉在可视底、超高时随抽屉内部滚到底可达。**三处 dvh/svh 各按需选**：主内容交给文档滚（无显式高度）；抽屉/scrim 用 `dvh`（要「贴合当前可见、随栏收放」）；聊天坞用 `svh`（要「永远停在栏之上、不随栏变动」）。

**修法（二）——scrim 显隐改 `opacity`+`visibility`（非 `display`），这才是「收起后黑遮罩没消失、糊住整页」的真因**：第一版只把 scrim 几何改对，仍留一手祸根——原先靠 `body.sidebar-open` 开关 `display:block/none`。**主内容改文档滚动后（本节上半），iOS Safari 对「document 滚过、再 `display:none` 掉的 `position:fixed` 合成层」经常不重绘**，留下一层暗色鬼影盖住整页、还拦点击（旧内部滚动布局 body 不滚时没这问题，是文档滚动新引入的合成坑）。照抄本仓库 `.facet-scrim`（§3.75）验证过的做法：scrim **常驻 `display:block`**，显隐用 `opacity`/`visibility`/`pointer-events`——`body.sidebar-open` 开为 `opacity:1;visibility:visible;pointer-events:auto`，收起回 `opacity:0`（`.22s` 淡出）、`visibility:hidden`（延迟 `.22s` 在淡出后生效）、`pointer-events:none`（**立即**生效，收起瞬间就不拦点击）；`prefers-reduced-motion` 关过渡。**通用规则**：**移动端把主滚动交给文档后，全屏 `position:fixed` 覆盖层别再用 `display:none` 显隐（iOS 会留鬼影/拦点击），改用「常驻 + `opacity`/`visibility`/`pointer-events` 切换」。**

**修法（三）——scrim 与抽屉「零重叠」，别再靠层序硬扛（附：`translateZ(0)` 反噬记）**：修法（二）里我曾顺手给 scrim 加 `transform:translateZ(0)`（想提合成层保证重绘），结果**在 iOS 上把 scrim 的单独合成层画到了 z 更高的抽屉之上**——抽屉 `z60` > scrim `z55` 本不该被盖，但 WebKit 里「被 `translateZ`/`will-change` 提层的元素」会无视 z-index 盖过未同等提层的兄弟 → **抽屉底部凭空蒙一层黑**（老板追问「为什么抽屉打开时底部也有黑遮罩」）。教训：**别用「提合成层」去治重绘，它会连带打乱 z 序**。根治方向不是继续调层序，而是**从结构上让 scrim 与抽屉不重叠**：scrim 的 `left` 由 `0` 改为 `min(280px,82vw)`（= 抽屉宽），只盖抽屉**右侧**的主内容区。抽屉本就不透明、其后无需垫暗层；两者零重叠后，scrim/抽屉谁在上层彻底不重要，`translateZ` 也一并删掉。**通用规则**：**抽屉类 scrim 只需盖「非抽屉区」——把 `left` 顶到抽屉右沿即可，别用全宽 scrim 垫在不透明抽屉之后再靠 z-index/合成层硬压（那是一整类层叠 bug 的温床）。**

**修法（四）——scrim 高度改 `dvh`→`lvh`：装饰暗层要铺到「屏幕真底」，别停在 URL 栏上沿**：真机截图暴露最后一处——抽屉展开时右侧暗层只铺到 `dvh`（可见区底＝Safari 悬浮 URL 栏上沿），**栏背后那截露出白 html 底、屏幕底部多出一条没压暗的白带**。真因＝我修法（一）图省事把「抽屉 + scrim」一把都设成 `dvh`，但二者诉求相反：**scrim 是纯装饰暗层、没有要停在栏上的内容，就该一路铺到屏幕真底（连 URL 栏背后也蒙上）→ 用 `lvh`**；**抽屉是白底（与 html 画布同色）、栏后天然无缝，且装着要够得到的设置块 → 用 `dvh` 停在栏上**。故 scrim 高度 `100dvh`→`100lvh`，抽屉维持 `dvh`。**通用规则订正（覆盖修法一的「一把 dvh」）：视口单位按「这层要不要把内容停在栏之上」分流——有内容要停栏上用 `dvh`（抽屉）；纯装饰要铺满真底用 `lvh`（scrim/背景暗层）；要永远浮在栏之上用 `svh`（聊天坞输入区）。别一把梭同一个单位。** ⚠ **本条随即被修法（五）再订正**——抽屉最终也用 `lvh`（见下）。

**修法（五，收口）——抽屉与 scrim「全出血」都用 `lvh` + 开抽屉「锁文档滚动」，一次性了结白带/黑白残留**：修法（四）只把 scrim 提到 `lvh`、抽屉仍 `dvh`，结果二者**高度不齐**——抽屉（dvh）止步 URL 栏上沿、栏后露白 html 底，右侧 scrim（lvh）铺到真底 → 屏幕底部左白右暗一大块白块（老板：「更坏了」）。教训：**抽屉与其上的 scrim 必须同高**，否则必留错位色带；「有内容用 dvh」的分流对「白底 = 与 html 同色、栏后无缝」的抽屉并不必要，反而制造错位。**故抽屉也改 `100lvh`、与 scrim 全出血铺到真底**，设置块用 `padding-bottom:var(--fab-clear)` 抬到 URL 栏之上（其下是抽屉自己的白底，scrim 已 `left:280` 不在此列、不露暗）。

再一层：**「收起后黑/白遮罩不消失」反复出现、只是残留物颜色随当时底部元素变**——真凶是**主内容改文档滚动后（本节上半），iOS 对「文档滚过 + `position:fixed` 覆盖层」常合成不重绘、留鬼影**（改 opacity/去 translateZ/挪 left 都只治标）。**根治＝开抽屉时锁文档滚动**：`app.js` `openSidebar()` 记 `window.scrollY`、把 body 冻成 `position:fixed`（CSS `body.sidebar-open{position:fixed;left:0;right:0;width:100%;overflow:hidden}`、配合内联 `top:-scrollY`），`closeSidebar()` 清样式并 `scrollTo(0,scrollY)` 还原；`toggleSidebar` 改走 open/close，仅移动端锁（`_sbMobileMQ`）。文档不滚，fixed 层就稳定、收起无残留，顺带挡背景误滚。**通用规则（最终）**：**① 抽屉与其 scrim 同高、都用 `lvh` 全出血铺到真底（内容项各自 `padding` 避让栏/指示条）；② 移动端把主滚交给文档后，任何 fixed 覆盖层的开合都要「锁文档滚动」（记录+还原 scrollY），否则 iOS 合成鬼影收不干净——这比在覆盖层上折腾 display/opacity/合成层都治本。**

**验证（收口）**：Playwright 390×844——**锁滚**：`scrollTo(0,500)`→`openSidebar()`：body `position:fixed`/`top:-500px`/`lockY=500`/背景冻结（scrollY_while_open=0）；`closeSidebar()`：body 复位 `static`、`top` 清、`scrollY` 还原 500（无跳）。**全出血**：抽屉高 844、scrim 高 844、`left=280`；展开稳定后抽屉列 x=140 y740→840 逐点全 `sidebar`/`side-controls`（设置块 ~790-815 抬起、上下均白底），主区 x=350,y820 命中 scrim；截图确认整列纯白到底 + 右侧暗到底、无白带/暗带/接缝；收起 scrim opacity0/visibility hidden。`node --check` app.js 通过、CSS 结构自检过。

**验证（抽屉）**：Playwright——390×844 展开（待过渡稳定）：scrim 矩形 `left=280`（= 抽屉右沿）、`scrim_overlaps_drawer=false`、`reaches_true_bottom=true`（底 844=真底）；抽屉列 x=140 从 y100→830 逐点命中全是抽屉/子元素（nav/员工行/`side-controls`/`sidebar`）、**无一命中 scrim**；主区 x=350 命中 scrim（点它可关）；截图确认抽屉整列纯白到底、设置钉左下、右侧主区蒙暗一路到底。`closeSidebar()` 后 scrim `opacity→0`、`.22s` 后 `visibility:hidden`、`pointer-events` 立即 `none`、命中穿透到 `.entry-line`（**不拦点击、不糊页**）；375×480 短屏注入 10 员工：抽屉内部可滚（scrollHeight 855>clientHeight 480）、滚到底 settings 可达；1440×900 桌面：侧栏 `position:static`、`overflow:visible`（涟漪不裁）、scrim `display:none`——桌面零回归。**几何通用规则**：**移动端全屏/半屏 fixed 覆盖层要「铺满可见区」，别用 `top:0;bottom:0` 或 `inset:0`（其 `bottom:0` 在 iOS = lvh 底、钻 URL 栏后）；有内容的从 `top:0` 起给 `height:100dvh`（停栏上），纯装饰暗层给 `height:100lvh`（铺真底）。**

### 3.80 浮动聊天卡里 Radix 下拉菜单「鼠标点了不生效」：拖动手柄经 React portal 抢走菜单项的 pointerup（2026-08-18，用户反馈）

**现象**：老板反馈聊天窗口里「显示/隐藏过程细节」开关不管用、「切换会话（历史会话）」也不管用。二者都是浮动聊天卡（`floating-card.tsx`）**标题栏**里的 Radix 下拉菜单项，鼠标点了毫无反应；卡外的下拉（如侧栏「切换主题」）一切正常。

**定位（Playwright 实测）**：先排除——键盘方向键聚焦菜单项 + 回车**能**正常选中并生效（`ol-show-process` 写入、菜单收起），说明 onClick/onSelect 逻辑没问题、Collection/roving focus 也正常，问题只在**指针路径**。给 document 挂捕获期监听打点：点菜单项时 `pointerdown` 落在 `dropdown-menu-item`（@x1056），但 `pointerup`/`click` 被**重定向**到卡片根 DIV（@x801），且期间卡片 `style` 属性变了两次（`willChange` 一置一清）。Radix 菜单项要求「同一元素上按下+抬起」才判定选中——目标一变，选中永不触发。

**根因**：标题栏兼作拖动手柄，`onPointerDown` 里 `e.currentTarget.setPointerCapture(e.pointerId)` 起拖。Radix 把菜单内容 **portal 到 `document.body`**（DOM 上已脱离卡片），**但 React 合成事件仍沿组件树（而非 DOM 树）派发**——菜单项在 React 树里是标题栏的后代，故点菜单项的 pointerdown 会「冒泡」到标题栏的 `onPointerDown`。原有守卫 `e.target.closest('[data-no-drag]')` 对 portal 里的项**失效**：菜单项的 DOM 祖先链是 `menu-content → portal → body`，不含卡片那个 `data-no-drag` 容器（那是它 React 父级、不是 DOM 父级），于是守卫放行 → `setPointerCapture(标题栏)` 把该指针后续事件（含 pointerup）全部改派给标题栏 → 菜单项收不到自己的 pointerup。开菜单（点 trigger）不受影响，是因为 trigger 是标题栏的**真实 DOM 子节点**、落在 `data-no-drag` 内、守卫拦住了。

**对策**：标题栏 `onPointerDown` 首行加 **DOM 包含判断** `if (!e.currentTarget.contains(e.target as Node)) return`——真实目标不在标题栏 DOM 子树内（即来自 portal 浮层）就不当拖动、直接返回，不再 `setPointerCapture`；真拖标题栏时 target 被包含、照常起拖。一行修复同时治好两个症状（两个菜单同在标题栏）。修后实测：鼠标点「隐藏过程细节」`ol-show-process` `1→0` 且菜单收起；鼠标点「历史会话」某条，卡片会话 ID 由 `…142059-5e362c` 切到 `…125930-e0002d`。

**通用规则**：**给「兼作拖动手柄 / 会 `setPointerCapture` / 会在 pointerdown 里改 DOM」的容器加事件守卫时，`e.target.closest(...)` 这类走 DOM 祖先链的判断对 portal 出去的子组件（Radix 菜单/下拉/弹层）会失效——它们在 React 树里是后代、在 DOM 树里却挂到了 body。要用 `e.currentTarget.contains(e.target)`（DOM 包含）把「来自 portal 浮层的合成事件」挡在拖动/捕获逻辑之外，否则 setPointerCapture 会悄悄抢走浮层的 pointerup、令其点击整体失灵（且键盘可用、极易误判成别处的 bug）。**

### 3.87 巡检雷达的状态与真实动作对不上：「巡逻中」在引擎里根本没有信号（2026-08-20，老板反馈，承接 3.86）

**现象（老板原话）**：「即将巡逻 → 下次~1分 → 即将巡逻，按理说这个过程里应该已经巡逻了，但是我没有看到巡逻动画，而且即将巡逻是什么意思？我理解的状态有巡逻倒计时、巡逻中、处置中、巡逻倒计时这样的状态流转，现在小呆呆在员工列表的状态完全跟实际动作对不上。」

**根因两条**：
1. **「即将巡逻」是分钟取整的产物，不对应任何引擎动作**。3.86 从旧 UI 照搬的文案是 `Math.round((nextSweepAt - now)/60000)`，不足 30 秒即显示 0 分 → 写「即将巡逻」。而本机 `patrolSweepMin` 被调成了 **1 分钟**，倒计时永远在 0~1 分之间 → 文案就在「即将巡逻 ↔ 下次~1分」之间来回跳。旧 UI 这套文案是按默认 6 分钟设计的，1 分钟间隔下直接退化成噪声。
2. **「巡逻中」这一状态在引擎里没有任何可观测信号**。`sweepIdleStops()`（`app/server.js`）是一次**微秒级的纯内存扫描**（遍历 runs 注册表 + 静置 ≥5min/≤24h、同 run 30min 冷却、任务非终态、员工不忙等过滤），**不产 run、不广播任何事件**；只有扫到真空停才 `spawnPatrol()`。而 `/api/patrol-status` 的 `active` 判的是「小呆呆有没有在跑的 run」——**那已经是「处置中」**。于是前端能表达的只有「倒计时」和「处置中」两档，中间「他确实巡了一轮、只是什么都没捞到」这一跳**完全不可见**；而绝大多数扫描恰恰什么都捞不到，所以动画"从没见过"。3.86 还给待机态挂了持续小涟漪，反而强化了「他好像一直在忙」的错觉——正是"对不上"的观感来源。

**修复：把状态机对齐真实动作（四态）**
| 相位 | 引擎事实 | 视觉 | 副标题 |
|---|---|---|---|
| `off` | `patrolEnabled=false` | 不渲染 | 打烊 · 暂不巡视 |
| `countdown` | 引擎静止，等下一跳定时扫描 | **只有极慢光环，无涟漪** | 巡逻倒计时 · 剩 N 秒/分 |
| `sweeping` | 刚跑完一轮 `sweepIdleStops` | 单道快波 1.6s，**不循环** | 巡逻中 · 扫了 N 条，无异常／发现 N 处空停 |
| `handling` | 他有在跑的 run（`active`） | 大波连绵 + 光环快呼吸 | 处置中 · 在查 XX |

- **引擎新增（唯一缺的那个信号）**：`sweepIdleStops()` 末尾广播 `patrol-sweep {at, scanned, candidates, spawned, nextSweepAt}`，并记 `_lastPatrolSweep`；`/api/patrol-status` 增 `lastSweepAt` / `lastSweep`（供刚打开页面的前端补上「上次巡逻」而不必等下一跳）。
- **前端**：`PatrolPhase` 由 `idle/active` 改为 `countdown/sweeping/handling`；provider 加 `patrolSweeping`（`patrol-sweep` 点亮、1.6s 自灭，并顺手 `refresh()` 让顺延后的 `nextSweepAt` 立刻归位）；倒计时抽成 `PatrolCountdown` 组件自带 1s 心跳（**不足 1 分钟按秒走字**，只重渲这一个 `<span>`，不带着整条员工列表每秒重渲）；处置中副标题用引擎早就在发、前端一直没用的 `checking` 字段点名「在查谁」。
- **徽标口径同步收紧**：右下角「巡查中」三点徽标只在 `handling` 亮。巡逻中/倒计时不亮——那两态由雷达表达，别把待命画成在忙。

**取舍**：
- **1.6s 的 `sweeping` 动画是「刚扫过」的回执，不是「正在扫」的进度**。真实扫描是微秒级的，如果诚实地按真实时长渲染，等于什么都看不到；所以选了「事件触发的一次性短动画」而不是「持续动画」，并只放**一道**波（处置中才是三波连绵）——两者视觉必须可区分，否则又回到"看不出他在干哪件事"。
- **倒计时态刻意不放涟漪**。涟漪＝「有动作」的语言，倒计时期间引擎一动不动，继续冒波就是在撒谎。这是对 3.86 的直接修正。
- **`patrol-sweep` 无条件广播（哪怕 spawned=0）**，因为"扫了但没事"恰恰是最常见、也最需要被看见的那一跳。代价：SSE 上每 `patrolSweepMin` 分钟多一条小事件（本机 1 分钟间隔 → 每分钟一道波，嫌频繁可在「巡视设置」把间隔调回 6 分钟）。

**验证**：引擎侧起隔离实例（`OFFICE_LAB_PORT=8795` + 独立 `OFFICE_LAB_RUNS_DIR`，生产未动、用完即杀）实测——`POST /api/chain-config {patrolSweepMin:1}` 即时重布定时器（`nextSweepAt` 变 42 秒后），SSE 流上如期收到 **一条** `{"type":"patrol-sweep","scanned":0,"candidates":0,"spawned":0,"nextSweepAt":…}`，`/api/patrol-status` 随后带上 `lastSweepAt`/`lastSweep`。前端侧 Playwright 实测三相位：`countdown` 涟漪 `display:none`、只剩 `patrol-aura-idle`、副标题「巡逻倒计时 · 剩 35 秒」并在 2.1s 后走字到「剩 33 秒」；`sweeping` 单波 `patrol-ripple-sweep` 迭代数 **1**（不循环）、0.7s 时 290px、第 2/3 波 `display:none`、光环也只 1 次；`handling` 三波 `patrol-ripple-wide infinite`、延迟 `0/1.47/2.94s`。`node --check` + `tsc -b` 通过。**`sweeping`/`handling` 两相位的真机连线（真 SSE → 动画）需引擎重启后才生效**（改动在 `server.js`）——当时生产有一条 run 在跑，未擅自重启。

### 3.88 窄窗聊天正文被裁：grid 轨道被 ```代码块``` 顶宽，容器上的 `min-w-0` 管不了轨道（2026-08-20，老板窄窗截图）

**现象（老板截图）**：488px 宽的聊天窗（悬浮窗尺寸）里，正文右侧被**齐刷刷切掉**（「现在是线上域名」「起本地址跑」「而不是…」都断在同一条竖线上），代码卡右边界溢出窗外，而且**没有横向滚动条可滑**——只能看见被裁后的残句。

**取证**：窄窗下把所有 `scrollWidth > clientWidth` 的元素按超出量排序，链条一路指到同一个源头：
```
div.grid.min-w-0.gap-2         clientW 413   gridTemplateColumns: 570.375px   ← 轨道被顶宽
  └ div.text-sm.[overflow-wrap:anywhere]   min-width: auto   width 570        ← ★ 真凶（Markdown 根）
      └ pre.my-2.overflow-auto             width 570
  └ div.min-w-0.rounded-xl…（OLCard）      width 568（被轨道拉宽）
      └ pre.max-h-80.min-w-0               clientW 538（同样是被拉宽的结果）
外层 div.scroll-fade…overflow-x-hidden      clientW 473 / scrollW 618          ← 超出 145px 被直接裁掉
```
**根因**：`OLContent` 那层 grid 没写 `grid-template-columns`，于是是一条隐式 `auto` 轨道——**轨道的最小尺寸 = 各子项 min-content 贡献的最大值**。容器自己写了 `min-w-0` 但那**管不了轨道**；决定轨道的是**子项**的 `min-width`。同层的 OLCard 有 `min-w-0`（贡献 0），而 `Markdown` 根 div 是默认 `min-width:auto` → 它的 min-content 由内部 ```代码块``` 决定：`<pre>` 是 `white-space:pre`、**不换行**，一条长命令就把 min-content 顶到 570px。轨道遂被钉在 570，整列所有内容（含正文段落、OLCard）跟着按 570 排版，再被外层 `overflow-x-hidden` 裁到 473——**正文被裁、且因为是 hidden 而非 auto，连滑都滑不了**。

`Markdown` 根上那句 `[overflow-wrap:anywhere]` 治不了这个：它只作用于**可断行文本**，对 `white-space:pre` 的 `<pre>` 无效。所以「长标识符能换行」早就修好了（见该文件注释），而「代码块顶宽整列」是同一位置漏掉的另一半。

**修复两处（互补，不是重复）**：
- **`markdown.tsx`：Markdown 根加 `min-w-0`**（治本）。它几乎总是作为 flex/grid 项出现（气泡里、消息列里），min-content 贡献归 0 → 轨道收回容器宽 → `<pre>` 自己 `overflow-auto` 在卡内横向滚动。一处修好所有用到 Markdown 的地方（聊天、运行详情、文件预览、员工详情）。
- **`olcard.tsx`：`OLContent` 的 grid 加 `grid-cols-[minmax(0,1fr)]`**（结构性护栏）。显式把唯一那条轨道钉成 `minmax(0,1fr)`，此后**任何**子项（未来新卡片类型、宽表格、忘了 `min-w-0` 的组件）都不可能再撑宽整列。这层装的是任意 markdown 段 + 各种卡片，最容易漏。

**通用规则（值得记住的那条）**：**flex 项漏 `min-w-0` 会撑宽父级——这条团队已经知道（`transcript.tsx` 里到处是 `min-w-0`，还写了注释）；但 grid 的 `auto` 轨道是另一道坎：给 grid 容器加 `min-w-0` 没用，轨道宽度由子项的 min-content 决定。** 容器侧的正解是 `grid-cols-[minmax(0,1fr)]`，子项侧的正解是逐个 `min-w-0`。判据：只要那一列可能装「不换行的东西」（`<pre>`、`white-space:nowrap`、宽 `<table>`、长 URL），两条至少要有一条。另外**外层用 `overflow-x-hidden` 会把这类 bug 从"出现横向滚动条"变成"内容被静默裁掉"**——更难发现、观感更糟（用户只看到句子少了半截）。

**验证**（Playwright 实测 4700 产物，488×846 模拟悬浮窗）：修前 `.scroll-fade` `clientW 473 / scrollW 618`（溢出 145）、Markdown 轨道 570px；修后 **`scrollW 473`、溢出 0**、`documentElement` 溢出 0、抽样 8 段正文 `scrollWidth-clientWidth` 全为 0（不再有裁切）；剩余唯一「超出」的元素只有 `<pre>` 自身（`overflow-x:auto`、clientW 381/413 已在容器内），**那正是期望行为——代码不换行，只在自己的框里滚**。桌面态 1280×860 回归检查：`documentElement` 与滚动区溢出均为 0、代码卡 381px 在 443px 列内、正文无溢出。`tsc -b` 通过。纯前端改动，**新 UI 重新构建生效**（`build:watch` 已自动产出），引擎无需重启。

### 3.89 聊天窗「活动气泡」在员工明明在跑时不显：只信「变化才发」的广播，漏了轮询快照（2026-08-20，老板反馈）

**现象（老板反馈）**：员工在跑（侧栏名牌是工作中、头像在动、会话列表也显示着活动文案），但打开的聊天窗底部**没有那条三点打字气泡与活动文案**。

**取证（生产实例实时抓的一条）**：

```
GET /api/runs → 20260820092957-2c9ae3
  status: "running"          ← 引擎确认在跑
  activity: "思考中… ~1.3k"   ← 引擎确认在思考
runs/20260820092957-2c9ae3.jsonl 末尾事件： … result → lab
                                              ↑ 上一轮的收工，本轮还没吐第一条 assistant/tool
```

**根因**：`run-detail.tsx` 的判定是

```js
const activelyThinking = live && (lastMeaningful?.type !== 'result' || liveActivity !== null)
```

两条支路在上面这个状态下**同时为假**：

1. `lastMeaningful` 是上一轮的 `result`（本轮处在「思考前奏」——思考块与工具活动只走全局 `run-activity` 广播、**不落 per-run 事件流**，所以 per-run 流里确实还没有本轮的任何事件）。
2. `liveActivity` 恒为 `null`——它只由 `run-activity` SSE 点亮，而引擎**只在活动文案发生变化时才广播**（`app/server.js` 的 `if (activity !== run.activity)` 与 `if (act && act !== run.activity)`，那是刻意的天然限流）。于是**「开窗那一刻」拿不到任何补发**（SSE 没有 last-value 语义），**「长工具调用期间」文案不变也一条都不发**。切窗/刷新页面时 `liveActivity` 又被按 `runId` 重置回 `null`，等于每次开窗都重新掉进这个盲区。

而**轮询早就把 `run.activity` 拿在手里了**（`/api/runs`，10s 一跳）——代码里却只把它当**兜底文案**用（`{liveActivity || run.activity || '…正在处理…'}`），**没让它参与显隐判定**。判据用了最实时但会缺跳的信号，忽略了慢一点但**始终有值**的快照。

**修复**：把「本轮在生成」改成三个互补信号的并集，任一为真即认——

```js
const activelyThinking = live && (liveActivity !== null || !!run.activity || lastMeaningful?.type !== 'result')
```

- ① `liveActivity`：`run-activity` 广播，最实时，负责文案走字；
- ② `run.activity`：轮询快照。**开跑即非空、`onTurnComplete` 与中断/出错都会清空**（`run.activity = ''`），正好补①的开窗盲区与长工具调用盲区；
- ③ `lastMeaningful !== 'result'`：本轮已吐过内容。

另补一路：订阅 `run-status`，本 run 转 `running`/`starting` 时先点亮兜底文案「处理中…」（`a ?? '处理中…'`，不覆盖已有的真实文案），转终态归零。**新一轮开跑（resume / 排队消息被接 / 自动续跑）时 `run-status` 是第一手信号**，比等第一条 `run-activity` 早，也比等下一跳轮询早。

**为什么不会反向误显（收工了气泡赖着不走）**：`run.activity` 虽有最多 10s 的轮询滞后，但 `live` 走的是 `runStatus ?? run.status`，而 `runStatus` 由 `run-status` SSE **即时**更新——收工瞬间 `live` 就是 `false`，整个表达式短路，气泡先于轮询消失。滞后只可能让气泡**多显**（在真的在跑时），不会让它**多留**。

**通用规则**：**「变化才广播」的事件流不能单独作为 UI 状态的判据**——它没有 last-value/补发语义，订阅者在任意时刻接入都可能长时间收不到任何一条。凡是这类信号，要么服务端在订阅时补发一次当前值，要么客户端拿**轮询快照**兜底判定（本例走后者，因为快照本来就在手里）。同理可查的还有：任何 `if (新值 !== 旧值) broadcast(...)` 的引擎广播，前端若拿它当「有没有在发生」的唯一依据，都有同款盲区。

**验证**：`tsc -b` 通过；`build:watch` 已产出新 dist（4700 `vite preview` 直接生效，需硬刷新）。失败态的真机复现依赖「某员工正好处于思考前奏/长工具调用」，本次是拿生产实例的实时快照（上方取证）坐实判定分支，未在浏览器里现场蹲到那一瞬。纯前端改动，引擎无需重启。

### 3.91 引入 GSAP 作全站动效底座 + 小呆呆接管横幅拟人化（2026-08-21，老板指定「用 GSAP 做比较俏皮的动画」）

**起因**：老板截图指着聊天窗底部那条巡视员接管提示——一句静态文案 + 盾牌图标 + 「取消接管」按钮，到点后画面上就是一行僵住的「0s」。原话是「用 gsap 创作比较俏皮的动画，比如小呆呆的头像从窗口外探出然后加上文字气泡等等拟人化」，并要求**把 GSAP 当成系统内的动效底座**、后续更多动画都走它。

顺带发现这是一处**迁移退化**：旧 UI（`app/public/app.js:1778-1833` + `style.css:999-1033`）那版横幅本来就有头像脉冲、进度条、和 taken/cancelled/reply 三种收尾动画，搬到新 UI 时只留了文案。同时丢了两件功能：文案不再走花名册（硬编码「巡视员」，旧 UI 是 `patrolName()`），以及不再据 `run.patrolGraceUntil` 补渲染（旧 UI 的 `syncPatrolBanner`）——**宽限窗内新开或切换聊天卡，因为错过了 `patrol-pending` 那一发 SSE 就什么都看不到**。

#### 为什么引 GSAP，而不是继续堆 `@keyframes`

本仓库前端一直是纯 CSS 动画（`.emp-dots`、巡检雷达的 `patrol-ripple`/`patrol-aura`、`.ol-msg-in`），那些都是「一个元素的一段循环」，CSS 完全够用、也不该改。这次需要的是 CSS 结构上做不了的三件事：

1. **多元素编排**——探头 → 气泡从他嘴边弹出 → 按钮跟进，各段错开、可整体反放。用 `animation-delay` 手工对齐三四段是维护地狱，改一个时长要顺推后面全部。
2. **运行时调速**——末 3s 要把「待机呼吸」这条**已经在跑的循环**加速成催促（`breathe.timeScale(2.3)`）。`@keyframes` 只能换一套 `animation` 重来，视觉上会跳一下，而且会丢当前相位。
3. **与真实时长同步**——收尾/入场的节奏要跟引擎给的 `deadline` 对齐，CSS 只能写死秒数。

底座落在 `web/src/lib/motion.ts`：注册 `useGSAP`、`gsap.defaults` 对齐既有 CSS 手感（`.ol-msg-in` 的 `cubic-bezier(.22,1,.36,1)` ≈ `power3.out`，免得 GSAP 动的和 CSS 动的两种节奏并存）、导出统一缓动语汇 `EASE{settle/pop/bounceIn/breathe/linear}` 与 `reducedMotion()`。**三条约定写在文件头**，新增动画一律照办：① 走 `useGSAP` + `scope`（靠它自动 revert，禁止裸 `useEffect` 建 tween 不清理）；② 只动 transform/opacity，不动 width/height/top/left（唯一例外是整条横幅的 height 展开收起，无 transform 替代且只跑一次）；③ 每处都要有 reduced-motion 分支。

#### 构图：「探出」靠裁切，不靠画

呈现口径是老板在同一轮里追加定的三条，都往「更沉浸」收：

- **无底色、无边框**——横幅本身透明，只有头和气泡浮在会话面上。原先那层琥珀底 + `border-t` 让它读作"系统告警条"，去掉之后读作"有个同事凑过来说话"。
- **有倒计时就不要进度条**——同一件事别用两种控件说。秒数本身足够，末 3s 再靠配色转 destructive 加压。
- **取消改成气泡右上角的圆形 X 图标钮**——比另起一颗按钮更像"把这句话关掉"。icon-only 按仓库根 `CLAUDE.md`「前端 E2E 可达性规范」补了 `aria-label`，`data-testid="patrol-cancel-btn"` 沿用旧 UI 的命名。

关键一招是**根节点 `overflow-hidden` 把头的下半截掉**，而那条裁切边正好压在输入框的上边线上——于是他读作从输入框后面探进来，而不是"贴了张头像"。头用 `-mb-4` 让下半截落到裁切边之外，`transformOrigin: 'center bottom'` 让歪头以"脖子"为轴。动作序列：`yPercent 130→0` + `rotation -16°→0` 用 `back.out(2)`（overshoot 就是"探"的俏皮感）→ 气泡 `scale .5→1` 且 `transformOrigin: 'left bottom'`（从他嘴边长出来）→ 待机呼吸 + 微歪头循环（`y -3` / `rotation 3.5°`，`yoyo` + `repeat: -1`，**这条是"活的"的关键，静止的头像只是张图**）。收尾两态各一套人物动作：取消是「点个头 → 缩回输入框后面 → 条子收起」，真接管是「整个翻进来 → 连头带气泡走进会话里」。

#### 坑一：位移一律用 `fromTo`，不要用 `from`

第一版按钮那条写的是 `.from(btn, { autoAlpha: 0, x: 10 }, 0.4)`。表现是**取消按钮根本不出现**。

排查数据（dev 里插桩打出来的）：时间线构建正确（`duration 0.66`、4 个子 tween、按钮 target 是真实在文档里的节点、构建后 `getComputedStyle(btn).opacity === '1'`），时间线也**真的跑完了**（`onComplete` 触发、`progress() === 1`），可按钮的 inline style 永远停在**起始态** `transform: translate(10px, 0px); opacity: 0; visibility: hidden`，且事后 `gsap.getTweensOf(btn).length === 0`。

根因是 `from()` 的语义：**终值靠"读当前值"**，读取时机与 `immediateRender`（`from`/`fromTo` 默认为 `true`，会在创建时先把起始态刷上去）在 React 的挂载/re-sync 时序里一撞，就可能把终值读成起始态自己——于是它"从 0 动到 0"，肉眼就是元素消失。GSAP 官方指引里也写了同款警告：多个 `from()`/`fromTo()` 命中同一元素同一属性时要给后者 `immediateRender: false`。

**规则**：本仓库里凡是**位移/显隐**类动画一律用 `fromTo`（起止都写死，不读当前值）。`from` 只留给「终值就是元素的自然布局值、且只有这一条 tween 碰它」的场合——本组件里只剩根条的 `from(root, { height: 0 })`（终值必须是自然高度，正是要读的那个值）。

#### 坑二：随时间变的量不能交给自走的 tween

秒数与进度第一版想用一条 `duration = 剩余毫秒` 的 tween 自己走完。不行：GSAP 的 **`lagSmoothing`**（默认 `500, 33`）会把大于 500ms 的帧间隔当成 33ms 处理——**标签页隐藏期间时间被"抹平"，切回来 tween 落在过去**，显示的秒数就和真实剩余时间脱节。这直接违反旧 UI 定下、一路沿用的口径①「**只按引擎 deadline 渲染、自己不计时**」（多端一致、刷新/切窗口不各算一套）。

改成**一个 `gsap.ticker` 回调，每帧从 `deadline - Date.now()` 现算**，秒数变化时才写 `textContent` 并弹一下、剩余 ≤3s 时一次性切催促态。既保住了真值口径，又顺带得到一个好处：**倒计时期间零 React 重渲染**（整条横幅在计时期间不进 render，只有 phase 变化才重渲染）。

另一条沿用的口径②：**到点不自动收横幅**，停在 0s 等引擎的 `patrol-detected`/`patrol-escalate` 来收尾——因为「派没派出去」只有引擎说得准。

#### 调试开关

真实宽限窗只有几秒、还得先让员工真空停才触发，逐帧调动画不现实。加了 dev-only 旁路 `?patrolDemo=<秒>`：假开一次倒计时，到点自动播「已接管」那套收尾（替引擎的 `patrol-detected` 走一遍）。`import.meta.env.DEV` 守卫，生产构建里整段被 tree-shake。**后续调其它 GSAP 动画建议沿用这个套路**——比"想办法让真实事件在恰当时刻发生"便宜得多。

**验证**（Playwright 实测 4701 dev + 真实 run）：逐帧采样核对入场（`h:0→50`，头从 `y 62.4px / rot -16°` 起）、待机呼吸（头 `y` 在 `-0.17~-2.98px` 往复）、末 3s 催促（`data-urgent=true` 与文案切换准点落在 3s）、两种收尾（取消约 1.6s：点头→气泡淡出→头 `y→62.4`→`h 50→1`→卸载；接管约 1.5s：升起 `scale 1.09`→连头带气泡 `x→46` 淡出→collapse）；`prefers-reduced-motion: reduce` 下头像 transform 恒为 `matrix(1,0,0,1,0,0)` 而秒数照跳；亮/暗色与 390px 窄屏各扫一遍（气泡不换行、X 不被 `overflow-hidden` 裁）。`oxlint` 无新增告警、`tsc -b` + `vite build` 通过。依赖 `gsap@3.15.0` + `@gsap/react@2.1.2`（只用 core + `useGSAP`，主 chunk +约 66KB min / +约 20KB gzip）。**真实 SSE 链路（`patrol-pending` → `patrol-detected`）本次未现场蹲**——引擎侧事件形状没动、横幅只换了呈现，但端到端仍留待下一次真实空停时复看。

### 3.92 聊天窗停靠为主页面第三栏：为什么**不能**换 portal 容器（2026-08-21，老板指定）

**起因**：聊天一直是浮在内容之上的自由浮动卡（`web/src/components/floating-card.tsx`），随手开很方便，但它**盖住看板**——想边翻看板边跟员工对话，只能反复挪窗或切前后层。老板要求「让聊天窗口支持停靠在主页面右侧，独立第三栏」，主内容让位收窄而不是被盖住。

同轮拍板两条口径：① **同时只停靠一张**，其余会话继续走浮动窗（不做页签、不做纵向分屏）；② **停靠是一种「模式」**——第三栏开着时，点侧栏员工/看板卡片打开的会话直接进第三栏换内容，上一张自动弹回浮动窗。

> **⚠ 口径②已于 2026-08-24 翻案，见 §3.98**：第三栏改为「占住即钉住」——有卡占着时新开的会话一律走浮动 popup，换栏只剩标题栏停靠开关这一个显式入口。本节其余内容（不换 portal 容器、层带划分、钳位基准、幻影空栏）仍然有效。

#### 核心取舍：portal 换 container = 子树重挂 = 丢状态

最直觉的实现是「停靠中的卡改成 portal 到外壳里的第三列容器」。**这条路不能走**：React 的 `createPortal` 换 `container` 时，reconciler 会删掉旧 portal 再建新的，**子树整体卸载重挂**。对这张卡来说代价是致命的——`RunDetail` 里已经加载的 transcript、`useRunStream` 的翻页游标、输入框里没发出去的草稿全部归零，每次点一下「停靠」都要重新拉一遍历史。停靠是个高频的视图切换动作，不是重开窗口。

改成两件事凑出第三栏，卡片**始终 portal 到 body、组件树位置一动不动**：

1. 停靠态只换定位——`fixed inset-y-0 end-0` + 固定宽度（贴窗口右缘的通高一栏），不再用浮动那套 `pos/size`；
2. 把栏宽写进全局 CSS 变量 `--ol-dock-w`，外壳的 `SidebarInset` 用 `pe-(--ol-dock-w)` **预留出这块空间**。

于是主内容真的收窄（实测 `main.right === dock.left`，零重叠、无横向溢出），视觉与交互上就是第三栏，而组件状态一点不丢（实测停靠前后消息数不变、草稿原样）。栏宽走 CSS 变量的额外好处：**拖宽时可以逐帧直写 DOM**（面板自身 `width` + 变量同帧写），主内容与面板不会出现「栏动了内容没动」的撕裂，也不必让 React 每像素重渲染整个外壳。

#### z 层带怎么分

停靠面板固定 `z-30`。三条边界都有理由：

- 在 sidebar 的 `z-10` / rail 的 `z-20` **之上** —— 它是比侧栏更靠前的一栏；
- 在浮动卡带 `[40,49]`（`use-card-stack`）**之下** —— 浮动窗是自由窗，本来就该能盖过停靠栏。**副作用要接受**：一张浮动卡正好停在停靠栏左边缘时，会挡住那条拖宽手柄（自测时先踩到，一度以为拖宽失效）。这是层带划分的必然结果，不是 bug；
- 在 Radix 弹层 `z-50` **之下** —— 否则停靠栏里打开的下拉/菜单会被面板自己盖住（这是 `use-card-stack` 当初把整个卡片带压在 50 以下的同一条原因）。

#### 自测抓出的两个真 bug

**① 钳位算错了基准。** 上限写成 `window.innerWidth − MAIN_MIN_W(320)`，忘了左侧栏那 256px。拖到极限时主内容只剩 **49px**（实测），下限形同虚设。正解是按**主内容区**算可用宽：以 `SidebarInset` 的左边界为基准（它是流内的 `flex-1`，左边界只由侧栏宽决定、与停靠栏宽无关，所以拿它当基准是稳定的），`avail = documentElement.clientWidth − insetLeft`，上限 `avail − 320`；用 `clientWidth` 而非 `innerWidth`，顺手排掉滚动条那十几像素。修后实测拖到极限主内容剩正好 320、反向拖到极限栏宽正好 340。

**② 幻影空栏（带 `?run=` 深链刷新必现）。** 现象是外壳留出一条 420px 的空白栏、里面**没有卡**。根因是 `dockedCid` 与 `cards[]` 的记账脱钩：

- StrictMode 把 `DeepLink` 的 effect 双跑，同一 tick 里 `openRun(id)` 被调两次；
- 而 `cardsRef` 当时是**渲染期赋值**的镜像（`cardsRef.current = cards`），第二次调用时它还是旧值 → 误判「这条会话还没开」→ 另起一个 cid；
- 卡片本身被 `setCards` 里的 `cs.some(c => c.runId === id)` 去重挡住了、没有多开，**但 `dockedCid` 已经指向那个从未进入 `cards` 的 cid** → 谁都不是停靠卡，而占位变量照写。

修法两层：`cardsRef` 改成**同步**镜像（增删一律走 `setCardsSync`：先写 ref 再 `setState`，同一 tick 内的连续调用看到的是真值——顺带修掉这条早就存在、只是以前不显眼的重复开卡竞态）；再加一条不变量守卫 `dockActive = !isMobile && cards.some(c => c.cid === dockedCid)`——**必须真有这张卡才占位**，即便日后 cid 记账再出偏差，也不可能出现空栏。

**通用规则**：只要有「一个 id 指向列表里的某一项」这种派生状态，② 就是模板化的坑——**渲染期赋值的 ref 在同一 tick 的连续调用里是旧值**（StrictMode 双跑、批处理、事件里连点都会撞上），而 `setState(fn)` 的 updater 看到的是新值，两边用不同的真相来源就会脱钩。要么两者都走同步 ref，要么给派生状态加「指向的东西必须存在」的守卫。本例两条都做了。

#### 几个刻意的选择

- **不做动画**：停靠/取消停靠瞬时换栏。给外壳 `padding` 加过渡会让整块看板逐帧 reflow（看板是全站最重的视图），代价不值。真要做应该只给面板做 transform 滑入（不触发 reflow），留待后续。
- **关掉停靠栏里的会话 → 模式保留**（第三栏收起、变量归 0、主内容恢复满宽，但下次开会话仍进第三栏）。停靠是工作区偏好，不该被"关掉一条会话"这种动作重置。
- **停靠态严禁写浮动几何**（`saveGeom` 加 `!docked` 守卫），否则取消停靠弹回去时位置/尺寸被停靠那套值污染。实测取消停靠后精确回到 x960/y64/w460/h804。
- **移动端整段不生效**：<768px 没有第三栏的空间，聊天仍是既有的全屏页，停靠按钮不出现、变量恒 0（即便 localStorage 里 `on:true`）。

**一处诚实的软边界**：钳位在拖拽时与窗口 resize 时生效。若栏宽已到上限、此时再把侧栏从图标轨展开成全宽，主内容会短时窄于 320px 下限——没为侧栏开合单独接一路 re-clamp（那要跨 `SidebarProvider` 边界读状态，不值当）。

**验证**（Playwright 实测 4701 dev + 真实 run，1440×900）：状态不丢（11 条消息数不变、草稿原样，来回各验一次）；零重叠（`main.right === dock.left === 965`、横向溢出 0、`--ol-dock-w` 与 `padding-inline-end` 同为 460px）；模式生效（停靠着点另一个员工 → 新会话进栏、上一张回浮动几何且仍在 `cards`）；拖宽同帧同步 + 两端钳位；深链刷新直接停靠且无空栏；关掉停靠会话后变量归 0、再开又进栏；Radix 菜单 `elementFromPoint` 命中菜单（z50 > z30）；侧栏折叠后 `main.right === dock.left === 1005`；移动端 390px 无按钮、变量 0、卡片满宽。`oxlint` 无新增告警、`tsc -b` + `vite build` 通过。

### §3.98 第三栏「模式化换内容」翻案为「占住即钉住」：稳定的一栏不能被顺手一点冲掉（2026-08-24，老板改口径）

**起因**：§3.92 同轮拍板的口径②是「**停靠是一种模式**——第三栏开着时，点侧栏员工/看板卡片打开的会话直接进第三栏换内容，上一张自动弹回浮动窗」。用了两天老板改口：「打开第三栏布局之后再点击员工头像，应该把最新点击的聊天窗口用 **popup** 展示，第三栏聊天窗**保持稳定**。」口径①（同时只停靠一张）不变。

**为什么原口径站不住**：第三栏那张通常是**正在盯的主线**——要边翻看板边跟他对话，才有第三栏的必要。原口径下顺手点一下侧栏别的员工（很多时候只是想扫一眼他在干嘛），主线就被顶掉了。虽然上一张弹回浮动窗、状态一点没丢（§3.92 的「不换 portal 容器」保住了这点），但要重新找窗、重新摆位，**「稳定的一栏」名存实亡**。真实使用里「随手看两眼、看完就关」的频率远高于「换主线」，把高频动作绑到破坏性最大的效果上，方向错了。

**新规则**（`run-detail-provider.tsx`）：

- 落位只剩一条判据 `dockSlotFree()` = **停靠模式开着 且 没有任何一张真实存在的卡占着第三栏**。满足才自动落进第三栏，否则一律浮动 popup。于是「自动进栏」只剩两个时机：栏里那张被关掉之后、模式开着但一张卡都没有（如刷新后首开）。
- 已开着的卡再被点到：**在第三栏的原地不动**，浮动的抬到最前（§3.92 之前就定的「再次点员工 → 窗口置顶」保留）。
- **换第三栏内容只剩标题栏停靠开关一个显式入口**：把别的卡按进去，原来占着的那张让位弹回浮动。破坏性动作必须显式触发——这是本次翻案的落点。
- 实现上收口成 `addCard()`（新开）/ `focusCard()`（已开着的再被点到）两个入口，`openRun`/`newChat`/`newConsult`/深链四条路径全走它们，不再各自散着写 `if (dock.on) setDockedCid(...)`——散着写正是原口径能悄悄长在四个地方的原因。

**顺带修掉一个视觉互踩**：浮动带 `z≥40` 盖过停靠栏的 `z-30`（§3.92 的层带划分，本身没错），而新卡的出生位置一直按**整窗右缘**算 `innerWidth − 480 − offset*28`。两条一撞：停靠栏开着时新开的 popup 正好糊在第三栏上面，「第三栏稳定」就只剩**内容**没变、视觉上仍被压住——口径只落实了一半。改成出生位置按「窗口右缘 − `--ol-dock-w`」算：读的就是外壳用来预留空间的那个变量，保证「浮窗认为的右边界」与「主内容真实的右边界」是同一个数，不会各算各的；记忆几何（`ol-chat-card`）也做一次落地钳位。**只在出生时钳一次**——之后用户自己把窗拖到栏上面盖着是他的自由，不该被纠正。

**同步补的一处竞态防线**：`dockedCid` 也改成**同步镜像**（`setDockedCidSync`，增删先写 ref 再 `setState`）。新规则要在开窗那一刻读「栏空不空」，而渲染期赋值的镜像在同一 tick 内是旧值 → StrictMode 双跑或连开两张时会把「空着」误判成真，两张卡都去抢第三栏（后写的赢，前一张成没人认领的孤儿）。这与 §3.92 给 `cards[]` 加 `cardsRef` 同步镜像**是同一个坑的另一半**：那次修的是「列表」，这次是「指向列表某一项的 id」。§3.92 结尾那条通用规则（*渲染期赋值的 ref 在同一 tick 的连续调用里是旧值*）第二次生效——凡是要在事件回调里**读派生状态做分支**，就别用渲染期镜像。

**验证**（Playwright 实测 4700 真实数据）：栏空着点员工 → 落进第三栏（`--ol-dock-w:460px`、`border-s`、z30）；栏被占着连点两个员工 → 两张 popup（z49/48 层序正确，`right` 843/815 均 < 停靠栏左边界 876，**零重叠**）；再点已开着的 GG Bond → 抬到 z49、第三栏那张纹丝不动；显式点「停靠到右侧」→ 换栏成功、原来那张弹回浮动；关掉第三栏那张 → 变量归 0、模式保留，下次点员工又落进第三栏。`tsc -b` + `vite build` 通过、`oxlint` 无新增告警。

### §3.100 弹窗「点一下卡半拍」的两笔账 + 动作卡攒批在重写里整块丢了（2026-08-24，老板报「系统的弹窗都很卡顿」）

**一、弹窗卡顿：CPU 花在了「跟这张弹窗无关的地方」**

Playwright + CDP tracing 实测 4700 真实数据（1440×900、3739 节点、机器空闲时）：开一次 facet 覆盖弹窗 **86.9ms**（单个 JS 长任务 86.3ms + 全文档样式重算峰值 33.2ms），关一次 **162.4ms**（重算 82.3ms + JS 59.9ms）。把看板全折叠（节点 3739→1156）后开窗降到 47.8ms —— 说明成本**跟着页面规模走，而不是跟着弹窗内容走**（`facet 0/21` 的小弹窗与 `43/86` 的大弹窗开销一样）。拆出两笔账：

1. **弹窗的开关 state 住在看板组件里**（`KanbanView` 的 `cov`/`disp`）→ 开一次、关一次，各把整块看板重渲染一遍。而这块树很贵：一屏 **129 个 Radix DropdownMenu、192 个 Radix Tooltip、563 个 button**，`EntryRow` 还是普通函数组件（没 memo）、且收 5 个内联箭头回调（memo 加了也白加）。
2. **Radix modal 的副作用打在整篇文档上**：开窗时 `<body>` 被加 `pointer-events:none`（已抓到）+ 4 个顶层兄弟节点被加 `aria-hidden`。`pointer-events` 是**继承属性** → 3700+ 节点全篇样式失效重算，开一次关一次各来一遍。这解释了「**所有**弹窗都卡」而不只是 facet 那个：同一个设置弹窗，在轻量视图（1734 节点）21.3ms、在看板（3733 节点）32.6ms。

**落点**：① 弹窗 state 上提到外层 `KanbanView`，看板收成 `memo(KanbanBoard)`（props 恒空）、动作出口走**空依赖 useMemo 的 context**（引用永不变，所以消费它的行不会因开关弹窗而重渲染）；② `EntryRow` 上 memo + `toggleSel`/`manualPass` 走 `useCallback`；③ 192 个门禁点的 Radix Tooltip 换回**原生 `title`**（信息量一样，省掉 192 套 provider/context/id）；④ 行操作菜单**点开才挂 Radix**（99% 的行永远不会被点开，没必要把这套成本摊进每次渲染）。顺带把 `EmployeesProvider` / `FileViewerProvider` 的 context value 用 `useMemo` 包住 —— 原来每次渲染新建对象，轮询每跳（哪怕花名册一个字没变）都让全站消费者重渲染一遍，是同一类病。

**实测收益**（同一台机器、空闲时）：open 86.9 → **32.1ms**，close 的 JS 从 59.9 → **7.3ms**（关窗的 wall time 里剩下的主要是 `duration-100` 退场动画本身）；页面里 Radix tooltip 触发器 192 → **0**、常驻下拉 129 → **1**。

**一条被实测否掉的方案（别再捡回来）**：给看板卡片加 `contain: layout style paint`，想压住 body 属性变化的失效传播。注入实测 open#2 32.1 → 48.4ms、重算不降 —— **继承属性的失效走的是整棵样式树，containment 拦不住它**（style containment 只管 counter/quotes）。所以没加。剩下的 30~45ms 全文档重算是 Radix modal 的架构成本，真要拆只有两条路：`<Dialog modal={false}>` 自己接管点击外部/焦点陷阱（改焦点与滚动锁语义，要单独拍），或把看板列表虚拟化（减节点）。都没做。

**二、动作卡攒批：接口留着、没人接线，能力整块丢了**

老板报「一轮里有多个需要拍板的事项时，点一次就发一条」。查下来是**重写期的静默回归**：旧 UI（`app/public/app.js` 的 `cardBatch`）有完整攒批 —— 「本轮只剩一张待处理动作卡 → 点了立即回发；有兄弟卡或已暂存 → 进暂存区，凑齐点『发送 N 项』一次合并回发」；新 shadcn UI 的 `CardCtx` 里 `onStage` 类型**定义得一字不差、注释也在**，但 grep 全仓 **零个调用方传过它** → 每次点选都直接走 `onReply` 单发。类型系统对「可选 prop 从没被传过」是完全沉默的，这类回归只有靠端到端点一遍才会露出来。

**落点**（新增 `components/card-batch.tsx`）：攒批器做成**独立 React context**（`CardBatchProvider`，`key={runId}` 挂载 → 切会话自然清空），**不走 `CardCtx` 透传**——否则暂存态每变一次都要让 `Transcript` 那个装着几百条事件 + markdown 的 `useMemo` 整体失效重算。动作卡挂载时向它登记「我还等你处理」（`registerAction`，纯 ref 计数、不触发渲染），点选时问一句 `shouldBatch()` 决定暂存还是直发；规则**沿用旧 UI**（老板 2026-08-24 确认）。暂存态在卡上是琥珀「待发送」+「撤销」（区别于绿色「已处理」），攒批条给逐项撤销、整批总备注、`发送 N 项`；发送失败保留暂存供重试。

**三、顺着「意见 + 选择」发散查出的三个同类缺口**

- `approval` / `decision` / `toggle` / `defect` / `multiselect` **只有按钮、没有输入位** → 想说「批准，但注意 X」只能另发一条文字，意见和决策对不上号。补**卡片级「+ 补充意见」**（默认收成一行，填了之后任何一个选项的回复都带上它），攒批条再给一个**批次级总备注**（老板选的「两级都给」）。
- `gate` 卡（选项 + 自由输入并存）的**快捷选项会把已输入的文字和已贴的附件静默丢掉** —— 这是个真 bug，不是缺功能：用户先写意见再点快捷项，写的东西无声消失。改成快捷项一并带走文本 + 附件标记。
- **权限审批区**：多条挂起要逐条点（引擎侧一个 `reqId` 一次挂起、只能逐条 resolve，但点击可以只点一次 → 加「全部拒绝」/「全部允许…」，后者走二次确认，批量放行不该手滑）；更要命的是**拒绝理由从来没往引擎传** —— `POST /api/runs/:id/permission` 早就接 `message`（原样交给 SDK 当拒绝原因、员工看得到），前端只发了 `{reqId, behavior}`，于是员工被拒后不知道为什么、只能瞎猜重试。补上逐条可填的拒绝理由。

**验证**（Playwright 实测 4700 真实 run，回发请求全程 `route.abort()`，绝不真给员工发消息）：3 张未处理决策卡场景下连点两张 → **回发请求 0 次**、卡片转「待发送」、攒批条显示「已选 2 项」；逐项撤销 → 回到「已选 1 项」；「重选」→ 攒批条消失且 3 张卡全部恢复可点；卡片级意见框与批次总备注均可填。看板侧：facet 弹窗开关、行操作菜单（懒挂载后菜单项齐全）、头像派工弹窗、批量预检条均正常。`tsc -b` 通过、`oxlint` 无新增告警。

**两处诚实的边界**：① 「只剩一张卡 → 直接发」这条分支走的是原有 `onReply` 代码路径（未改），我在真实会话里没蹲到「窗口内正好只有一张未处理动作卡」的时机去点它验证，是**间接验证**——3 张卡场景若登记计数坏了就会退化成直发、而实测是 0 次请求，说明计数与判据在工作。② 卡片不做虚拟化，滚出视口的旧未处理卡仍在登记数里，因此「早前遗留一张未处理卡 + 现在新出一张」会判成攒批（与旧 UI 查整个滚动区里 live 卡的口径一致，不算新增偏差）。

### §3.99 facet 覆盖明细：明细搭轮询的车 + 开场动画期铺 744 个节点 + 平铺成墙（2026-08-24，老板报「facets 弹窗很卡顿 / 平铺太杂乱、空间利用率低」）

**与 §3.100 的关系**：同日、同一句抱怨的两笔不同的账，别混。§3.100 记的是**与弹窗内容无关**的成本（弹窗开关连累整块看板重渲染、Radix modal 给 `<body>` 加继承属性引发全文档样式重算）；本节记的是**这张弹窗自己那份内容成本**。§3.100 清完之后再实测「86 项那张」，仍有**单个 141ms 长任务 + 弹窗内 744 个 DOM 节点**，且这坨渲染正好落在 Dialog 的 zoom/fade 开场动画上——动画掉帧，肉眼就是"卡一下"。两笔都清掉才不卡。

#### 一、明细本不该搭轮询的车

`coverage.rows`（逐条 facet + criterion 原文）一直随 `/api/tasks` 全量下发，**每 15s 一轮**。实测：222KB 的载荷里它占 **53%**（摘掉后 105KB）。而全站只有「facet 覆盖明细」这一个弹窗读它——看板的健康条、条目行的覆盖小条用的都是 `summary` 与 `reqRollup`（§3.68 那套显示层派生），一条 row 都不碰。**为一个偶尔打开的弹窗，给每 15s 一轮的轮询扛半个载荷**，是典型的「聚合接口顺手全给」惯性。

改法与一处刻意的不彻底：

- `/api/tasks?slim=1` 摘掉 rows（新 UI 三处调用点全切：看板、员工详情、聊天窗档案选择器）；新增 `GET /api/coverage?file=…` 只给**一份**档案的明细，开窗才拉（86 行那张 54KB，只在真打开时付）。
- **默认不带 `slim` 仍返回全量**（老板拍的）。旧 UI(`app/public/app.js`) 是在卡片渲染期就地用 `cov.rows` 拼 facet 抽屉的，口径一动就崩；新老共存期用一个查询参数分流，比"两边一起改一起回归"便宜得多。代价是引擎里多一条 if——认。
- 越权守卫：`/api/coverage` 先过 `resolveRepoFile`（既有的双根 + 越权跳过），**再**要求解析结果落在 `TASKS_DIR` 内。实测 `../../CLAUDE.md`、非 tasks 目录的文件、不存在的档案、空参数一律 404。

#### 二、开场动画期间不铺内容

Dialog 的进场是 `duration-100` 的 zoom+fade。旧版一开窗就同步铺「全部 REQ × 全部 facet」（每条还带 2~5 个 Badge 组件），于是 141ms 的 JS 长任务与动画抢同一批帧。改成两条：**动画跑完（留 140ms 余量）+ 数据到齐才铺**，其间是骨架屏；**一次只铺选中 REQ 那十几行**。开窗实测从「141ms 长任务」变成**一个长任务都没有**，弹窗内 DOM 节点 **744 → 218**。

> 顺带一提：骨架屏与内容区高度写成同一个 `h-[62svh]`，铺上内容时弹窗不跳高——否则"先出壳后填内容"会换来一次视觉抖动，等于用一个毛病换另一个。

#### 三、版式：平铺的墙 → REQ 目录 + 明细表

老板同轮的第二个诉求是「平铺太杂乱、空间利用率低」。选了**左右分栏**（同轮给了三个候选：左右分栏 / 单栏折叠 / 缺口优先）：左侧 REQ 目录（编号 + 条数 + 覆盖构成小条，配色沿用看板健康条的 SEG），右侧一行一条（`✓ F13 P1 auto 判据…`，超长省略号、点行展开全文）。三条附带口径：

- **顶部状态徽标兼作筛选器**（点「未覆盖 3」只看没过的，再点取消）。打开这个弹窗十有八九是来找缺口的，把汇总数字直接做成入口，比再加一排筛选控件省地方。
- **从版本级 facet 条点进来，默认落在第一个有缺口的 REQ**——默认「全部」就等于又把那面 86 项的墙糊回来了。「全部」永远是目录第一项，一点就回得去；从条目点进来仍直接定位那条 REQ（`highlightReq` 优先）。
- 选中某个 REQ 时行内把 `REQ-0212-` 前缀省掉只留 `F13`，省出来的宽度给判据。`level`/`kind` 从 Badge 组件降级成两个定宽的 muted 文本——一行里挂三个 Badge 组件，视觉噪声和渲染预算都不划算。

#### 四、自测抓出来的真 bug：grid item 的自动最小尺寸是 max-content

现象：判据文字**齐着弹窗右边"切断"，没有省略号**。第一反应是 `truncate` 没生效，实测却是 `text-overflow:ellipsis / white-space:nowrap` 都在——**省略号被顶到屏幕外去了**：右栏那 80 多行 nowrap 判据把两栏所在的 flex 行**顶到 3727px 宽**（弹窗只有 895px），多出来的部分被弹窗的 `overflow-hidden` 裁掉。

根因是 `DialogContent` 是 **grid** 容器，而 **grid item 的自动最小尺寸是 `max-content`**——不给 `min-w-0`，这一格就按最长那行的宽度撑开，`flex-1 + min-w-0` 在里层做得再对也没用（里层缩不缩，取决于外层这一格有多宽）。这与 §3.88「grid `auto` 轨道被代码块顶宽、容器 `min-w-0` 管不了轨道」**是同一族的第二例**：`min-w-0` 必须打在**真正决定宽度的那一层**上，打在里层等于没打。修后实测判据右边界 1097 < 弹窗右边界 1124、`scrollWidth > clientWidth`（省略号真生效）、文档无横向溢出。

#### 五、一处过渡期兜底

前端产物由 `pnpm build:watch` **自动**滚动到 `web/dist`，引擎重启却是**手动**的（重启会打断在跑的员工）。这中间必然有一段「UI 已经新、引擎还旧」的窗口，此时 `/api/coverage` 是 404。所以弹窗捕获失败后**退回老路**：拉一次全量 `/api/tasks` 自己挑这份档案的 rows。慢，但不开天窗。这不是临时补丁——只要"产物自动、引擎手动"这个不对称还在，新端点就都该配一条回退路径。

**验证**（Playwright 实测 4700 真实数据；**新端点在隔离测试引擎上验**：4899 + 独立 `OFFICE_LAB_RUNS_DIR` + `AUTOCHAIN=0` + `PATROL=0`，无凭证故企微 sidecar 与飞书对账都不会起，生产引擎与在跑的员工全程未动，验完即停）：开窗 **0 个长任务**（原 141ms）、**DOM 744 → 218**、默认落点 17 行而非 86；「全部」→ 86 行；「人验 20」→ 20 行且状态齐一，取消 → 回 86；点行展开 33→45px、再点收起 33px；`slim` 与全量的 `summary`+`reqRollup` **逐字节一致**、`/api/coverage` 的 rows 与全量里那份**逐字节一致**（口径零漂移）；404 守卫四例；引擎侧 `node --check` 通过，前端 `tsc -b` + `vite build` 通过、`oxlint` 无新增告警。

**落地待办**：两个新端点要**引擎重启**才生效；重启前走上面的兜底路径，功能不缺、只是省不到那 53% 载荷。

### §3.110 开聊天窗停在半中间：程序贴底自己把「跟随态」打掉了（2026-09-01，老板反馈「点击员工打开聊天窗口后应该自动滚动消息列表到最底下」）

聊天窗（`web/src/components/run-detail.tsx`）本来就有跟随贴底：`stick` 这个 ref 记「用户是不是还在底部」，`events` 一变就对底部哨兵 `scrollIntoView`。代码在，行为不在——开窗十次有七八次落在半中间，而且此后**新消息也不再跟随**（这是比"开窗没落底"更重要的那个症状，它把根因指出来了）。

#### 根因一：`scroll` 事件是异步派发的，贴底那一跳的事件跑到 `onScroll` 时，度量已经过期

原判据是「量到没贴底 → `stick.current = false`」，且这个状态是**一次性**的（没人再把它打回 true，只有用户点「回到最新」才恢复）。而历史回放是逐条 SSE 消息到达 → 每条一次渲染 → 每次贴底一跳；贴底触发的 `scroll` 事件排进队列，等它真正执行时，下一条消息或刚解码完的图片已经把 `scrollHeight` 撑高了几百像素，于是这次度量的结论是「没贴底」。**跟随态就此永久熄灭**，剩下的消息全部落在视口下方。

对策不是加防抖或放宽阈值（阈值放到多大都会被一张截图撑穿），而是**让程序滚动可被辨认**：`pinNow()` 写完 `scrollTop` 后立刻记下浏览器钳完的真实值，`onScroll` 见到「量到没贴底、但 `scrollTop` 恰好还等于我们写进去的那个值」就认领为自己那一跳、直接 return，不动 `stick`。用户用滚轮/触摸上翻必然改变 `scrollTop`，判定照旧生效——「用户上翻后不许被拽回底部」这条不能为了修贴底而牺牲，它是同一个函数里的对立约束。

> 通用口径：**自动滚动与「用户是否上翻」的判定共用一个 scroll 事件流时，必须能区分事件的来源。**只靠"位置像不像底部"是不够的——异步派发 + 内容异步撑高，位置这个信号本身就是过期的。

#### 根因二：只在「事件到达」这一个时机贴底，赶不上异步撑高

markdown、动作卡、图片都是渲染之后才把高度撑起来的，最后一条消息到达时贴的那一次必然偏早。旧 UI 早就踩过并解决了（`app/public/app.js` 的 `scrollChatToBottom`：本帧 + 下一帧 + 120ms 三连补贴，外加给未加载完的 `img` 挂 `onload`），**新 UI 重写时没把这份经验带过来**——又一次「同一个坑在两套 UI 上各踩一遍」。

新 UI 这次做了一处改进：图片不再逐个挂 `onload`（开窗那一刻挂只覆盖当时已存在的 `img`，后到消息里的图片漏网），改为在滚动容器上**捕获阶段**监听 `load`（`load` 不冒泡，捕获阶段才收得到），任何图片任何时候加载完，只要还在跟随态就再贴一次。

#### 顺带修掉的残留：切会话继承上一条的 `stick=false`

同一张卡从会话列表切到另一条会话时，`stick` 是 ref、不随 `runId` 重置——上一条被翻上去留下的 `false` 会让新会话直接停在顶部。现在 `runId` 变化即无条件重置为跟随态并贴底：**开窗/切会话是「用户表达了要看最新」的动作，不该继承上一条会话的浏览位置。**

#### 一处实现选择：`el.scrollTop = el.scrollHeight` 而不是哨兵 `scrollIntoView`

`scrollIntoView` 依赖哨兵元素已完成布局，且会**连带滚动所有可滚动祖先**（第三栏停靠态下聊天窗多一层滚动祖先，见 §3.92 / §3.98）。直接写 `scrollTop` 只动这一个容器，也顺便给了根因一需要的那个"我写进去的值"。

**验证**（Playwright 实测 4700 真实数据，三条真实会话）：菲菲 / 迷糊老师 / GG Bond 开窗即 `scrollHeight - scrollTop - clientHeight == 0`，最长那条 `scrollHeight` 4644px、含 9 张图；手动置 `scrollTop=400` 后「回到最新」浮钮出现、且不被拽回底部。`tsc -b` + `pnpm build` 通过。纯前端，无需重启引擎。

### §3.112 带卡片的员工消息正文没气泡：分叉分错了粒度——「这条消息有卡吗」不该决定「正文长什么样」（2026-09-02，老板看截图问「怎么有的员工消息没有气泡」）

老板发来一张 `20260902021351-ee2132`（GG Bond）的聊天截图：同一屏里，自己发的话有紫气泡、GG Bond 前几条也有灰气泡，但那条答「筛选栏改造」的长回复**整段裸在画布上**——没有气泡、没有底色、也没有复制按钮。

#### 复现规律：不是偶发，条件是「这条消息里带了 olcard 卡片」

对着 run 档把那条消息（第 1586 条）按卡片协议切一遍，正好三段：

```
md   136 字   「这两点戳中了要害——现在的筛选栏是给「合并看板」设计的…」
card 390 字   type=table（截图里那张「明细」表）
md   678 字   「**任务 2（筛选项 + 联动机制）我的方案：**…」
```

屏幕上就是「裸文字 / 卡 / 裸文字」，与切段结果一一对上。

#### 根因：分叉发生在「整条消息」这个粒度上，而气泡是「段」的属性

```tsx
{hasCard(text) ? (
  <OLContent text={text} ctx={ctx} />   // ← 整条交给卡片渲染器
) : (
  <Bubble role="assistant" copyText={text}>…</Bubble>
)}
```

`OLContent` 逐段渲染是对的，但它对 md 段是**直接 `<Markdown>`**、没有任何外壳。于是「有卡」这个属性从一段传染到了整条：纯文字消息有气泡、带卡消息没气泡，同一个员工在一屏里两副长相。

**这不是新设计，是 React 版迁移时丢掉的行为。** 旧静态 UI 的 `renderEmpText`（`app/public/app.js`）本来就是按段分派的：

```js
for (const seg of OLCards.parse(body)) {
  if (seg.kind === 'card') cardRow(seg.data, ts)                              // 卡裸放
  else if (seg.text.trim()) msgRow('emp', `<div class="md-mini">…</div>`)     // 正文进 .bubble emp
}
```

而且 React 版的**用户侧也是这个口径**（`splitUserMessage` 把聊天记录卡提到气泡外、`body` 仍进气泡，见 §3.9x 那轮「画框套画框」的取舍）——只有员工侧漏了。所以这次不是要定新规矩，是把两套 UI + 两侧消息里唯一那个例外补回去。

#### 对策：把「md 段的外壳」变成 OLContent 的参数，而不是它的硬编码

`OLContent` 新增可选 `wrapMd(mdText)` 渲染参数（不传＝裸 markdown，卡片演示页那类调用方行为不变），transcript 传员工气泡进去。**刻意不把 `Bubble` 直接 import 进 `olcard.tsx`**：气泡属于 transcript 的消息布局语义，反向依赖会和 transcript → olcard 撞成循环。也刻意**没顺手让卡片也套气泡**——卡片自带 `Shell` 的圆角边框，套上就是双层框，这正是当初把卡提到气泡外的原因。

复制按钮随气泡一起回来了，**每个正文段各一个、复制该段的 markdown 原文**（与旧 UI 逐 `msgRow` 挂 `COPY_BTN` 同口径；见 §3.10x 复制动作那轮定的「复制源取原文、不读 DOM innerText」）。

> 通用口径：**混排渲染器里，「容器级的分叉」和「段级的样式」是两件事。**只要在容器层写下 `hasX(whole) ? A : B`，X 就会从一段传染到整条——正确的形状是「逐段分派 + 把段的外壳交给调用方」。旧 UI 早就是这个形状，重写时只保留了「逐段」、丢了「外壳」。

**验证**（Playwright 实测 4700 真实数据）：拿 `20260728093243-4b5c7f`（md → decision 卡 → md 三段的真实消息）在跑着的实例上查 DOM，三个子项判定为 `md-in-bubble`（有 `[data-slot=bubble-content]` + 复制按钮）/ `card`（`bg-card` 外壳、无气泡）/ `md-in-bubble`，截图确认卡片仍是单层框、正文两段都在气泡里。`tsc -b` exit 0、`vite build` 通过。纯前端，无需重启引擎。

### §3.116 员工越守规矩解释机制，汇报越容易被绞碎：围栏正则不认行首，正文里白话提一句 ```olcard 就开栏（2026-09-07，老板截图「卡片的展示会截断一条信息的气泡连贯性」）

老板发来一张波比聊天窗的截图（run `20260907053624-d858bf`，v5.22 发测汇报），说卡片把一条消息的气泡连贯性截断了。屏幕上确实很怪：一个**带内部滚动条**的框里装着一段汇报正文，下面一个框里躺着**一坨裸的 JSON**（`olcard { "type": "table", …}`，换行被折叠成流式段落），再往下 `**③ 发测 MR（真实链接）**` 连星号一起显示成了字面量，而再下面那张链接卡**却渲染得好好的**。

**看着像样式问题，其实是解析器把一条消息切碎了。**

#### 根因：`FENCE` 不认行首，于是「谈论围栏」和「使用围栏」没法区分

```js
const FENCE = /```olcard[^\n]*\n([\s\S]*?)```/g      // 旧
```

这条消息的正文里，波比自己解释了一句（上一轮他误把卡片当工具调用，这轮特意说明）：

> 之前的卡片被误当工具调用了——卡片是正文里的 \`\`\`olcard 围栏，不是工具。

正则从这句话**行内**那个 \`\`\`olcard 就开栏（`[^\n]*` 吃掉「围栏，不是工具。…」剩下的半句），`\n` 之后 `[\s\S]*?` 懒惰地找收栏，找到的第一个 \`\`\` 是**下一张真卡的开栏**。切出来的段于是全错位一格：

| 段 | 旧正则切出来的东西 | 屏幕上的样子 |
|---|---|---|
| card | 整段 ①② 正文（`---` / `## 波比发测汇报` / 「① 做了什么」…） | JSON 解析失败 → `__error__` 卡，`__raw` 摊在 `<pre>` 里 → **那个带滚动条的框** |
| md | 真表格卡的 JSON（少了开头三个反引号，多一个落单的收栏 \`\`\`） | 当 markdown 渲染 → 换行被 HTML 折叠成**一坨流式 JSON**；落单的 \`\`\` 又开了个代码块，把后面「③ 发测 MR」关进去 → **星号成了字面量** |
| card | 链接卡 | 正常（`lastIndex` 恰好又对上了） |

**最刺人的一点是它的选择性**：谁在汇报里认真解释「卡片是 \`\`\`olcard 围栏」，谁的汇报就被自己的渲染器绞碎——员工越守规矩、越讲清机制，越容易触发。而这条消息里同时还有三张写法完全合规的卡，其中两张照样渲染，故障看起来像"偶发的样式问题"，不像解析事故。

#### 对策：围栏必须独占一行（开栏与收栏都要），未闭合的收到文末

```js
// 新（web/src/lib/olcards.ts 与 app/public/cards.js 同一份口径）
const FENCE = /^[ \t]{0,3}```[ \t]*olcard[^\n]*\n([\s\S]*?)(?:^[ \t]{0,3}```[ \t]*$|$(?![\s\S]))/gm
```

- **行首锚定（`m` 标志 + 行首最多 3 空格缩进）**＝直接采用 CommonMark 对围栏代码块的定义。行内提到 \`\`\`olcard 是**谈论**，独占一行才是**使用**——这个区分本来就该由「行首」来做，我们此前只是漏了。
- **收栏也锚行首**：否则卡片 JSON 字符串里出现 \`\`\`（比如 `code` 卡教人怎么写围栏）会提前收栏，是同一个 bug 的镜像。
- **末尾未闭合仍收到文末**（`$(?![\s\S])`）：员工漏打收栏时，宁可渲染成一张卡，也别把 JSON 泼在会话里。同样是 CommonMark 的行为。
- 一处**引擎侧**同源缺口一并修：`server.js` 的 `extractImprovementItems`（从会议收尾发言里抽改进项卡）用的是同一条不认行首的正则，主持人在总结里提一句围栏就会抽出整段正文当 JSON。

> 通用口径：**「谈论一种标记」和「使用这种标记」必须在词法层就可区分**，别指望内容里不会提到自己的协议——AI 员工的工作恰恰包含解释协议。判据要用结构（行首、独占一行、缩进），不能只用关键字匹配。

#### 顺手把「一条消息读成一条消息」补上（老板拍板：归组连贯）

解析修好后，这条消息恢复成 `md → 表格卡 → md → 链接卡 → md → 清单卡 → md` 七段，但仍是「窄气泡（80% 宽、w-fit）/ 宽卡（100%）/ 窄气泡」参差排列，段间 8px——看着还是三四条独立消息。老板在三个方案（归组连贯 / 只修解析 / 卡片铺进气泡）里选了**归组连贯**：

- 同一条消息内**正文段与卡片左右同宽**、段间距收到 **2px**、**相邻圆角削平**（首段圆上角、末段圆下角、中间全平）、**整条只留一个复制按钮**（复制整条原文、含围栏——那才是员工真发出来的这条消息）。
- **卡片仍然不套气泡**：§3.112 定的「画框套画框」口径不变，这次只把边界连起来，不加第二层框。
- 实现上刻意没做 prop 钻透：`OLContent` 收一个 `joined`，圆角类名走一个**只装 className 的 `ShellCorner` context** 下发给 `Shell`（`Shell` 深埋在 `OLCard` 十几个 type 分支下面，钻 prop 要改每个分支）。另外靠的是 Tailwind 的规则顺序——`rounded-t/b-*` 排在 `rounded-*` 之后，所以 `'rounded-xl rounded-t-none'` 就是"上平下圆"，不必自己算四角。

#### 验证

- **回归测试** `app/test/olcard-fence.test.js`：把**两份前端源码里的 `FENCE` 字面量抠出来**直接跑（不 import 解析器——`cards.js` 是浏览器 IIFE、`olcards.ts` 是 TS）。既验行为（行内提及不开栏 / 单卡多卡 / ≤3 空格缩进 / 漏收栏收到文末 / JSON 里含 \`\`\` 不提前收栏），也钉住「两份有意重复的实现别各自漂移」（`source` + `flags` 必须逐字相等）。12 例 + 1 例一致性全绿。
- **Playwright 实测跑着的 4700 实例 + 真实数据**（就那条出事的消息）：7 段顺序 `md / table / md / link / md / checklist / md`，零 `__error__`、零裸 JSON 泄漏；7 段宽度与左边界全等（374px @ left 849），`row-gap: 2px`，圆角 `14/14/0/0 → 0/0/0/0 … → 0/0/14/14`，复制按钮 1 个。
- `tsc -b` exit 0、`vite build` 通过；`node --check` 两份 js 0 error。纯前端刷页面即生效，引擎那处随下次重启生效。
- **未做**：旧 UI `app/public` 只修解析，归组连贯没回港（那是另一套行布局 CSS，新 UI 才是在用的那套）。

### §3.121 移动端不是「窄一点的桌面」：四类结构性缺陷让手机/悬浮窗上的工作台只能看不能用（2026-09-08，老板：「优化一下移动端 ui/ux 的样式，现在移动端样式适配很糟糕，还有聊天窗口的也很糟糕」）

**现场**（老板截图是 440px 的托盘悬浮窗，与手机同属移动态——`use-mobile` 判「窄屏 或 粗指针 或 移动 UA」，440 < 768 直接进移动分支，所以**悬浮窗的排版就是手机的排版**，这条口径以前没人写下来）：

- 任务档案标题被截成「大货备货节点时…」「简易…」——徽标 + 4 个头像 + 档案键跟标题挤同一行；
- **聊天窗的发送键被裁掉半个**（实测组合器工具行 `scrollWidth 374 > clientWidth 364`）；
- 「会话」页整行内容跑到视口外，条数/时间与折叠箭头全部看不见；
- facet 覆盖抽屉里 256px 的 REQ 目录横着摆，判据正文只剩 100 多像素；
- 条目的「当前阶段/来源/进入日期」在触屏上**完全拿不到**（只有 hover 卡这一个出口）。

**四类根因（没有一条是「边距再调小点」能解决的）**

1. **`min-width:auto` 三连**——flex/grid 项的自动最小尺寸是内容宽，**外层不给 `min-w-0`，内层写多少个 `truncate` 都没用**。同一个 CSS 机制在这里以三种症状出现：`AccordionTrigger` 缺 min-w-0 → 会话行顶穿视口；`CardHeader` 是 **grid** → 员工/运行观测卡里「最近：…」那行的 truncate 从来没生效过（桌面宽屏看不出，窄屏才现形）；`Button` 基类自带 `shrink-0` → 任务档案选择器（十几个字的档案名）撑起整行、把最右的发送键挤出去。判据：**凡是「里面写了 truncate 却没生效」，先查外层能不能收缩**（与 §3.72「宽度随内容长」同族）。
2. **hover-only 的信息在触屏上等于不存在**。条目名的 HoverCard 是登记表字段在看板上的唯一出口，手机上永远打不开。对策不是把它改成点按（桌面还要 hover 那条快路），而是**给窄屏另开一条底部 Sheet**：完整需求名 + 登记表三字段 + 行操作的大按钮版（`facet 明细 / 打开档案 / 派工 / 人工通过`）。桌面点名字同样能开，两条路并存不冲突。
3. **断点是两套**。JS 侧（悬浮键、全屏聊天页、禁用停靠）用 `MOBILE_BREAKPOINT=768`，排版却用 Tailwind 默认的 `sm=640` → **640~767 的机型拿到「移动外壳 + 桌面排版」的杂交态**（有悬浮键和全屏聊天，条目行却还按单行挤）。这次把改动到的结构切换统一压到 `md(768)`，并在 `index.css` 的媒体查询上写明「与 use-mobile 同一个数」的同源约束。
4. **28px 是鼠标的尺寸**。行操作 `⋯`、聊天顶栏四颗键、卡内发送键都是 28px，权限审批的「允许/拒绝」用 `size=sm` 只有 **24px**——而它是「卡住整条会话、必须现在拍」的键。窄屏统一抬到 36~40px、桌面维持紧凑，写法一律成对（`size-9 md:size-7`），不牺牲桌面密度。

**取舍**

- 档案头改**折行**（标题 `basis-full`，徽标/头像/档案键落第二行）而不是「窄屏藏掉徽标和头像」：那两样正是「这版归谁、卡在哪」的一眼信息，藏掉等于逼人点进去看。也刻意没做「两份 DOM 各显一套」——那会让每张卡多渲染 4 个头像，看板本来就是几百个节点的性能敏感区。
- 批量操作条不再是「`w-fit` 居中胶囊」：三个按钮 + 一句话在 390px 必然溢出，而**状态条溢出的代价是「取消」跑到视口外、用户被卡住**。改贴边两行（第一行「已选 N 条 + 取消」、第二行两个动作各占一半），中间插一个 `basis-full` 的空 span **强制断行**——不加它，「预检通过」会挤进第一行的余量里，两个动作一上一下参差。
- 覆盖抽屉窄屏改**上下分栏**（REQ 目录压成限高 8rem 的可滚区）而不是横滑标签条：目录是「多选一」的导航，限高可滚最省地方，判据正文拿满宽；同时 `kind` 列在窄屏让位——要读的是判据原文。
- 会话 ID 那行、侧栏「折叠成图标轨」键在窄屏**直接不给**：前者是 20 位随机串纯占位（复制入口折进「更多操作」），后者在抽屉形态下点了只是关掉抽屉，**是一颗「看着像功能、其实只是关闭」的假键**。
- 文档预览/覆盖抽屉在窄屏放到近满屏（`w-[calc(100%-1rem)]` + `92svh`）：文档是拿来读的，留一圈 2rem 边距等于把本就窄的正文再切一刀。

**验证**：Playwright 真跑 390 / 440 / 1440 三档 + 线上真实数据。关键量化——组合器工具行 `scrollWidth == clientWidth == 368`（发送键完整可见）、文档 `scrollWidth == clientWidth == 390`（全站零横向溢出）、抽屉导航行实测 44px、员工卡内层 0 处溢出、控制台 0 error/0 warning；桌面 1440 截图逐屏对照看板与聊天窗**无回归**。

**未做**：`olcard` 那 26 种卡片没逐个走窄屏（表格卡/时间线卡仍靠横滑）；旧 UI `app/public` 一律不动（在用的是 `web/`）；软键盘弹起的实机行为只能靠 `useVisualViewport` 既有机制，桌面浏览器测不到。

| 覆盖条 | 44×5 | 56×6 | 44×5（md 起 56×6） |
| 空优先级格 | `.entry-pri.none { display: none }` | 恒占 28px | 窄屏不渲染 |
| 「球在谁手里」列 | **有**（头像+名字 / 待老板 / 已终结） | **整列丢了** | 补回（`entryBall`） |

**一行 67 → 57px，三处来源**：

1. **一处隐形的 5px**：第二行那个 div 没写 `text-*`/`leading-*`，于是继承 `body` 的 16px/24px —— 里面 20px 高的状态签被一个 24px 的行盒撑成 25px。**每一行白吃 5px**，166 行就是 830px。判据：**放小字号元素的容器自己也要降字号/降行高**，否则行盒按继承来的大字号算。
2. **幽灵左槽**：勾选框占位每行留 22px，而**整份档案里一条可勾选的都没有**（只有「待预检/待复验」能勾）。改成「这份档案有可勾的才留位」——有则留，保住同卡内左边界对齐；没有则连位都不留。
3. **空格子不留位**（沿用旧 UI 的 `.entry-pri.none`）：没有优先级、没有终结态时窄屏整格不渲染。桌面要留位保跨行列对齐，窄屏没有列可对齐，留着就只是空地。

**「布局空泛」不是间距问题，是那一行没东西可放**。第二行只有三样，`⋯` 又用 `ms-auto` 顶到最右，中间必然空。两处对策：

- **`⋯` 在窄屏绝对定位到第一行右端**（行容器 `relative`，`absolute end-1 top-1`；md 起回常规流当最后一列）。它是「这条的操作」，贴在标题行末尾比吊在状态簇后面更合直觉，也不再需要用空白把它推到右边。
- **把旧 UI 有、新 UI 丢掉的「球在谁手里」补回来**（`lib/status.ts` 的 `ENTRY_NEXT` / `entryBall()`，键集原样搬自 `app/public/app.js` 的 `ENTRY_STATUS.next`，与 `server.js ENTRY_STATUS_ENUM`、`文档格式规范.md` 三处同源）：终结→「已终结」、待人工/预检/复验/跳过/隔离→「待老板」、其余→下一棒员工（头像+名字）。**空地不是靠加间距去填，是靠把该显示的信息补回来**——「这条现在卡在谁手里」正是看板上最该一眼看到、而此前只能逐条点开档案才知道的东西。顺带桌面也补上了这一列（原来那格只在终结时才有字，其余时候是空的）。

**验证**：`vw=426` 实测行高 `67 → 57`（line1 20 + gap 4 + line2 20 + 内边距 12 + 发丝线 1），一屏从 2 张卡多一点变成 3 张卡多一点；桌面 1440 逐屏对照，行高/列对齐/hover 卡与改动前一致。

### §3.125 档案是「给引擎记账」的，不是「给人做决定」的：137KB 里人要看的占 3.6%，而晨检单当天报的 12 条里 9 条不是这个版本的（2026-09-09，老板：「任务档案查看观感很差，晨检验收这个交互很奇怪：1 内容并不准确，2 内容也是抽象用语，不适合人类阅读」）

三条投诉，逐个取证，全部成立——而且**它们是同一个病的三种症状**。

**① 不准确。** 当天 v0.1.0 的晨检单报「待你拍板 **12** 条」：其中 **9 条是示例项目 v5.x 的需求储备**（REQ-0304/0219/0225/0319/0322/0295/0266/0242/0323），**命中率 3/12**；而档案里当天真正等他拍的 **15 条**（菲菲重新梳理后立的 A–M + GG Bond 路由的 2 项）**一条都没报**。两个根因：

- `version-report.js` 的 `summary/stuck/decision` 三处直接拿**全局 park 台账**。讽刺的是 `deriveVersionItems` 早就按 REQ 做过 join（只认本版条目）——**一个模块里，同一件事有一处做对了、三处各自绕过去**。这类「主路径做对了、旁路各写一遍」的漏，本页记过不止一次。
- 这张单子**从来没读过任务档案的「待确认事项」**，只读 park 台账。而 README 的设计原则第一条就是「任务档案是唯一状态源」——**违反它的正是引擎自己出的那份单子**。

**② 抽象用语。** 给老板看的表里印着 `REQ-0341-F29(HUMAN_INHERENT)` ×8 堆一格、`forbidden_action`/`fake_green`/`over_budget` 三个英文 key、`引擎派生状态：in_qa`，拟定口径里甚至出现 `草稿表 sampling_tech_sheet_doc 有行且工艺指示内容非空即算已制单`——**表名进了给老板看的单子**。

这里的判断不是"翻译成中文就好了"，而是：**这些词是引擎的内部状态，它们出现在人的界面上是泄漏，不是信息。** 人不需要学一遍词汇表——词汇表的作用已经在门禁里兑现过了（gate 据它放行/拦下）；到人这一层要回答的是另一个问题：

| | |
|---|---|
| ❌ 「这条 facet 是 HUMAN_INHERENT」 | 状态。人得自己翻译成行动 |
| ✅ 「这条机器测不了，要你亲眼看：**备货单列表出现「首单/返单」列**」 | 行动。人照着做就行 |

所以 `humanize.js` 的每个翻译产出三段：**一句人话 · 你要做什么 · 谁来做**。关键在第二段——`HUMAN_INHERENT` 能告诉人"要人看"，但**看什么**只能从 facet 的判据原文来，所以翻译函数必须吃 `criterion`。这也是为什么它不能是一张简单的字典。

**③ 观感差。** 实测档案 **137,139 字节**：

| 段 | 字节 | 占比 |
|---|---|---|
| 时间线（99 条，平均 **783 字/条**） | 77,568 | **56.6%** |
| 覆盖矩阵（106 行机器账） | 41,525 | **30.3%** |
| 目标+背景+登记表+流程状态+待确认 ← **人真正要看的** | 5,001 | **3.6%** |

**86.9% 是机器台账与 agent 叙述**，而查看器是 `<Markdown>` 一坨平铺——要滚过 77KB 才能找到"今天等我拍什么"。

**三条症状的同一个根：档案是「给引擎和 agent 记账」长出来的，从来没为「人要做决定」设计过。** 台账、术语、park 台账都是引擎自己用得顺手的形态，人只是被迫读它。

---

**对策的核心判断：人打开档案只有四个时刻，每个时刻问的是完全不同的问题。**

| 什么时候打开 | 真正在问 | 给他什么 |
|---|---|---|
| **早上第一眼**（最高频） | 昨晚发生了什么？现在卡在谁手上？ | **只给 delta**——自上次看之后变了什么。12 条上限，超了如实报截断 |
| **要拍板时** | 这问题是什么、选哪个、**不拍会怎样** | 问题 + 拟定 + **不拍的代价**（必填，缺了亮红） |
| **要验收时** | 哪些真做完了、哪些是自称做完的 | 按「谁来做」分组：要你亲眼看 / 只读了代码 / 没测，同类只解释一遍风险 |
| **回头复盘时** | 这版为什么拖这么久、返工在哪一步 | 时间线压成**里程碑**（拍板/返工/交付/过检），普通进展不进 |

四条设计判断，每条都有它想避免的具体失败：

① **首屏只放「等你的三件事」，任务目标/背景折叠。** 那两段第一天看过一次，之后再也不需要——而它们现在占着首屏。

② **「不拍的代价」必填，引擎校空。** 这是本轮最重要的一条。`拟定口径：选填、可就地改` 这种条目，人**看不出它重不重要**，只能逐条追问"这条不拍会怎样"——那就等于没交付。**人做决定靠的是后果，不是选项。** 实况：那份档案 15 条待拍**一条代价都没写**。

③ **拍板按钮派工菲菲，引擎不直接改档案。** 「要点」页的按钮是「按拟定的来 → 派菲菲落实」，不是「引擎替你把状态改成已定」。因为拍板结论要回写长表格 + 同步受影响的 facet/功能树 + 记时间线——那是 owner 的活，引擎手改长表格锚点易失配、并发会互相覆盖（§3.3 事故）。**老板只做决定，回写永远由 owner 做**，这也和 office-lab 既有分工一致。

④ **解析全在引擎侧，前端只摆。** 档案解析器（登记表/覆盖矩阵/待确认/facet 全集/三道需求闸）都在引擎里；前端再实现一套 TS 版必然漂移——**同一份档案会有两个答案**，这在本仓是反复出现的病（`ENTRY_STATUS` 三处同步、`文档格式规范.md` §3.4 的列契约都是这笔老债）。

### §3.126 「阅读器不够美观」量下去是一个渲染 bug：`overflow-wrap:anywhere` 继承进表格，把 7 列登记表压成一字一行（2026-09-09，老板：「markdown 阅读器不够美观，而且移动端兼容好像不太好」）

**先量再改。** 用 Playwright 在 390px 打开真实任务档案，第一屏就撞上一个比"不美观"严重得多的东西：

> 「需求条目登记表」的 `REQ-0338` **竖着排成 R/E/Q/-/0/3/3/8**，首列宽 **30px**、单行高 **109px**。

根因是**两条各自合理的样式叠加**后互相成全：

1. `table { width: 100% }`（旧 `w-full`）→ 表格被钉死在容器宽，**永不溢出**；
2. 外层为正文长标识符/路径加的 `[overflow-wrap:anywhere]`（§3.88 的产物）**被单元格继承**——实测 cell 的 computed 值就是 `anywhere`——于是**把列缩到一个字符宽也仍然"合法"**。

结果：外层那个 `overflow-auto` **永远不触发**（表格从不超出容器），表格于是选择**自我压碎**而不是横向滚动。`anywhere` 在正文里是解药，进到表格里是毒药。

**这类 bug 的共同特征值得记住：它不是某处写错了，而是两个正确的决定在同一棵 DOM 树上相遇。** §3.121 的 `min-width:auto` 三连是同一族——都得靠"量 computed 值 + 量 scrollWidth/clientWidth"才能看见，肉眼看截图只会得出"有点挤"。

**改法（三条口径，写进文件顶部注释）：**

- **表格双形态**：宽屏＝可横滑表格（`w-max min-w-full` 允许超出容器 + 容器横滑 + **两侧渐隐遮罩**只在真可滚时出现）；**窄屏且列数 ≥3 → 卡片模式**（一行一张卡、`列名: 值`）。判据不是"卡片更好看"，而是**本仓文档的表格全是"一行一个实体"**（登记表/覆盖矩阵/facet 表/待确认），天然适合卡片；而 7 列 × 长文本即便能横滑，390px 上也读不了。
- **h1–h6 六级全部显式定义**。旧版只到 h3（h3 还与正文同为 14px），h4/h5/h6 落到 Tailwind preflight 的 reset → **渲染成普通段落、层级完全消失**，而本仓模板大量用 `####`。**只定义到 h3 = 默认剩下三级不存在**，这不是"样式简约"，是信息结构丢失。
- **`>` 引用不再灰化**。这些文档用 `>` 承载最重要的口径（「★诚实铁律」「为什么这么设计」），旧版 `text-muted-foreground` 把**最该看的段落变成最灰的段落**——样式默认值与内容语义正好相反。

**三个自己踩的坑（比上面的修复更值得记）：**

**一、我在修 bug 的同一个文件里，又犯了同一个 bug。** 卡片模式第一版把容器顶到 **1532px**：`grid-cols-[auto_1fr]` 的 `1fr` 轨道最小宽 = 内容 min-content，而 **`overflow-wrap:break-word` 不改 min-content，只有 `anywhere` 改**——这句话就写在这个文件顶部的注释里，是 §3.88 的结论。**证明"写了注释"不等于"下次会想起"**：所以这次把它写成了带 `⚠` 的就地注释（在那个 `<dd>` 上方），而不是只留在文件头。

**二、按 React children 判 `type === 'thead'` 必然失败**——因为**我给 thead/tr/th 都提供了自定义组件**，那些元素的 `type` 是我的组件函数、不是字符串。症状很轻（卡片里列名全渲染成「—」），但它是"自己的抽象把自己的判据打掉"这一类错误。修法：读 react-markdown v10 传的 **hast `node`**（带真实 `tagName`，不受组件替换影响）。**凡是要在自定义渲染里反查结构，就别用被自己替换过的那一层。**

**三、`useIsMobile()` 不能放在 `Markdown` 上。** `Markdown` 是按**每条聊天消息**渲染的，而该 hook 每个实例挂 3 个监听器（matchMedia change / resize / orientationchange）——几百条消息的会话就是几百个监听器，一次窗口缩放触发几百次 setState。下沉到 `MdTable` 后，没有表格的消息零成本。也刻意**不**用「两份 DOM + `md:` 隐藏」的省事解法：覆盖矩阵 101 行双份渲染，本仓在看板头像那次（CHANGELOG 2026-09-08）已明确否决过。

**校验口径**：Playwright 真跑线上数据两档对照——390px 页面横向溢出 **0**、136 张卡、0 张 table、列名正确；1440px 仍 6 张真表格（表头底色/斑马纹/横滑）、横向溢出 **0**；两档 console **0 error**。**如实记未验项**：代码块（```）观感没在应用里眼见——看板现有任务档案没有一份含围栏（`grep -c` = 0），改动限于边框/底色 + reset 嵌套 `code`。

### §3.128 收工汇报写「【等你拍板】无。」，会话里照旧挂一张「等你拍板 / 无。」的空拍板卡——徽标那半认「无」、卡片那半不认（2026-09-09，老板：「怎么现在聊天窗口总是会追加等我拍板卡片，即使没有东西」）

**现象**：菲菲收口汇报，末行按工牌写 `【等你拍板】无。`；员工徽标已经是绿的「已完成」，可气泡下面还是长出一张 gate 卡（琥珀色「等你拍板 / 无。」+ 拍板输入框 + 附件按钮）。**同一条消息，状态那半判"没事"，卡片那半判"等你"**——于是"等我拍板"变成了每条汇报的固定尾巴，真有事项的那张卡混在里面反而不显眼了。

**根因是一个谓词被写了两遍、且两遍不一样。** 新 UI 重写时把「空门」判定各自实现：

| 位置 | 判据 | 「无。」 |
|---|---|---|
| `web/src/lib/status.ts`（徽标） | `/^无/` — 前缀匹配（照抄旧 UI `runStatus`） | 空门 ✓ |
| `web/src/lib/olcards.ts`（合成卡） | `item === '无' \|\| '（无）' \|\| '(无)'` — **等值**比对 | 不是空门 ✗ |

员工写「无。」「无，有进展我汇总给你」是常态（工牌只规定末行写 `【等你拍板】无`，没规定不许加标点和后半句），等值比对必然漏网。**这不是"少写了一个变体"，而是同一个业务谓词有两份实现——只要有两份，迟早分叉；分叉的表现就是界面自己跟自己矛盾（绿灯 + 催拍板同时在屏上）。** 对策不是补几个变体，是把它收成 `markers.ts` 里的 `isEmptyGateItem()` 一处事实源，徽标与卡片都 import 它。

**顺手暴出的第二、三处漂移（都是旧 UI `parseGate` 早就有、重写时没带过来的）：**

1. **正则不锚行**：`/【等你拍板】\s*(.+)/` 从**全文任意位置**取**第一处**。于是①正文里白话提一句「末行要写【等你拍板】无」也会开门；②老话题里早期那处 marker 会盖掉末行那处真结论（旧 UI 明确取**最后一处**，同引擎 `lastMarkerBlock` 语义）。改回 `^[ \t]*【等你拍板】[ \t]*(…)?[ \t]*$` + `matchAll` 取末处。
2. **marker 行没从正文剥掉**：有事项时旧 UI 会把那行从气泡里剥走、只让 gate 卡承载（`run.result` 原文不动，引擎 `parsePendingGate`/autoChain 与徽标全不受影响）；新 UI 没剥 → **同一句话在气泡和卡片标题里显示两遍**。复制按钮仍复制未剥的 `text`——那才是员工真发出来的这条消息。
3. **兜底条件从「有没有动作卡」松成了「有没有卡」**：`gate && !hasCard(text)`。员工只贴了 info/table 这类展示卡、拍板意图写在散文收尾时（波比那种），gate 卡被展示卡"顶掉"、**老板那条真要拍的反而没有交互面**。改回旧 UI 的 `ACTION_CARD_TYPES`（decision/approval/toggle/gate）判定 → `hasActionCard()`。

**通用口径（这轮真正的产出）：跨模块共享的"业务谓词"必须单点定义，尤其是当它同时驱动两个可见输出时。** 徽标和卡片是老板同一眼里看到的两个东西，它们对"有没有事项"的答案必须由同一行代码给出；判据写两遍时，界面就有能力自我矛盾，而这种矛盾不会报错、只会让人学会忽略其中一半（真拍板卡混在每条汇报的假尾巴里 = 门禁失效的经典形状，同 §3.116 那族）。

## 3.130 「挂任务档案」下拉两处一起坏：半透玻璃面在密内容上读成"没有背景"，前端一次 owner 分组静默推翻了服务端的时间序（2026-09-09，老板：「选择档案弹窗，背景颜色没了，而且没有按照时间排序」）

**现象**（同一张截图两个毛病）：聊天窗组合器上的「挂任务档案」下拉打开后，① 顶部一段被底下那条薰衣草聊天气泡染成一片紫、正文透出来，看着像没有背景；② 23 份档案里当天刚更新的 `v0.1.0`（`updated: 2026-09-09`）排在**第 6 位**，v5.21/v5.19/v5.17.2 这些老档案反而在它上面。

**病一 · 背景**：这是 shadcn 主题原配的「玻璃面」——`bg-popover/70` + 一层 `::before`（`absolute inset-0 / -z-1 / backdrop-blur-2xl / backdrop-saturate-150`）。实测（Playwright 读 computed style）确认它**并没有失效**：`backgroundColor` = 白 70%、`::before` 的 `backdrop-filter` = `blur(40px) saturate(1.5)` 都在。**坏的不是实现，是这套面在本工作台的适用性**：玻璃面成立的前提是"底下是大片低频背景"，而这里底下永远是看板行、彩色状态标、聊天气泡——70% 半透 + 模糊在这种高频彩色底上不产生"毛玻璃"观感，只产生"背景色没了"，长列表还更难对行点选。对策＝菜单面改**实底 `bg-popover`**、顺手把那层 `::before` 删掉（实底之后它是一层看不见但仍在合成的层）。改在 `ui/dropdown-menu.tsx`（Content + SubContent）与 `ui/select.tsx`，**没动 `ui/hover-card.tsx`**——它是被动悬浮提示、不承载点选，观感问题也没被点到，留着它的玻璃面。

**病二 · 排序，是这轮真正值得记的**：服务端 `/api/tasks` 已经排好了（`server.js` 按 `frontmatter.updated` 倒序、缺失回退文件名日期），实测返回就是严格的 09-09 → 07-09。但 `run-detail.tsx` 拿到之后**又排了一次**：

```js
// 原代码，注释还写着「服务端已按活动时间倒序，稳定排序保组内次序」
.sort((a, b) => (a.frontmatter.owner === run.employee ? 0 : 1) - (b.frontmatter.owner === run.employee ? 0 : 1))
```

这个 comparator 只比 owner，稳定排序**确实**保住了组内次序——注释说的每个字都对，但它把列表切成了「本员工的」和「其他人的」两段，**时间轴只在段内成立**。本机 23 份档案里 `owner=feifei` 的有 5 份，于是在菲菲窗口打开选择器时，那 5 份不管多老都在最前，当天更新的 `v0.1.0` 落到第 6 位。改法＝**删掉分组、只按活动时间倒序**（owner 只是档案上的一个字段，不该改变时间轴；挂档案是照"我最近在弄哪个版本"找的）；同时把取时间的口径抽成本地 `taskTime()`，与服务端同源（`updated` 优先 / 回退文件名日期 / 存量档案的 `updated` 后面常跟一长段行尾说明，故只取开头那个日期戳）。

**通用口径：服务端已经排好序的列表，前端再 `.sort()` 一次就等于重新定义了排序，哪怕 comparator"只管另一个维度"。** 稳定排序保的是"comparator 判相等时的相对次序"，不是"原有语义整体不变"——只要你的 comparator 对某一对返回非 0，那一对的原次序就被你的维度接管了。同 §3.128 一族：那次是同一个谓词写了两遍、迟早分叉；这次是**同一个排序口径分在两层、后一层静默盖过前一层**。判据：前端要在服务端排序之上再加维度时，写清"最终顺序 = 什么"，别写"我只是在服务端次序上加一层"。

**校验**：`tsc -b` exit 0、`vite build` 已重建 `web/dist`（4700 服务的是 dist）；Playwright 打开真会话里的这个下拉复测 —— 背景 `rgb(255,255,255)` 实底、`::before` 的 `backdrop-filter` 为 `none`，条目顺序 `v0.1.0(09-09) → v5.22(09-07) → v5.21(09-04) → v5.20(08-29) → v5.19(08-25) → v5.18(08-20) → v5.17.4(08-19) → …` 严格时间倒序，截图确认聊天气泡不再透出来。**未做**：`hover-card` 的玻璃面（见上）、旧 UI `app/public` 的同类选择器（legacy 面，另一套样式与排序，没有这两个毛病）。

**落点＝新增 `web/src/components/image-viewer.tsx`（Provider + 浮窗 + `ShotThumb`），三处刻意的设计判断**：

- **不复用 `FloatingCard`（聊天那扇窗）**。表层理由是它的几何/持久化键（`ol-chat-card`）、停靠态（第三栏）、移动端 history 接管全是为"聊天"定制的；**硬理由在 z 轴**：FloatingCard 活在 `use-card-stack` 的 `[40,49]` 带里，而那个上限 49 是**刻意**的（Radix 的菜单/下拉/弹窗固定 z-50 且 portal 到 body，卡片抬到 ≥50 就会被自己里面打开的下拉盖住，见 `use-card-stack.ts` 注释）。但图片可以从**档案预览 Dialog / 派工弹窗**（z-50 且 modal）里点开——落在 49 就会被自己的来源盖住。图片窗因此自带 `[60,90]` 的层序：它是"用户刚刚要求置顶的那个东西"，本就该盖住一切，且它里面没有下拉菜单，不吃 49 那条约束。

**浮窗本身的几个判断**：出生尺寸先给个中等窗，`img.onLoad` 拿到 `naturalWidth/Height` 后按真实比例调成"刚好装下"（**只调一次**，用户动过手就不再自作主张）；滚轮缩放**以指针为锚点**（长截图必须能盯住某一块放大，居中缩放做不到）；贴合态（zoom≤1）**不许拖图**（那只会把图拽出窗外）；双击复位；Esc 关最上面一扇；同一张图重复点**不开第二扇、只把已开那扇抬到最前**；多张图各自一扇窗、出生位置层叠错开。移动端不做拖拽窗（没地方拖），走整屏查看层，**底色必须不透明黑**——半透明时背后聊天页的顶栏（头像/＋/更多）会透上来，跟本层标题栏叠成一排看不懂的图标。

### §3.137 交付物「看得见、拿不走」：发布话术要人自己拼、交付文件只是一行路径（2026-09-23，老板：「波比能给出我统一话术方便我转发给发布管理员」「不确定 lab 能不能点击文件就打开相应的目录…避免我单独打开文件管理器去拖拽」）

**现象不是 bug，是一段没被机器接走的手工活。** 上线后老板要做两件事：① 把两条 MR 链接拼成一段固定格式的企微话术（`【示例项目5.21版本发布】` + 后端/前端链接）转发给发布管理员；② 开一次文件管理器，把 release SQL 与 RELEASE_CHECKLIST 拖进企微对话框。两件事 lab 都"显示过"——`link` 卡里有真实 MR、汇报正文里有文件路径——**但显示不等于可取走**：`link` 卡的按钮只能新开 tab，路径只是一行文字。

**取舍一：话术卡不替代 `link` 卡，两张都出。** 一度想把 `link` 卡直接改成"可复制的一段文本"，那会丢掉「点开看改动」这个真实用途。**它们服务的是两个动作**——`link` 给「我要点开确认一眼」，`code`（`lang:"text"`）给「我要整段复制转发」。于是波比的发布交付固定成三张卡：`link`（点开看）+ `code`（整段复制）+ `file`（取文件），写进工牌硬格式，缺一判收工不合格。格式本身照老板 9/4 那条企微原件定型（版本号不带 `v`、链接带 `/diffs`、某端无改动也要明写「本次无改动」），**不留自由发挥余地**——话术的价值就在于收件人每次读到的是同一种东西。

**取舍二：「打开文件夹 / 复制文件」只能由引擎做，不能由浏览器做。** 浏览器打不开宿主机的资源管理器，剪贴板也只能写文本（写不了"文件本体"）。所以新增 `POST /api/reveal`，由跑在本机的引擎 `spawn` 系统命令：Windows `explorer /select,<abs>` 定位、`Set-Clipboard -LiteralPath` 把文件塞进剪贴板（企微里 Ctrl+V 直接粘成附件——这比"打开文件夹再拖"还少一步，是实现过程中顺手加的那一档）。平台命令抽进 `app/reveal.js` 单测，钉住两个易错点：**`/select,<路径>` 必须是同一个 argv 项**（拆开或加空格就退化成"只打开我的文档"），**explorer 成功也常返回退出码 1**（据退出码判失败＝把成功报成失败）。

**★ 一处不显眼但致命的鉴权坑：socket 层的"本机"在代理后面是假的。** 这两个动作发生在**引擎宿主机**上——手机经隧道点一下，弹出的窗口在办公室那台机器上、剪贴板也写在那边，对点的人毫无意义，更不该允许。第一版鉴权写的是 `req.socket.remoteAddress` 是否回环——**恒真**：4700 是 `vite preview`，`/api` 被代理到 4800，无论请求来自本机浏览器还是隧道外的手机，引擎看到的都是 `127.0.0.1`。那道"只放行本机"的闸从落地那一刻起就是全放的，而且**它看起来完全正常**（本机测试自然通过）。对策：`web/vite.config.ts` 三个 proxy 一并开 `xfwd: true`，判据改成「socket 回环 **且** `x-forwarded-for` 首跳回环」；前端再按 `location.hostname` 把按钮禁掉（可见性那一层），服务端 403 是兜底不是唯一防线。**通用口径：凡是「判断请求来自哪里」的逻辑，都要先问一句「这条链路上有没有代理」——只要有，socket 层的地址就只是上一跳，不是来源。** 本仓 4700/4800 的分工（复盘 §3.83）让每一个 `/api` 都必然过代理，这不是偶发拓扑。

**顺带一条口径**：`/api/file` 的下载分支单独写、不复用预览分支。预览那条是"读成 utf8 塞进弹层"、上限 1MB，两条口径都只对文本成立；下载要二进制流式 + `Content-Disposition`（中文名必须走 RFC 5987 的 `filename*`，裸 `filename=` 放非 ASCII 会被截成乱码），上限另给 64MB。**同一个端点服务两种意图时，宁可分支写全，也别让一套参数将就两种约束。**

**★ 上线第一轮就被截图打回两处，都在「显示」这一层（2026-09-23 老板：「效果看起来不太行」「展示的样式有问题」）**：

- **`file` 卡把整张卡顶出聊天窗右边缘，三个按钮被裁掉**。卡内每个文本都写了 `truncate`，一个都没生效——**grid/flex 子项的自动最小尺寸是 `max-content`**，容器 `grid gap-1.5` 与行 `flex items-center` 都没写 `min-w-0`，于是那条 `docs/项目跟踪需求/01-v0.1.2/RELEASE_CHECKLIST.md` 把行撑到内容宽、行把卡撑宽、卡越出窗口。**这是本仓第四次踩同一条**（§3.72 看板台账 / §3.88 聊天正文被裁 / §3.99 facet 弹窗 / §3.121 移动端三连），而 §3.121 明明白白写过「凡是写了 truncate 却没生效先查外层能不能收缩」。写过四遍仍然复发，说明**这条不该靠记忆、该靠肌肉记忆**：新写任何「一行文本 + 右侧固定按钮」的行，`min-w-0` 应当和 `flex` 一起打出来。
- **话术卡只剩一条横向滚动条，两个 MR 链接一个都看不全**。`code` 卡一律 `whitespace-pre` 对 SQL 是正确的（折行毁掉缩进的可读性），但**这张卡的用途不是读代码，是「转发前扫一眼链接对不对」**——同一个卡型开始承载第二种阅读意图，渲染却仍按「代码」那一种来。改成按 `lang` 分：`text` 折行（URL 里没有空格，必须 `overflow-wrap:anywhere` 才断得开），其余不折，`wrap` 字段可显式覆盖。**通用口径：一个卡型开始服务第二种阅读意图时，先问一句「排版规则还成立吗」，别默认继承。**

两条都不是逻辑错误，是**只有把真实内容放进真实宽度里才会显形**的问题——我在设置页的卡片预览廊里看过卡（宽 552px、示例路径短），一切正常。**教训：验证展示层要用真实长度的真实数据、在最窄的那个容器里看；示例数据的「好看」什么都不证明。** 已把话术卡与 `file` 卡都加进预览廊，并在 420px 窄窗下复验（14 张卡同宽 552px、窄窗下按钮全在框内、话术卡无横向滚动）。


## §3.145 悬浮输入框连出三次「末张卡被盖住」：叠层 + 量高度回填这条路本身就脆，改回文档流（2026-10-07）

**背景**：老板要求聊天输入框「改悬浮、不跟消息列表硬切」。初版做法：审批 / 巡视 / 攒批 / 短语行 / 输入框叠成一个 `absolute` 底座浮在消息区上，ResizeObserver 量底座高度，回填给消息区 `paddingBottom` 与「回到最新」浮钮的位置。

**同一天连出三次同一症状（末张卡下半截压在输入框底下）**，三个根因各不相同：
1. 「算贴底」容差 100px：叠层之前无害，叠层之后差 100px 就是半张卡被盖、却既算「在底部」不出浮钮、也不补贴底。
2. 卡片原地变高（动作卡 / markdown / 代码块异步排版）不产生新事件，只靠新消息触发的贴底贴不到。
3. **停靠 / 取消停靠会重建整窗 DOM**，而观察器是在 `useLayoutEffect(..., [])` 里对 `ref.current` 挂一次——之后一直盯着已脱离的旧节点，量到 0 高，留白只剩常量那一截。

另有一次「回到最新」停在差一截处：`scrollIntoView(哨兵)` 对准的是留白**之上**的哨兵。

**取舍**：每修一处都能过，但这条路的本质是「用测量去模拟布局」——任何测量失真（时机、节点换代、异步变高）都直接变成内容被遮。老板拍板「消息滚动区直接减去底座高度」：底座回到文档流（`shrink-0`），消息区 `flex-1` 自然止于其上沿，**不需要任何测量，也就没有量错的可能**。观感上的「不硬切」改由样式承担（底座无分隔线、与消息区同底色、输入框自身小圆角卡片）。放弃的是「消息从输入框后面渐隐滑过」那点效果。

**保留下来的修正**（与叠层无关、本来就该有）：贴底容差收到 32px；ResizeObserver 盯消息区容器本身 + 每个直接子元素（border-box），跟随态下内容变高 / 容器被压矮即补贴底；翻页补偿只补「顶部多出来的高度」而不回到发请求时的旧位置（旧做法会在请求在途时把已经往下滚的人拽回去）；「回到最新」直接 `scrollTo(scrollHeight)`，平滑滚动途中的 scroll 事件不改跟随态。

**通用教训**：
- **挂在 DOM 节点上的观察器 / 监听器，用 callback ref（或 state 化的节点）驱动 effect**，别在 `[]` 依赖的 effect 里读 `ref.current`：组件不重挂、节点却换代（portal 目标变化、条件包裹层变化）时，后者会静默盯着死节点。callback ref 还必须是稳定引用（`useCallback`），否则每次提交先 null 后节点，观察器反复拆装。
- **能用布局表达的，别用测量去模拟布局**。「A 不能盖住 B」首选让 A 不与 B 重叠（文档流），而不是让 B 量出 A 的高度再躲开。


## §3.151 「打开文件夹」不 work：其实每次都开了，开在浏览器后面（2026-10-19，老板：「卡片里打开文件夹不 work」）

**排查**：先直调 `POST /api/reveal` 返回 `ok`；再用 `Shell.Application.Windows()` 枚举资源管理器窗口，发现同一个 `安装包` 目录已经开了两扇（老板点的一次 + 排查调的一次）。即 §3.137 的 `explorer /select,` 一直工作正常——**窗口被 Windows 前台锁压在浏览器后面**：后台进程（引擎 → explorer）不许抢前台，新窗口只在任务栏闪一下，用户看到的就是「点了没反应」。§3.137 上线时没暴露，大概率是当时 explorer 恰好在前台或测试者自己切过去看了。

**对策**：`app/reveal.js` 新增 `focusRevealCommand(platform, dir)`（仅 win32），`/api/reveal` 在起 explorer 后再起一个 powershell：等该目录的资源管理器窗口出现（先快照已有 HWND，≤1s 内优先取新出现的那扇，否则取最后一扇匹配窗——Shell.Windows 按创建顺序），最小化则还原，发一次 Alt 键解除本进程前台锁，再 `SetForegroundWindow`。不等它、不据它判成败——置前失败也不影响文件夹已打开。实测：后台进程调用后前台窗口即为该目录，端到端约 2–3s（powershell 启动 + 等窗口）。

**排查中顺带踩到的坑**：Git Bash 的 heredoc 在本机会把 `\\` 折成 `\`，测试脚本里的 Windows 路径被吞成 `D:WorkProjects…`（`\t` 变制表符），explorer 收到坏路径就退化成「打开我的文档」——差点被误判成 `/select` 本身有问题。**教训：「点了没反应」先确认动作是否真发生（枚举窗口/看进程），而不是先怀疑命令；构造含反斜杠的测试数据别过 shell 转义。**

## §3.152 §3.151 的置前从未生效：`-Command` 传脚本，路径反斜杠被 powershell.exe 吃掉（2026-10-20，老板：「为什么在文件管理器里打开还是不 work」）

**两个叠加原因**：
1. **引擎没重启**：PID 启动于 10-19 09:06，§3.151 的 `reveal.js` 改于 16:32；引擎不热加载自身代码（`fs.watch` 只盯 `tasks/`），跑的一直是「只起 explorer」的旧逻辑。
2. **就算重启也不行**：`focusRevealCommand` 用 `powershell.exe -Command <多行脚本>` 传参。脚本里有双引号（`DllImport("user32.dll")`），Node 在 Windows 拼命令行时把它转成 `\"`；powershell.exe 重新解析 `-Command` 时把**路径里的反斜杠一并当转义吃掉**——`$d` 实测为 `D:WorkProjectsoffice-lab`（len=24）。于是 `Shell.Windows()` 永远匹配不上窗口，`$h=0`，不置前，**退出码 0 静默失败**。

**为什么 §3.151 当时以为验过**：排查里已经见过 `D:WorkProjects…`，但归因给了测试脚本的 heredoc；所谓「后台进程实测前台即为该目录」并没走生产代码的 `-Command` 传参路径（手动 `-File` 跑脚本是成功的——这正是本次对照出根因的方法）。单测只断言「拼出来的脚本字符串里有 `$d = '…'`」，覆盖不到「经命令行送进 powershell 后还是不是它」。

**对策**：改 `-EncodedCommand`（脚本 UTF-16LE → Base64）：Base64 里没有引号/反斜杠/非 ASCII，转义问题与中文目录的命令行代码页问题一起消失。单测改为断言 `-EncodedCommand` + 参数纯 Base64 + 解码后路径原样。实测（后台进程，与引擎同条件）：`D:\Workspace\Projects\office-lab` 与 `docs\示例项目需求\00-通用资料\数据修复SQL` 两处都匹配到新窗且置前后 `GetForegroundWindow()==h`。

**教训**：① **「静默成功」的辅助进程要能自证**——验收时让脚本自己吐出关键中间量（匹配到的句柄、置前后前台是不是它），别从外部看前台窗口标题（用户同时在用电脑，前台一直在变）。② **Node→powershell 传任何非平凡脚本一律 `-EncodedCommand`**；`-Command` 只适合无引号的单行。③ 改引擎后「已修」的前提是**确认在跑的进程加载了新代码**（看进程启动时间 vs 文件 mtime）。
