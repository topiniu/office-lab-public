### 3.3 健壮性：judged-dead + 自动续跑 + 强制接管（事故驱动）
- **事故根因（2026-07-15）**：feifei 单 turn 一次性写三份大文件，流式 4.5 分钟后触发 `Connection closed mid-response`，子进程异常但不触发 close → status 永远 `running` → `/reply` 恒 409 吞掉用户「继续」= 僵尸 run。
- **watchdog**：`sweepStalled` 每 30s 巡检，基础宽限 150s + 思考预算×系数（重活容忍更久，真卡死是零字节）；判死则 `abort()` → 触发 `handleStreamEnd` 走续跑。
- **`shouldAutoRetry`**：用户主动停/无 session/达上限 → 否；watchdog 判死 / 结果含连接错误文案 / 流中途抛错且无结果 → 是；上限 `MAX_AUTO_RETRIES`(10) 防烧钱死循环。
- **`handleStreamEnd` 三分支**：① 用户强制接管（僵尸 run 暂存消息优先投递）② 自动 resume 续跑 ③ 终态（用户停=interrupted / 其余=error）。
- 由此衍生的产出纪律（写进工牌）：**多文件产出逐个写、一回合一个文件**，禁止一回合并行写多份大文件（就是这次事故的直接教训）。
- **空收工 → 如实报错、不自动续跑（事故根因 2026-07-27，run `20260726054047-f0259f`，菲菲）**：上面的 watchdog/`shouldAutoRetry` 兜的是**进程层异常**（连接中断 / 零字节卡死 / 流中途抛错）；这次暴露的是**模型层过早收手**——SDK 正常回了 `result`（`is_error:false`），但内容为空。复现：菲菲一轮里 `Edit` 因 `old_string` 锚点过期报「String to replace not found」（任务档案 #13 那行被 GG Bond 回写扩写过，她凭旧印象的锚点 `…absent |` 已不存在），随后模型只产出空思考块便 `end_turn`。引擎 `onTurnComplete` 据此判 `done`、亮绿灯「✅ 本轮收工」、`appendLessons`、进 `autoChain`；而 `autoChain` 在空 `result` 里找不到任何 `【下一棒】/【交回】/【等你拍板】` 标记 → 命中「既无下一棒也无交回=终止（安全默认）」→ **静默死停**。后果：需求说明落了盘，但任务档案登记 #14 未加、未派 GG Bond，界面却一片"成功收工"的绿，老板以为交出去了、实则卡半途。
  - **❌ 第一版对策（自动续跑）当天即回退——重要反面教训**：最初在 `onTurnComplete` 里做「空 result → 原地热推一次纠偏续跑（`pushTurn` + `MAX_EMPTY_RETRIES=2`）」。重启上线后立刻演成更严重的线上事故：① **自动续跑期间 run 恒 `running` → `/reply` 409 拒收用户消息**——把原本"静默停但用户随时能继续"直接放大成"**菲菲彻底不工作、连话都递不进去**"（用户原话：「看起来菲菲彻底不工作了」）；② 用户 resume 的正是那条退化会话（a300d77b，尾部结束在思考块上），**每轮都空**，2 次纠偏白锁 ~10 分钟、烧 token，且第 2 次虽被提示词带着**正确诊断出锚点问题、还写了临时文件**，仍旧结束在思考块上 → `result` 又空。**核心误判被这次坐实**：`result` 空 **≠ 这一轮没干活**——它只表示「最终消息没有文本」，中途完全可能有文本 + 工具调用，只是结束在思考块/工具调用上。据此自动续跑既误判又扰民。
  - **✅ 现行对策（被动暴露，不自动重试）**：空 `result` → 直接置 `error` 终态。不绿灯误导、不 `appendLessons`、`autoChain` 不接棒；红灯「⚠️ 本轮未正常收工…回复『继续』重试一轮；反复空转则新开话题/重新派工」+ 推手机。关键是 **run 立即回到可交互态（`/reply` 不再 409）**，把恢复节奏交回用户。进程层异常仍归 watchdog/`shouldAutoRetry` 自动 resume；模型层没正常收尾**不自动重试**（自动重试的代价见上）。
  - **教训**：① 本系统「每轮以收工汇报 + 标记结束」是硬不变量——**空 `result` 不是合法终态**，绝不能当 done 亮绿灯；但②**「不合法」不等于「该由引擎自动替它续」**——续跑要占住 `running`、屏蔽用户，对退化会话是净负担。修 A 类问题（静默）别引入 B 类问题（卡死）：**能被动暴露 + 交回控制权，就不要主动接管**。③ 判「有没有真产出」不能只看末尾 `result` 字段（末块是思考/工具就为空），也不能只信 SDK 的 `is_error:false`。④ 长行文档/表格的 `Edit` 锚点极易因他人回写过期——员工侧稳妥做法是**先重读再改 / 对长行改用 node 就地写 / 改完用 node 独立核验落盘**，已写进写文档三员工红线做事前预防（菲菲红线 8/9，GG Bond、迷糊各红线 9；#13 那行正是 GG Bond 回写扩写的）。
  - **同一过敏纠偏再咬迷糊 + SOP 侧的边界修正（run `20260727044513`／`7db1f8be`，2026-07-27）**：上述自动续跑虽已回退，但**运行中的 server 未重启、老逻辑仍在跑**——迷糊做 v5.14 回归时又撞上：它先去核验「后端跑的是不是最新 v5.14 构建」，判出 java 进程（11:42–43）比 jar（11:46）旧，便**自助 `restart gys-web`**；重启转后台又迟迟不就绪，等待期每轮空 `result` → 过敏纠偏反复点炮，约 46 分钟没进正式回归。两层根因：① **引擎侧**印证了「空 `result` ≠ 没干活」——迷糊全程在读档/建任务/等重启，纠偏却判它空转（修复同上，**待 server 重启生效**）；② **方法论侧**——QA 员工**不该自己 build/restart/deploy 后端**。深挖发现「须重新构建部署后端」这句**不在任何 SOP/模板里、是派工被临时手写进去的**，且与同段「人工预检已通过」矛盾（预检必然已构建+运行最新产物）。**对策**：迷糊新增红线 10「不碰构建/部署/运行环境——默认信任人工预检，只读探活、不满足即停交回」，并做到**即便派工文案叫它重构建/重启也拒绝**（自由文本派工挡不住手写冗余指令，规则必须钉在员工侧、能抗命）；工作流 ① 的「前置已过人工预检」说明同步扩写到覆盖构建/运行环境。**教训**：员工的自愈边界要划清——「判断对」不等于「有权处置」，越界去动基础设施（重启服务）比停下喊人代价大得多；且引擎兜底改完必须**重启部署才算数**，代码改了不重启 = 老坑照踩。
  - **✅ 迭代对策：兜底取本轮实说文本 + 连续空转熔断（2026-07-28，run `20260727063352-a77ed4`／session `2ef4c395`，菲菲）**：现行「被动暴露」把 A 类静默治住了，但**没治「误报」**——上面 ④② 反复坐实的「`result` 空 ≠ 没干活（中途有文本+成功工具调用、只是结束在思考块/工具块）」这一类，仍被一律判红灯「未正常收工」。这次复现：菲菲从「接着聊刚刚的需求讨论」起连续多轮结束在思考块，其中若干轮**明明有完整 `text`＋成功 `lark_update_requirement`（数据已落库）**，却次次红灯；老板连点 4 次「继续」都在 resume 同一坏会话复现空收工，观感是「怎么都恢复不了」。对策两条，**都严守"不假装成功、不自动接管"的既定哲学**：① **兜底取文本**——`beginTurn` 每轮清 `run._turnText`，`consumeStream` 累积 assistant 的 `text` 块（后到覆盖留最后一段），`result` 空白但本轮有实说文本时用它当 `run.result`＋置 `_resultFromFallback`（绿灯并注明「结尾停在思考块，已取本轮回复内容展示」）。这只 surface **模型确实说过的话**，不是替它续跑、不占 `running`、不碰 B 类卡死雷区。② **连续空转熔断**——`run._emptyStreak` 只在真·空（纯思考零文本）时累加、任何非空 done（含兜底）归零；≥2 轮连空把 lab 文案从「回复继续重试」升级为「已连续空转 N 轮、状态已坏，**请勿再回复『继续』**，直接新开话题/重新派工」，把用户从「对着坏会话反复续」的死循环里主动劝离（此前只在文案末尾一句软提示，容易被无视）。**边界不变**：真·空仍红灯；不恢复自动续跑；进程层异常仍归 watchdog。**教训延伸**：修 A 类（静默）后要回头收 A 类的"过度矫正"——把「不合法终态」一刀切成红灯会误伤「合法但收尾姿势不对」的一轮；正确姿势是**按"这一轮到底有没有对用户说话"分层**（有→如实展示、无→红灯），判据落在流式过程里累积的文本、而非只看末尾 `result` 字段。同样，别只把「反复空转就别续了」写成一句提示指望用户自觉——**该由引擎数着 streak 主动升级劝离**。


### 3.31 后台任务/子agent 可观测性 + 员工状态正确映射 + 后台完成自动接棒 + 长思考心跳（2026-07-28，事故复盘）

问题（两条事故坐实）：① **员工派发后台任务/子 agent 后，这期间毫无可观测状态、员工对外还显示「done」**。run `20260727055755-fa1728` 第 180 行，迷糊收工汇报原话「两个后台任务在跑（基线 App-run + 源码研究子 agent）」，随即引擎 `onTurnComplete` 亮绿灯判 `done`——而 `curl -m 600`（10 分钟）后台 bash + 子 agent 仍在跑，看板/侧边栏此刻显示员工空闲，老板得手敲「继续」才让员工回去查结果。② **迷糊长思考静默卡 6 分钟**。run `20260728124450-a527de` 第 447→448 有 +369s 零事件空档，是老板敲「？」「继续」才捅醒。**共同根因**：`normalizeEvent` 的 `default` 分支把 SDK v0.3.x 的一批控制消息**全丢了**——`background_tasks_changed`（活动后台任务集 level 信号）、`task_started`/`task_progress`/`task_notification`（后台任务 bookend + 进度 + settle）、`thinking_tokens`（长思考实时估算）。加上 `includePartialMessages:false` 时长思考块本就零事件、watchdog 重活宽限 `150s+24000×12ms=438s` 也没触发这段 6 分钟。

**与 §3.25 的区别（别混）**：§3.25 治的是**子代理在同一 turn 内跑完**（父级被阻塞、事件靠 `parent_tool_use_id` 分层）的**渲染**问题；本节治的是**后台任务/子 agent 跑到 turn 结束之后仍活着**（`run_in_background` bash、被 background 的 foreground 任务）的**状态映射 + 生命周期**问题——前者是「turn 内可视化」，后者是「turn 外还在跑，引擎却判 done」。

**机制取舍（复盘核心）：**
- **level 信号是成员唯一权威源**：`background_tasks_changed` 用 replace 语义（SDK 文档明示「swap your set」）维护 `run._bgTasks`，`task_started/progress` 只补元数据（desc/lastTool/时长），**不作为「还在不在跑」的判据**——避免漏掉 bookend（edge）导致僵尸「后台运行中」指示。`skip_transcript` 的内务任务（观察者/auto-dream 等 SDK 自发任务）不计入可见后台。level 是 per-process，冷起/resume（新子进程）时重置为空。
- **状态映射做成前端派生态、`run.status` 内部不变**：本轮 result 收工但 `_bgTasks` 非空时，收工文案改「✅ 本轮收工，但仍有 N 个后台任务在跑」，但 `run.status` **仍置 `done`**——不引入新枚举值去 ripple `STOP_META`/`autoChain`/watchdog 全链路。「后台运行中」作为前端从 public 快照 `run.bgTasks` **派生**的显示态（`runStatus` 返回 `working-bg`、信息蓝徽标区别前台 primary/收工 success）。取舍：内部语义最小改动、显示层如实分层，是「改 A 类问题别引入 B 类问题」的一贯保守取向。
- **不误关 query 是命门**：`_bgTasks` 非空时 `scheduleIdleClose` **跳过**——空闲窗一关 = `_input.close()` = gen() return = 杀子进程 = **连后台任务一起杀**。等 `syncBgTasks` 见后台清空后再排空闲窗。
- **后台完成自动接棒（老板拍板），且与 §3.3 的「空 result 不自动续跑」不矛盾**：§3.3 禁的是**模糊信号**（`result` 空 ≠ 没干活，自动续跑会误判 + 锁 running + /reply 409 扰民）；后台任务 `task_notification` settle 是**明确信号**（有 status/summary/output_file），自动唤起员工查看结果续跑是完整 Claude Code 的既有行为，风险层级不同。防重复注入用 `_turnActive`（见到 assistant 消息即真、result 置假）+ 5s grace 观察 SDK 是否自续：自续则不注入、且把 `done` 补回 `running` 让看板如实显示；不自续才由引擎 `sendToRun` 注入一条唤起消息。两条运行时路径（SDK 自续 / 不自续）都覆盖，具体走哪条待真机确认（见验证）。
- **后台事件不推手机/托盘，系统通知只留「员工级」（2026-07-29 用户设定）**：起/停后台任务是 run 内部子事件，`onBgSettled` **不发 Bark、不发托盘 `pushNotify`**——push 只留给员工本身层面的事件（run 收工/异常/中断/审批挂起，走 `maybePushRunStopped`）。理由：后台完成会自动接棒续跑，那一轮 run 收工本就按配置推一条（员工级），后台再单独推就是重复噪音；且「后台运行中」在 UI 里已可见（徽标 + lab 行 + `run-bg-settled` 页内 toast），无需升级成手机推送。取向对齐「能被动暴露就不主动打扰」。
- **思考心跳只广播不落库**：开 `includePartialMessages:true` 后 SDK 才发 `thinking_tokens`；消费它驱动「思考中… ~Nk」实时标签**只 `broadcast(run-activity)`、不 `appendEvent`**，`runs/<id>.jsonl` 体积不受影响。同时刷新 `_lastActivity`——给 watchdog 一个「模型确实在思考」的真实存活信号，真·卡死（连 thinking_tokens 都没有）才是零事件。**收紧 watchdog 宽限常量（150s→~90s、下调 think factor）留到运行时确认 `thinking_tokens` 随本 SDK+Opus 稳定流出之后再落地**——否则会误杀长思考（先加信号、再据信号收紧，不拍脑袋改阈值）。

**改动落点**：`server.js`（`handleControlMsg`/`syncBgTasks`/`onBgSettled`/`scheduleBgResume` + `consumeStream` 消费 + `onTurnComplete`/`scheduleIdleClose`/`beginTurn`/`startRun` 挂钩 + `includePartialMessages:true`）、`app/public/app.js`（`runPill`/`runStatus`/`EMP_ST_ICONS`/`renderEmpStatus`/`setRunPill` bg 感知 + `run-bg`/`run-bg-settled` SSE 分支）、`style.css`（`.emp-badge.st-background`/`.pill.background`，信息蓝）、`roles/mihu-teacher.md`+`roles/feifei.md`（「后台任务在跑 ≠ 收工」纪律）。新增全局 SSE 事件 `run-bg`/`run-bg-settled`。验证：`node --check` 双通过 + CSS 结构自检（注释/括号/`*/`）通过；端到端（后台任务可观测 / 自动接棒 / 思考心跳 / 四条回归不退）需**重启 server** 才算数（见 §3.3「代码改了不重启 = 老坑照踩」教训）。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.33 `【下一棒】自己`＝自续：把自环守卫从「终止」改成「继续干下一块」（2026-07-30，事故复盘）

问题：老板睡前让 GG Bond「开完直接来预检」（run `20260729171004`）。它干完一块后**正确地写了完好的 `【下一棒】GG Bond｜<续做指令>` 想自续到预检门**，但 `autoChain` 有一条 `if (nextKey === run.employee) return  // 自环 → 终止`——把「派给自己」当死循环丢弃，run 静默停住，通宵没干完。根因是**SOP 与引擎能力自相矛盾**：菲菲派工 prompt 明写「继续自续下一棒直至预检门」，引擎却禁止自续。（`【等你拍板】无` 不背锅：引擎/前端都把 `无` 判为无门；真正终止点是自环守卫。）

**机制取舍（复盘核心）：**
- **自环 ≠ 死循环，是长任务的正当自续**：单条 dispatch run = 一次 SDK `query()`，SDK 在**单次调用内**已 agentic 干到无工具调用为止，但模型习惯干完一块就 emit `result` 让出——`claude -p` 那种「跑一轮就退」没有跨 run 的「goal 模式」。要「全速建到预检门」这种跨多轮的长自治，只能靠 office-lab 在 run 之间接续，`【下一棒】自己` 就是这个自续原语。旧守卫为防「无限自环」一刀切终止，把正当自续也误杀了。
- **自续＝新起同员工 run，不是 resume 老会话**：员工那条自我交接指令本就是按「全新上下文、先读滚动实施记录续做、别从头重来」写的——新 run 契合它，且**避免单会话上下文通宵膨胀**（cost + 撞上下文上限）。所以选 self-spawn 而非 self-resume。
- **防失控用「独立预算」而非复用 `maxDepth`**：`maxDepth` 是 **call 嵌套**天花板（A 派 B 派 C…），与「同一员工连续自续」是两个正交维度；自续若占 `maxDepth`，几轮就撞顶。故新增 `chainConfig.selfChainMax`（默认 40）独立计数（`run.selfChainDepth` 沿自续链累加）。40 只是**失控回落**——正常应先撞到真门/预检门（`【等你拍板】人工预检` 作为最后一个 line-leading 门 → parsePendingGate 命中 → 停）自然收束。空收工熔断（`_emptyStreak`）继续兜底空转轮。
- **血缘继承原委托者、抑制误导提示**：自续 run 的 `callerRunId` 继承**原委托者**（菲菲），非上一自续轮（否则最终 `【交回】` 会回到已死的自续轮 → return-unknown）；`threadRootId` 保持同链（看板归组）。且自续轮**跳过** `createDispatchRun` 那句「完成后用【交回】、勿用【下一棒】新开 run」的 callerHint——那提示是给 call/return 常规流用的，会**直接劝退自续**（`selfContinue` 标记控制）。
- **取舍诚实**：放开自环后理论上存在「模型每轮写点没用的东西 + 自续」的非空空转，空收工熔断（只逮纯思考零文本）逮不住——`selfChainMax` 是这类的唯一硬底。默认 40 偏宽（照顾「通宵建大件」诉求），可经 `chain-config.json` 调。

### 3.40 巡视员「合法收工」裁决无处落库 → 同一会话被反复空停巡查 7 次（2026-08-01，事故复盘）

**根因分层（两条叠加）：**
- **① 「判合法收工」这第三种结局无处落库**：巡视有三种结局——`resume`（记 `target._patrolNudges`）、`升级老板`（记 `target._patrolClosed`）、`判合法收工`。前两种都在 run 状态上留了痕，唯独**最常见的第三种什么都不写**：目标依旧是 `done` + 挂任务 + 无 marker，`patrolCandidate` 每次都重新判它是空停候选。裁决只活在任务时间线的散文里，引擎读不到、学不会「这条已经问过了」。
- **② `_` 前缀 patrol 状态被 `stripPrivate` 落库时丢弃、重启即失忆**：`saveRegistry` 的 `stripPrivate = k => k.charCodeAt(0)===95 ? undefined : v`（`server.js:258`）把**所有下划线开头字段**从 `index.json` 抹掉。设计本意是「进程内句柄（`_q/_input/_abort`）重启本就作废、别落库」，但 `_patrolClosed/_patrolNudges/_patrolSweptAt` 这类**裁决/节流状态被误归此类**——于是每次重启，升级锁、续跑计数、30 分钟巡逻冷却全部归零，坏候选从头再被巡一遍。这批日志跨了 07-31~08-01 多次重启，正好把「7 次」凑齐。

**修复口径（老板选定：修引擎死循环）：** 引入**持久裁决签名 `patrolClearedSig`**（非 `_` 前缀→落库、跨重启生效）。
- 巡视 run 收工时若**没** `resume_employee` 续跑其目标（=判了「合法收工」或「升级老板」），`autoChain` 给目标盖 `patrolClearedSig = 目标当时 updatedAt`；`patrolCandidate` 命中该签名即排除。
- **自动重新武装**：目标日后真被续跑并产出新停顿时，`onTurnComplete` 会刷新其 `updatedAt`（`server.js:2333`，就在 `autoChain` 调用前一行）→ 签名失配 → 重新纳入巡查。**真空停不会被永久漏掉，只是同一次停顿不再重复问。**
- **实现串联**：`createDispatchRun` 透传 `patrolTarget`（仅巡视 run 有，标它裁决哪条目标）→ `spawnPatrol` 建巡视 run 时带上 → 巡视 run 收工时 `autoChain` 顶部据此盖签名（放在 `chainConfig.enabled` 判断**之前**，因定时巡逻 `sweepIdleStops` 独立于自动接棒开关，不能被 return 跳过）；`resume_employee` 工具续跑目标时置 `run._patrolDidResume`（本轮续了就别盖签名）+ 撤销目标旧签名（它马上做新活）。

**通用教训**：① **每一种结局都要在状态上留痕，否则系统会把「已处理」当「未处理」无限重试**——三条分支只给两条记账，漏掉的那条（还恰是最高频的）就是死循环的种子。② **`stripPrivate` 这类"按命名前缀一刀切"的持久化过滤是把双刃剑**：它省事，但会把「本该跨重启记住的决策状态」和「本就该丢的进程句柄」一起误杀——凡是**裁决/去重/节流/计数**类状态，命名上就别用 `_` 前缀，或给白名单。③ **agent 在会话里喊出的「这看起来是 harness 的 bug」值得当一等信号看**——这次小呆呆连续 7 次精准报出「重复入队」，是最省事的根因线索。

**改动落点**：`app/server.js`（`patrolCandidate` 签名判定 / `autoChain` 顶部裁决落库 / `createDispatchRun` + `spawnPatrol` 透传 `patrolTarget` / `resume_employee` 工具置标记）。未改 HTTP 端点、SSE 事件、run 形状对外契约（仅新增两个持久字段 `patrolTarget`/`patrolClearedSig`）；**需重启 server 生效**，重启后现存卡住候选各再被巡至多一次即盖签名、循环终止；未动生产 `runs/`。详见 CHANGELOG `[Unreleased]` 同名条目。

### 3.49 后台任务诈尸：settle 唤起「已被同线程新会话顶替」的旧会话，两会话并发同分支互相踩写（2026-08-03，事故驱动）

问题：老板发现同一员工（ggbond）同一线程的两条会话「聊着聊着忽然插进来别的会话内容」——在新会话里干活，旧会话却自己活过来抢着改同一批文件。

复现与根因（追 runs 逐帧坐实）：两条会话同属线程 `…2905e3`、同分支 `feature/v5.16-pattern-change-notify-lab`。

1. **旧会话 `…062019` 被后台任务"泊住"**：06:29 它起了个跑超 120s 被转后台的 Bash（`bjt3xug0r`「全仓定位权限码与auth.json」）。前台 turn 结束后，本应收工，但 §3.30 的既有逻辑「**后台任务在跑就保持 query 存活**」（`close = 杀子进程 = 杀后台任务`）让这条 run 的 query 不关、停摆泊住。
2. **新会话 `…071315` 接管本线程**：07:13 派工「续做 ②③④⑤」，正常推进、08:48 起回写任务档案 `2026-08-03-v5.16-纸样变更通知.md`、08:57/09:25 与老板对话。此刻线程的"现役会话"已是新会话。
3. **旧会话诈尸**：09:05 那条后台任务 settle，`onBgSettled`→`scheduleBgResume` **无条件唤起其属主（旧会话）**。旧会话泊了 **~117 分钟**后醒来，按提示「查看结果并继续推进」自作主张去核 ②③④⑤ 代码、把看板 5 条目全推「待预检」、改**同一份**任务档案——撞上新会话正在写的内容，旧会话侧报 `File has been modified since read`。两会话就此并发同分支、互相踩写。

根因：`scheduleBgResume` 的**唯一去重判据是 `run._turnActive`**（本 run 自己此刻有没有前台 turn），**从不检查「本会话是否已被同线程更新的活跃会话顶替」**。引擎里 `busyRunFor`（同员工是否已有 running/starting）这道守卫，巡查 sweep、autoChain、交回排队都用了，**唯独后台接棒这条路没用**。这是 §3.30「后台任务自愈」的补充缺口：那次治好了「员工起后台活后 run 被误判空闲、老板得手动敲继续」，但只设想了"一条会话 + 它的后台活"这条直线，没考虑「属主会话早已被同线程新会话顶替、或被中断废弃」——于是一条本该 settle 后安静关闭的僵尸会话，反被后台完成信号"救活"。

对策与取舍：
- **接棒前加「未被顶替」守卫**（`supersededBy()`）：唤起前若存在「同员工 + 同 `threadRootId` + `startedAt` 更晚 + 当前 running/starting」的会话，判为本会话已被顶替，**跳过唤起**，只落一条 lab 说明（「已被会话 X 接管、后台结果仍在磁盘可 Read」），**不跨会话注入**那份结果——跨会话自动灌内容正是"串线"本身，宁可要人工/新会话按需 Read。
- **刻意按 `threadRootId` 判、不按员工一刀切**（关键取舍）：老板明确要「同一员工多线程并行」的能力。若守卫写成「同员工有任何活跃 run 就跳过」，会误伤——员工在两条**独立线程**并行，其中一条的后台任务 settle 时另一条恰好在跑，就会被错误跳过。按线程判则：独立线程各自的后台接棒互不干扰，**只有被同一线程新会话顶替的旧会话才不复活**。多线程并行安全、僵尸诈尸被拦，两个目标同时满足。
- **收尾自然闭合**：`onBgSettled` 里已先 `delete` 掉该后台任务，跳过唤起后 `syncBgTasks` 见后台清空 + 非前台在跑 → 触发既有 `scheduleIdleClose`，泊住的僵尸会话正常排空闲窗关闭，不残留。

通用教训：**① 任何"自动唤起/接棒/重投"类自愈动作，注入前都要问一句「这条会话现在还是它这条线程的现役吗」——`_turnActive`（自己忙不忙）不等于"没被顶替"（有没有更新的接班人）；自愈机制的守卫要覆盖"属主已被替换/废弃"这一路，否则会把该安息的会话救活。② 会话/资源的"活跃"判定要选对粒度：按"员工"判会误伤多线程并行，按"线程"判才既拦僵尸又放行并行——粒度错了，守卫要么漏拦要么误伤。③ 跨会话自动搬运内容＝串线源头，能不自动注入就不注入，留痕 + 按需 Read 比"自作主张接着干"安全。**

**改动落点**：`app/server.js`（新增 `supersededBy()`；`scheduleBgResume` 定时回调在 `_bgResumePending` 校验后、注入前加顶替守卫）。未改 HTTP 端点/SSE 事件/run 形状对外契约（仅多一条 `lab` 事件）。`node --check` 通过；**待老板重启 server 后**用「同员工双会话同线程 + 旧会话遗留后台任务」场景实测：预期旧会话 settle 后不再诈尸、只落 lab 说明并关闭。详见 CHANGELOG `[Unreleased]` 同名条目。


### §3.61 `_turnText` 兜底把「SDK 反复自催仍无产出」的空转轮伪装成绿灯收工（2026-08-09，用户提问驱动）

**现象**：老板翻与菲菲的一条会话（run `20260809051651-be53e4` / session `4e94e142`）——「现在开工，建档案派 GG Bond」那一轮**既没建成 v5.17 任务档案、也没派 GG Bond、更没写任何收尾标记**，界面却显示 **✅ 本轮收工**；老板追问「？」后又空转一轮。且**小呆呆巡视没抓到**。

**逐日志定位（真实 run 日志，非凭记忆）**：这条会话在引擎侧是 **5 个正常收 `result` 的 turn**，不是一直挂着。前 3 轮正常绿灯。问题在第 4、5 轮：模型早期吐了句没用的一行（「明白，开工。先把档案建起来…」），**随后在 SDK 内部反复空转**——`claude.exe` 检测到「本轮无可见输出」，自注入 `[Your previous response had no visible output. Please continue…]` 逼它再说，模型又只产思考块，如此 ≥2 次，**始终没产出档案/收尾**，这一 turn 的 `result` 最终为**空**。

**根因（一条精确的链，别归错到 watchdog/巡视）**：
1. **真凶是 `_turnText` 兜底误开火**。该兜底是 §3（«空收工» 迭代对策 ①，2026-07-28）为治「模型说了真话、只是结尾停在思考块，却被一律判空收工红灯」而加的：`result` 空但本轮有实说 `text` → 取那段文本当收尾、绿灯。可在这里，那段 `text` 是**早期一句陈旧旧话、不是收尾**；模型随后空转到 turn 结束。兜底把这句噪声捞出来 painted 绿灯。
2. **三连恶果**：① 空转被伪装成成功收工（误导绿灯，老板以为档案建好了）；② `run._emptyStreak`（连续空转熔断，只在「真·空=纯思考零文本」时累加）被这假绿**每轮归零**，所以连着 2 轮空转也没触发「已连续空转 N 轮、别再续、新开」的升级；③ 空 `result` 里无 `【下一棒】/【交回】/【等你拍板】` 标记 → `autoChain` 命中「既无下一棒也无交回=终止（安全默认）」→ 静默停。
3. **为什么两道守护都没救**：**字节 watchdog** 与本案无关——它兜的是「进程冻死/连接中断」（零字节静默），而这里每个 turn 都正常收了 `result`、进程没冻。**巡视（小呆呆）** 06:27 确实事件驱动来过一次（run `20260809062709-69a764`），但那是针对上一轮（合法闲聊「5.16 进度为什么去企微查」）、正确判了「合法收工、无需介入」；真正的空转发生在**这次巡视之后**的第 4/5 轮，而这两轮被假绿成 `done` 且是 `chat` 类（非 `dispatch`+挂任务），不进 `patrolCandidate` 候选池 → 没有新巡视被触发。

**对策（对准真因，守住既定哲学）**：引入一个 **100% 特异的空转信号——一轮内 SDK「no visible output」自催次数**（`run._sdkNudges`，`beginTurn` 每轮清零）。它只在「这轮真的没产出可见输出」时由 `claude.exe` 注入，正是空转铁证。`consumeStream` 数它（这类无 `tool_result` 的 user 消息本被 `normalizeEvent` 当输入回显丢弃、不落库，但在丢弃前先数一笔）。**给 `_turnText` 兜底加闸**：本轮自催 ≥ `SILENT_SPIN_NUDGES`(=2) 次 → 判空转 → **不许**用残留旧文本假绿，保持 `result` 空 → 落到 `onTurnComplete` 的空收工红灯 + `_emptyStreak` 累加，红灯措辞点明「SDK 已催 N 次仍只思考没收尾」。

**关键取舍**：① **只认「no visible output」这条精确信号**，不认泛化的续跑提示（`Continue from where you left off` 之类可能是正常 resume，误计会误伤合法长活）——用出事的真实 session 回放校准：阈值 2 时前 3 轮合法轮自催=0（仍绿）、第 4 轮=2（正确判红），泛化信号会把第 5 轮的正常续跑也算进去、抬高误报。② **不加 `maxTurns` 硬砍 SDK 轮**——会误伤「通宵建大件」的合法长活（§4「防失控用独立预算」同源、§6 已知短板照顾）。③ **不动巡视/字节 watchdog**——它们各司其职、本案不该由它们兜；把判据落在「turn 收尾这一刻到底有没有真产出」才是对的层。④ **不自动重试**——延续 §3「模型层没正常收尾不自动重试」（自动 resume 曾把静默停放大成彻底卡死）：红灯 + 推手机 + run 回到可交互态，恢复权交回老板。

**通用教训**：**「兜底救误判」的补丁，本身要能区分「它要救的合法态」与「长得像但其实是病态的态」，否则就从『治漏报』变成『造新漏报』。** `_turnText` 兜底当初为救「结尾停在思考块的真收工」而生，却因为只看「有没有说过话」、不看「说的是不是收尾/这轮是不是在空转」，把「早期一句废话 + 反复自催空转」也一起「救」成了假绿——还顺手废了旁边的空转熔断。判据必须落在**能把两者分开的那个特征**上（这里＝SDK 自催次数），而不是一个两者都满足的宽条件。与 §3.58「面板状态要派生自唯一事实源、别信手写副本」、§3.56「答进度要读源不读表」同一条主线：**信号要选那个真正区分对错的、最靠近事实的量。**

**她为什么会空转（根因在角色侧，引擎兜底只治症状，SOP 侧补的第二刀）**：上面的引擎修复只保证「空转不再被假绿掩盖」，但没回答「菲菲为什么一开始会空转」。翻可见行为（她的思考正文没落进 session 文件、0 字符，故从行为推）得两条叠加的驱动：
1. **她把自己"说进"了一个角色矛盾**。前一轮老板问「5.16 进度你为什么去企微查询？」，她**过度反省**、把自己定性成「企微＝纯 I/O 渠道，开工/派工/看进度不是我在这儿该干的、我越界了」。老板下一句恰是「现在开工，建档案派 GG Bond」——于是她进了死结：刚亲口论证「建档案/派工不是我这渠道该干的」，紧接着被命令就地建档案、派工。**关键是这其实是看板的重量级 run**（她手上有完整文件工具、完全能写 `office-lab/tasks/` 档案、能交接），根本不是被锁工具的企微轻量人格——她**把两顶帽子戴混了**，用「企微渠道人格」的克制约束了一个本该放手干的看板动作，对"动手写档案"这个动作扣不下扳机。
2. **从零仿写高格式档案的完美主义**。v5.17 档案没有现成锚点（要她造），她一路读参考对格式（v5.16 交接卡 → v5.15 档案 → task-archive 模板），到最后还在说「我还差版本主档的骨架格式，读完就落盘」——**读了一堆仍觉得没准备好、永远差最后一个参考、就是不落盘**。这类「开放式、无锚点、格式要求高」的任务里，谨慎的模型极易过度斟酌。

两者叠加 + extended-thinking + SDK「无可见输出自动催」的机制，把「拿不定主意」忠实翻译成了反复空转。**SOP 侧对策（`roles/feifei.md`）**：① **两顶帽子改按「这一轮手上有没有文件/任务档案工具」区分、不看渠道名**——运行时她分不清"自己在企微还是看板"，但"手上有没有工具"是确定的：有＝看板主人格、老板说开工即授权、建档案/派工是本职；只有企微纯 I/O 工具才守「只登记不开工」。并显式写明「上一条『企微没有开工权』只约束企微那顶帽子，绝不能套到看板动作上」。② **新增红线 11「先落骨架再迭代」**：最多各读一个近例+模板就 `Write` 出骨架落盘，禁止为凑完美格式反复读参考却不落盘，一轮内落不了盘就 `【等你拍板】` 说卡在哪。③ **巡视判据补进这两种空转**，让小呆呆能识别逼回。

**追问「她能知道消息来自哪个渠道吗」→ 不能，于是再补一刀显式上下文**：核代码坐实——企微与看板是**两条分开的会话**（企微 → `personaReply` 轻量人格、无文件工具、系统提示写死「你在企业微信里」，且该路还被看板「整理需求」ingest 复用而使那句失真；看板 → 重量级 `startRun` run，`buildRolePrompt` 只把角色文件全文 append 上去、传入的 `kind` 根本没用、**无任何渠道字段**）。**消息本身不带渠道标签**，她运行时只能靠 企微-centric 的身份自述脑补——这正是她把看板 run 误当企微的机制根源。既然「渠道」信号不可靠/缺失，就不该让判断依赖它：一方面判据钉在「手上有没有工具」（她能确定观察到的事实），另一方面在 `startRun` 里**仅对菲菲**追加 `FEIFEI_BOARD_CONTEXT`，把「本轮=看板主人格、有全套工具、非企微、老板说开工即授权」作为**确定事实**直接钉进系统提示，取消她"靠感觉猜渠道"的环节（只注入真实工作 run，会议只读不注入）。

**关键取舍（引擎 vs 角色，两层各treat各的）**：空转是「机制放大 + 角色误判」的合力，**两层都得治**——只修引擎（兜底不假绿）会让她继续空转、只是不再假装成功；只修角色（讲清边界）则挡不住别的员工/别的情形再触发同类空转。所以引擎侧加**通用**的空转熔断（对全体员工、任何空转成因都兜底暴露），角色侧加**针对性**的边界厘清 + 反完美主义规则（治菲菲这次的具体成因）。这与 §3.55/§3.57「机制兜底 + SOP 红线双管」一贯。

**通用教训**：**一个 agent「反复空转/不产出」往往不是单纯的模型能力问题，而是「它给自己叠加了一个自相矛盾的约束」+「任务开放无锚点诱发完美主义」的合力。** 修法要分两层：机制层做通用兜底（把病态如实暴露、别假绿），角色层拆掉那个自相矛盾（这里＝按能力而非渠道名判身份）并给开放任务一个「先落骨架」的强制锚点。尤其警惕**过度反省**——菲菲上一轮为「越界查进度」道歉时把自我约束放得过宽，下一轮就误伤了本职工作；纠偏话术要精确划界（越界的是 X，不代表 Y 也不能干），别让 agent 从一个极端荡到另一个极端。

**改动落点**：`app/server.js`（`SILENT_SPIN_NUDGES` 常量 + `beginTurn` 清零 `_sdkNudges` + `consumeStream` 数自催 + `result` 兜底闸 + `onTurnComplete` 空转红灯措辞；`FEIFEI_BOARD_CONTEXT` 常量 + `startRun` 仅对菲菲追加显式看板上下文）＋ `roles/feifei.md`（身份权威源两顶帽子按能力区分 + 红线 11 先落骨架 + 巡视判据补空转）。`node --check` 绿、真实 session 回放通过。引擎改动（含 `FEIFEI_BOARD_CONTEXT`）**需重启 server**；`roles/feifei.md` 下轮起 run 即读取、无需重启。详见 CHANGELOG `[Unreleased]` 同名条目。


### §3.65 巡查宽限窗：聊天会话空停的「小呆呆接管倒计时」，补盲区顺带根治 §3.39 抢跑竞态（2026-08-10，用户复盘驱动）

问题：老板复盘菲菲周报会话（`20260803033333-0b13ac`）——她第二轮停在「我看下 v5.17 里有什么」这句思考块上，引擎 `_turnText` 兜底（§3.61）把这句意图当收尾、`fallbackDone` 假绿收工，活（看 v5.17、定周计划、出周报）没干完却**没有任何巡查介入**。追问「为什么小呆呆没兜」，查清：`patrolCandidate` 要求「挂了任务 或 写了『【等你拍板】无』」才算候选，聊天裸停两者皆无 → 事件版与定时版都不巡。这正是 §3.42 记过的已知盲区（聊天型 done + 无 marker 不进候选池）。

**为什么之前刻意不巡聊天停（原取舍）**：① 聊天是老板在直接对话，人就在跟前、回一句即可续，引擎抢着自愈是"抢话"且有竞态——§3.39（REQ-0259）就栽在事件版巡查抢在老板回话前几秒触发、把菲菲 resume 去交了棒，和老板紧随的新需求撞车；② 分不清「活干一半丢下」和「对话自然停顿」，得有个信号，`taskFile`/`【等你拍板】无` 就是"我在工作模式"的信号；③ 小呆呆高频轻量，每次聊天停都点火噪声/成本大。

**这次的解法＝落地 §3.39 当时搁置的「未取的 D」**：§3.39 复盘里写过一条没做的选项——「给事件版巡查加 ~90s 去抖 + 老板回话即取消来根除竞态」，当时因「要动热路径 + 给流水线自愈加 90s 延迟」而搁置。老板这次要的「8s 接管倒计时 + 可取消」正是这个宽限窗，且把两个顾虑都化解了：**① 8s ≪ 90s，延迟顾虑消失；② 只作用于聊天停、派工流水线仍即时**（有 `taskFile` 的自愈无人盯、不加延迟），热路径只在 `/reply` 入口加一句幂等的 `cancelGracePatrol`。于是一箭双雕：补上 §3.42 盲区（聊天停现在会被巡，只是延后可撤销），同时根治 §3.39 竞态（老板一回话，待派的巡视当场撤销）。

**几个设计取舍**：
1. **engine 权威、前端只渲染**——deadline 落 `run.patrolGraceUntil`（持久数字字段，避 §3.40 `stripPrivate` 丢弃），前端 rAF 按 deadline 倒计，自己不计时；多端一致、刷新/切窗不丢、关掉浏览器窗口照样到点派。前端计时会让"没人看的窗口永不触发"，违背"延后但终究要处理"。
2. **取消＝复用 §3.40 的 `patrolClearedSig`**——「取消接管」和「老板回话」都把这次停顿判为"老板自己接手了"，置 `patrolClearedSig=updatedAt`，连定时 sweep 也不再补刀；日后真续跑产出新停顿 → `updatedAt` 变 → 签名失配 → 自动重新纳入。不新造一套"已忽略"状态。
3. **判定一分为二**——抽 `patrolEligible`（纯"实质停顿"判据）作共用底座；`patrolCandidate`（＝eligible + 挂任务/marker）**收窄只给定时 sweep**用，避免低频扫描去复活远古闲聊；事件版聊天停走宽限窗、不靠 sweep。这样"即时/延后/兜底"三条路判据同源、职责清晰。
4. **重启补偿**——`rearmGracePatrols()` 启动时依 `patrolGraceUntil` 复原未过期窗口、已过期的立即补派，避免 8s 窗口正好卡在一次重启里丢掉。
5. **0=关闭**——`chainConfig.patrolGraceSec=0` 退回旧的即时接管，一键回退、留后路。

**验证**：`node --check` 绿；隔离 server 实测配置端点（默认 8 / clamp 0..120 / 只传该字段不冲 `enabled`，无 §3.35 回归）、seed 一条带未来 `patrolGraceUntil` 的聊天 done run 重启后 rearm 保住窗口、`patrol-cancel` 清窗口+落 `patrolClearedSig`、幂等、404。**真实空停触发 `scheduleGracePatrol`、到点 `fireGracePatrol` 拉起小呆呆、前端横幅动画三条依赖真模型+浏览器，需在运行中的 App 人工终验。**

**改动落点**：`app/server.js`（`patrolEligible` 抽取 / `patrolCandidate` 收窄 / `scheduleGracePatrol`+`fireGracePatrol`+`cancelGracePatrol`+`rearmGracePatrols` / `autoChain` 空停分流 / `/reply` 与新 `/api/runs/:id/patrol-cancel` 撤销入口 / `chainConfig.patrolGraceSec` + POST clamp + `patrol-status` 透出）＋ `app/public/{index.html,app.js,style.css}`（`#patrol-banner` + `showPatrolBanner`/`finishPatrolBanner`/`cancelPatrolTakeover`/`syncPatrolBanner` + 三条 SSE 接入 + 小呆呆弹窗 `pat-grace` 输入 + 横幅/倒计时/终态动画 CSS）。未改现有 SSE 事件形状/run 契约（仅新增持久字段 `patrolGraceUntil` 与三个 `patrol-*` 事件）；**需重启 server 生效**。详见 CHANGELOG `[Unreleased]` 同名条目。

### §3.70 跨线程消息不再硬注入正在跑的会话：每员工「待处理队列」+ 同线并入·跨线入队·收工排空（2026-08-11，用户复盘驱动）

**根因（老板反映「同一窗口完全乱掉」）**：所有 run 共用一个工作树 → 同员工不能并发两条会话，历史上遇到「别的员工给正忙的员工发消息」就用**塞进它当前正在跑的会话**当妥协（cc 走 `pushTurn`、return/`/reply` 走 `enqueueTurn` coalesce）。当来消息属于**另一条任务线**时，这条消息被灌进员工正在做的**另一件事**的上下文里——模型分不清「我到底在做哪件事」，输出错乱。妥协在**同线程**下没问题（用户对当前会话追问、同链 call/return 落回本会话本就是连续的），错只错在**跨线程**也一并硬灌。

**取舍**：不上「每会话独立 worktree 的真并行」（生命周期/隔离改动大，留后续）。改走**串行队列**——同员工仍同时只跑一条会话，但跨线程来消息不再污染当前会话，而是先扣在该员工的**待处理队列**，等它当前会话彻底收工空出来再**单独起一条新会话**处理。判据是「**来消息的任务线 == 目标当前在跑那条会话的任务线**」：`threadOf(run)=run.threadRootId||run.id`，复用 §3.49 `supersededBy` 的同线程 idiom。

**三条投递路径统一接入**（`app/server.js`）：
- **cc/抄送**：目标忙且**同线** → 维持 `pushTurn` 并入；**跨线** → `queuePending(kind:'cc', deliver:'new')`，工具回执改为「已排入待处理队列，忙完当前会话后单独起会话处理」。

**排空时机**：`handleStreamEnd` 末尾（takeover/retry 分支都提前 return，走到这里 = query 已 `clearLive` 释放且不重启 = 员工这条会话真结束）`if (!busyRunFor(emp)) drainPending(emp)`——FIFO 弹一条投递，投递后员工即忙，其余留队由下条会话收工链式排空。**持久化**（`runs/pending.json`，受 `OFFICE_LAB_RUNS_DIR` 隔离，仿 `MEETINGS_FILE`）：重启后全员空闲，`server.listen` 回调里逐员工 `drainPending` 一次自动排空，不丢跨重启的积压。`drainPending` 对「交回项但委托会话已被删」有兜底：用报告文本另起新会话，不静默丢结果。

### §3.81 迷糊「交回」被 QA 覆盖率闸门 fail-closed 静默吞掉 + 巡视对「有标记未执行」的盲区（2026-08-19，老板提问驱动）

**现象（老板发现）**：迷糊会话 `20260819013336-bfe74f`（v5.18 R2 测试会审·只读对齐评审）收尾里 `【交回】菲菲`、`【等你拍板】无` 都写了，却既没真回到上游、小呆呆也没报异常；手机端显示「✅ 收工」如常。

**根因（两条叠加、互相掩护）**：
1. **fail-closed 把合法交回一起吞了**。这条 run 从一条 **chat 线**（线程根 `20260818150348-a59ebb`「清 5.18 残留」闲聊）经 `spawnForward` 一路漂下来，`taskFile` 沿链继承为 `null`（档案只在派工正文里被引用、从未落到结构化字段）。`autoChain` 判迷糊「真交回上游」→ 进 QA 硬闸 `computeCoverageForRun(run)`，其首行 `if(!run.taskFile) throw 'QA run 缺 taskFile'` 抛错 → catch 走 fail-closed：**只 `appendEvent(⛔ QA 门禁计算失败)` 后 `return`**，`【交回】` 从未执行。安全门禁「宁可拦死」的设计，把一次**没有覆盖率可算、本就不该被它管**的合法回发也拦死了。
2. **巡视因「结果里有交接标记」把它当合法收尾放行**。`patrolEligible` 里 `parseReturnHop(result)` 一命中就 `return false`——但标记只是「写了」，autoChain 已在真正投递前 abort。**标记的「存在」被当成了「执行成功」**，于是事件版与定时版巡视全部跳过它 → 彻底静默死停、无人发觉。

**修复三处**（`app/server.js`）：
- **闸门不适用 ≠ 报错**（`autoChain` 迷糊分支）：`_gateApplicable = !!run.taskFile || _toBobby`。无 `taskFile` 且非「发波比(发测出货)」→ QA 覆盖率闸门**不适用**（没有 facet_doc / 覆盖率可算），直接放行到下方 return-hop 正常回发，且**不**派菲斯拉影子陪练（无档＝非正式 QA 裁决、无从审）；仅「发波比」这种真出货即便无档也仍拦（无档无从验证覆盖）。这直接让本例的 `交回` 恢复正常回发。
- **fail-closed 绝不静默死停**（新 `escalateBlockedHandoff(run, detail)`）：闸门真算不动 / 无档却要发测时，拦下交接的同时打**持久**「交接受阻」签名 `run.handoffBlockedSig = run.updatedAt`（非 `_` 前缀→跨重启有效）+ 立即推一条「⛔ 交接受阻·待接管」（`pushNotify` 本地 Toast + `sendBark`）给老板，不再只在时间线留行红字、手机端却报正常收工。
- **巡视破除标记豁免**（`patrolEligible`）：`handoffStuck = run.handoffBlockedSig === run.updatedAt` 时，不因交接标记而放行——让这次「写了标记但没执行」的未决阻断仍能被事件版/定时兜底捞到。同一个 `escalateBlockedHandoff` 也接到了 return-hop 的 `return-unknown / return-no-caller / return-busy / return-nosession` 等 stranded 交回上（此前它们同样是「广播 handoff-blocked 后静默 return」）。

**为什么不给 chat 线自动补绑 taskFile**：本例是「只提问不写用例」的对齐评审，若强行把正文里的档案路径绑上去再跑覆盖率闸门，反而会要求它给出本阶段根本不产出的 RED 校准，把一次干净的回发变成无休止的覆盖率 bounce。正确语义是「**无档＝闸门不适用、放行**」，而非「猜个档来跑闸门」——把不该跑的门跑起来，比不跑更糟。

**验证**：`node --check` 通过。未改 SSE 事件形状 / run 契约（仅新增持久字段 `handoffBlockedSig` 与一条 `reason:'escalated'` 的 `handoff-blocked` 广播）；**运行时的真机回发与巡视重新纳管依赖真模型多员工会话，需在运行中的 App 终验**。**需重启 server 生效**（走托盘、勿强杀）。详见 CHANGELOG `[Unreleased]` 同名条目。

### §3.85 托盘看门狗把「引擎在忙」判成「引擎死了」：替身撞端口自杀，伪装成「lab 崩溃好几次」（2026-08-20，老板报「崩溃好几次」）

**现象（老板报）**：「lab 崩溃好几次」。查 `app/runs/tray.log`：`12:30:04 被监控的外部服务已停止，托盘接管拉起` → `12:30:05 已拉起 node` → `12:30:31 已拉起 node` → `13:02:03 已拉起 node`，半小时内三次拉起，气泡一路弹「服务异常退出（code=1），正在自动重启」。

**取证结论：引擎自己一次都没崩。**
- `node.exe` 在 Windows 事件日志 / WER 里**零** APPCRASH 记录（同期只有 `chrome-headless-shell.exe` 在 `13:01:44` 报 `0xe0000008`、`svchost` 若干），无 OOM abort、机器没重启也没休眠 → 不存在「引擎自己崩」这回事。
- **run jsonl 的写入时间戳把真相钉死了**：`20260819175853-5f1b39.jsonl` 最后写入 `13:01:44`、`20260820045321-4d85db.jsonl` 写到 `12:57:25`。也就是说 12:30 被判死的那个实例，此后**又正常干了半小时活**，一直到 13:01:44 才真的走。
- 推论：12:30 那两次拉起的 node **必然撞 EADDRINUSE**（端口 4800 被仍在干活的真引擎占着）→ 走 `server.on('error')` 的 `process.exit(1)` → 托盘记为「异常退出 code=1」→ 4s 后自动重启 → 再自杀。**用户感知的「崩溃好几次」= 替身自杀的气泡串**，真引擎全程在跑。

**根因（三条，全在 `tray/office-lab-tray.ps1`，同一个认知错误的三处复发）**：把「**服务是否活着 / 端口是否被占**」这个**内核事实**，用「health 能不能在 1~2 秒内应答」这个**性能指标**去代理。引擎忙一下（多会话流式 + jsonl 落盘 + §3.83 新上的大响应 br 压缩）就被判死：
1. **心跳单次超时即判死**：监控模式下 `Invoke-RestMethod -TimeoutSec 2` 一次 catch 就 `Write-TrayLog '被监控的外部服务已停止'` 并直接 `Start-Server`。一次抖动 = 死亡判决书。
2. **判死时把把手扔了**：同一分支 `$script:monitorPid = $null`。此后托盘**再也管不到真引擎**——`$manageable` 只认 `running` 状态下的 monitorPid，右键「停止/重启」只作用于那个自杀的替身。这正是为什么最后只能手动硬杀（`13:01:44` headless chrome 被连带打崩即其指纹），而不是走优雅退出。
3. **防重复拉起的判据也是 health**：`Start-Server` 里 `-TimeoutSec 1` 应答与否当作「端口是否有主」。注释里写得明明白白「不重复拉起，否则 node 撞 EADDRINUSE 变僵尸」（§2026-07-28 的老教训），**这道防护被 1 秒超时从内部绕过了**。

**两个观测缺口（所以事后什么现场都不剩）**：
4. cmd 重定向是 `> "$OutLog" 2> "$ErrLog"`（**截断**）。三次拉起相隔 4~30s，替身写下的 `[fatal] 端口 4800 已被占用` 被下一次拉起当场冲掉，三轮全没。
5. 崩溃自动重启分支**只弹气泡不写 tray.log**（退出码不落盘），tray-owned 的 `Stop-Server` 也不记一行 → 事后**无法区分「用户点了重启」和「进程崩了被自动重启」**。排查时正卡在这个二义性上，只能靠 jsonl 时间戳侧面还原。

**修复（五条，全在托盘侧；引擎一行未改）**：
- **端口有没有主，只信 TCP 监听表**：新增 `Get-PortOwnerPid`（`Get-NetTCPConnection -State Listen`，失败退回 `netstat -ano`）。`Start-Server` 先查监听表——端口有主就**绝不拉第二个 node**；再探 health 只用来区分「活着且响应」（→ 监控模式）与「占着端口但不应答」（→ 监控-unhealthy，不拉替身）。
- **一次超时不算死**：心跳新增 `$script:probeFails` 连续失败计数，满 3 次（≈12s）才允许判死，单次超时提到 3s（没提到 5s：心跳跑在 WinForms UI 线程上，阻塞太久会连累托盘菜单响应）。
- **判死也不丢把手**：连续失败但端口仍有主 → 判「卡顿而非退出」，`monitorPid` 校准为端口主 PID 并保留；只有「连续 3 次失败 **且** 端口无监听」才认定真退出并接管拉起。`$manageable` 同步放开到 `unhealthy` 状态——卡顿/半死实例正是最需要「停止/重启」接管清理的时候，原先菜单恰恰在此刻灰掉。
- **保住崩溃现场**：新增 `Archive-Log`，启动前把非空旧日志**追加**进 `server.{out,err}.history.log`（带转存时间/字节数分隔线），再让 cmd 照旧截断写新一轮 → 历史全留、单轮日志不互相穿插、history 超 4MB 滚存一份 `.1`。
- **崩溃与停服都留痕**：崩溃分支写「异常退出 code=N，自动重启第 M 次」，**并顺手记下当时端口的占用者**（`code=1` + 端口另有其主 = 撞端口自杀的指纹，日志里一眼可辨）；达上限、以及 `Stop-Server`（区分「用户操作 / 程序内部」）各补一行。

**取舍**：没有走「拉起前先 kill 端口占用者」这条路——那等于把误判从「多起一个自杀进程」升级成「误杀正在干活的引擎」，代价反了。也没有取消崩溃自动重启（真崩时它是对的），只是把「什么叫崩了」的判据从性能指标换成内核事实。

**验证**：PowerShell AST `ParseFile` 无错；把 `Get-PortOwnerPid`/`Archive-Log` 从真文件里抽出来跑自测——`4800→11004`（当时的活引擎 PID）、`4700→32112`（vite）、`59999→0`（无监听）；`Archive-Log` 连转两轮各留一条、实质空日志跳过（自测中抓到「只判字节数会把 BOM+换行的空日志也转存」，已收紧为 `IsNullOrWhiteSpace`）。**「误判→自杀」的整链真机复现需要制造一次引擎卡顿，未做**；**改动需退出并重开托盘才生效**（托盘有单实例互斥锁，直接再起会静默退出）。


### §3.101 同一次停顿把两道防线一起打穿：空转闸的判据挂在「文本信号」上被绕过，巡视员的升级又被降噪吞掉（2026-08-24，老板提问驱动）

**现象（老板原话）**：「看一下 20260824015731-60a5b7 会话，怎么中断了而且小呆呆巡视没有巡视到」。

**查完是两个独立的坑，且第二个把第一个盖住了**——中断没被判成异常（所以没人被告警），巡视员其实巡到了但结论没人看见（所以像没巡）。两者叠加的净效果与 §3.61、§3.81、§3.84 是同一族：**一次该被看见的停顿，彻底静默。**

#### 坑一：空转熔断的判据挂在「SDK 注入的那句话」上，而这次 SDK 没说那句话

逐 jsonl 定位（`app/runs/20260824015731-60a5b7.jsonl` 尾部）：

| 时间 | 事件 |
|---|---|
| 02:01:17 | `tool_use` Read v5.19 任务档案（前一句文本＝「…先读它。」） |
| 02:01:19 | tool_result 返回（档案很长） |
| 02:02:10 | assistant `msg_…kQ3i6` —— **只含一个 thinking 块**，无 text、无 tool_use |
| 02:02:53 | assistant `msg_…kTrFsk` —— **又只含一个 thinking 块** |
| 02:02:53 | `result` `subtype:"success"` / `is_error:false` / `result:""` |

两条 assistant 的 `message.id` 不同、`cache_creation` 8738→8767 只差约一个思考块的量 —— **这是两次独立的 API 请求**，即 SDK 自己已经重试过一次，第二次仍只吐思考块才放弃。所以它**是** §3.61 那种空转，只是走了另一条路：

**§3.61 装的闸只认「`no visible output` 那条 user 消息文本」**（`run._sdkNudges`）。当年校准阈值时看到的空转形态是 `claude.exe` 注入一句 `[Your previous response had no visible output. Please continue…]` 逼模型再说；判据就挂在这句话上。可 SDK 还有一条路——**直接重发请求，一条 nudge 都不注入**。于是 `_sdkNudges` 恒为 0、闸门形同虚设 → `_turnText` 兜底照常开火，取上一句陈旧文本「…先读它。」当收尾 → `status:done` + `isError:false` + **✅ 绿灯**。

**这就是 §3.61 修的那个「兜底假绿」原封不动地复发了一次，只不过绕过了当初专门为它装的闸。**

**对策：判据从「文本信号」换成「事实」。** 新增 `barrenTurns()`——数本轮**零产出顶层 assistant 消息**（该 `message.id` 全程既没吐过 text、也没发起 tool_use ＝ 纯 thinking）；`isSpunTurn()` 改为 **`_sdkNudges` 达阈 或 零产出轮次达阈（`BARREN_TURN_LIMIT`=2），任一即判空转**。旧闸保留（它对它那条路仍然有效），新闸补上它照不到的角。判空转 → 不许用残留旧文本假绿 → `result` 保持空 → 落 `onTurnComplete` 的红灯 + `_emptyStreak` 累加，与 §3.61 现行哲学完全一致（**不假装成功、不自动接管、恢复权交回老板**）。

三个必须踩准的实现细节，任一错了新闸就变成新的误报源：

1. **必须按 `message.id` 归并**。SDK 把一条 assistant 消息**按内容块拆成多次透传**（thinking 一次、tool_use 再一次，`message.id` 相同）——这是常态形状。按「每次透传算一条」去数，**每一个「先思考后调工具」的健康轮次都会被记成空转**。
2. **只数顶层消息**（`parent_tool_use_id` 为空）。子 agent 自己那轮空转与本轮收尾无关，计进去会让「派了 Task 的正常轮」随机变红。
3. **阈值必须 > 1**。单条纯思考正是 §3.61 迭代对策要救的「说了真话、只是结尾停在思考块」，一刀切会把那类合法轮重新打回红灯——修 A 类别把 B 类修回来。

顺带修掉一处旧疏漏：**SDK 后台 settle 后自动续跑的轮次不走 `beginTurn`**、计数器不归零，于是上一轮的零产出会串到这一轮。补在「首个 assistant 且 `_turnActive` 为假」处清账（`_turnMsgs` 与 `_sdkNudges` 一起）。

#### 坑二：巡视员判了、升级了，但推送被降噪逻辑吞掉，同时还把「已裁决」签名盖上了

**小呆呆其实巡到了**，而且很及时——事发 16 秒后（02:03:09）就派出 `20260824020309-2e5946`，判定也合理：「对端就是老板本人在直接发问，按判据这种情况默认不续，留给老板决定下一步」，还抛了一张 `decision` 卡给老板三选一。

但它正文只写了白话「无需我方动作，等你拍板。」，**没写标记行** `【等你拍板】<事项>`。于是：

1. `parsePendingGate()` 返回 null；
2. `maybePushRunStopped()` 里那行降噪守卫（「巡视 run 除非以真门收尾否则不推」，当初为治「每条巡视都弹一次 toast」而加）**把整条推送吞了** —— 托盘 Toast、手机 Bark 一条都没发；
3. 雪上加霜：`autoChain` 那条「巡视 run 收工且没 resume → 给目标盖 `patrolClearedSig`」（§3.40 裁决落库）同时生效，菲菲那条 run 被标记「这次停顿已裁决」→ `patrolEligible` 直接 false → **定时 sweep 也不再补刀**。

净效果：**巡到了、判了、升级了，老板全不知情**，而且这次停顿被永久封存为「已处理」。老板的体感「小呆呆压根没巡」完全成立——从他能看到的任何界面上，这趟巡视等于不存在。

**对策：宁可多推、不漏升级。** 新增 `patrolEscalating()` 取代「只认严格标记」：规范标记 / `decision` 卡 / 白话请示正则（`PATROL_ESCALATE_RE`）任一命中即算升级、必推；推送的 `gate` 字段也给个兜底文案，别让一条升级看着像普通收工。

**关键的一层反向护栏（自测当场抓到）**：必须先放过「显式写了 `【等你拍板】无`」的那类——那是协议里「合法收工·无需动作」的规范收尾。少了这层，兜底正则会把标记里「等你拍板」**四个字本身**当成白话请示，于是**每一条判合法收工的巡视都弹一次 toast**，§降噪的初衷当场作废。唯一例外：标了「无」但同时抛了 `decision` 卡 → 仍判升级（卡就是在问老板）。

**SOP 侧同步收口**（`.claude/agents/chaorenq.md` 是引擎实际加载的工牌，`roles/chaorenq.md` 同改）：红线新增「升级必须落标记行」（`decision` 卡只是选项载体、不替代标记行；并明写「引擎已加白话兜底，但那是**保险丝不是许可证**」）与「`resume_employee` 不许拿占位符试探」——同一趟巡视里它先调了一次 `runId:"skip"`、白报一个 `[续跑失败：找不到会话 skip]`。

#### 通用教训

1. **「判据挂在哪」比「阈值调多少」重要得多。** §3.61 的闸门本身是对的、阈值也校准过，但它把判据挂在**上游某个组件恰好会说的一句话**上。上游换了实现（改成静默重发请求），判据就整条失效——而且**失效方式是静默的**：闸门还在、代码还在、日志上什么都不缺，只是永远不触发。判据应当挂在**本层能直接观测到的事实**（这一轮到底有没有产出 text/tool_use），而不是**别人给的信号**。这与 §3.58「面板状态要派生自唯一事实源」、§3.61 结尾「信号要选那个真正区分对错的、最靠近事实的量」是同一条主线的第三次复发。
2. **降噪与「不漏告警」是一对张力，缺省必须偏向不漏。** 那行降噪守卫本身是对的需求（每条巡视都弹 toast 确实骚扰），但它把「要不要惊动老板」的判断**完全外包给了被巡者自己的措辞格式**。凡是「靠下游正确书写某个格式才能触发告警」的设计，都要假设它有一天写不对——**兜底识别 + SOP 硬要求，两手都要有**（引擎侧兜底是保险丝，SOP 侧仍要求写标记，不能只留一边）。
3. **「已裁决」类的封存签名，必须与「老板真的被通知到」绑定。** §3.40 盖签名是为了治「同一会话被巡 7 次」的死循环，方向没错；但签名一盖就**同时关掉了事件版和定时版两条兜底**，此时若通知那条路是断的，这次停顿就再也没有第二次机会。**任何「不再重试/不再检查」的闭合动作，前提是它闭合前那次输出确实到达了人。**
4. **同一族 bug 修过一次不代表关上了门。** 本节坑一是 §3.61 的复发（同一个 `_turnText` 兜底、同一种假绿），坑二是 §3.81/§3.84 的复发（「写了/没写某个标记」被当成万能免检符或万能静默符）。三次都栽在「**把一个布尔判断托付给模型的措辞**」上。凡是这种托付，都该在引擎侧留一条**不依赖措辞**的旁路。

**改动落点**：`app/server.js`（新增 `barrenTurns`/`isSpunTurn`/`BARREN_TURN_LIMIT`/`patrolEscalating`/`PATROL_ESCALATE_RE`；`beginTurn` 加 `_turnMsgs`；`consumeStream` 加按 id 归并的产出记账与跨轮清账；`maybePushRunStopped` 换判据并加 `gate` 兜底）、`.claude/agents/chaorenq.md` + `roles/chaorenq.md`（红线两条 + 白话不算升级的说明）、`app/test/spin-and-patrol.test.js`（新，12 例）。未改 HTTP 端点 / SSE 事件 / run 形状 / 标记解析等前后端契约。

**验证**：`node --check` 通过；**先拿两条真实事故 jsonl 回放校验**（菲菲那轮：barren=2、nudges=0、判空转、不再兜底、`result` 保持空 → 落红灯；小呆呆那条：`parsePendingGate` 确实抽不出门＝复现旧漏，而 `patrolEscalating` 判 true ＝ 会推送），**回放当场照出上面那个「`【等你拍板】无` 被误判成升级」的反向 bug**、修完复跑全绿。随后把回放固化成**不依赖 runs 数据**的回归测试（server.js 是 import 即 listen 的单体，无法直接 import 纯函数，故按名从源码抠出定义再 eval；抠不到即抛错，日后重构改了函数名会立刻红）。全量 `npm test` **80/80 通过**（原 68 + 新 12），跑测试带 `OFFICE_LAB_RUNS_DIR` 隔离、未碰生产 `runs/`。**改动需重启引擎才生效**（§3.3 结尾的老教训：代码改了不重启 = 老坑照踩）。

## 3.105 「关掉那个终端窗口整个程序就没了」——托盘对 web 端口只旁观不接管，故障现象与真凶隔了三层（2026-08-26）

**用户报的**：启动托盘之后有一个残留的终端窗口，关掉它整个程序都关掉了。

**排查过程值得记，因为我第一版判断是错的。**

### 错的那一版：Windows Terminal 控制台移交

第一反应是：默认终端已是 Windows Terminal（实测 `HKCU:\Console\%%Startup` 的 `DelegationTerminal = {E12CFF52-…}`），于是 `启动托盘.cmd` 里 `start "" powershell -WindowStyle Hidden` 的控制台被移交给 `WindowsTerminal.exe`——窗口属于 Terminal 而不属于 powershell，`-WindowStyle Hidden` 与脚本内的 `ShowWindow(SW_HIDE)` 双双失效。听起来严丝合缝，而且能解释「日志写着已隐藏、窗口却还在」。

**实测把它否掉了**：照 `启动托盘.cmd` 的原样起一个 powershell，结果是 `MainWindowHandle=0`、子进程是 `conhost.exe`、`GetConsoleWindow()` 返回**非 0**（所以脚本内隐藏有效）。三条正式入口（`.cmd` / `.vbs` / 开机自启 `.lnk` → `wscript` → vbs）**都不留窗口**。

> 顺带一个反直觉的观测：同样一句 `GetConsoleWindow()`，在**继承现成 ConPTY** 的进程里返回 0（我从 git-bash 里跑的探针就是），在 `start` 新起的进程里返回非 0。所以「拿 GetConsoleWindow 判自己有没有窗口」本身就依赖启动方式，不是个稳定判据。

### 真凶：托盘对 4700 只旁观不接管

进程树一拉就清楚了。当时机器上挂着**四条手工终端起的前端链**（父进程全已死＝终端早关了，只剩孤儿）：

```
[4868] sh.exe  corepack pnpm preview      ← 真正占着 4700 的那条
  └ corepack → cmd /c vite preview → vite(node)   ← 监听 4700
[39688] sh → pnpm build:watch
[30200] bash → npx vite --port 4700       ← 抢端口输了的重复实例
[33580] cmd → corepack pnpm dev
```

而托盘的 `Start-Web` 当时是这么写的：

```powershell
try { Invoke-WebRequest "http://127.0.0.1:$WebPort/" -TimeoutSec 1 | Out-Null; $webBusy = $true } catch { $webBusy = $false }
if ($webBusy) { Write-TrayLog "新 UI 端口 $WebPort 已在跑，跳过拉起"; return }
```

**一句日志，然后 return。** 托盘把自己降级成旁观者：界面的实际宿主是那个手工终端，托盘既不知道、也不告诉用户、更接管不了。于是——

- 关掉那个终端窗口 → `sh.exe` 死 → 它下面的 corepack/cmd/vite 全死 → **4700 没了**；
- 而引擎（4800）是托盘用 `CreateNoWindow` 起的、父进程早退、孤儿运行，**毫发无伤**。

**用户感知「整个程序都关掉了」，实际死的只有界面。** 故障现象（关一个看似无关的窗口）与真凶（几天前某次手工 `pnpm preview`）隔了三层，几乎不可能自行归因。实测坐实：清掉那四条链后 4700/4701 双双落地，4800 依旧 200。

### 为什么这是个真缺陷，而不是「用户不该手工起」

**引擎侧早就有对称的正确做法**：端口被占时转「监控模式」，记下 `$script:monitorPid`、弹气泡明说「已接管，可右键停止/重启」，右键停服时 `taskkill` 那个外部 PID。**web 侧缺了这一整套**——同一个托盘里，两个端口一个有主人、一个没有。

不对称本身就是 bug 的温床：引擎那条路被 2026-08-20 那次事故（§3.85）打磨过，web 这条路从没被逼问过。

### 对策（把引擎那套原样搬过来）

1. **端口真伪判定统一走 `Get-PortOwnerPid`**（TCP 监听表＝内核事实），不再拿 HTTP 探测当代理——这条 §3.85 的结论早写在「端口真伪判定」那段注释里，web 侧漏用了。
2. **`Test-IsDescendant`**：`$script:webproc` 拿到的是 **cmd 外壳** PID，真正监听 4700 的是它下面好几层的 vite node，**直接比 PID 永远不等**，会把自己起的也误判成外部。沿 `ParentProcessId` 上溯判子孙关系才对（实测能穿过 `sh → corepack → cmd → node` 四层）。
3. **外部占用 → 转 web 监控模式**：记 `$script:webMonitorPid`、日志点名到具体进程与命令行、弹气泡明说「⚠ 关掉那个终端窗口界面就会没（引擎不受影响）」。
4. **`Stop-Web` 支持接管收编**：「重启服务」时把外部那棵树也停掉，并沿祖先链把同属这条前端链的 `sh/corepack/cmd` 一并收（只杀叶子的话祖先会立刻再拉一个占回端口）。
5. **安全护栏**：只杀「进程名 ∈ node/cmd/sh/bash/pwsh/powershell 且命令行含 vite|pnpm|npm|corepack|office-lab|web」的；4700 万一被无关程序占着（实测拿 `python -m http.server` 试过，判 False）**不擅自动手**，只记日志。
6. **托管方露脸**：托盘状态行加 `界面⚠外部托管(PID xxx)`，状态气泡加「引擎托管 / 界面托管」两行。**不露脸正是这次归因难的根源。**

### 通用教训

- **「跳过」是个危险的默认**。`if (busy) { log; return }` 读起来无害，实际是把一个资源的所有权悄悄让给了未知第三方，而且不留把手。凡「发现别人占着就跳过」的地方，都该问一句：**那之后谁负责它？用户怎么知道？我还能不能收回来？**
- **同一进程里管着两种资源，处置方式必须对称**。引擎有监控模式而 web 没有，不是"web 比较简单"，是 web 那条路还没被事故逼问过——不对称就是下一个 bug 的位置。
- **排查时先证伪自己最漂亮的假设**。Windows Terminal 移交那套解释太顺了，顺到我差点直接照它改；实测五分钟就否掉了。**能被一条命令验证的假设，别拿它当结论。**

**改动落点**：`tray/office-lab-tray.ps1`（新增 `Test-IsDescendant` / `Describe-Proc`；`Start-Web` 换判据 + 转监控模式 + 气泡告警；`Stop-Web` 加接管收编 + 安全护栏；`$script:webMonitorPid` 状态位；状态行与状态气泡露出托管方）。未改引擎、前端与任何前后端契约。**托盘需重启生效**（本次已重启并实测：外部占用能被认出、接管能释放端口、非前端进程不误杀、托盘子树零可见窗口）。

## 3.109 会话会「自我毒化」：一次空转把整条会话变成绝症，而引擎唯一的恢复动作是把病灶重新喂回去（2026-08-31，老板提问驱动）

### 起因

老板问：「lab 的员工经常有中断的问题，需要减少、杜绝；而且**会话怎么可能出现不能恢复的情况**？」

直接触发是 run `20260831080340-e5f6c2`（菲菲 / session `55b19d93`）：改 v5.21 五张 facet 表的表头，改完两张就停了，老板回「继续」又空转一轮，引擎第二次红灯写的是「请勿再回复继续，直接新开话题」。活儿留在半截（`docs/示例项目需求/06-v5.21/…` 里 61/92 行是新表头、126/159/187 行还是旧的）。

### 现象与量化（先把「偶发」这个假设证伪）

引擎自己的 run jsonl **丢掉了 `stop_reason` 与 `output_tokens`**（`normalizeEvent` 只留 `message` 的透传形状，而 SDK 透传的是**未定稿的增量消息**、`stop_reason` 恒为 null），所以只看引擎日志永远只能看到「纯思考、无产出」这个表象。这次改去翻 CLI 自己的会话档 `~/.claude/projects/D--Work-Projects/*.jsonl`（864 条、21,984 条顶层 assistant 消息），才拿到真判据：

| 指标 | 值 |
|---|---|
| 零产出消息（只有 thinking，无 text 无 tool_use） | 87 / 21,984 = **0.40%** |
| ↳ `stop_reason=end_turn`（模型自己收嘴） | **82** |
| ↳ `stop_reason=max_tokens` | 4，且 `output_tokens` **清一色 64,000** |
| 受影响会话 | 19 / 864 |
| 引擎侧空收工轮 | 74 / 2,589（2.9%），36 条 run |

而决定性的一条是**条件概率**：

```
P(下一条零产出 | 上一条正常)   =  0.26%   (55/21054)
P(下一条零产出 | 上一条零产出) = 40.5%    (32/79)      ← 156 倍
```

19 条会话吃掉了全部 87 条（`11/60`、`9/23`、`8/22`、`6/17`…）。**一坏就成串** —— 这不是运气，是第一次失败**导致**了后面的失败。

### 根因一：思考从来没有天花板（那道闸整整失效）

`THINKING_BUDGET = { heavy: 24000 }` 的注释写着「防一轮想 3 万+ token 失控」，实现却只是把数字塞进子进程 env `MAX_THINKING_TOKENS`。而 SDK 类型定义里白纸黑字（`sdk.d.ts` 的 `maxThinkingTokens` @deprecated）：**Opus 4.6 起该值只当 on/off 用**（0=关，非 0=adaptive），数字本身被丢弃。

于是 08:34:01 那条消息 `stop_reason=max_tokens`、`output_tokens=64000` —— 模型把**整个输出上限**烧在了一个思考块里，21 分 47 秒，零产出。全库仅有的 4 次 `max_tokens` 全是整齐的 64,000，全是这个洞。

**改成非 deprecated 的 `thinking: { type:'enabled', budgetTokens }` 之后，实测依然不封顶。** 同一道心算题：

```
budgetTokens=1024    thinkingSig= 7852   output_tokens=3132
budgetTokens=16000   thinkingSig= 4320   output_tokens=1772
```

小预算那次反而想得更长。原因在 SDK 源码里：`thinking:{type:'enabled',budgetTokens:N}` 与 deprecated 的 `maxThinkingTokens:N` **翻成同一个 `--max-thinking-tokens N` flag**，Opus 侧一并按 adaptive 处理。

> **所以这条的结论不是「换个 API 就好了」，而是「平台侧此刻给不了硬顶，硬顶必须自己做」。** 若当时止步于「改成新 API」就交付，等于交了一个没验证的假修复——**能被一次实测证伪的假设，别拿它当结论**（同 §3.105 那条教训，两周内第二次用上）。

### 根因二：唯一的「恢复」动作，是把病灶重新喂回去

CLI 的行为已经查清（会话档 `#69→#70→#72`）：模型吐一条纯思考 → CLI 注入一次 `[Your previous response had no visible output. Please continue…]` → 再吐一条纯思考 → CLI 放弃、`result` 为空但 `subtype=success`。引擎红灯，老板回「继续」，引擎 **`options.resume = run.sessionId`**，于是：

- 上下文里躺着 6 条「我思考完了然后什么都不说」的**它自己的前例**，其中一条是 64k token 的巨型思考块；
- 模型照着自己的历史学，再演示一次；
- **每空转一轮，就往 transcript 里再追加一条坏样例。**

这就是那 156 倍的机制。「不可恢复」不是物理定律，是**引擎缺一个恢复动作**——它只会 resume，不会裁毒尾、不会换会话、不会重新播种。

### 对策（三条，按「防触发 → 早熔断 → 真恢复」排）

1. **空想失控刹车（引擎侧唯一真正生效的硬顶）**：`THINKING_RUNAWAY_TOKENS = 30000`，靠 SDK 的 `thinking_tokens` 心跳实时盯住**单段连续思考**，破顶当场 `abort` 并带一句明确纠偏 resume（「别再一次性推演完整个方案，立刻做下一个最小具体动作」——只说「继续」它很可能接着想）。取值依据：健康消息 `output_tokens` p99.9 = 15,682、最大 28,428，30k 不误伤；失控那次是 64,000，30k 能在烧掉一半前截停。
   估算值的语义（每块重置 / 全轮累计）SDK 没承诺，**两种都得吃**：读数回落即视作按块重置、基线清零；否则以「上一个内容块定稿时的读数」为基线算增量。两种语义下顶都是「这一段连续思考 30k」。
   **掐得早还有个关键副作用：那坨巨型思考块进不了 transcript，会话因此不会被毒化。**
2. **早熔断**：`finalizeTopMsg` —— 顶层消息换 `message.id` 即结算上一条是不是零产出，**连续 2 条**（`BARREN_ABORT_STREAK`）判中毒、当场掐断本轮。旧逻辑要等轮末 `result` 才判，那时 CLI 已自催过一次、又追加了两三条坏样例。中间夹一条正常消息即连击归零 —— 单条零产出有约六成能被 CLI 自催救回来，不误杀。
3. **真恢复：换会话，而不是 resume**。判中毒即**弃用该 `sessionId`**、起一条全新会话，由引擎组装交接播种：任务档案路径 + 进度快照 + 最后一条指令原文 + 员工自己说过的最后两段话 + 最近 15 个工具动作，**全部取自引擎侧事实（run jsonl / `_snapshots` / `run.taskFile`），不靠模型回忆**，并明写「不要从头重来、不要重复已落盘的改动」。自动重开限 1 次（`MAX_SPIN_RESEEDS`）兜住烧钱死循环；额度用尽后**老板回任意一句话也走换会话**，那句话作为「老板刚说」附在交接后面。

> 为什么敢自动重开：§3.61 曾试过「自动热推纠偏续跑」并回退，但那次退的是 **resume 同一条坏会话**（会把 run 锁在 running 数分钟、`/reply` 409 拒收用户消息）。这次换的是**新会话**，且 `/reply` 侧的无感排队/接管机制（§3.70）此后已经补齐，那条退因不再成立。上限设成 1 次也是照顾这一点。

### 顺带查清的两处旧账（本次未改，记账）

- **`_sdkNudges` 判据恒为 0**。§3.101 当时只是**怀疑**「SDK 直接重发、不注入 user 消息」，这次在 CLI 会话档里看到了真相：CLI **确实注入了**那句 `no visible output`（`#70` / `#81`），但它是 `isMeta: true` 的消息，**SDK 不透传给消费者**。所以那条判据从写下的那天起就是死的，真正在起作用的一直是 §3.101 补的「零产出轮次」。
- **run jsonl 丢了 `stop_reason` / `output_tokens`**，导致引擎自己分不清「想爆了（max_tokens）」和「模型收嘴（end_turn）」——这次诊断必须去翻 CLI 私有档才做得下去。补上是廉价的，诊断价值很高。

### 通用教训

- **「护栏写了」不等于「护栏生效」。** 这道思考顶带着一段言之凿凿的注释活了很久，而它在模型升级到 Opus 4.6 的那一刻就静默失效了——没有任何报错、没有任何指标掉头。**凡是依赖外部平台语义的护栏，都要有一条能证明它此刻仍然生效的观测**，否则它只是一句注释。
- **自愈动作必须先问「病灶在哪」。** resume 之所以救不回来，是因为病灶就写在被 resume 的那份 transcript 里。**任何「重试」机制都该先回答：我重试的输入，包不包含上次失败的原因？** 包含就不是重试，是复读。
- **条件概率比总量更能定性。** 0.40% 的零产出率看着像噪声，可 0.26% → 40.5% 这个跳变一眼就说明它是自我强化的。**判断一个故障是"偶发"还是"会滚雪球"，看 P(再犯|已犯)，别看总占比。**
- **引擎自己的日志要留得下判据。** 表象（纯思考、无产出）在 run jsonl 里，真判据（`stop_reason`）在 CLI 私有档里——这条边界让一次本该十分钟的归因变成了翻两套日志。**观测口径要覆盖到"你将来会拿它做什么判断"。**

**改动落点**：`app/server.js`（`THINKING_RUNAWAY_TOKENS` + `brakeRunawayThinking` + `handleControlMsg` 的 `thinking_tokens` 分支；`BARREN_ABORT_STREAK` / `MAX_SPIN_RESEEDS` + `finalizeTopMsg` / `markPoisoned` / `canAutoReseed` / `tailRunEvents` / `buildReseedPrompt` / `reseedPoisoned`；`handleStreamEnd` 新增 ①.5 中毒换会话与 ①.6 空想纠偏两个分支；`shouldAutoRetry` 拒绝 resume 中毒会话；`onTurnComplete` 判中毒并触发重开、红灯文案改为「引擎正在换会话」；`/reply` 中毒时走换会话且放宽 `sessionId` 409 守卫；三条 query 统一走 `thinkingConfig()`、不再用 env）、`app/test/session-reseed.test.js`（新，17 条）。**引擎改动，需重启生效（走托盘，别强杀）。**

### §3.111 抄送(cc)的终点是悬空的：三方会审「全都判合法收工」，然后永久停在「_待菲菲汇总_」（2026-09-01，老板：「怎么三方会审也会中断」）

**现象**：菲菲在 run `20260901063554-dc604c` 里发起 REQ-0326~0330 五条三方会审——`cc_colleague` 双发：GG Bond 做技术体检（`20260901065038-18c917`）、迷糊做可测性体检（`20260901065101-80a036`），随后自己收工，收尾写着「两人完成时看板会通知我，我接着收敛」。两人分别在 14:58 / 15:04 把结论逐条填进《三方会审记录》后收工。**然后什么都没发生**：三条 run 全是 `status=done`，无崩溃、无 abort、无 watchdog，`pendingQueues` 三个队列全空，会审记录里五处「**会审结论 / 拟冻结口径**：_待菲菲汇总_」一处没动，47 个 facet 一条没冻结。老板看到的是「三方会审中断了」。

**根因：三条交接原语里，只有 cc 没有终点。**

| 原语 | 语义 | 谁把链条接下去 |
|---|---|---|
| `【下一棒】` | 交棒即停 | `spawnForward` 新建下一棒 run |
| `【交回】` | 回发即停 | resume 委托者会话（`callerRunId`） |
| `cc_colleague` | 并行知会、**不回发** | **（空）** |

cc 派生的兄弟 run 是 `callerRunId: null`（设计如此，注释也明写「不回发」），`ccFrom` 全仓只用于 `logConversation` 记流水。**没有任何「扇出全部收工 → 唤回发起人」的汇合点**——fire-and-forget 只做了 fire。

**三层防线同时放行，而且每一层都判对了**——这是本条最值得记的部分：

1. **菲菲**基于一个**不存在的机制**收工（「看板会通知我」）。她需要的能力是真实需求（会审必须等各方产出才能汇总），只是引擎没给，于是她自己编了一个。
2. **小呆呆巡菲菲**（14:52）：当时两人**还在跑**，「等同事」确实是合理协作等待 → 判合法收工，正确。
3. **小呆呆巡两个子 run**（14:58 / 15:05）：站在它们的判据上，「发起方明确豁免回发」→ 判合法收工，也正确。

**没有任何一轮的视角是「这条扇出的汇合点没人接」。** 三次巡视各自局部最优、全局死锁——巡视是「按单个 run 的判据判它该不该停」，而这个洞在**run 之间的空隙**里，任何单点判据都看不见它。

**对策：抄送汇合闸（`tryFireCcJoin`）。** 谁 cc 出去，引擎负责在扇出全部到终态那刻把他唤回来，同会话 resume（保上下文）+ 注回各子 run 的收尾摘要 + 进度快照。判据全是机器可得的事实：子 run 状态 + 队列残留，一条都不靠猜语义。

设计取舍（每条都是刻意的）：

- **不改 cc 的「不回发」语义**。子 run 仍然不写【交回】、不停等——汇合由引擎在**它到终态**那刻触发，员工侧零心智负担。若改成「cc 子 run 必须回发」，就等于把 cc 退化成【交回】，并行性没了。
- **不做「发起 cc 后禁止收工」的反向门禁**（曾经的候选方案）。cc 的语义本就是并行，会审型场景发起方天然只能停下等；逼它自转圈轮询才是真浪费。**能力缺口要用能力补，不要用门禁把需求禁掉。**
- **子 run 异常终态（error/interrupted）也算「到齐」**。摘要里带上 status，由发起人判要不要重派。理由：不能因为子 run 死法不好看就永远不唤发起人——那又是一次静默死停。
- **发起人已把棒交出去（`【下一棒】`/`【交回】`）→ 不唤**。它这条线在别处活着，再唤＝同员工/同线并发第二条 run 撞工作树。
- **老板亲手按停的会话不自动唤回**（`userStoppedAt` 持久标记，`startRun` 里撤销）。人为中止意图优先于机器自愈。
- **队列残留用动态数、不存计数器**（`ccQueuedFor` 现扫 `pendingQueues`）。计数器会因投递失败/重启/手动清队列而漂移，一漂就永远汇合不了——宁可多扫几条队列。
- **汇合关系落库**（`ccChildren` / `ccOriginRunIds` / `ccJoinFiredAt` 都不带 `_` 前缀，过 `stripPrivate`）。重启即失忆会原样重现本事故。
- **顺手砍掉一片巡视浪费**：cc 子 run 一旦触发了汇合，就给它盖 `patrolClearedSig`、不再派巡视——它按语义本就「做完你这份即可、无需回发」，历史上每条都要小呆呆判一次「合法收工」，纯烧钱（§3.101 那笔「79 次巡视只 2 次真停」的账，这里还回来一部分）。归口人从「小呆呆猜它该不该停」换成「发起人拿着它的收尾摘要判」，判据更硬。

**通用教训**：

- **fire-and-forget 只写了 fire，就是一处静默死停的预埋。** 凡是「派出去不等回」的原语，都要回答一句：**它的终点由谁接？** 接不上就不叫异步，叫丢。
- **每个局部判据都判对了，系统仍然可以死锁。** 巡视这类「按单点判据审单点」的机制，天生看不见「谁也不为这条缝负责」的洞——洞在 run 之间，不在任何一个 run 里面。补这种洞只能靠**结构性的汇合点**，不能靠再加一个更聪明的判官。
- **员工凭空发明的机制，是引擎缺能力的报警。** 「看板会通知我」不是幻觉的随机噪声，而是它确实需要一个通知机制、而引擎没有。听见这种措辞就该去查引擎有没有这条路，而不是只去纠正员工的话术。

**改动落点**：`app/server.js`（`CC_JOIN_MAX_FIRES` / `isTerminalRun` / `ccQueuedFor` / `bindCcChild` / `tryFireCcJoin` / `notifyCcOrigins` / `sweepCcJoins`；`cc_colleague` 三条投递路径均登记子 run；`autoChain` 三处挂钩（子 run 到终态即试汇合、发起人自己空停时试汇合、汇合已触发则免巡视）；`handleStreamEnd` 异常终态同样试汇合；`drainPending` 回绑队列投递的 cc；`/api/runs/:id/stop` 落 `userStoppedAt`、`startRun` 撤销；定时兜底并入 `armPatrolSweep` 周期 + 启动扫一遍）、`app/public/app.js`（`cc-join` 的 toast 文案）、`roles/feifei.md` / `roles/ggbond.md`（「等各方产出可以停下等、但要写清等谁等什么」写进 SOP）、`app/test/cc-join.test.js`（新，12 条，含事故重演）。**引擎改动，需重启生效（走托盘，别强杀）。**

### §3.114 别人 `nvm use 16` 之后，lab 一崩就再也起不来：托盘空转 5 次重启，把「环境不对」伪装成「服务不稳定」（2026-09-04，老板：「lab 最近重启很多次，不知道是不是有性能问题」）

**现象**：老板报「最近重启很多次，是不是有性能问题」。查的时候 **lab 已经彻底停了**——4800/4700 都没有监听，而老板并不知道。托盘日志：

```
[09-04 13:39]    C:\nvm4w\nodejs 符号链接改指向 v16.20.2      ← 别的项目的 nvm use（符号链接时间戳）
[09-04 16:13:46] 服务异常退出（code=-1073740791），自动重启第 1 次
[09-04 16:13:49] 服务异常退出（code=1），自动重启第 2 次
[09-04 16:13:53] … 第 3 次   [16:13:57] … 第 4 次   [16:14:01] … 第 5 次
[09-04 16:14:04] 服务已停止（code=1）：自动重启达上限（5 次），等待手动启动
```

五次 `code=1` 在 `server.err.log` 里是同一句：`ReferenceError: DOMException is not defined at @anthropic-ai/claude-agent-sdk/sdk.mjs:34`。

**根因：PATH 上那个 node 不属于 lab，属于「最后一次 `nvm use` 的人」。** 托盘用 `Get-Command node` 取 PATH 上的 node，而 PATH 上是 nvm 的符号链接（`C:\nvm4w\nodejs` → `AppData\Local\nvm\v16.20.2`）。那次 `nvm use 16` 是**别的项目**要的：`frontend/web-app` 的老 umi dev 常年挂着（实测 1769 MB，从 9/1 起就在跑），需要 node 16。`DOMException` 是 Node 17+ 才有的全局，`app/package.json` 也写着 `engines.node >= 18`——**但托盘只检查 node 存不存在，从不看版本**。

**这条最值得记的不是「少了个版本判断」，是它的伪装形态：**

| | 真实情况 | 老板看到的 |
|---|---|---|
| 失败性质 | 一次性、**确定性**的环境不满足 | 「崩了 5 次，越来越不稳」 |
| 该做的事 | 停下来说清「node 版本不对」 | 重试 5 次然后失联 |
| 归因方向 | 环境漂移（第三方改了共享资源） | **性能问题** |

看门狗的重试语义只对**瞬时故障**成立。对确定性失败，重试不但救不回来，还会把一次干净的报错**放大成 5 条噪音**、并把归因彻底带偏——这与 §3.85（看门狗把「引擎在忙」判成「引擎死了」）是同族：**看门狗的判据必须能区分「这次值不值得再试」，否则它制造的故障叙事比故障本身更贵。**

**对策一：启动前版本门禁 + 与全局 nvm 解耦。** PATH 上的够用（>=18）就照旧用（不夺权）；不够则去 nvm 版本根（`NVM_HOME`，回退 `%LOCALAPPDATA%\nvm`）挑 **>=18 的最高版本**用绝对路径起，日志点名「PATH 上是 v16、本次改用 v24.2.0、**不改全局 nvm**」；一个合格的都没有就**弹窗说清原因并退出**——不带着必然失败的 node 去空转重启。版本一律 `node -v` 实测：PATH 上是符号链接，**路径名不含真实版本，猜不得**。

不去全局 `nvm use 24` 是有意的：那个 umi dev 大概率就是靠 16 活着，lab 不该为了自己好过而去动别人的共享资源。**要的是「lab 用哪个 node」与「机器默认哪个 node」解耦，不是把默认改成自己喜欢的。**

**对策二：PATH 也要对齐，否则只修好一半。** 首轮验证时引擎已经跑在 24，**界面仍在 16**：4700 起不来，`web.err.log` 报 `node:util does not provide an export named 'styleText'`（`styleText` 是 Node 20.12+）。因为新 UI 那条链是 `corepack.cmd → pnpm → vite`，**pnpm/vite 的 bin 包装脚本各自去 PATH 上找 `node`**，绝对路径只管得住直接 spawn 的那一个进程。故把选中的 node 目录顶到 `$env:PATH` 最前（**仅托盘进程及其子进程，不动机器/用户级环境变量**）。教训：**「用绝对路径起进程」只约束第一层；进程树里任何一层再去 PATH 查一次，约束就断了。**

### 顺带查清的两处旧账（本次未改，记账）

1. **首次崩溃那个 `code=-1073740791`（`0xC0000409`，Windows fail-fast）不是 JS 堆 OOM**：近两周共 3 次（09-01 13:47、09-04 10:06、09-04 16:13），**stderr 一个字没留**，全库 `FATAL ERROR` / `heap out of memory` 零命中（V8 的堆溢出是会打这两句的）；崩前 stdout 只有 wecom 轮询与 `[ui-contract] patrol-sweep`，没有繁重 run。
2. **这台机器确实在内存打满边缘**：提交内存 **53 GB / 61.7 GB（86%）**、物理可用 4.2 GB / 31.8 GB、Memory Compression 2.8 GB；托盘历史两次直接报过 `启动 node 失败：页面文件太小，无法完成操作`（07-28 09:59、09-01 13:35）——那是 Windows 提交上限打满的原话，与「静默 abort、来不及打任何 stderr」高度吻合。内存大户**不是 lab**（最大是那个常年挂着的 umi dev）。

这两条只解释「偶发那一崩」，**不解释「崩完起不来」**——后者百分之百是版本门禁的缺失。两个原因叠在一起，正是「重启很多次」这个错觉的来源：底噪级的偶发崩溃提供了触发器，缺版本门禁把每次触发放大成 5 条。

### 通用教训

- **看门狗必须会区分「值得重试」和「注定失败」。** 对确定性的环境不满足，正确动作是**响亮地停**，不是安静地重试到上限——后者把一条准确的错误信息埋进 5 条重复噪音里，还让用户以为是稳定性/性能问题。
- **共享的隐式依赖会被第三方改掉。** PATH 上的 `node`、全局 pnpm、系统 Python 这类「谁都能 `use` 一下」的资源，对本服务而言不是配置而是**别人的可变状态**。要么在启动时校验并给出人话诊断，要么钉死自己的那一份。
- **「一次性的确定性失败」被重试放大后，故障叙事会漂移到完全错误的方向。** 本次漂到了「性能问题」——排查时先分清「同一个错误重复 N 次」和「N 个不同的错误」，前者只有 1 个 bug。
- **绝对路径只管第一层进程。** 进程树里任何一环再去 PATH 上找同一个可执行文件，前面的钉死就失效了；要么全树对齐 PATH，要么每一层都显式传。

**改动落点**：`tray/office-lab-tray.ps1`（`$NodeMinMajor` / `Get-NodeMajor` / node 候选选择与门禁 / `$env:PATH` 前置）。**托盘改动需重启托盘才生效**（重起前 `runs.running=0`，只停托盘进程、引擎未动）。

### §3.117 员工把工具调用「写成正文」：那一步压根没执行，而引擎照旧发绿灯——v5.22 一整轮看板回写就这么丢了（2026-09-07，老板截图「气泡里怎么躺着一坨 invoke XML」）

老板发来一张波比聊天窗的截图：气泡正文里躺着一大段

```
card <invoke name="mcp__office-lab-collab__set_entry_status"> <parameter name="no">REQ-0334</parameter>
<parameter name="status">待测</parameter> <parameter name="stage">已发测(FE!2211合入master+部署)→…</parameter> </invoke>
```

看着像渲染没处理好某种标记。**实际是：模型没有产出真正的 `tool_use` 块，而是把调用当文本写了出来。** 那一步因此**根本没有执行**——可这一轮 `result` 非空、收工标记齐全、语气笃定，引擎照旧亮「✅ 本轮收工」。

#### 代价：4 轮结尾都是假调用，末轮那次没人接

run `20260907053624-d858bf`（波比 v5.22 发测），5 个收工轮里 **4 轮的最后一句就是一个假调用**：

| 轮次 | 结尾泄漏的调用 | 结局 |
|---|---|---|
| 05:43 | `olcard` | 就是 §3.116 那条被绞碎的汇报（假调用 + 围栏错位撞在一起） |
| 06:31 | `Bash`（逐仓核实 MR 合入） | 下一棒续跑侥幸救回 |
| 06:32 | `mcp__guarded__reconcile_release_chain` | 下一棒续跑侥幸救回 |
| **06:34（末轮）** | **`mcp__office-lab-collab__set_entry_status`** | **没人接 → 回写彻底丢失** |

坐实：`tasks/2026-09-04-示例项目-v5.22.md` 里 REQ-0334 仍是「QA通过」、`released_test: false`、`status: QA_IN_PROGRESS`——而那一轮的收工汇报写的是「回写看板：条目→待测，落时间线，刷版本级状态」，run 状态「已完成」。

**危害不在少写一行，在于「声称做了、事实没做，而且系统站在它那边发绿灯」。** 三道既有防线全部看不见它：`emptyStop` 只管空 result（这轮 result 很丰满）；`validateSignoff` 只管有没有交接标记（标记写了）；小呆呆巡视只在「空停」时被派（这轮"正常收工"）。**它们量的都是「有没有说」，没有一道在量「说的那件事有没有真发生」。**

#### 对策：收工那一刻判假调用 → 判未正常收工，但不自动续跑

`stall-guard.js` 加纯函数 `leakedInvocations(text)`，`onTurnComplete` 在算完 `emptyStop` 之后接线：命中即 `isError = true`、run 上落 `leakedInvoke: [工具名…]`、lab 事件**点名具体工具**并说清「这类假调用零副作用——看板回写 / 对账 / 命令都没发生，别按汇报的字面相信它」，推手机，恢复权交回老板。

**刻意不自动续跑**（老板在「判未收工不续跑 / 自动续跑重做 / 只报警仍算收工」三个方案里拍的板）：2026-07-27 那次「自动热推纠偏续跑」把 run 锁在 running、`/reply` 409 拒收用户消息，已经回退过一次；处置形态与空收工那套保持同构（红灯 + 说清楚 + 回复「继续」即重做），别再走一遍老路。`error` 态天然不接棒、不沉淀教训、不排空闲窗。

**判据先剥代码块、再要求结构完整**——这条和 §3.116 是同一天、同一条教训的两次应用：

```js
const stripCodeSpans = s => String(s || '')
  .replace(/^[ \t]{0,3}```[\s\S]*?^[ \t]{0,3}```[ \t]*$/gm, '')   // 闭合围栏

不剥的话，**第一个被这条门禁判死的就是"讲解这个 bug 的那份汇报"**——员工写 SOP、写复盘、教后来者「别把调用写成正文」时必然要引用这段语法。判据要能区分「谈论一种标记」与「使用这种标记」，靠的是结构（围栏内/外、有没有参数），不是关键字。

#### 前端：假调用降级成一行细行，不再往气泡里泼 XML

`web/src/lib/leaked-invoke.ts` 把泄漏块从正文剥出（围栏里的引用不动，顺带吃掉紧贴在前的 `card` 字样与 `<function_calls>` 包裹标签这两种纯残渣），transcript 把它渲染成正文**之后**的一行红细行「⚠ 未执行的工具调用（写成了正文）· <工具名> · N 个」，展开看原样留证。正文里只留真话，复制也只复制干净正文；整条消息都是假调用时只剩那行细行。

老板发线上后回了一句「线上发布完成」，波比这一轮直接红了，屏幕上是：同一句话的两个气泡（各挂一坨 XML）+ 一句英文 `The model's tool call could not be parsed (retry also failed).` 说了两遍。

拆开 run `20260907065645-c4b5f2` 的尾部（#178~#182）看得很清楚：

#179 assistant text  同一段话（1452 字，截断位置差 18 字）        ← SDK 的重试

**这就是 §3.117 那个「假调用」的响亮版**：同样是调用被写成正文，只不过这次**写到一半被截断**，SDK 试着把这段文本当调用解析、重试一次仍失败，于是报错收场。两种结局的差别值得记住：

| | 静默版（§3.117） | 响亮版（本条） |
|---|---|---|
| 文本形态 | 完整的 `<invoke>…</invoke>` | 截断在属性中间 |
| SDK 行为 | 当普通文本收下，`end_turn` | 尝试解析 → 重试 → 放弃报错 |
| 引擎旧行为 | **✅ 本轮收工（绿灯）** | ❌ 本轮以错误结束 |
| 危害 | 声称做了、事实没做，**没人知道** | 至少是红的，但那句英文对老板零信息量 |

也顺手澄清了「一次真调用一次假调用」的规律：同一条会话里 06:56 那轮 **16 次真调用、零泄漏**，09:07 这轮全是假的——**同一个员工、同一套工具，差别不在意愿而在调用通道那一刻是否退化成文本**。所以门禁只能由引擎量事实，SOP 叮嘱无用（§3.117 的结论在这里被二次验证）。

**这一轮真实的代价**：v5.22 的**上线坐实与 `released_prod` 回写全没发生**——档案仍是 `released_prod: false`、四条 REQ 停在「待测·发线上 MR 已建」，时间线也没有「已合入 release」那条。红灯至少没骗人，但也仅止于此。

1. **引擎把那句英文翻成人话**（`PARSE_FAIL_RE` + `onTurnComplete` 的 lab 文案）：说清「模型这次的工具调用格式坏了 / **本轮零动作**，命令与回写一个都没执行 / 上面那两条重复的话是重试痕迹 / 回复「继续」重来 / 已知诱因是一条 Bash 塞超长复合命令 + 嵌套引号」。原文照贴在括号里，不藏。
2. **重试留下的重复气泡吞掉**：条件收窄到「纯文本事件 + 带假调用 + `<invoke` 之前的正文逐字相同」三条同时成立——**不能要求整段相同**（重试那次截断在别处，实测 1470 vs 1452 字），中间夹了任何别的事件就重置，不跨轮误吞。
3. **SDK 自己的报错文本不再当员工发言渲染**：它同时以 assistant 文本块 + result 事件两种身份到达，红框已完整展示，气泡侧一律跳过（整条只有它的事件连头像行一起跳，否则留一个空气泡 + 孤零零一个头像）。

**验证**：Playwright 实测 4700 真实数据（就那条红了的 run）——那句话的气泡 **2→1**、英文报错气泡 **1→0**、假调用细行 1 条、气泡里残留 XML **0**、无孤立头像行；`node --check` 0 error、`tsc -b` + `vite build` 通过、全库 `npm test` 516 条全绿。**引擎那条翻译需重启才生效**（重启前仍显示「❌ 本轮以错误结束」）。

##### 出错行本身也重做了（同日，老板：「这个红框错误信息的展示太难看了」）

翻译成中文之后还剩一个问题：**承载它的那个框**。旧的 `case 'result'` 是**全宽**方框 + `border-destructive/50` 重红边 + 无底色 + 14px 正文，而里面常常只有一句裸英文；紧跟着下面又是一行「❌ 本轮以错误结束」。于是同一件事报两遍（一个英文一个中文），且这个框是整幅画面里最扎眼的元素——**它的视觉重量与它承载的信息量完全不成比例**。

改成 `RunErrorRow`，与 `LabRow` / `QuietRow` 同一套语言：贴左、宽度随内容（上限 92%）、发丝红边 + 极浅红底、12px；一行中文摘要**只说「怎么了」**，`ERROR_HINTS` 认已知签名（工具调用格式坏了 / 上游限流 / 上游过载 / 被中止），未知签名把原文压成一行当摘要；英文原文点「原文」展开，折叠留证。

一个值得记的小教训：**第一版把「怎么办」也塞进了这一行**（「…本轮零动作，回复「继续」重来一轮」），实测直接被 truncate 吃掉后半句——**恢复指引是最不该被省略号截掉的那部分**。既然紧邻的 lab 行本就是引擎给的恢复指引，两处就该分工：**红胶囊说「怎么了」，lab 行说「怎么办」**。短原文也不给折叠——它本身就是摘要，别让人多点一下才看到一句话。

验证（真实数据，靠聊天窗的「加载更早」翻页翻回那条事件再拍）：**1280px 全宽 → 306×30px 胶囊**，深浅两主题均不截断，展开后见英文原文。

## 3.129 托盘自己那扇窗：Win11 默认终端交接让「藏窗口」结构性失效，兼 §3.105「实测否掉」的翻案（2026-09-09，老板报「启动托盘还是会启动一个常驻的终端窗口，关掉终端后整个 lab 都会被关掉」）

**用户报的**：和 §3.105 一字不差的抱怨。但那次的真凶（4700 挂在手工 `pnpm preview` 终端链上）已在 08-26 修掉且依旧成立——**这是同一句抱怨下的第二个窗口，属于托盘自己**。

### 一、原来那两道防线为什么必然失效

`HKCU:\Console\%%Startup` 的 `DelegationTerminal = {13ebf103-9abc-5e7d-8935-f6d79a10eaee}`＝**Windows Terminal**。默认终端不是 conhost 时，任何**新建控制台**的进程都会被交接给 `WindowsTerminal.exe`，**窗口由另一个进程创建**。于是：

- `启动托盘.cmd` / `office-lab.vbs` 的 `-WindowStyle Hidden`：作用对象是「本该由本进程创建的那个控制台窗口」，交接后的 WT 窗口不属于本进程，不吃这个 flag；
- 脚本内的 `ShowWindow(GetConsoleWindow(), SW_HIDE)`（belt-and-suspenders 那道）：交接后 `GetConsoleWindow()` 返回的是系统留作兼容的**替身窗口**——属主还是 powershell 自己，所以 `SW_HIDE` 确实返回成功、`IsWindowVisible` 也确实变 False——**而屏幕上那个 HWND 属于 `WindowsTerminal.exe`，纹丝不动**。

**这就是那条假成功日志的来源**：`app/runs/tray.log` 里 `已隐藏自身控制台窗口（防误关连带停服）` 写得理直气壮，窗口还在。日志越自信，归因越难。

### 二、§3.105 的翻案：三个判据全在交接边界的里侧

§3.105 用三条实测「否掉」了交接假设，观测值今天复现得一模一样——**但那三条结构上都看不见交接**：

| §3.105 的判据 | 为什么测不出交接 |
|---|---|
| `MainWindowHandle = 0` | 控制台程序的控制台窗口从来不是 .NET 眼里的 MainWindow，**交接与否恒为 0** |
| 子进程是 `conhost.exe` | 交接是「先起 conhost、再移交」，conhost 照样在；`CREATE_NO_WINDOW` 下参数还是 `0x4` |
| `GetConsoleWindow()` 非 0 | 非 0 的**正是那个替身**，它的存在恰恰是交接的证据，却被读成了「没交接」 |

唯一测得出的判据是**跨进程枚举可见窗口 + 按控制台标题匹配**。今天用它一枪命中：

```
探针进程自报: GetConsoleWindow=0xA0A7E  属主=powershell 自己  SW_HIDE 后 IsWindowVisible=False
屏幕上真实可见: HWND=0xA0B2E            属主=WindowsTerminal.exe (PID 9812)   标题=OLTRAY-PROBE-WINDOW
```

两个 HWND 不是一个东西。给 `0xA0B2E` 发 `WM_CLOSE` 后，探针的收尾行（`parent-clean-exit`）**没写出来**＝进程被硬杀。

> **教训（§3.105 那条的第二面刃）**：那节的结论是「能被一条命令验证的假设，别拿它当结论」。这次补上对称的另一半——**证伪也要选对判据**。拿三个都看不见目标现象的探针去"否掉"一个假设，得到的是**假阴性**，而且比没测更危险：它给错误结论盖了「已实测」的章，让同一个 bug 多活了两周。判据选择的检查方式很朴素：**先问「如果假设为真，这个判据的读数会不一样吗」**——上表三行的答案全是「不会」。

### 三、连带的第二个事实：关掉窗口，死的只有托盘

同一个探针顺手测了爆炸半径（父 powershell + 一个用 `CreateNoWindow` 起的 `cmd` 子进程，仿 `Start-Server` 起 node 那套）：

- **托盘（父）被硬杀**：`Quit-Tray` / `Stop-Server` 一行都没跑（收尾日志缺失）；
- **服务（`CreateNoWindow` 起的子孙）活到自然结束**：60/60 心跳全在。代码侧也印证——托盘没有 JobObject，`server.js` 也没有父进程守望（`TRAY_PID`/`ppid` 零命中）。

所以「整个 lab 被关掉」的准确说法是：**引擎和界面变成孤儿继续跑，丢的是全部控制面**——托盘图标、悬浮窗、health 轮询、Toast 审批回执、崩溃自动重启。这也解释了本次修完后重启托盘为什么直接进「双监控模式」：4800 上 PID 192、4700 上 PID 18500 都是**上一个托盘死前留下的孤儿**，正是这条链的现场证据。与 §3.105 同族的观感陷阱：**用户说「全没了」时，先分清是「进程死了」还是「把手没了」**——后者的修法完全不同。

### 四、对策：别造窗口，而不是造完再藏

`CREATE_NO_WINDOW`（.NET `ProcessStartInfo.CreateNoWindow`）**压根不创建窗口，因此不触发默认终端交接**——屏幕上无窗可关。这招本文件里一直在用（`Start-Server` 起 node、`Start-PnpmProc` 起 pnpm），**只是从没用在托盘自己身上**。

实现＝脚本开头**自我重启一次**：无 `OFFICE_LAB_TRAY_NOWINDOW` 标记时，用当前宿主 exe（`MainModule.FileName`，pwsh/powershell 都照原样延续）以 `CreateNoWindow=$true` 把自己重新拉起、置标记、引导进程立即退出。三个必须记住的细节：

1. **必须放在单实例 mutex 之前**。否则引导进程先占住 `OfficeLabTray_wangzichenglong`，重启出来的真身会被判「已有实例在运行」而静默退出——**托盘永远起不来**，而且日志看起来一切正常。
2. **一处改动覆盖全部入口**：`.cmd` / `.vbs` / 开机自启的 `.lnk`（→ `wscript` → vbs）/ 右键「用 PowerShell 运行」/ 手工 `-File`。这正是原来那道 belt-and-suspenders 想达到的效果，只是站错了层——**在「窗口已被别人创建」之后再补救，无论怎么写都晚了**。
3. **失败要降级、不能不起来**：重启异常时清掉标记、落一行响亮日志，就地继续跑（可能带窗口，但托盘可用）。`OFFICE_LAB_TRAY_DEBUG=1` 整块跳过——调试启动器要的就是可见窗口。

顺带把那条假成功日志改成**不再谎报**：`SW_HIDE` 后用 `IsWindowVisible` 复核，并读 `DelegationTerminal` 判是否交接，三种结局各自成文（仍可见 / 已隐但交接给第三方终端 / 真隐掉 / 压根没有控制台窗口）。

**验证**（真实入口，非替身）：跑 `启动托盘.cmd`，`tray.log` 的链条是

```
16:48:01 ==== 托盘启动 (PID 15608) ====                  ← 引导进程
16:48:02 已自我重启为无窗口实例（子进程 PID 4736，CreateNoWindow），本引导进程退出
16:48:02 ==== 托盘启动 (PID 4736) ====                   ← 真身
16:48:03 本进程无控制台窗口（无窗可误关）
16:48:05 托盘图标已就绪，进入消息循环
```

真身 `MainWindowHandle=0`、conhost 子进程为无窗口的 `0x4`、`GetConsoleWindow()` 返回 **0x0**（比 §3.105 那次的"非 0 替身"干净得多，这个读数本身就是交接没发生的证据）。风险点单独验过：**`CreateNoWindow` 的 PowerShell 里 WinForms 能不能用**——NotifyIcon `Visible=True`、顶层 Form 拿到句柄、`Application.Run` 消息循环 8 跳后干净退出，全绿；这是本次唯一真风险（托盘的图标、悬浮窗、Toast 全靠它）。

残留：引导那一下仍会闪一个 WT 窗口（引导进程退出即消失），**但常驻期不再有可被误关的窗口**。想连闪都没有得改系统「默认终端应用」为 `Windows 控制台主机`——那是改用户全局设置，刻意不动。

### 通用教训

- **交接/代理边界上的判据要选在外侧**。凡「窗口/句柄/宿主可能属于另一个进程」的场景，自报式 API（`GetConsoleWindow`、`MainWindowHandle`）问的是「我以为的我」，只有跨进程枚举问的是「屏幕上真实的那个」。§3.105 那次栽在这，这次靠它翻案。
- **"藏" 是补救，"不造" 是修复**。同一份文件里对 node 用的是 `CreateNoWindow`、对自己用的是 `SW_HIDE`——**正确做法就在同一屏代码里，只是没往自己身上套**。改动前值得扫一眼：这个问题我在别处是怎么解的？
- **假成功的日志比没有日志更贵**。`已隐藏自身控制台窗口` 让两次排查都绕开了真正的怀疑对象。凡是"我做了某个动作"的日志，能复核就复核后再写；复核不了就把话说软。

## 3.130 托盘 59 次启动、56 次无声消失：「查不出来」本身才是那个缺陷（2026-09-09，老板报「怎么托盘没了」）

**用户报的**：§3.129 修完窗口、托盘正常起来之后，过了一段时间「托盘没了」。

### 一、先把数字摊开：这不是新问题

全量翻 `app/runs/tray.log`（跨 7-22 至 9-9）：

| 事实 | 数 |
|---|---|
| `==== 托盘启动` | **59** |
| `停服请求（用户操作）`（右键「退出/停止」留下的） | **3** |
| `FATAL`（顶层 `trap` 写的） | **0** |
| `已有托盘实例在运行，本次静默退出`（启动时撞上活着的前一个实例） | **0** |

**56 次消失，一次痕迹都没有。** 且 59 次启动没有一次撞上活着的前实例——每次去启动，上一个都已经死了。所以「托盘会自己没」是**长期存在的既有行为，不是 §3.129 那次改动引入的**（§3.129 之前的 PID 7772、之后的 4736 / 18084 都一样地无声消失）。

### 二、真正的缺陷：两种死法在日志上完全同形

`Application.Run($appContext)` 之后**一行日志都没有**，收尾只有一句 `$notify.Dispose()`。于是：

- 「消息循环自己返回了」（有人调了 `Application.Exit` / `ExitThread`）
- 「进程被外部杀死或硬崩」

**在日志上是同一个样子——什么都没有。** 再叠加两件事：托盘无窗口，stdout 无处可去；WinForms 默认的 `UnhandledExceptionMode` 对回调里漏出的异常不留痕。结果是**59 次机会，一次归因所需的信息都没留下**。这与 §3.85 / §3.129 同族：**判据缺失时，重复发生本身不产生任何知识**。

补上四件（这才是这轮的主要产出）：

1. **`Application.Run` 返回后立刻留痕**（`消息循环已返回（PID …）` + `托盘进程正常结束`）——**有这行＝循环自退，没这行＝被杀**，两种死法从此可分；
2. **心跳每 ~5 分钟一行**（state / 托管 PID / 监控 PID / 内存）——把死亡时刻从「40 分钟的窗口」收窄到 5 分钟；
3. **`Application.ThreadException` + `SetUnhandledExceptionMode(CatchException)`**，外加 `AppDomain.UnhandledException`、`SystemEvents.SessionEnding`——注销/关机、UI 线程异常、非 UI 线程异常各自成文；
4. Tick 里原先**唯一在 try 之外**的两处（`Drain-Activations` / `Poll-Notifications`，都做 WinRT COM + HTTP）各自兜住并记名。

### 三、一个被控制实验否掉的漂亮假设

`Poll-Notifications` 里 HTTP 那句有 try、**后面整段 WinRT Toast 没有**，而它在 Tick 里又恰好在 try 之外。「一次 COM 失手 → 异常漏出 Tick → WinForms 默认行为终结进程 → 无窗口所以连报错都看不见」——严丝合缝，也完全对得上"无声消失"。

**控制实验直接否掉**：同一个探针跑两遍，一遍装 `SetUnhandledExceptionMode(CatchException)` + `ThreadException`，一遍**全不装**，都在 `Timer.Tick` 里主动 `throw`：

```
装了:   THREADEX CAUGHT: RuntimeException: deliberate-tick-boom → tick 3,4,5 → 循环干净退出
没装:   （无任何捕获日志）                                      → tick 3,4,5 → 循环干净退出   ← 也活着
```

原因：PowerShell 把 scriptblock 包成委托时**自己把异常吞了**，根本没走到 .NET 的未处理异常路径。所以那套加固**不是**托盘死因的修复，它的价值只是**把此前被静默吞掉的错误变成日志**。

> §3.129 刚写下「能被一条命令验证的假设别当结论」，隔一小时就差点在同一份文件上又栽一次。这次的差别只在于**先跑了对照组**——单跑"装了之后没崩"那一半，会得到一个完全错误的因果结论，而且看起来像已验证。**加固措施的验证必须带对照组**：不然你证明的只是"加了之后是好的"，不是"不加就是坏的"。

### 四、加了留痕，4 秒内抓到第一条真东西：Toast 链路被一条坏事件永久毒死

新日志一上线就开始每 4 秒刷一条（此前完全不可见）：

```
通知轮询失败（忽略本轮，不影响探活）：索引操作失败；数组索引的计算结果为 Null。
```

顺着查到 `Show-StopToast` 的**第一句**：

```powershell
$meta = @{ done = @('✅','收工'); error = @('❌','异常停止'); interrupted = @('⏸','中断') }[$ev.status]
if (-not $meta) { return }     # ← 本该拦住它，但晚了一行
```

`notifyLog` 里混着非收工事件——实测 20 条里 **13 条是 `kind=lark-sync`、根本没有 `status` 字段**。而 PowerShell 的 `$hash[$null]` **抛异常**而不是返回 `$null`（`$h[$null]` 单独一跑就复现这条错误原文），所以那句 guard 永远等不到执行。

**真正致命的是它和游标的组合**：

```powershell
foreach ($ev in (@($r.events) | Sort-Object seq)) {
  Show-StopToast $ev                                                     # 抛 → foreach 当场中断
  if ([int]$ev.seq -gt $script:notifySince) { $script:notifySince = … }  # ← 永远执行不到
}
```

游标推进写在弹卡**之后**，于是一条坏事件让 `notifySince` 永久停在它前面 → 4 秒后拉回同一批 → 又抛在同一条 → **Toast 审批/收工回执整条链路被永久毒死**（poison pill）。而这个异常一直被上面那个 PowerShell 委托吞掉，**一行日志都没有**——「Windows 通知」这个功能在菜单里勾着、实际早就是死的，没有任何人能知道。

对策两条，结构那条更重要：

1. **游标先推进、再弹卡，且单条失败不拖累整批**（坏事件只被跳过一次，不再重放）；
2. `Show-StopToast` 先 `[string]$ev.status` 判空再索引（非收工事件直接跳过）。

顺带让报错带上失败时的输入（`since=… init=…`）——正是靠「since 一直不动」才判出这是卡死而非偶发。**同 §3.129 那条：日志要说清是哪个输入炸的。**

验证：重启前每 4 秒一条、共 85 条；重启后 ~11 轮零报错，心跳正常。

### 五、当前状态：死因仍未定，但下次会留下证据

托盘为什么消失，**这一轮没有答案**。已排除：崩溃（无 WER / 无 dump / Application 与 System 事件日志皆空）、计划任务或仓内脚本杀 powershell（全库 grep + `Get-ScheduledTask` 均无命中）、Tick 异常（控制实验否掉）。引擎（node）在同期稳定运行数小时不受影响——**死的只有托盘那个 powershell**，这个不对称是下一步的线索。

下次消失时，日志一定能回答第一个分叉问题：**有没有「消息循环已返回」那一行**。心跳把时刻钉到 5 分钟内。

### 通用教训

- **重复发生 ≠ 会积累证据**。同一个故障发生 56 次却零信息，因为缺的是判据不是次数。凡"偶发、查不到原因"的东西，第一步该是**补留痕**，不是继续等下一次。
- **加固措施要带对照组验证**。只验"加了之后是好的"会把一个错误因果盖上"已实测"的章（§3.105 同款陷阱的第三次）。
- **兜底 catch 是功能开关的隐形杀手**。`catch { return }` / 被框架吞掉的异常，会让一个勾在菜单里的功能长期处于"死着但看起来活着"的状态。**吞异常必须留痕**，哪怕只是一行。
- **游标/偏移量必须先推进再干活**（至少要能跳过毒丸）。"处理成功才推进"看起来更安全，实际是把**一条坏数据变成永久停机**。

## 3.131 不重写跨平台托管程序，而是补上「测得了」：引擎反过来看护托盘 + 托盘首次有测试（2026-09-09，老板问「我们有没有必要重新开发一个跨系统的托管程序？」→「按你建议来，提升托盘和 lab 本体的健壮性」）

### 一、先回答那个问题：没必要，而且推动它的理由本身站不住

托盘 1264 行 / 44 函数，平台耦合面 WinForms 35 处、System.Drawing 29、WebView2 26、WinRT Toast 7、taskkill+CIM 19、P/Invoke 5。看着确实"该重写"。三条否决：

1. **动机错位**：当天三个 bug 里两个已修，第三个（无声消失）**根因未知**。为未确诊的 bug 重写是最典型的坏理由——不知道重写会不会把它一起带过去。
2. **跨平台是「计划」不是「需求」**：`tray/README.md`、`app/README.md`、部署分册三处都写着 macOS「下一轮做」，当前 macOS/Linux 就用 `bootstrap.mjs` 前台跑，没有真实坐席在等。
3. **最关键：跨平台托管程序消不掉平台差异，只会把它搬个地方。** 部署分册自己已认了 macOS 的两个能力差距——**悬浮窗做不到真置顶**、**系统通知没有按钮**。这两条是 OS 限制不是 PowerShell 限制，换 Electron/Tauri 一样没有。重写换来的不是"差异消失"，而是"差异改用 JS 写"，同时付出：打破 README 里显式的**零安装**设计价值（Electron 150MB+ / Tauri 要 Rust 工具链），并**重新踩一遍已用事故换来的判据**（§3.85 忙 vs 死、§3.105 端口真伪与接管收编、§3.114 node 版本门禁、§3.129 窗口宿主、§3.130 游标毒丸）。

**真问题不叫跨平台，叫「那 1264 行里最容易错的一半本来可测，却被焊死在 WinForms 回调里测不了」**：`app/test/` 30 个测试文件对托盘的覆盖是 **0**，当天三个 bug 全靠人肉复现。

### 二、引擎反过来看护托盘（`app/tray-watchdog.js`，17 条单测）

存在理由是那个不对称：**托盘死了引擎不会跟着死**（§3.130 实测——托盘被硬杀时 `Quit-Tray`/`Stop-Server` 一行不跑，`CreateNoWindow` 起的 node/vite 变孤儿活到底）。既然引擎活得比托盘久、又天生无窗口，它就是唯一现成的看护者。于是**互为看护，谁都不是单点**：托盘→引擎（health 轮询 + 崩溃重启，既有）；引擎→托盘（本模块）；两个都死 → 开机自启兜下一次登录。

三条刻意的设计约束，每条都有对应断言：

- **只"恢复"、绝不"引入"**（`sawTrayAlive` 闭锁）：必须先亲眼见过托盘活着才允许拉起。否则在「用户就想前台跑 bootstrap、根本没打算开托盘」的机器上，引擎会凭空弹出一个托盘图标——那是引擎替用户做决定。闭锁把语义钉死成「把消失的那个恢复回来」。
- **判活走命名 mutex，不枚举进程比命令行**。§3.130 已吃过一次亏：查询进程自己的命令行里也含 `office-lab-tray.ps1`，`Where-Object CommandLine -like` 把**查询者本身**数成了托盘。mutex 没这个问题（对象只在有进程持有句柄时存在），语义已实测：活实例时 `OpenExisting` 命中 / 不存在的名字抛 `WaitHandleCannotBeOpenedException` / `New-Object Mutex($true,name,[ref]$isNew)` 二次抢占得 `createdNew=False`。顺带在托盘引导阶段也加了这道廉价判活，免得看护每次敲门都白起两层进程。
- **探不到（null）≠ 不在**，必须是独立第三态。PowerShell 起不来/超时的时候把它当"死了"就去拉起，那正是 spawn 风暴的入口（§3.85 同族：判据必须能区分「这次值不值得动手」）。另配冷却 60s + 30 分钟窗口内最多 5 次，超了停手并点名。

### 三、★ 本轮最贵的一课：单测替我的错误盖了章，只有端到端才抓到

第一版 `trayRelaunchSpec` 写的是 `{ windowsHide: true, detached: true, stdio: 'ignore' }`。理由听起来无懈可击——"脱离进程组，好让托盘比引擎活得久"。我还**顺手写了一条单测断言 `detached === true`**，它当然通过了。

端到端一跑，托盘死活起不来，而 **tray.log 一行都没有**。隔离实验（同一句 `Write-Output "PS_RAN_OK"; exit 7`）：

```
windowsHide:true       → exit=7  跑起来了 ✔
detached:true          → exit=0  没跑     ✘
windowsHide+detached   → exit=0  没跑     ✘
两个都不给             → exit=7  跑起来了 ✔
```

根因：Node 在 Windows 上把 `detached` 翻成 **`DETACHED_PROCESS`**——子进程**一个控制台都没有**，而 PowerShell 5.1 的 ConsoleHost 必须有控制台，于是**启动即退出，退出码还是 0**。表现有多阴：拿到了 pid、`close` 事件给 0、日志写「已拉起一个」，而托盘压根没跑。（对照：`windowsHide` = `CREATE_NO_WINDOW` 会分配控制台、只是不给窗口，所以能跑——这也正是 §3.129 的正解。）

「活得比引擎久」根本不需要 detached：Windows 上 Node 不在父退出时杀子进程，且同型证据现成——托盘用 `CreateNoWindow` 起的 node/vite 在托盘被硬杀后活到自然结束（§3.130）。实测复核：拉起托盘的那个 node 脚本退出后，托盘仍判活。

**两处对策**：① 规格去掉 detached，并把整段隔离实验数据写进代码注释 + 一条「绝不能 detached」的反向断言（翻案留下的护栏）；② **拉起后必须回头复核**——`setTimeout` 15s 后再判一次活，不活就打一行响亮的日志点名「去看 tray.log 有没有『==== 托盘启动』」。若当初就有这条复核，这个 bug 会在第一次拉起时自己叫出来。

> **教训（§3.130「加固要带对照组」的下一层）**：那节说的是*验证*要有对照组。这次是更前一步——**单元测试断言的是"我打算怎么做"，它天然无法告诉你"我打算做的这件事是错的"**。凡涉及「进程创建标志、系统调用参数、平台行为」这类**你只能假设、不能推导**的东西，单测的价值接近零，必须跑真链路。判据很简单：*这条断言是在检查我的逻辑，还是在检查我对平台的假设？* 后者一律要端到端。

### 通用教训

- **「该不该重写」先问「重写能不能消掉那个差异」**。跨平台不让平台差异消失，只让它换语言。能力差距（真置顶、通知按钮）是 OS 给的，换宿主不改变它。
- **单测断言"我的意图"时价值接近零**。凡是关于**平台行为/系统调用标志**的假设，只能端到端验；否则测试会替错误盖章（`detached: true` 就这么活下来的）。
- **重构与改行为分两步**。抽取时发现的"注释与实现不一致"要原样保留 + 用测试钉住实际语义，别顺手改——出问题时才分得清是哪一步。
- **测试绑在活文档上就会被业务改动打红**。正解通常不是弱化断言，而是**把不变量做成引擎的性质**（收口翻译），这样断言对未来的内容自动成立。

### §3.138 待处理队列「收工排空」其实是「关流排空」：收工后还要空等 3 分钟、有后台任务则无限期（2026-09-28，老板反馈驱动）

**现象**：菲菲 10:07 转给 GG Bond 一条插单（REQ-0378），GG Bond 正忙另一条会话、入待处理队列（§3.70）——这段是设计内。但 10:31 那条会话收工（「等你拍板」）后，排队的活**又挂了整整 3 分钟**才在 10:34:16 起会话；老板看着看板上「收工了、排队的还不动」判成「排队机制太慢」。

**根因**：§3.70 写的是「收工排空」，实现却挂在 `handleStreamEnd`——**流结束**才排空。而常驻 query 收工后不关流，要等 `IDLE_CLOSE_MS`（180s）空闲窗到点才 close；若该会话还有后台任务，`scheduleIdleClose` 直接不排空闲窗，队列就**无限期**等下去。「收工」与「关流」被当成同一时刻，实际差了一个空闲窗。

**对策**：`onTurnComplete` 里 `autoChain` 判完（它可能接棒回自己 → running → `busyRunFor` 自然挡住）立刻 `drainPendingAfterTurn`。**取舍**：两种情况刻意仍留给关流时排空——① 还有后台任务：settle 后 SDK 会自动续跑这条会话，提前起新会话＝同一员工两条并跑同一工作树；② 巡视宽限窗未决：小呆呆可能把它续跑回去，同理。宁可这两种慢，也不引入并跑。

**已知残留（未修）**：老板在队列已起新会话 B 之后再回复旧会话 A，`/reply → sendToRun` 不查员工级忙碌，A 会与 B 并跑。这个洞改前就在（3 分钟空闲窗只是把窗口挪后、从没挡住），本次只是让它更可能被碰到；彻底修需要给 `/reply` 加员工级忙碌判定（排进 A 的待处理，或提示老板），留待拍板。

- **不自动开 lane**（派工时按「主检出被占」自动建树）——建树有副作用、分支名要人定、误判代价是在错误基线上开工；只把「开」降到一次调用/一次点击。

- **【运行环境】块读缓存**：`createDispatchRun` 十余处同步调用点不能 await，状态由每分钟一次的异步刷新 + 每次 `/api/lanes` 请求保温；块里明写「开会话那一刻的快照，以 `lane_status` 现值为准」。

### §3.141 整机内存耗尽：猪猪的浏览器先倒、引擎 3 秒后被掐死，守航会话整夜停摆（2026-09-30 00:43）

- **现场**：Windows 事件日志 00:43:22 `chrome-headless-shell.exe` APPCRASH（异常 0xE0000008，Chromium 的「分配不到内存」）；00:43:25 引擎退出码 0xC0000409、stderr 一行都没有；托盘 00:43:26 拉起新进程。之后 0 条会话在跑——被打断的两条守航会话停在 interrupted。
- **根因**：整机提交内存耗尽（上限 58GB，空闲时也只剩 ~11GB）。前一天把 QA 改成按运行环境并行（§3.139 补），两条迷糊会话各甩并发 3 的 headless，浏览器数翻倍；叠上两个运行环境各两个 Java 服务、两个 umi dev server（其一 9-24 起没停过）、猪猪渲染进程常驻 4.3GB。**并行的收益我算了，并行的资源账没算**——并发闸从「员工串行」放开后，资源的真实瓶颈（整机内存）没有任何闸。
- **第二层**：崩溃本身只丢了几分钟，真正丢掉一整夜的是「被打断 → 目标循环判暂停等老板」。那条口径（v0.11.0 审查 #7）是为「老板手动重启、半截活可能有未提交改动」设计的，套在「基础设施倒下、老板在睡觉」上就错了。
- **对策**：① 引擎统一发全机 headless 槽位（默认 3，空闲内存 <4GB 降到 1），跨会话生效；② 非正常退出后守航会话自动接回原会话（带快照），每条最多 2 次，防「一跑就崩、崩了又接」。
- **教训**：放开一道并发闸时，要问「它原本顺带挡住了什么资源」——员工串行顺带把浏览器数压在 3 以内；闸一拆，这个上限得有人接。

### §3.144 重启后自动接回扩到共驾会话 + 正常关停：§3.141 只补了「守航 × 崩溃」一格（2026-10-06，老板：「lab 因为内存或者其他原因停掉了，自动重启后能自动让各个员工继续没有完成的工作吗」）

- **现状盘点**：§3.141 的接回只覆盖「守航态 × 非正常退出」。另外三格都漏：① **共驾会话**被打断后一律停在 interrupted 等老板——当初的口径是「共驾＝老板在场」，可 lab 半夜倒下时老板同样不在；② **正常关停**（托盘「重启」、SIGTERM/SIGINT）走 `gracefulShutdown`，它先把在跑会话落成 interrupted 再存盘，下次启动时 registry 里已经没有 running → 进不了 `_bootInterrupted`，**连守航都接不回**——讽刺地，退出越体面越接不上；③ 审批挂起态只在内存（未改，员工被接回后会自己重新发起那一步）。
- **顺带的一个 bug**：`gracefulShutdown` 对 `liveRuns` **全量**落 interrupted，包括「早已收工、只是 query 还在空闲窗里没关」的会话——一次重启就把一批闲着的员工标成「被中断」，守航目标循环的 `interrupted` 判据也会被它误触发成「暂停等老板」。
- **对策**（`resumeGuardedAfterBoot` → `resumeInterruptedAfterBoot`）：
  - 启动时 `_bootInterrupted` 收两种来源，带上 `how`：registry 里仍 running/starting 的（crash），以及带持久记号 `shutdownInterruptedAt` 的 interrupted（shutdown）。记号一次性，启动即消费，不管接没接——免得下次启动又被翻出来。
  - `gracefulShutdown` / `handleStreamEnd(shuttingDown)` 只对真在跑（running/starting）的落 interrupted + 打记号，已收工的保持 done。
  - 共驾会话也接，但多一道**时间窗：只接最近 2 小时内被打断的**。理由：lab 停了很久再开，多半是老板有意关的，不该把旧活翻出来。守航态仍按契约期限判。
  - 统一边界：要有 sessionId、老板没按过停、非只读窗；**排除巡视 run**（巡视有 `sweepIdleStops` 定时兜底，再接一遍就重复）；同员工同工作区只接一条（`busyRunFor` 挡住，`startRun` 同步入 `liveRuns`，循环内即生效）；每条最多 2 次（持久 `bootResumes`）。
  - 接回提示按类型分化：守航核对覆盖矩阵 + 附 `guardedResumeNote`，共驾核对任务档案 / 实施记录 / git；措辞按 how 区分「非正常退出」与「被重启（正常关停）」。
- **验证**：隔离实例（`OFFICE_LAB_RUNS_DIR` 临时目录 + 新端口 + `OFFICE_LAB_PATROL=0`）预置 6 条 run：共驾 crash 新近→接；共驾 crash 3h 前→不接；带关停记号→接（措辞为「正常关停」）；老板按停过→不接；done→不动；`bootResumes=2`→落 ⛔ 不接。全部符合（假 sessionId 故接回后 SDK 报错转 error，属预期）。`gracefulShutdown` 的记号路径未端到端验：Windows 上托盘 `taskkill /T` 不带 /F 对无窗口 node 通常不生效，3 秒后 /F 强杀，实际多走 crash 路径——两条路径现在都能接回。
- **教训**：补一个洞时把它所在的「矩阵」画全（守航/共驾 × 崩溃/正常关停）。§3.141 只修了出事那一格，同一张表上另外两格是同一个洞。

### §3.146 自动接回次数做成设置项（默认 2→10）+ 指数退避开关（2026-10-07，老板：「接回次数写死的 2 次吗」→「做成设置项，另外增加指数尝试的开关，默认尝试次数改到 10 次」）

- **现状**：§3.141/§3.144 的接回上限是常量 `BOOT_RESUME_MAX = 2`，计数 `bootResumes` 按会话持久累计、永不清零——长会话偶发被打断两次后，额度就在整个生命周期里用光了。
- **对策**：
  - 上限进 `chainConfig.bootResumeMax`（默认 10，可设 0–50，0＝不自动接回），设置 → 通用 可改，`POST /api/chain-config` 增量合并；计数口径不变（仍是每会话累计、不清零）。
  - 指数退避 `chainConfig.bootResumeBackoff`（默认开）：第 n 次接回前等 `0`（n=1）/ `30s·2^(n-2)`（n≥2），封顶 30 分钟——10 次依次约 0/30s/1m/2m/4m/8m/16m/30m/30m/30m。**取舍**：上限从 2 放到 10 后，若是会话自己跑的东西把机器拖垮，不退避就是 10 次连环崩；第 1 次仍立即接，保住「偶发一次重启马上续上」的体验。
  - 退避等待期间的三个边角：① 到点再判一次（`bootResumeEligible` + 仍是 interrupted + 未超上限 + 自动接棒仍开），期间老板回话 / 巡视续跑 / 按停都会让它作罢；② 任何 `sendToRun` 都撤掉排着的接回（清 `bootResumePending`）；③ 等待中引擎又停了：`bootResumePending` 持久记着当时的打断原因，下次启动照原因接着排，**不算新的一次**（次数在真正接回时才 +1）。
- **验证**：隔离实例（临时 `OFFICE_LAB_RUNS_DIR` + 端口 4799 + 关接棒/巡视/守航/接回）验接口：默认返回 10/true；POST 99→钳到 50、关退避均落盘；POST 0 可存。退避定时器路径未端到端跑（需真会话 + 等待），靠代码审读。
