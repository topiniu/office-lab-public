### 3.1 常驻流式会话生命周期
- 每个活跃 run 持有：`_q`（长活 query）、`_input`（promise 队列 async generator 输入通道）、`_abort`（AbortController）。
- `startRun`（首轮/resume 冷起）→ `consumeStream` 逐条消费 → 每个 `result` = 一轮收工 `onTurnComplete`（落 done/接棒/沉淀/推送，**query 不关**）→ 空闲 `IDLE_CLOSE_MS`(3min) 后 `_input.close()` 优雅收束。
- 续轮（`/reply`、autoChain 回发）走 `sendToRun`：query 仍活则 `pushTurn` 热推（**prompt 缓存热**）；已 close 则 `resume` 冷起。
- 取舍：3min 空闲窗对齐 <5min 的 prompt 缓存 TTL——留窗口内多轮享缓存，超窗才释放子进程省资源。


### 3.2 模型与思考预算分档
- 全员统一走 **Opus**（含闲聊）：早期菲菲/波比及所有 chat 走 Sonnet，被感知成「变笨/变浅」，遂全部提到 heavy。Sonnet 仅留给后台通知精炼器。
- 思考预算封顶 `MAX_THINKING_TOKENS`（heavy 24k）：曾见单轮空想 36500 token / 65 分钟，加天花板兜底防失控；全员 Opus 后从 12k 放宽到 24k 让其「想得开」但仍有上限。


### 3.5 自动接棒（方案 B + 混合扳机）
- **方案 B**：员工间交接**只走 office-lab 派真实 run**，禁止用 Task/Agent 工具把别人的环节嵌套进自己 run（那样 office-lab 看不到、对方状态不亮、交接等于没发生）。
- **混合扳机**：收工汇报里 `【下一棒】<员工>｜<指令>` → 前进(call，新建 run，`callerRunId` 供回发)；`【交回】[@runId]｜<报告>` → 回发(resume 委托者会话，不新建)；`【等你拍板】<事项>` → **门优先**，有门一律停、无视是否也写了下一棒。
- **标记解析铁律（2026-07-14 两轮踩坑定型）**：① 标记必须**独占一行**（指令里常引用标记名）；② **全文搜索取最后一条**（不 slice，长 prompt 会截掉真标记）；③ 指令/报告**支持多行**（吃到下一个标记行/结尾）。
- **服务端强制守卫**（不信 agent 守规矩）：`maxDepth` 天花板、回发 self/busy/unknown/no-caller 拦截；**深度只计 call 不计 return**（中枢型员工反复派活收回不虚增深度）；**裸式【交回】<员工名>｜纠偏为 call**（防中枢型员工活派不出去）。
- **`【下一棒】自己`＝自续（不是死循环，2026-07-30 改，见 §3.32）**：员工派给自己 = 继续干下一块，新起一轮同员工 run 续做；用独立 `selfChainMax` 预算兜底（不占 `maxDepth`）。此前是「自环→终止」，掐死了「全速建到预检门」这类长任务自续。
- 早期「聊天一律不接棒」导致跟员工聊天时其收尾的【下一棒】被丢弃 → 2026-07-14 放开，靠标记而非 kind 判断（聊天随口回答不带标记，天然安全不接棒）。
- **会话看板**：`logConversation` 落 `conversations.jsonl`，按 `threadRootId` 分组（同一交接链共享 root），dispatch/chat/call/return/blocked 五类。


### 3.6 教训自动沉淀（trajectory memory）
收工汇报的 `【教训】<一句话>` 行由 server 自动去重 append 到员工 `memories/*.md`（带日期 + runId），下次派工自然读到——把「手动追加靠自律」升级为「从真实 run 自动落库」。


### 3.7 注入前导（dispatchPreamble）
派工/回发消息头统一拼三块，减轻 agent 负担、给团队感：
- **任务快照**：server 复用 `/api/tasks` 同款抽取器（`extractEntries`/`extractNextSteps`/`extractPendingDecisions`）从最新档案现抽 1-3K 注入。动机：任务档案曾达 152KB（时间线占 50%），要求 agent 每次全量读占派工读负担 ~85%；改为注入快照后 agent 读快照即可开工。
- **同事近况**（peer awareness）：从 runs 注册表抽其他员工最新动态，从孤立 session 变成有团队感。
- **猪猪(Zhuzhu)对接**：仅对 `injectFor` 员工（默认迷糊）注入，逼其开工前 GET 线上对接文档拿最新协议（基地址会在机器间漂移、散落硬编码易漏 → 集中一处配置，一律以设置页/注入块现值为准；2026-08-13 曾因 SOP/代码默认值写死旧 IP 与设置页打架致迷糊 curl 超时误判"环境卡死"，已清所有写死副本）。


### 3.9 人工 Pass（唯一服务端写档案点）
`.md` 原则上只由员工 Claude 写；`POST /api/task/manual-pass` 是唯一例外——用户自测通过时勾掉「流程状态」首个未勾项 / 把条目「状态」列置「人工Pass」，跳过对应 agent。不做 git commit（守禁自动提交），改动留工作区。


### 3.17 需求 intake 入口 = 复用，不是新子系统（2026-07-23）

企微搬不了原始多方对话（合并转发不支持、逐条转发丢发件人——SDK 只认 text/image/mixed/voice/file），退化为「多选复制文本（带发件人+时间戳）+ 截图」进料。落地时发现**不用造新子系统**：现有「跟菲菲 chat + 附件」链路（附件拼 `- <路径>｜<名>` + `[请用 Read 工具查看]`、`/api/upload`）+ 看板菲菲是 `claude_code` 完整 agent 自带 **Read 工具（Claude 原生能读图）** + 「读多方对话提炼需求」SOP，三者叠加即端到端可跑。所以 intake 入口只是：① 顶栏一个「整理需求」按钮预置框架指令（`openIntake` 复用 `openChat`+composer+attach）；② 给 dispatch 菲菲补 `feifei-caps` 以统一登记出口。取舍：**能靠既有能力拼出来的，就别造第二套**（与"企微 intake 汇合飞书、避免平行台账"同一取向）；截图理解直接吃 Read 工具的多模态，省掉自建视觉管道。企微内直接读图是另一条（sidecar 下载 media，SDK 能力待验证），不阻塞本入口。


### 3.25 子代理（SDK sub-agent）的一等可视化（`parent_tool_use_id` 提维，2026-07-25）

问题：员工用 `Task`/`Agent` 起子代理时，Agent SDK 把子代理的 assistant/user 消息打上 `parent_tool_use_id`（= 那个 Task 调用的 id）混在**同一条 query 流**里。引擎从 v0.1 起就在 `normalizeEvent` 里把这个字段**透传却从不读**——下游（状态派生 `deriveActivity`、聊天渲染 `renderEvent`）都当它不存在。后果：① 子代理跑时，侧边栏/会话头显示的"正在检索代码"其实是子代理的动作却**错挂在员工本人名下**，Task 调用只回静态"正在起辅助子任务"；② 聊天窗口把子代理的思考+工具+文本**拍平**渲染、顶着员工头像冒出、并进父级工具组，把员工自己的主线淹没，父级 Task 行还把子代理整篇报告塞进 140 字摘要。一句话：子代理是引擎里**早已存在、却从没被当作一等公民**的东西。

**机制取舍**：
- **把 `parent_tool_use_id` 提成一等维度**，而不是继续拍平——状态分层到"员工·子代理X 正在…"，聊天流把子代理事件收进父级下方的可折叠嵌套块。这是最小但正确的改动方向：字段本就在流里，只是没人读。
- **默认收起（用户拍板）** 而非默认展开：子代理过程可能几十行，主线要保持员工自己的叙述为主，要看细节再点开。
- **单指针 vs 通用交织重构**：关键不变量——**一个 query 内，子代理在其 Task tool_use 与对应 tool_result 之间跑完，其间父级被阻塞不出消息** → 子代理事件是**连续块**，不与父级交织。因此前端用单个 `appendRoot` 指针（+ 各上下文自存 `curToolGroup`：主线 `mainToolGroup`、子代理 `sa.tg`）即可，`switchContext(pid)` 在事件入口切上下文，**无需**做「任意时刻多路并发 DOM 目标」的通用交织重构。这是刻意省下的复杂度。
- **块挂在哪**：`.tool-group` 是**默认收起**的 `<details>`，若把子代理块塞进父级工具组的 `.tg-rows` 里会被双重折叠、看不见。故改为按当前 `appendRoot` `appendNode` 追加——依连续块不变量，子代理事件紧跟父级 Task 之后到达，块自然落在那个 Task 工具组**下方**、作为主线里可见的一等行（子代理再起子代理时则落在外层子代理体内，递归成立）。

**已知局限（供复盘）**：SDK 只暴露**一层** `parent_tool_use_id`（直接父）。子代理再起子代理时，深层块靠"父行 `toolRows[pid]` 仍在 → `appendNode` 落外层子代理体"递归成立，但若拿不到深层 meta 会退化成通用 `agent` 标签。这些员工（菲菲/GG Bond/迷糊/波比）极少深层嵌套，v1 接受；真出现多层再考虑用 id 链还原完整层级。

**改动落点**：`server.js`（`trackSubAgents` 注册表 + `deriveActivity(ev,run)` 分层 + `toolActivityLabel` 动态 Task 标签）、`app/public/app.js`（`switchContext`/`ensureSubAgent`/`appendRoot` + `appendNode`/`lastMsgRow`/`msgRow` 作用域化 + Task 收工盖结果戳）、`style.css`（`.subagent-group` 等）。验证：`node --check` 双通过 + 隔离实例（临时 runs、未碰生产）确认服务启动与资源刷新；真机点验交用户。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.26 多头并行：抄送(cc)第三种交接原语 + 共享总线写收归引擎（2026-07-27）

问题：从 v0.1 起，员工间交接只有 `【下一棒】`（call，交棒即停）/`【交回】`（return，回发即停）两种，`autoChain`（`onTurnComplete` 后解析标记）是一棵 **call/return 深度优先树**——概念上永远同一时刻只有一个员工在推进。老板在一次验收里踩到痛点：让 GG Bond 修个小问题，SOP 却逼「起草文档→交菲菲分诊→菲菲交回→才开工」全程串行等。核查后确认：**不同员工的 run 本就能并存**（`liveRuns` 是 Map，`busyRunFor` 只挡「同一员工开第二条」，不挡跨员工并发；`/api/dispatch` 同样只按员工挡），串行纯粹是「缺一个扇出原语」+ SOP 约束。真正的并发雷区只有一个：所有员工共写的 `tasks/*.md`（§3.3 的 Edit 锚点失配静默失败会被并行放大）。

**机制取舍**：

- **抄送做成「回合内工具」而非「回合边界标记」（承重决策）**：老板要的「GG Bond 一边改代码、一边知会菲菲并行更新 facet、自己不停等」本质是**回合内**事件——在一个长回合中途知会、然后**继续这同一回合**。而标记只在 `result`（回合已结束）才被 autoChain 解析，给不了「继续」。故做成 in-process MCP 工具 `cc_colleague`：调用时作为副作用派生兄弟 run + **立即返回**，发起方回合从不中断 = 教科书 fire-and-continue。有现成先例（`stage_requirement_intake`/`feifei-caps` 同是「副作用派生 + 立即返回」的 bypass 下可用工具）。
- **刻意不走「引擎 re-push 续跑」让发起方继续**：那正是 §3.3 当天被回退的错误方案（自动续跑锁死 running、`/reply` 409）。工具天然绕开——发起方压根没结束回合，无需引擎推它。
- **兄弟 run 血缘**：`callerRunId=null`（cc 是知会不是委托、不回发）、`chainDepth+1`（复用现有 `maxDepth` 天花板兜「A 抄 B、B 抄 A」乒乓与链深失控）、继承 `threadRootId`（会话看板自然归到同一线程组，前端从「线性链」变「扇/树」时间戳流，零新增 SSE 类型：复用 `handoff`/`conversation` 加 `kind:'cc'`）。
- **广度闸（新增风险类）**：`maxDepth` 只挡单链**深度**，挡不住扇出**广度**（每 run 抄 2 人、8 层内可爆 256 条并行 run，线性接力从未有的成本/DoS 风险）。加两道保守闸：单回合 cc ≤2、同一 threadRootId 并存活跃 run ≤4，超限拒绝 + `handoff-blocked`（reason `cc-fanout-cap`/`cc-thread-budget`）。
- **共享总线写收归引擎（并发安全的核心）——且这条被「全员 bypass」逼成唯一解**：`tasks/*.md`（frontmatter 状态 + 时间线）此前由员工各自用 Edit 读-改-写，并行下必然 clobber + 锚点失配静默失败。收归引擎后由 `append_timeline`/`set_task_status` 工具 + per-file 锁 + 原子 temp→rename 串行落盘，引擎持磁盘为准、无「锚点」概念 → 同时根治两类竞态。**⚠️ 关键根因，务必记住别再走回头路**：四员工全 `permissionMode:"bypassPermissions"`，而 `startRun` 在 bypass 下**不挂 `canUseTool` 回调**（`if(!isBypass) options.canUseTool=…`）——所以「用 canUseTool 拦截档案写、加进程内 advisory 锁」这条看似自然的路**对现有员工全部失效**；bypass 下仍恒生效的只有 deny 名单。把写收归引擎是 bypass 下能给共享总线原子性的唯一可靠手段。将来若有人想「给档案写加个锁」，先想清楚 bypass 这道坎。
- **不上 git worktree 隔离（诚实取舍）**：三条并行流天然按文件分区（GG Bond 改代码/实施记录、菲菲改需求/facet、迷糊改用例），真正重叠的只有 `tasks/*.md` 一个文件。worktree 是「隔离任意文件并发」的重武器，用在这里反而要写「状态文件三方结构化合并器」（谁的 status 赢、时间线怎么按时间戳交织），且砸掉「产物永远是仓库里那一份活文件 + `fs.watch` 实时刷」的核心不变量。worktree 留给未来「两员工要并发改同一个**产品代码文件**」时再说。
- **deny 路径分区（Option A）P0 未做**：唯一跨员工共享写热点是 `tasks/*.md`（已收归解决），产品文件已被现有 feifei/bobby code-lock + 各角色写各自不同文档天然分区、且只有一个编码角色；给迷糊加 code-lock 会与既有「迷糊准写测试」意图冲突、收益边际，故按下不表。

**协作红线松动（老板 2026-07-27 拍板）**：验收/预检修复走**并行分诊**——GG Bond 立即开修 + 并行 cc 菲菲定性，不必串行停等她分诊。**但缺陷 vs 变更的分类权仍归 facet 主人菲菲、GG Bond 红线#1「不擅自扩大需求」不变**——松动的只是「等待」，不是「谁来分类」。这是对「UAT→PM 分诊→开发」这条事故换来的红线的**受控**松动，边界钉死在「无歧义地明确要修 → 可并行；涉 facet/验收标准歧义或扩范围 → 仍等菲菲结论」。

**改动落点**：`server.js`（`makeCollabTools`：`cc_colleague`/`append_timeline`/`set_task_status` + 档案写助手 `engineAppendTimeline`/`engineSetFrontmatterScalar`/`atomicWrite`/`withArchiveLock`；`startRun` 给全员挂 `office-lab-collab`；`createDispatchRun` 加 `threadRootId`/`ccFrom`；`beginTurn` 归零 `_ccThisTurn`；`CC_MAX_*` 常量）、`app/public/app.js`+`style.css`（cc 徽标/toast）、四份 SOP（`ggbond`/`feifei` 工牌 + `roles/`）。**P1 待办**：标记式 `【抄送】`（回合边界扇出）+ `allMarkerBlocks` 取全部、登记表状态列收归、迷糊/波比工牌同步、cc 并行视觉区分、标记解析回归测试。验证同 CHANGELOG `[Unreleased]` 同名条目（含 5 路并发 `append_timeline` 不丢的独立测试）；真机端到端交老板走一遍。


### 3.44 聊天窗口「无感排队追加」+ ⚡接管中间态：把被 409 挡掉的 SDK 原生流式输入还回来（2026-08-01，用户复盘驱动）

问题：老板反馈聊天窗口里员工运行中的两处输入体验断裂：① 点「⚡接管」文字**立刻消失**、要等真正接管完成才由冷续跑补出气泡，中间一段空窗用户不知系统在干嘛；② 记忆里「CC 是可以无感追加消息的——用户只管点发送，系统自己决定何时真正喂给进程」，但工作台运行中回车却被 **409『still running』拒收**（`server.js` 旧逻辑），且占位符还写着「Enter 是排队追问」，**名不副实**。

**根因**：引擎底层用的 Claude Agent SDK 本就是**流式输入模式**（`makeInputChannel` 的 async generator 喂给 `query`），SDK 原生支持「运行中 push 一条消息 → 盖 uuid 入队 → 在下一个自然边界 coalesce 进下一轮」——这正是「无感追加」。这条能力一直存在，只是 `/reply` 运行中分支**一刀切 409**（那是历史上「空 result 自动续跑」翻车后为求稳的产品选择，见 §3.3），把排队通道也一起挡了。真机确认：`sdk.d.ts` 明确 `Query.interrupt()` + 异步消息 coalesce（`interrupt_receipt_v1` / `still_queued`）。

**修复（老板两项拍板）：发送时在跑=默认无感排队、保留 ⚡接管=立刻打断；接管沿用 abort+冷续跑、只补中间态。**
- **`/reply` 运行中改三岔**（`server.js`）：① 显式 `takeover` 或卡死 → 硬打断（保持原 `_abort.abort()`→`handleStreamEnd` 冷续跑，不动生命周期）；② 非接管非卡死且 query 仍活 → **`enqueueTurn`** 无感排队；③ status=running 但 query 已不活（异常）→ 回退硬接管。
- **`enqueueTurn` 刻意不走 `beginTurn`**（关键取舍）：`beginTurn` 会重置 `_turnText/_turnActive/_ccThisTurn`——那是**当前正在跑的那一轮**的状态，mid-turn 翻新会污染它、误判空收工/抄送计数。排队只做三件事：立即 append `user-msg`（带 `queued` 标记回显气泡）、`_input.push`、广播 `run-queued`；status 不动，等 SDK 真正开跑这条时 `consumeStream` 见 assistant 消息自然把 status 顶回 running（`server.js:2398` 既有逻辑）。`_queuedCount` 仅供 UI，`onTurnComplete` 复位。
- **为什么接管不改用 `q.interrupt()`**（取舍）：SDK 原生 `interrupt()` 更优雅（停在下个工具边界、会话保温、不冷起子进程），但要重构 `handleStreamEnd` 的 abort 三分支（接管/自动续跑/终态都挂在「abort→consumeStream 抛错→统一收尾」上）——生命周期风险大。本次**只补中间态**、机制沿用 abort，把 `interrupt()` 留作后续。
- **中间态闭环**（`app/public/{app.js,style.css}`）：点接管后**输入框文字保留**（不再立刻清空）、禁用 + pill 翻「正在停止…准备插入」（`takingOver` 标志 + `enterInterrupting`/`exitInterrupting`），直到真正投递的 `user-msg` SSE 到达（`renderEvent` 里判 `!replaying && takingOver && !queued`）再清空——形成「文字保留→停当前动作→真正插入」的可见闭环。接管失败/会话终结（收工/error lab）有兜底解除、保留输入便于重发。

**新增前后端契约**：`user-msg` 事件多一个 `queued` 布尔；新增广播事件 `run-queued`（`{runId,employee,queued}`）与 `run-interrupting`（`{runId,employee}`）；`RUN_PILL` 加 `interrupting`（复用 accent+pulse，无新色）。未改 HTTP 端点形状、run 形状、标记解析。

**通用教训**：① **底层框架给的能力，别被上层一刀切的「求稳」策略永久埋掉**——409 当初是为治「自动续跑翻车」，却顺手把无关的「排队追加」也挡了；治具体病别下过宽的禁令，留一条「正常路径」的活口。② **占位符/文案是契约的一部分**：「Enter 是排队追问」写了却是 409，比不写更误导——文案说的和代码做的必须一致。③ **乐观 UI 要有「落定信号」**：接管的中间态靠「真正投递的 `user-msg` SSE」收尾，而不是点击即清——把「系统还在处理」如实显示到有确定信号为止，比「点了就假装完成」诚实。④ **mid-turn 改状态先问「这动的是哪一轮的账」**：`beginTurn` 对「新一轮」是对的，对「往在跑的轮里塞消息」是错的——同名操作在不同时机语义不同，排队路径必须绕开翻新逻辑。

**改动落点**：`app/server.js`（`/reply` 三岔 + `enqueueTurn` + `onTurnComplete` 复位 `_queuedCount` + `run-interrupting` 广播）、`app/public/app.js`（`sendComposed` 处理 `queued`、`renderEvent` 排队标签 + 接管收尾、`takeoverRun`/`enterInterrupting`/`exitInterrupting`、`setRunPill` 中间态、`RUN_PILL`、全局 SSE `run-interrupting`、占位符/注释订正）、`app/public/style.css`（`.queued-tag`，走语义 token，已过 §3.29 结构自检：括号 899/899、注释 171/171、无 `token*/`）。引擎改动**需重启 server**；前端按 mtime 刷 `?v=`。`node --check` 双通过；端到端（排队 coalesce/多条合并/中间态/卡死回退/非运行态回归）需隔离实例（带 `OFFICE_LAB_RUNS_DIR`、用完即停、勿动生产）眼校。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.46 委托者忙碌时下游【交回】改「无感排队」：补齐 call/return 与用户输入的对称性（2026-08-01，缺口驱动）

问题：B 完成后 `【交回】` 给 A，若 A 正在 working，`autoChain` 回发分支（`server.js` 约 2822）命中 `return-busy` **直接阻断**——B 的报告只留在 B 的收工汇报 / 看板时间线里，**不进 A 的会话，且无自动重投**；A 后来收工了引擎也不回头补送，得人工接管。漏看那条 `handoff-blocked` 提示 = B 的结果悬空丢失。

根因：**同一件事在两条路径上待遇不对称**。「用户 → 忙碌 run」早在 §3.44 就有了 `enqueueTurn` 无感排队（push 进在跑的 query、SDK 择时 coalesce），但「员工交回 → 忙碌 run」这条 autoChain 回发路径**从没接入**，遇忙 fail-safe 阻断。call（`【下一棒】`）遇忙停下是对的（并发改同一工作树会撞），但 return（`【交回】`）只是往上游会话塞一条消息、不动工作树，本可以像用户消息一样排队。

对策：回发分支加 `targetLive`（`liveRuns.has(id) && _q && _input`）判定——A 在跑且会话仍活 → `enqueueTurn(target, prompt, 'dispatch')` 排队 coalesce 进 A 下一轮（复用用户 `/reply` 同一机制），不打断、不丢；仅「running 但 query 已不活」的异常态保留 `return-busy` 硬阻断，`no-caller/unknown/self/nosession` 守卫与「回发不计深度」不变；`handoff` 广播加 `queued` 标记。

通用教训：**加了一条通用能力（无感排队），要回头盘点「所有本该享受它的入口是否都接上了」**——`enqueueTurn` 当初只接了用户 `/reply`，employee 交回这条同构入口被漏掉，于是同样的「往忙碌会话塞消息」一个顺一个卡。能力与入口要成套推，别只打通最显眼的那条。

**改动落点**：`app/server.js`（`autoChain` 回发分支 `targetLive`/`reason`/`queued`）。`node --check` 通过；引擎改动**需重启 server**；端到端（A 忙时 B 交回排队 coalesce / A 空闲走 resume / running-not-live 仍阻断）需隔离实例眼校。详见 CHANGELOG `[Unreleased]` 同名条目。


### §3.60 会议室：为什么用「一次性隔离 query」而不是复用 run 骨架（2026-08-07，功能驱动）

**需求**：老板想要一个「会议室」——让员工坐下来复盘某次/历史迭代的经验教训、互相吐槽、自我审视、表达改进希望。

**关键设计抉择：会议室刻意「不复用」流水线的 run 生命周期骨架。**

工作台的员工引擎是一条精心设计的脊柱：`createDispatchRun → startRun → consumeStream → onTurnComplete → autoChain → handleStreamEnd`，配套常驻流式 query（多轮热推 prompt 缓存）、watchdog 自愈、方案 B 自动接棒（解析 `【下一棒】/【交回】/【等你拍板】` 标记）、巡视（chaorenq）、审计（feisila）。第一直觉是「会议＝多开几条 run 互相 cc」。**否决了**，因为会议的语义与流水线正交，硬塞会互相污染：

1. **标记语义冲突**：会议发言里出现「下一棒把这条改进项交给 ggbond」这类**自然语言**，一旦走 `autoChain` 就会被误解析成真的派工接棒——会议本无接棒语义。
2. **监督机制误伤**：会议发言天然「说完就停」，会被 watchdog 当空停、被巡视当「该干没干」、被审计当 QA 结论去证伪——全是噪声与误判。
3. **形态不匹配**：会议是**严格串行**（一次一人说、下一位要读到上一位的话），不需要常驻 query / 空闲窗 / 无感排队 / 后台任务那套为「一个员工干一件长活」设计的机制。

**采用的方案**：一条**独立的轻量编排器** `runMeeting`。每次发言＝一个**一次性 SDK `query()`**（`speakOnce`）：喂「当前会议纪要（含老板串场）＋该员工工牌（`buildRolePrompt`）＋会议叠加提示（`meetingOverlay`，把「派工干活」重定向成「复盘发言」、明令禁写派工标记）」，迭代到 `result` 取文本即结束。**这些 query 完全不进 `runs`/`liveRuns` 注册表**，所以 `autoChain`/watchdog/巡视/审计根本看不到它们——零污染，且不必在那些机制里到处加「if 会议则跳过」的特判（那才是会腐烂的耦合）。

**复用 vs 不复用的边界**（复用「身份/持久化/渲染」，不复用「派工/接棒」）：
- 复用：`buildRolePrompt`（工牌人格）、`resolveModel`（每人正常档位）、`logConversation({kind:'meeting'})`（进会话看板）、`nextSeq`+jsonl+SSE 断点续传（仿 `appendEvent` 写 `appendMeetingEvent`）、OLCards 协议（主持人收尾发改进项卡）、前端 `avatar`/`empHtml`/`OLCards.renderCard`。
- 不复用：整条 run 生命周期脊柱与四标记解析。

**只读硬闸**：会议是「聊天不是干活」，`speakOnce` 的 query 下发 **blanket 写工具 deny**（裸工具名 `Write/Edit/MultiEdit/NotebookEdit` = 整工具禁，跨平台可靠，不踩 `codeLockDeny` 那种 `./x/**`/`//abs/**` 的 Windows 路径 glob 坑）＋写类 git deny。因此会议**零副作用**：员工能 Read 复盘/记忆/tasks 去引真实事故增强可信度，但改不了任何文件（符合老板选的「不回写记忆/复盘」）。

**成本取舍**：老板选了「每位员工用其正常档位」（多为 Opus，小呆呆 Sonnet），换人格保真。护栏用 `meetingActive`（一次只跑一场）＋ rounds≤5＋participants≤6＋`MAX_THINKING_TOKENS` 走 light 档，把「6 人 × N 轮 Opus」的开销钉在可控范围。这是 §6 已知短板「全员 Opus 成本」在新功能上的主动收口。

**通用教训**：**当一个新场景与既有主流程「正交」（语义不同、监督机制不该介入、形态不匹配）时，宁可另起一条轻量旁路复用其「原语」（身份/持久化/渲染），也不要硬塞进主流程再到处打特判**——后者会把两套语义搅在一起，且每加一个特判都在给那条脊柱积债。会议室与 run 引擎共享 `RUNS_DIR`/SSE/OLCards/工牌，却各走各的生命周期，就是这条原则的落地。

**产物沉淀（会后纪要，2026-08-07 追加）**：老板选了「对话＋纪要，但**不回写各员工记忆库**」。落法是——会议结束时**由引擎（非员工）**把发言落成 `docs/复盘会议纪要/复盘会议纪要-NoNNN-<日期>.md`，含「可落地改进项」（解析主持人收尾 `olcard` 的 checklist/multiselect 条目）+ 完整发言记录。**关键取舍：写盘的是引擎不是 agent**——这既满足「留下可追溯产物」，又不破坏「会议 agent 全程只读」的不变量（若让 agent 自己写纪要就得放开写权限，反而污染了干净边界）；同时刻意**不**把改进项灌进 `memories/*.md`（那是正式流水线 `【教训】→appendLessons` 的地盘，一场闲聊/复盘会不该自动往权威教训库塞条目，避免噪声沉淀），员工需要就按路径 Read。每场会议另分配一个**单调递增唯一编号**（`No.NNN`，持久化 `seq.json`、删会议不回收）作稳定标识。

**改动落点**：`app/server.js`（会议引擎 `runMeeting/speakOnce/createMeeting/appendMeetingEvent` + `writeMeetingMinutes`/`extractImprovementItems` + seq 计数 + 6 个 `/api/meetings*` 端点）、`app/public/{index.html,app.js,style.css}`（会议室视图/发起弹窗/多发言人直播流/纪要链接/编号）。需重启 server。详见 CHANGELOG `[Unreleased]` 同名条目。


### §3.79 只读咨询窗（consult）：并发闸只该挡「写」，不该挡「聊」（2026-08-18，老板痛点驱动）

**痛点**：老板反馈「GG Bond 正在开发时，我要另开一窗找他排查别的 bug，开不了」。查下去发现前端早就能开多张浮动聊天卡（`web/` 的 `RunDetailProvider.cards[]` + `use-card-stack` 层序），真正的墙是引擎的并发闸：`/api/dispatch` 命中 `busyRunFor(employee)` 直接 409。

**根因辨析（这一步是本节的关键）**：并发闸（§见 CHANGELOG v0.2.x「并发闸」条 + §3.49）要防的是**两条可写会话并发改同一个工作树**——所有 run `cwd: ROOT`、无 worktree 隔离，同员工两条会话会互相踩写代码/实施记录/任务档案（§3.49 的旧会话诈尸事故就是这个形态）。**冲突源是「写」，不是「聊」。** 闸按「员工」这个粒度一刀切，于是把零风险的问话/读码一起挡了——典型的**守卫粒度选错**（与 §3.49 「按线程判而非按员工判」是同一类错误的另一个面）。

**方案**：新增 `consult` 会话档——**零写能力**，因此工作树天然安全，并发闸对它不适用（`busyRunFor` 直接跳过 consult）。三条不变式：

1. **绝对不能写**：`permissionMode:'default'` + `allow=CONSULT_ALLOW`（纯只读：`Read/Glob/Grep` + 只读 Bash `ls/rg/git log|diff|show|blame/tail` 等）+ `deny=consultDeny()`（写工具**裸名**全局禁 + `git commit/push/checkout` + `mvn`/`npm run`/`manage-*` + 重定向/`rm`/`mv`/`sed -i`）。白名单外不硬拒、落既有 `canUseTool` 审批卡（只读窗本就是有人坐在窗前时才开的）。**且一个 MCP 都不挂**——`office-lab-collab` 会写档案且带 `cc_colleague`（能派生兄弟 run！）、`backend` 能重编重启、猪猪能跑真机；零挂载比逐个 deny 可靠（工具根本不出现在工具表里，实测 SDK 直接答「not enabled in this context」）。
2. **绝不进流水线**：`autoChain` 首行 return（不解析 `【下一棒】/【交回】` → 不接棒）、`patrolEligible` false（只读窗「问完就停」是常态，不是空停）、`supersededBy` 不参与顶替、`appendLessons`/`maybePushRunStopped`/`releaseCopyCardMissing` 跳过、`logConversation` 三处不记（会话看板只留正式协作流水）。
3. **不影响忙闲**：`busyRunFor` 与前端 `empRepRun`/`mostRecentRun`/忙闲派生/履历统计一律排除；`buildTeamPulse` 也排除（否则「同事近况」会把咨询窗读成"他正在忙"，污染别人的协作判断）。

**背景注入的取舍**：老板开只读窗最常问的就是「你现在改的那摊跟这个 bug 有关吗」，所以必须给坐标——但只给**指针+摘要**（正式会话 run id / 任务档案 / 上一轮收尾摘要 + 三个代码仓当前分支，分支直读 `.git/HEAD` 不 spawn git），正文让它自己按需 Read。这是 §3.49 教训「跨会话自动灌内容＝串线源头，能不自动注入就不注入」的直接沿用。

**与 §3.60（会议室）的抉择相反，为什么**：§3.60 的通用教训是「正交场景宁可另起轻量旁路，别硬塞主流程再到处打特判」。只读窗**刻意选了相反的路**（复用 run 骨架 + 加守卫），因为两者的复用面完全不同——会议只需要「工牌 + 一次性 query + 落盘」，而只读窗要的是**完整聊天体验**：流式 transcript、附件、OLCards、历史翻页、置顶/删除、会话切换、SSE 断点续传、`/reply` 无感排队。另起旁路等于把 `run-detail.tsx`（800 行）和 `useRunStream` 全再实现一遍。且守卫是**集中的**：7 处，全都在既有函数入口一行 `if (isConsult(run))`，无一处散在业务分支里。**教训升级为**：「另起旁路 vs 复用骨架」取决于**复用面的大小与特判的分布**——特判少且集中（守卫都在入口）就复用；特判会散进业务分支、或复用面只有一两个原语，就另起旁路。别把 §3.60 当无条件教条。

**成本闸**：每员工同时只允许一条在跑的只读窗（`liveConsultFor` → `409 {error:'consult exists', runId}`，前端据此把已开那张卡抬到最前）。语义正好＝老板要的「第二个窗口」，也防手滑开出一堆 Opus 会话。

**已知代价（不修，写进文档）**：正式会话正改到一半时，只读窗读到的是**中间态文件**，分析可能失真——这是「边改边问」的固有属性，不是 bug。真要「两条会话各看一份干净代码」，那是 worktree 泳道（需连带解决共享 dev 库 `192.0.2.103:3306`、端口单例、归并锁，成本远高，另议；见 `全时双态协作-设计.md` §「不在同工作树硬切」）。

**验证手法（可复用）**：① 从实文件 eval 出 `busyRunFor`/`liveConsultFor` 跑 9 组用例（含「正式+只读并存时两个闸各认各的」）；② `autoChain` 守卫用**依赖 Proxy 哨兵 + 正式会话对照组**做确定性验证——只读会话在触碰任何流水线状态前就 return，对照组命中 `chainConfig.enabled`（**证明守卫确实是唯一原因**，而不是"恰好没进那条分支"）；③ 隔离实例（临时 `OFFICE_LAB_RUNS_DIR` + 4789 端口）真机跑一条只读窗，实测 `Write` 被判 not enabled 且目标文件确未生成、只读 `git log` 静默通过、第二条 409、`/api/conversations` 零记录、全程未派生新 run。**注意「让模型自己写标记来测守卫」不可靠**——它读了 `CONSULT_MANDATE` 后正确地拒绝写标记，那一轮测不出东西；守卫要用①②这类确定性手法验。

**改动落点**：`app/server.js`（`isConsult`/`CONSULT_ALLOW`/`consultDeny`/`CONSULT_MANDATE`/`consultBackgroundBlock`/`liveConsultFor` + `startRun` consult 分支 + 7 处守卫 + `/api/dispatch` consult 路径）、`web/src/**`（`newConsult` + 只读卡 UI + 三个入口 + 忙闲派生排除）。详见 CHANGELOG `[Unreleased]` 同名条目。

### §3.136 教训注入的相关性打分对「工具链类教训」系统性失灵：答案在磁盘上躺着，读侧够不着（2026-09-21，run `20260921074152-5a44fd` · §3.6 写侧 / §3.103 读侧的第二次补齐）

**现象**：同一条 run（见 `引擎-权限与安全.md` §3.135）里，波比花约 **7 分钟、27 条 Bash** 在现场摸索 glab 的认证 host、配置文件位置、项目数字 ID、哪种命令形态能跑通——其中一条 `find /c/Users/example -name config.yml -path '*glab*'` 单条就跑了 **80.6 秒**。而这些答案 `memories/bobby.md` 里**已经记了 5 遍**（第 117/133/135/137/144 行，从 08-18 记到 09-07），结论完全一致。

**根因**：§3.103 补的读侧 `buildLessonsBlock` 是**纯相关性打分**——中文 bigram 在「教训正文 × 派工文本」上的字面重叠。于是：

> **越是纯工具链 / 环境类的操作性教训，越选不上。**

它们的词是 `host:port`、`ssh remote`、`-R 参数`、`Exit 49`；而派工头讲的是业务（「规格正确性链 / REQ-0342 / QA 收束」）。字面交集近乎为零。拿那条 run 的真实派工原文回放打分，8 条 glab 教训在 125 条里排 **118 / 121 / 123 / 124 / 125** —— **全部垫底，一条没注入**。被选中的 14 条全是「双库 DDL」「收尾五件套」这类业务词密集的。

这不是打分调参问题，是**判据与需求正交**：这类教训的价值恰恰在于「跟本轮说什么无关，每次都用得上」，而相关性打分度量的正是「跟本轮说什么有多像」。用它去选这类教训，方向本身就是反的。同一个坑记了 5 遍还年年重踩，**"重复记录"本身就是"该无条件注入"的信号**，却被一个只看相似度的选择器持续过滤掉。

**对策**：给教训库开一个**常驻段**——`## 常驻…` 小节内的条目**不过打分、每轮无条件注入**，专放"固定事实 + 反复踩的坑"（环境/工具链/命令形态这类）。关键设计取舍：

- **常驻配额是纯加法，不摊薄相关性配额**（`maxItems = nPinned + LESSON_MAX_ITEMS`，字符同理）。否则常驻一多就吃掉近期教训的名额，等于拆东墙补西墙；而这样写，**没开常驻段的员工（ggbond/mihu/feifei）注入量与改造前一字不差**，回归测试直接钉住这一点。
- **常驻段自带独立上限**（8 条 / 2600 字，超出按原文顺序截断）——写飞了只截自己。它是要进每一轮 prompt 的，必须逼作者保持精简。
- `LESSON_MIN_ITEMS` 的兜底计数**只数相关性选出的条数**（`picked.length - nPinned`），否则常驻会把"相关性挂零时的兜底"名额吃光，退化成「只有常驻、没有近期教训」。
- 注入块标题与导语明确区分两类，并写清常驻的用法：「**动手前先照着做，别现场重新摸索**」——不说清楚，模型会把它当成又一段背景噪声。

波比的常驻段首批 5 条 1612 字：内网 GitLab 基址 + 三个项目数字 ID（101 / 102 / 98，含"两个前端默认分支是 release"这个 target 陷阱）、建 MR 的唯一稳妥形态（REST POST，附「别先试 `glab mr create`」及原因）、本机 `python3` 是 Microsoft Store 占位壳子（静默无输出、管道进去整条命令 Exit 49）、「已存在同源 MR 不是失败」、「建 MR ≠ 合 MR」。净增上下文约 1600 字符（~900 token，占起手 85k 的 1%），换回约 7 分钟。

**同时修的上游**：工牌 `.claude/agents/bobby.md` 与 `roles/bobby.md` 里**教的就是那条跑不通的路**（「用 `glab mr create` 逐仓把 MR 建出来」），且「绝对禁止……GitLab API」的措辞让人把"禁止用 API 合并"读成"禁止用 API"。已改为 REST POST 优先、`mr create` 降级为说明其失败原因，并显式点破「用 API **建** MR 是允许的准备动作」。**教训库救不了一张教错了的工牌**：读侧失灵与工牌过时是两个独立故障，叠在一起才凑出那 7 分钟。

**一般化教训**：**检索式记忆只覆盖"想得起来要找什么"的那一半。** 另一半——每次都该照做、但与当前话题字面不搭的固定事实——需要的是**无条件注入**，不是更好的检索。判断哪些该常驻有个便宜的信号：**同一条教训被重复写进库 ≥3 次**，就说明检索侧一直没把它送到。

**改动落点**：`app/server.js`（`LESSON_PINNED_MAX_ITEMS` / `LESSON_PINNED_MAX_CHARS` / `PINNED_SECTION_RE` + `buildLessonsBlock` 两段式选取）、`memories/bobby.md`（新增 `## 常驻` 段）、`.claude/agents/bobby.md` + `roles/bobby.md`（glab 口径）、`app/test/release-deliverables.test.js`（+2 例回归）。详见 CHANGELOG `[Unreleased]` 同名条目。

### §3.142 老板在档案上下文里开口，员工却不知道「这个」指这份档案（2026-10-06，run `20261006011711-ec8fa0`）

**现象**：老板从侧栏「运行环境 · 示例项目 v6.0.0」找菲菲，说「业务同事乙说：项目负责人，这个还需要加入第三方区别与晓娜，其他项目组的任务」。菲菲去翻了项目跟踪的需求、搜了后端代码，最后回「我倾向的理解：你 5 分钟前刚问过 GG Bond 备货单……另外这条跟本会话挂的示例项目 v6.0.0 档案没关系」。

**根因**：信息是全的、**框架是缺的**。派工头依次是：任务档案路径 → 任务快照（29 条条目）→ 【同事近况】→ 老板原话。没有任何一句话说「老板是在这份档案下找你」，于是档案被当成「顺带挂着的背景」；而离原话最近的一块恰好是同事近况，第二行就是「GG Bond：看一下 BHJH… 备货单为什么在今日跟进列表里」——指代不明的「这个」被近因最强的那块吸走了。同事近况原本的用途（交接判断）在这里变成了干扰源。

**对策**：
1. `bossTopicAnchor`：**仅老板亲口说的**消息（`createDispatchRun` 的 `fromBoss` 判据——非 caller / cc / 巡视 / 影子审计 / 自续 / 引擎续跑；以及会话内回话），在 `dispatchPreamble` 末尾、紧贴原话之前注入【老板这句话的上下文】：指代默认落在本档案、先去快照条目里找最贴近的；点名同事近况不是话题；明确点名别的系统 / 版本才跳出；拿不准时带着本档案里最可能的那条去问。同事交回等不加——那些消息的话题由消息自身决定。
2. `renderLaneBlock`：绑定了环境且环境挂了档案时，系统提示里点名「本环境挂载任务档案 X，老板在本环境里说的事默认就是它」。系统提示是会话级常驻，派工头是逐轮的，两处都说是为了冷 resume 后也不丢。

**取舍**：没有选择「把同事近况挪到快照之前」或「老板对话时不注同事近况」——同事近况对交接判断仍有用，挪位置只是碰运气；显式说「谁是话题、谁是背景」才是根治。也没有让员工「档案不相关就直接无视」——老板确实可能在某个环境里顺口聊别的事，所以留了「明确点名别的才跳出」的出口。

**一般化教训**：**注入的上下文要说清「它和老板这句话是什么关系」**，只堆信息不给框架，模型就按距离远近去猜关联。

**同日补：反方向——员工知道档案，引擎不知道**（会话 `20261005082355-7387b7`）。老板直接找 GG Bond 聊跟单线上问题，他聊着就开了 v0.1.3.1 修复，但这条会话从头到尾 `taskFile=null`、`lane` 缺省：会话卡没有环境徽标，【运行环境】一直是「未指定」。上面的话题锚只解决「引擎知道、员工没意识到」；这里是「员工推断出来了、却没有途径告诉引擎」。另有一个小洞：老板在会话里回话时附档案，`/reply` 只写 `run.taskFile`、不跟 `run.lane`（`laneKeyOf` 会按档案兜底算出环境，所以并发闸和冷启动注入其实对，但界面上看不出来）。
- **对策**：`bindRunToTask(run, taskFile)` 一个函数两个入口——`/reply` 附档案、员工调 `bind_task_file`。绑档案时会话若还没显式绑环境，就按档案认领环境（`laneForTask`）；已显式绑了别的环境则保持原绑定并说明。
- **为什么让员工自己绑、不让引擎从对话里猜**：猜错了会把代码引到别人的工作树里，代价远大于不绑；员工在对话里已经确认过，让他亲手登记，引擎只负责校验（档案存在、已挂别的档案就不许改绑）。
- **活会话的系统提示不会刷新**：【运行环境】块是开会话时拼进系统提示的，中途绑定后系统提示里仍是「未指定」。所以工具直接在返回结果里给出新环境的完整块，并写明「覆盖系统提示里未指定那段」；下次冷启动时 `laneBlockFor` 自然按新绑定拼。
