### 3.30 性能：反复重启堆积僵尸进程 + 打开超大会话卡死（2026-07-28，事故复盘）

**现象**：老板说「officelab 好像有性能问题，重启好几次了，网页也会偶尔卡死」。排查抓到两条**互相独立**的根因。

**根因 A：`uncaughtException` 兜底把启动期致命错误吞了 → 僵尸进程越堆越多。**
现场 `tasklist` 抓到 6 个 office-lab node 进程，`netstat` 显示只有 1 个真正 `LISTENING` 4700 端口，其余 5 个是僵尸。链条：`server.listen()` 没挂 `error` 监听 → 端口被占时 EADDRINUSE 作为 server 的 `error` 事件抛出 → 无监听则升级为 `uncaughtException` → 而引擎为了「单条 run 的异步异常不拖垮办公室」装了 `process.on('uncaughtException', e => console.error(...))` **只记录不退出** → 于是绑不上端口的进程**也不死**，只剩 `fs.watch(TASKS_DIR)` + `setInterval(sweepStalled)` 空转。每次「重启」若没先杀旧进程，新进程就绑不上端口、变成又一个僵尸。**教训：韧性兜底（uncaughtException 不退出）与「启动期致命错误必须退出」是矛盾的两种诉求——必须给 `listen` 单独挂 `error` 监听显式 `exit(1)`，让致命启动错误绕开兜底。** 修复：`server.on('error')` 命中 EADDRINUSE 即打印「已有实例在跑」并 `process.exit(1)`。

**根因 B：会话回放整段重放，超大历史压垮前端。**
`/api/runs/:id/events` 冷开时 `fs.readFileSync(整个 jsonl).split('\n')` 后逐行 SSE 全量重放。而 `runs/` 已膨胀到 291MB、最大单会话 10MB（数万条事件）。打开这种会话 = 服务端一次读 10MB + 前端逐条渲染几万个节点（每条文本还 `marked.parse`）——即便前端有 `MAX_CHAT_ROWS=1500` 的 DOM 上限，事件仍被全量处理一遍，主线程卡死。修复：加 `REPLAY_TAIL=3000`，冷开只回放尾部 3000 条；SSE id 保持**绝对行号**（= `appendEvent` 的 `nextSeq`），所以浏览器自带的 `Last-Event-ID` 断点续传照常工作（重连只补新事件、不重复）；有更早历史被省略时顶部给一条系统提示。**教训：任何「打开即全量重放/全量渲染历史」的路径，都要预设历史会长到病态量级，从设计上就分页/截尾，而不是等它撑爆才补。**

**尚未处理的跟进项**（本轮只修 A、B 两个直接卡点）：① `runs/` 291MB 无归档/裁剪机制、`index.json` 626KB 且 `/api/runs` 每次全量序列化返回；② 5 个僵尸进程要按 PID 定点清理——运维记忆明确「重启走托盘、不强杀、绝不 rm 生产 `runs/`」，故清理需人工确认后按 PID `taskkill`（它们都不占端口，定点杀不误伤在服务的实例）。

（存档）原始决策记录：设计系统切换 Linear → shadcn/ui（Zinc 底 + 保留薰衣草 primary，2026-07-28，后已退回）

承 §3.28（不迁 React 的取舍）。老板从「借解剖学」进一步要求「样式跟 shadcn/ui 一致」。这里做了两个层面的取舍：

- **视觉可以像 shadcn，但栈不迁**：shadcn 的设计语言（token=CSS 变量、组件样式编译后=普通 CSS）**能纯 CSS 复刻**，不需要 React/Tailwind。所以采纳其**视觉**、守住 §3.28 的框架取舍（零依赖/纯静态无构建）。这是「要 shadcn 的脸、不要 shadcn 的身子」的刻意选择。
- **保留薰衣草 primary（品牌不丢）**：shadcn 默认 primary 是中性近黑/近白，但它本就支持自定 primary。老板拍板保留薰衣草 `#5e6ad2` 只落在 user 气泡/主按钮/焦点环，其余（表面/描边/圆角/阴影）走 shadcn **Zinc** 中性底。既是 shadcn 观感，又保住辨识度。

**为什么改动量可控**：全站 CSS 早就走语义 token（§2 架构就定了 `--canvas/--surface-*/--hairline/--ink*/--primary`）——所以「重皮」主要是**重映 token 顶层**（`:root`/`[data-theme=light]` 换成 Zinc 的 OKLCH 值），全局自动传导，不用逐组件改色。这印证了「语义 token 层」当初的价值：换肤成本 = 改一处 token。再补三样 shadcn 特征：`--radius` 圆角尺度、`--shadow-*` 微阴影（**与原 Linear 明确的「无阴影」相反**，是有意采纳）、字距从 Linear 负字距收敛到 shadcn 平静口径。

**诚实短板 / 待观察**：① 用 OKLCH 与 shadcn 精确对齐，依赖较新浏览器内核（WebView2/现代 Chrome 满足，但若将来要兼容老内核需加 hex 回退）；② 阴影从无到有、字距变化、muted-foreground 文本对比度，这些我（改的人）**看不到像素**，需老板亮/暗两主题真机各扫一遍再微调——这是「盲改视觉」的固有风险，靠事后眼校收口；③ 未强制把所有 `8px` 圆角换成 `var(--radius-md)`（值相等、观感一致，留待顺手再收）。改动落点：`app/public/style.css`（token 层 + 圆角/阴影/字距/组件）、`index.html`+`app.js`（首帧 theme-color）、`app/README.md`+`CLAUDE.md`（设计系统表述）。


### 3.36 聊天窗口加载卡：工具结果内嵌 base64 图撑爆 jsonl（2026-07-31，用户反馈驱动）

问题：老板反馈 GG Bond 最新会话加载卡，过 Cloudflare 隧道更卡。定位到那条 run（`20260730084620-1d8486`）8.87MB 但**仅 1153 行**——平均每行 7.8KB。按类型拆：`user`（工具结果）类占 6.68MB / 298 行，单行最大 606KB。肥的是**工具结果里内嵌的 base64 截图**（截图/读图类工具把像素数据放进 `tool_result.content` 喂给模型「看」）。

**机制取舍（复盘核心）：**
- **两条独立的图片通道，别混**——① 用户/员工**看到的图**走「文件路径引用」：解析成 `office-lab/app/uploads/<file>`，前端渲染 `<img src="/uploads/…">`，浏览器**单独 GET** 取文件、可缓存，jsonl 里只存一小段路径文本；② 撑爆 jsonl 的 base64 走「工具结果内嵌」，是给**模型**看的像素，前端渲染工具结果时 `c.content.map(x => x.text||'')`——image block 无 `.text`、被映射成空串**丢弃**，界面根本不显示。同一张截图常被存两份（一份文件给人看、一份 base64 给模型看），只有后者是纯传输浪费。
- **为什么 `REPLAY_TAIL` 挡不住**：那道闸（§见 SSE 冷开回放）只截**行数**（尾部 3000 条），对「行少但每行巨大」的会话完全无效——1153 行远没触顶，8.6MB 照样整段推。教训：限流要同时看「条数」和「体积」两个维度，只截其一会被另一维度绕过。
- **修在源头（落库前剥），不是修在渲染端**：前端本来就不显示这些图，最省事的是渲染端忽略——但那治不了「传输 8.6MB」这个真瓶颈（尤其过隧道）。所以在 `normalizeEvent` 落库前就把 image block 换成 `[图片]` 占位、剥掉 base64（`stripToolResultImages`，命中才浅克隆、不改原 SDK 消息）。jsonl 从此不臃肿，SSE 推的量、浏览器 `JSON.parse` 的量一起降。
- **为什么剥了模型也不受影响（关键安全论证）**：jsonl 是**纯 display 日志**——全仓库只有三个动作：写（`appendEvent`）、删（删会话）、**读只有一处**（3341 的 SSE 回放给浏览器，已 grep 坐实）。**没有任何路径把 jsonl 回喂给模型**。模型当轮实时就从 SDK 上下文看过图；跨 resume 的记忆走 SDK 自己的 transcript（`options.resume=sessionId`，SDK 独立存盘），与我们这份 jsonl 完全两套。所以剥 jsonl 副本，模型该看见的照样看见。这条论证是「敢不敢删」的全部依据——**改 display 层数据前，先证明它不是任何模型/业务通道的输入源**。
- **存量清洗的并发安全**：一次性迁移 `strip-run-images.js` 就地改历史文件（临时文件+原子改名、坏行原样保留）。风险是「read→rename 之间 live run 追加会丢事件」——故**读 registry 自动跳过 `running`/有后台任务的活跃会话**，只清历史 done 会话；服务在跑也安全（只碰非活跃文件、原子改名不与冷开 SSE 读冲突）。踩到的一个观察坑：验证时发现文件行数从 1153 变 1176，一度疑迁移加行——实为该会话在两次测量之间**又被 resume 用过**（它一直是巡视测试样本），迁移在当时快照上零丢行。教训：拿「活文件」当基准量两次，差异可能来自文件本身在变，不是你的操作。

**改动落点**：`app/server.js`（`stripToolResultImages` + `normalizeEvent` case 'user' 接入）、`app/scripts/strip-run-images.js`（一次性迁移，`--dry` 预览、跳活跃会话）。`node --check` 通过；生产 `app/runs` 已执行迁移：38/223 文件含图，238.5MB → 213.8MB（省 24.7MB），aa5f29 8.87MB → 2.54MB（剥 26 处图、零丢行/零解析失败/零残留 base64、最大行长 606KB→38KB）。引擎改动需**重启 server** 对新事件生效。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.37 聊天历史分页加载 + 全局 loading 态（2026-07-31，用户反馈驱动）

问题：打开会话加载卡、过 Cloudflare 隧道更卡（§3.36 剥图后传输量降了，但冷开仍一次性推最近 3000 条 `REPLAY_TAIL`）；且全站零 loading 态，隧道下开机/打开会话/操作都有「真空期」，用户以为卡死。用户拍板：分页（首屏 ~40 条、滚顶按钮再拉 40）+ 全局 loading。

**机制取舍（复盘核心）：**
- **分页单位是「事件」不是「消息」**：我们消息流底层是扁平事件（每条助手发言、每次 tool_use、每个 tool_result、每条系统签都是一行 jsonl），没有天然的「一条消息」边界。故分页游标就用**行号（seq）**，`GET /history?before=<seq>&limit=40` 返回 `before` 之前一页、每条附 `_seq`。选 40 而非用户口述的 20：一轮问答常含 1 发言 + 数条工具调用 + 结果，20 条常只够半轮；40 条一屏能看到完整的最近几轮，又远小于 3000。
- **沙箱复用 `renderEvent`，而非写第二个渲染器（关键取舍）**：`renderEvent` 是全仓最 delicate 的 300 行——严格正序追加 + 依赖一堆**全局可变聚合态**（`curToolGroup` 工具组、`toolRows` 按 id 回填工具结果、`lastRenderedDate` 日期分隔、`appendRoot/subAgents` 子代理上下文）。要「倒序、成批 prepend 更老事件」，两条路：① 写一个独立的历史渲染器——但会与 renderEvent 长期漂移（两处各自处理派工 chip/聊天记录块/OLCard/子代理…），是维护炸弹；② **沙箱化复用**——`renderHistoryBatch` 存下全部渲染态、把输出目标 `activeChatRoot` 重定向到一个游离 `<div>`、`replaying=true` 抑制贴底，`for(ev) renderEvent(ev)` 渲染进游离容器，再还原全部态、把容器 children 整体 prepend。选 ②：零重复代码、实时渲染逻辑一个字节没动、未来 renderEvent 怎么改历史渲染自动跟上。代价是页内跨边界的 `tool_use↔tool_result` 断链会降级为孤立结果签（可接受）。这条是「delicate 的正序渲染器如何支持倒序分页」的通用解法：**别复制它，沙箱它**。
- **重连 gap：窗口一缩小就暴露的真 bug**：冷开窗口从 3000 缩到 40，原 `floor = Math.max(lastId, len - TAIL)` 立刻出问题——重连（带 `Last-Event-ID`）本意是补 `lastId` 之后的全部增量，但 TAIL=40 时若断线较久（`len-40 > lastId`），`max` 会取 `len-40`、**跳过 `[lastId, len-40)`**。TAIL=3000 时这个 bug 被掩盖（几乎不可能 `len-3000 > lastId`）。修法：冷开才用 `len-INITIAL_TAIL`，**重连分支直接用 `lastId`**、不再取 max。教训：一个常量从「大到几乎不触发边界」调到「小到常触发」，要重扫所有用到它的边界逻辑——掩盖的 bug 会立刻现形。真机验证 `LEI=100 → 从 101 连续到 1176`（旧代码 max→1136 会跳 101..1136）。
- **loading 态覆盖「真空期」而非「慢」本身**：真正的诉求不是让请求变快，是**别让用户以为卡死**。两处最高性价比落点：① 顶部进度条**包裹 `window.fetch` 一处驱动**（inflight 计数）——一次改动覆盖开机串行 fetch + 所有现有/未来操作，无需在每个 fetch 点插代码；② 打开会话时聊天区转圈——因为 SSE 连接+回放**不是 fetch**、进度条覆盖不到，且原本这段 `#run-output` 被 `visibility:hidden` 藏成纯空白（正是「真空」的来源）。全局 `/api/events` 后台 SSE 不做可视化（无感知需求）。
- **诚实短板**：① `/history` 与 SSE 冷开仍是「整文件读进内存再切片」，对已剥图文件（≤2.5MB）无所谓，未纳入本次优化；② 手动上翻大量历史后来实时事件会被 `MAX_CHAT_ROWS=1500` 顶部裁剪削掉（实时优先，可接受）；③ prepend 的视觉（滚动锚定、工具组成形、转圈观感）只能真浏览器眼校，headless 只验到了服务端契约 + 资源交付。

**改动落点**：`app/server.js`（`INITIAL_TAIL` + SSE 冷开/重连 floor + `/api/runs/:id/history`）、`app/public/app.js`（`activeChatRoot` 重定向 + `renderHistoryBatch` 沙箱 + `loadEarlier`/`ensureLoadEarlierBtn` + `chatOldestSeq` 追踪 + `result` 副作用 `!replaying` 守卫 + `installNetBar` 包裹 fetch + `showChatLoading`）、`index.html`（`#net-bar`/`#chat-loading`）、`style.css`（对应样式 + `net-slide` keyframe，复用 `st-rot`；已过 §3.29 结构自检：括号配平、注释 164/164 配对、无 `token*/`）。`node --check` 通过；隔离实例（`OFFICE_LAB_PORT=8795` + 独立 `OFFICE_LAB_RUNS_DIR`，用完即停、生产 8790 未动）验证 history 分页/边界/404 + 冷开 40 帧 + 重连 gap 修复 + 资源交付；浏览器交互态需重启生产后眼校。详见 CHANGELOG `[Unreleased]` 同名条目。

**追加修订（2026-08-11，用户反馈驱动）——分页计数单位从「事件」改回「有意义消息」**：上面选「分页单位=事件、每页 40 条」当时的理由是「没有天然的一条消息边界，40 事件≈最近几轮」。但随着子代理编排普及，**一轮问答里的事件构成彻底变形**：单条派工能带出一个子代理块 + 十几次 tool_use/tool_result + 多条「后台任务完成」系统签，40 个事件常常连一条真正的对话气泡都凑不满——老板反馈截图里满屏子代理与后台完成签、只夹着两三条气泡，正是这一后果。**根因**：把「配额」记在了噪声与信号混算的粒度上。**新解**：配额只数「有意义消息」（用户气泡、助手文字气泡、及渲染成用户气泡的少数 lab 事件），工具/子代理/后台/系统签**不占配额但仍随范围整段返回**（工具组与子代理块照常成形，沙箱渲染逻辑一字未动）。`server.js` 抽出 `isMeaningfulEvent`/`isMeaningfulLine`/`floorByMeaningful`：从游标往前数够 N 条消息才停、页顶恰落在第 N 条消息上；冷开 `INITIAL_TAIL_MSGS=12`、`/history` 每页 `limit=25`，并各配 `*_MAXSCAN` 兜底防超长工具噪声撑爆单页。**契约不变**：`_seq`=绝对行号、`hasMore`、SSE 断点续传（`lastId>0` 仍严格从 lastId 续、绝不套尾窗，§3.37 那条 gap 教训依旧成立）。通用教训：**当「一条记录」的信噪构成会随产品形态漂移时，按记录数配额迟早失真——配额要记在用户可感知的信号单位上，噪声只搭车不占额。**


### 3.47 隧道下首屏性能整备：字节 / 压缩 / 缓存三处浪费一并治（2026-08-01，用户复盘驱动）

问题：老板手机走 Cloudflare tunnel 访问工作台，**首屏加载重、员工状态与头像要好一会才出来**。工作台内网直连时几乎无感，一过隧道（每个往返 +数百 ms、带宽也窄）就被放大。

根因盘点（三处独立浪费，隧道把每处都乘以延迟系数）：
1. **头像图严重超规格**——一屏 5 个员工头像 ~2MB，`mihu.png` 竟是 **1440×1080 / 1.44MB** 的原图，而 `.avatar` 是 `object-fit:cover` 圆形、显示区间仅 16–56px。图片本身不可 gzip（PNG 已压），只能靠缩尺寸。
2. **文本资源零压缩**——`server.js` 静态分支一直是 `res.end(fs.readFileSync(abs))` 裸发，`app.js`(171KB)+`style.css`(109KB)+`cards.js`(45KB)+`marked`(35KB)+HTML(30KB) ≈ 390KB 明文过隧道。Node 内置 `zlib` 一直没用上。
3. **静态资源零缓存头**——除 index.html 外无任何 `Cache-Control`/`ETag`/`Last-Modified`，手机二次访问走浏览器启发式缓存、常整份重下，也没有 304 协商省流。
4. 附带：开屏 `loadEmployees → loadTasks → loadRuns` 三个 `await` 串行，隧道下白花两个 RTT。

对策与取舍：
- **头像缩图为何用 PowerShell + System.Drawing**：机器无 ImageMagick/sharp/cwebp/pngquant，而 `server.js` 有「除 SDK 外零运行时依赖」的约束——不为一次性资产处理引入 npm 原生包。Windows 自带的 System.Drawing 零依赖、实测可用，缩到长边 160px（56px 显示的 retina 余量足够）。脚本做成**可复用 + 幂等 + 非劣化**（长边 ≤160 跳过；缩后反而更大则保留原图）落在 `app/scripts/optimize-avatars.ps1`。**为何缩图而非只靠缓存**：强缓存只救二次访问，**首访仍要吞 2MB**——尺寸不治，隧道首屏就治不了。
- **压缩为何 br+内存缓存、q6**：br 比 gzip 再省一档，按 `Accept-Encoding` 优先 br、次 gzip、都不支持则裸发（正确降级）。压缩结果按 `abs+mtime` 缓存在内存——`app.js`/`style.css` 只在首次请求（或改文件 mtime 变）时压一次，之后命中缓存，不为每请求重复压 CPU。brotli 取 q6 而非默认 q11：压缩比接近、耗时低得多，且结果已缓存，首个请求也不至于卡。
- **缓存头为何分两档 + index.html 的坑**：带 `?v=` 的版本化请求（style/cards/app 由 index.html 注入 mtime）内容与 URL 一一对应 → `max-age=31536000, immutable` 一年不回源；其余（头像/logo/vendor/uploads）→ `max-age=86400` + `ETag`/`Last-Modified` 走 304 协商。**index.html 必须留 `no-cache` 且刻意不发 ETag/Last-Modified**：它是版本指针，靠注入的 `?v=<mtime>` 给子资源破缓存——若给它上 304 校验器，改了 `app.js` 但 index.html 自身 mtime 没变时会命中 304、复用旧壳里的旧 `?v=`，新资源永远加载不到。宁可每次重发（压缩后 ~8KB）也不能让指针被缓存。
- **契约不破**：只加响应头与 `Content-Encoding`，端点/响应体/run 形状/SSE 事件一律不动；SSE 长连接分支（`no-cache` keep-alive）不碰。

量化：`avatars/*`+`logo` **2264KB → 434KB**（`mihu` 1.44MB→57KB）；`app.js` br 后 **171KB → 52KB**；首屏文本整体压掉 ~70%；二次访问多数资源走 304/命中缓存。

翻车与诚实记录：缩图脚本**第一版没做「非劣化」判断就直接跑了**，把 `xiaodaidai.png`（未纳入 git 的 6.8KB 高优化索引色小图）用 System.Drawing 重存成 32 位 RGBA、反而涨到 58KB——**原始紧凑编码没有任何备份，无法找回**（图像内容完好、显示正常，只是这一张多占 ~51KB）。教训：**破坏性批处理要么先备份、要么第一版就带非劣化/幂等护栏，别"先跑一版看看"**——尤其对 git 未跟踪、无回滚的文件。脚本随即补上「缩后 ≥ 原大小则保留原图」，之后再跑不会复发。

通用教训：**「慢」先量化再归因**——首屏慢的直觉容易赖到「引擎/SSE/后端」，但逐层量一下字节就发现是三处纯静态浪费，与业务逻辑无关。内网无感 ≠ 没问题，**隧道/弱网是放大镜**，把平时被高带宽掩盖的浪费照出来；性能验收该按「过隧道/弱网」的口径看，而非只看本机。

**改动落点**：`app/server.js`（新增 `serveStaticFile`/`sendDynamicText`/`compressBuf`/`pickEnc` + 重写 index.html / 通用静态 / uploads 三处分支）、`app/public/app.js`（开屏 `Promise.all` 并行 + 头像 `decoding="async"`）、`app/public/avatars/*`+`logo.png`（缩图）、新增 `app/scripts/optimize-avatars.ps1`。`node --check` 通过；隔离实例（`OFFICE_LAB_RUNS_DIR`+独立端口）实测压缩/immutable/304/降级全绿。引擎改动**需重启 server**。详见 CHANGELOG `[Unreleased]` 同名条目。



### 3.83 隧道下第二次性能整备：dev server 上了隧道 + API 零压缩 + 同一端点四路轮询（2026-08-19，用户反馈驱动）

承 §3.47（那次只治了**旧 UI 的静态资源**）。老板反馈：「电脑有 cloudflare 的 tunnel 代理 4700 端口，但在别的机器访问速度很慢，特别是员工列表的数据和信息加载十有八九是失败的。」按 §3.47 留下的方法论——**「慢」先量化再归因**——逐层量了一遍，抓出三条互相独立、又刚好叠乘的病根：

- **① 隧道指的是 Vite dev server**。`~/.cloudflared/config.yml` 把 `localhost` 指到 `localhost:4700`，而 4700 上跑的是 `vite`（dev）。远程每开一次页要经隧道拉几百个**未打包** ES module + 一条 HMR websocket。更荒诞的是 `web/dist` 早就构建好躺在那儿（`index-*.js` 704KB → gzip 202KB，一个请求就够），**没有任何进程在服务它**——新 UI 迁到 `web/` 后，「本地开发怎么跑」被顺手当成了「远程怎么访问」，从没分开想过。
- **② API 响应一律不压缩**。§3.47 做的 br/gzip 只挂在静态文件分支（`serveStaticFile`/`sendDynamicText`），而所有 `/api/*` 走的是另一个出口 `json()`——一行裸 `res.writeHead + res.end(JSON.stringify())`。实测 `/api/runs` **3586KB 明文**、`/api/tasks` 176KB、员工详情 90~112KB，全裸奔。**这是「只治了看得见的那半边」的典型**：当时量的是首屏静态资源，API 不在镜头里。
- **③ 同一个 3.6MB 端点被四路并发轮询**。`/api/runs` 同时被 `employee-status-provider`(10s) + `run-detail-provider`(15s，全局常驻) + 当前视图(15s) + `employee-detail`(15s) 各自 `usePoll`。**≈11~14MB / 15s**。而员工的忙闲/最近摘要/「等你拍板」全派生自这个端点——所以症状精准落在「员工列表加载十有八九失败」：请求互相排队、慢链路上必然超时，而不是随机哪里坏。`usePoll` 还有两个放大器：上一跳没回来就发下一跳（叠着堆）、页面切后台仍照轮。

**三处对策（按收益排序）**

- **`json()` 单点收口**：GET 且 body >1KB → br(q5)/gzip + `ETag=sha1(body)` + `Cache-Control: no-cache`，`If-None-Match` 命中直接 304 空 body。**为什么 no-cache 而不是别的**：浏览器 `fetch` 会自动带 `If-None-Match` 重验、304 由浏览器透明还原成 200+缓存 body → **前端零改动**就吃到收益。**为什么用 `res.req` 而不是给 `json()` 加参数**：调用点约 150 处，Node 原生就在 response 上挂了 request，改签名纯属自找返工。SSE 与文件下载不经 `json()`（各自 `writeHead` 流式输出），所以压缩绝不能挂到通用 `writeHead` 上——那会把长连接缓冲住。
- **`/api/runs` 列表投影 `runListView`**：`instruction`/`result` 只发前 200 字，另发 `resultTail`（末 300 字）。**取舍点**：这俩字段占列表体积 **91%**（1656KB + 1597KB，其余全部字段合计才 ~180KB），而列表侧真实需求只有摘要 ≤60 字、两行截断预览、以及认 `result` **尾部**的机器可读标记【等你拍板】。**尾段必须单列字段**——只截头会把「员工待拍板」状态全判丢（标记在末行），而只发尾段又会让会话列表显示成「…句子后半截」。字段名沿用 SSE `run-status` 早就有的 `resultTail` 口径，不另造词。全文只在打开会话时由 SSE / `/history` 给，本来就不该由每 10s 一跳的状态轮询驮着过隧道。
- **`usePoll` 共享轮询**：module 级 registry 按 path 合流（4 路 → 1 路，`/api/health`、`/api/tasks` 同理）、在途去重、`document.hidden` 暂停 + 转可见补拉。**刻意保持导出签名与返回值不变**，17 处调用点一行不改——轮询策略是横切关注点，让它渗进每个视图才是真正的债。
- **隧道端 dev → preview**：4700 改跑 `vite preview`（服务 dist，vite 8 的 preview 自带 @polka/compression + sirv `dev:true/etag:true`，与 `build --watch` 改写产物兼容），本地 HMR 让到 4701；托盘同起 `pnpm build:watch` 保产物常新。**为什么不把 dist 挂到引擎 4800 同源**：那样要把旧 UI 让到 `/legacy/`、动 cloudflared 配置，收益主要是省一跳代理；老板拍板选了改动面更小的 preview 方案。**代价要写明**：远程看到的是构建产物，watcher 挂了就会看到旧版——所以 watcher 与 preview 必须同起同停、日志落 `runs/web.build.log`。

**量化（772 条真实 run，隔离实例实测）**

| | 改前 | 改后首次 | 改后未变 |
|---|---|---|---|
| `/api/runs` 线上字节 | 3586 KB（明文） | **320 KB**（br，107ms） | **0 KB**（304，19ms） |
| 同上 gzip / 明文 | — | 396 KB / 1417 KB | — |
| `/api/tasks` | 176 KB | **47 KB** | 0 KB（304） |
| `/api/runs` 轮询路数 | 4 路（10s+15s×3） | **1 路（10s）** | 后台标签页 **0** |
| 首屏静态请求数 | dev：数百个模块 | **15 个**（含字体） | 多数 304 |

**通用教训**：① §3.47 那条「隧道是放大镜」还得再加一句——**镜头要覆盖全部出口**。当时治了静态资源就宣布首屏整备完成，而 API 走的是另一个函数、另一条路，于是同一类浪费在半年后原样复现。凡是「压缩/缓存/限流」这类横切策略，落点应该是**唯一出口**（`json()` 一处），而不是「当前看到的那几个分支」。② **轮询是会自己繁殖的**：每个组件"顺手"加一行 `usePoll('/api/runs')` 都局部合理，四处合起来就是 14MB/15s——横切关注点必须收在 hook 层做合流，靠 code review 逐处提醒是治不住的。③ **「本地开发怎么跑」和「远程怎么访问」是两个问题**：dev server 上隧道这种事，本机一点感觉都没有。

**改动落点**：`app/server.js`（`json()` 收口 + `compressBuf` 加质量参数 + `runListView`）、`web/src/hooks/use-poll.ts`（重写为共享轮询）、`web/src/lib/types.ts` + `web/src/lib/status.ts` + `web/src/views/RunsView.tsx`（`resultTail` 对齐，且对旧服务响应向后兼容）、`web/vite.config.ts`（`preview` 块 + dev 让到 4701）、`web/package.json`（`build:watch`）、`tray/office-lab-tray.ps1`（`Start-PnpmProc`/`Start-WebBuild`，preview 与 watcher 同起同停）。`node --check` + `app` 单测 32/32 + `web` `tsc -b` 通过；隔离实例（`OFFICE_LAB_PORT=8795` + 独立 `OFFICE_LAB_RUNS_DIR`，用完即停、生产未动）实测投影/压缩/304/SSE 不缓冲全绿；新 UI 产物经 Playwright 实测轮询恰好 10s 一跳、后台 32s 零请求、转可见即补、零 console 报错。**引擎改动需重启生效**（走托盘、勿强杀）。详见 CHANGELOG `[Unreleased]` 同名条目。

### 3.148 第三次整备：引擎主线程被「侧栏 git 查询」占掉 88% + /api/runs 每次状态变化整包 4MB 重拉（2026-10-08，用户反馈驱动）

老板：「lab 网页性能感觉有问题」（附 SingleFile 快照）。快照本身只说明 DOM ~9k 节点、不离谱；**真问题要在活页面和引擎上量**。三步量出两条病根，权重和直觉相反：

- **先量浏览器**（Playwright 打 4700 + PerformanceObserver）：`/api/runs` gzip 后仍 979KB/次（明文 4.2MB，2049 条 run，自 07-08 起只增不减），**13 秒内拉了 4 次**、其中一次 5.6s，主线程一次 397ms 长任务。§3.83 的共享轮询只合流了「定时轮询」，而 `employee-status-provider` 订阅了 run-status / run-bg / handoff 等 7 种 SSE 事件、**每来一个就 refresh 一次整包**——6 个员工同时在跑时事件密集，整包被事件驱动着反复重拉，每次全站依赖它的组件全量重绘。
- **再量引擎**：直接 curl `/api/health`（最轻的端点）要 **5~6s**——说明不是带宽，是引擎主线程被占。对**正在跑的生产引擎**用 `process._debugProcess(pid)` 临时开 inspector（不重启、不打断员工），CDP 采 25s CPU profile：**88% 的时间在 `child_process.spawn` 本身**，调用链 `/api/lanes → status → repoState → git`。`/api/runs` 的打包/压缩只占 ~4%。
- **为什么 spawn 会同步卡**：本机起一次 `git.exe`，`spawn()` 这一步（CreateProcess）就**同步**阻塞调用线程 0.6~1.3s（全新 node 进程复现，大概率是终端安全软件扫进程创建）。异步 API 不等于不阻塞——libuv 的 `uv_spawn` 在调用线程上同步完成进程创建。侧栏「运行环境」面板 10s 一跳（操作中 3s），每跳 ~14 个 git（主检出 5 仓 + 每个工作区 2 仓 × status/log 两条），再叠引擎 60s 预热与每个多开的标签页——主线程基本一直被 git 堵着。§3.139 引入工作区时 git 数还少、且在别的机器上 spawn 便宜，所以没暴露。

**对策**

- **git 全部丢到 worker 线程**（`app/lanes.js` `GIT_WORKER_SRC`，eval worker）：spawn 阻塞的只是 worker 自己。**取舍**：没选「减少 git 次数」作为主解（如读 `.git/HEAD` 免 spawn）——那要自己处理 packed-refs / worktree gitdir 等边角，而 worker 一处收口覆盖 lanes.js 全部 git 调用（含建树/收树）。两个坑：① eval worker 在 `"type":"module"` 包里按 ESM 解析、没有 `require`，统一用动态 `import()`；模板字符串里的 `'\n'` 会被转成真换行导致 worker 源码语法错误（首版踩了）。② **`worker.unref()` 必须放在挂 `message` 监听之后**——挂监听会把 worker 重新 ref 上，单测跑完进程不退（首版踩了）。建不起 worker 才退回主线程 `runProc`。
- **仓库状态 20s TTL 缓存 + 全量 status 在途合流**：面板/多标签页/引擎预热共用一轮。**点名查单个工作区（含员工 `lane_status` 工具）一律取现值**——员工靠它判「后端是否陈旧」，不能吃 20s 前的 HEAD；收树前的脏树校验本就直接调 `repoState`。工作区增删（`writeReg`）清缓存。
- **`/api/runs?since=` 增量**：服务端给每条 run 的列表投影 JSON 记修订号（**比对投影字符串、不依赖 `updatedAt`**——很多字段改动并不刷新它），回「变了的条目 + 被删 id」；`epoch`＝进程启动标识，引擎重启 rev 归零，前端 epoch 对不上即整包。前端 `lib/runs-delta.ts` 合并进上一份、**未变的 run 沿用原对象引用、整体无变化返回原数组**；`usePoll` 据此在数据引用未变时不通知订阅者（下游 memo 不被打穿）。不带 `since` 的旧调用（旧 UI）不变；前端对「旧引擎忽略 since 回整包数组」向后兼容（先 build 前端、引擎未重启的窗口期）。顺带 `usePoll` 在途期间被 refresh 不再吞掉，回来补拉一跳（SSE 触发的刷新以前会被在途去重吃掉、等下一轮轮询）。

**量化**

| | 改前 | 改后 |
|---|---|---|
| `/api/lanes` 一轮对主线程的最长阻塞 | 每个 git 0.6~1.3s × ~14 | **36ms**（整轮 3.9s 在 worker 里跑） |
| 20s 内再查 | 同上 | **9ms**（缓存） |
| `/api/runs` 无变化时的响应 | 979KB gzip / 4.2MB 明文 | **67 字节**，18ms（隔离实例 2052 条） |

**通用教训**：① **「网页慢」先分清是浏览器慢还是后端慢**——一条 `curl /api/health` 的耗时就能分开；这次如果只盯前端，会把 4% 的问题当成全部。② **生产 Node 进程可以不重启就采 profile**：Windows 上 `process._debugProcess(pid)` 开 inspector + CDP `Profiler.start/stop`，零打断。③ **异步 API ≠ 不阻塞**：`spawn` 的进程创建是同步的，在杀毒/EDR 机器上一次可达秒级；高频 spawn 一律别放主线程。④ §3.83 的「横切关注点收在 hook 层」还差半句——**事件驱动的刷新也是轮询**，合流了定时器但没约束「每次刷新拉多少」，事件一密照样打满。

**改动落点**：`app/lanes.js`（git worker、`repoStateCached`、`status` 在途合流、点名查即现值）、`app/server.js`（`runsDeltaBody` + `sendJsonBody` 拆出 + `/api/runs?since=` + `lane_status` 取现值）、`web/src/lib/runs-delta.ts`（新）、`web/src/hooks/use-poll.ts`（runs 走增量、引用未变不通知、在途补拉）。`app` 全量单测 924/924；隔离实例（4893 + 独立 RUNS_DIR + 关自动接棒/巡视/守航，用完即停）验 delta 全量/增量/删除/epoch 失配/rev 越界五种路径与旧接口内容逐字节一致。**引擎改动需重启生效**（走托盘、勿强杀）。

### 3.149 多开聊天窗口后整页卡死：不是内存，是 HTTP/1.1 每主机 6 条连接被长连接吃光（2026-10-16，用户反馈驱动）

**现象**：老板「总感觉 lab 性能有问题」，要求查多开聊天窗口后的网页内存。

**实测（Playwright + CDP，每步强制 GC 后取指标）**：JS 堆 0 窗 15.6MB → 6 窗约 26MB、DOM 1.2 万 → 1.56 万，每窗 1~2MB、无泄漏——**内存不是问题**。但每开一窗同时测一次 `GET /api/lanes`：

| 聊天窗口 | 打开的 EventSource | 普通请求耗时 |
|---|---|---|
| 0~4 | 1~5 | 5~14ms |
| **5** | **6** | **>10s 不回** |

**根因**：全局 `/api/events` 1 条 + 每个聊天窗口（`use-run-stream.ts`）各自 1 条 `/api/runs/:id/events` 长连接；4700（vite preview 代理）是 HTTP/1.1，浏览器对同一主机最多 6 条并发连接。第 5 个窗口正好占满，此后轮询 / 发消息 / 加载更早全部排队挂死，关掉一个窗才放行。**这 6 条是同浏览器所有标签页共享的**——开两个 lab 标签各开两三个窗一样中招（实测中途一次 `page.reload` 就卡了 30s）。

**对策（方案 A：会话事件复用全局 SSE）**：
- 引擎：`app/run-subs.js`（新，纯函数 + 7 测）管「全局连接 ↔ 订阅的 runId」。`/api/events` 的 hello 下发 `clientId`；新增 `POST /api/events/subscribe {clientId, runId, lastId}`（回放口径与旧端点一致：`lastId=0` 冷开回放尾窗，`>0` 严格续传；回放与登记同一同步段，无缝无重；409 = clientId 已失效）与 `/unsubscribe`；`appendEvent` 额外 `runSubs.publish`，帧形状 `{type:'run-event', runId, _seq, ev}`（直接拼接已序列化的行，免二次 parse）。同连接同会话重复订阅按引用计数。**旧端点 `/api/runs/:id/events` 原样保留**（旧 UI `app/public` 在用）。
- 前端：`sse-provider.tsx` 暴露 `clientId`；`use-run-stream.ts` 改为订阅 `run-event` + POST 挂订阅，记已收最大 seq，全局连接重连（换 clientId）后按它续传。hello 不带 clientId（旧引擎）→ 退回每窗一条连接——所以前端先于引擎重启上线也安全。

**顺带挖出的第二个问题（改造前就存在）**：引擎被强杀（ECONNRESET）时，4700 的 vite 代理**不关浏览器那头**——EventSource 一直停在 `readyState=1`（OPEN）却再也收不到任何东西，原生重连永不触发，`run-status` 等推送全断直到刷新页面。而心跳是 `: ping` 注释帧，前端看不见、无法判活。现在所有会话都骑在这一条上，这个洞的代价更大了，故一并修：全局心跳改发 `data: {"type":"ping"}`（旧 UI 按 type 分发、忽略未知类型；新 UI 无 `'*'` 订阅者），前端超过 60s 没收到任何帧就自己关掉重连（只在 hello 带 clientId 后启用——旧引擎只发注释心跳，拿来判活会每分钟误重连）。

**验证**（隔离引擎 4810 + 临时 RUNS_DIR 抽 6 条会话、关 autochain/patrol/guard-goal/auto-title/tray-watchdog/boot-resume，dist 构建到临时目录、preview 4711 代理过去，生产 4700/4800 未动）：

|---|---|---|
| 6 个聊天窗口时的 EventSource | 7 | **1** |

**通用教训**：「卡」先量请求耗时再量内存——这次堆一直只有二十几 MB，按内存方向查会一无所获；HTTP/1.1 下任何「每个 X 一条长连接」的设计都有一个 6 的硬上限，且跨标签页共享。

### 3.150 输入框打字卡顿：父层输入 state + 失效的 memo 让整条会话每键重建（2026-10-19，用户反馈驱动）

**现象**：老板「lab 网页输入文字都会卡顿」，提议给聊天消息上虚拟化滚动。

**根因（不是消息太多，是不该渲染的在渲染）**：组合器的 `reply` state 挂在 `RunDetail`，每个按键都重渲染它；子组件 `<Transcript>` 没有 `React.memo`，它内部那个建全量元素树的 `useMemo` 依赖里有 `onReply`/`focusReply`——父层每次渲染都新建这两个函数（`async function replyText` + 内联 `() => ref.focus()`）。依赖恒变 → `useMemo` 每次都重算 → 整条会话的气泡/OLCard/工具组元素每键重建一遍再交给 React 协调。`Markdown` 自身有 memo 挡住了重新解析，但其余组件（AssistantBlocks/EventRow/OLCard 等）全量参与协调，长会话下每键几十到上百毫秒。注释里写着「攒批不从这里透传，否则暂存态每变一次都要让整条 transcript 的 useMemo 失效」——当初意识到了这个风险，却漏了回调本身就是不稳定依赖。

**对策**：`replyText`/`focusReply` 用 `useCallback` 稳定（必须挪到 `if (!run) return null` 之前，否则违反 hooks 顺序规则）；`Transcript` 包 `memo`。打字时 transcript 完全不参与渲染。

**取舍：为什么没按提议上虚拟滚动**：虚拟化解决的是「DOM 太多」，这里的问题是「不该重渲染的重渲染了」——上虚拟化只会把每键重建量从 N 条降到可视的 ~20 条，病根仍在；而聊天区有动态高度（markdown、可折叠工具组、卡片原地变高）、顶部「加载更早」prepend 的滚动锚定、贴底跟随三套已踩过坑的滚动逻辑，虚拟化要全部重做，风险与收益不成比例。冷开只回放最近 12 条有意义消息（§3.37 追加修订），常态 DOM 规模有限。**留观**：若老板手动上翻大量历史后**滚动**本身卡，再评估虚拟化。教训：**「卡」先用 Profiler/读渲染路径定位是「渲染太多次」还是「每次渲染太大」，两者对策不同；`useMemo` 的依赖里出现回调，先确认回调是稳定的**。
