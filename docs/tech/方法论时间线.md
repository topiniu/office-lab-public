> 本条是一次**效率复盘讨论的留痕**，不是已落地对策。缘起：老板反映"lab 现在员工效率很慢"，并给了关键对照——**裸 CC 里「直说改哪个 bug → 改完直接发测」，而到 lab，每次叫员工做事，他们都先花大量时间在前置 SOP 加载 / 环境监察 / 任务单摸清等周边事务上**。以下是诊断过程与结论，供后续做技术复盘时接着推。

**（一层诊断·真实但表层）** 先归因到"这几版为什么慢"：以 v5.16/v5.17/v5.17.1 三版为样本，慢的**不是主体开发**（GG Bond 落码都很快：v5.16 当天落码、v5.17 一天半 8 条、v5.17.1 一天做完热修），而是——① **开工后反复改主意/中途插单**（v5.16 插 7 项含 REQ-0275「立项→开发→3 轮预检打回→整条删除」的纯浪费；v5.17 插 4 REQ+5 BUG、REQ-0212 facet 被"够吗"逐次追加 4→7→9→F16；v5.17.1 REQ-0293 一天内改 3 次模型）；② **v5.17 起的机器门禁结构性不可通过**（大量 facet 天生真机企微/ERP 触发/多账号，机器造不出→"重做→机签失败→再重做"空转，终局仍靠老板"版本级独立风险审批"人工放行）+ 覆盖引擎 `split` bug + 红线 10 禁自助 rebuild 挡 RED 校准。**定性：真实，但都是"这一版"的表层，不解释"叫员工做任何事都有一层固定重税"。**

**（深层诊断·实测冷启动税）** 老板点破后重测：lab 员工每次开工的**固定"冷启动税"**（不管任务多小都要交）——

```
CC（一个热上下文，从不丢状态）              lab 员工（无状态 agent，每回合从磁盘冷启动）
┌────────────────────────────┐        ┌──────────────────────────────────────────┐
│ 会话持续存在·状态常驻内存      │        │ ① 顶层规则  agents.md+CLAUDE.md …   ~950 行 │
│  你："改这个 bug → 发测"      │        │ ② 角色 SOP  feifei/ggbond/…      100~200 行│
│  └─▶ 直接动手（前置税 ≈ 0）   │        │ ③ 任务档案  唯一状态源          114–227 KB │ ← 每回合整读
└────────────────────────────┘        │ ④ facet 文档 + 交接卡             数万字符   │
                                       │ ⑤ 环境探查  git×N仓/8217/猪猪base/DB       │
   前置税 ≈ 0                          │  ——— 以上 ~80–120k tokens 周边 ———         │
                                       │  └─▶ 才开始真正干活                          │
                                       └──────────────────────────────────────────┘
   实测：v5.16 档案 114KB / v5.17 档案 227KB(462 行) / 顶层 agents.md 404 行 + CLAUDE.md 322 行 + 角色 SOP 105~196 行
```

这层税不是偷懒或疏漏，是**架构核心取舍的固有代价**：lab 押"一队无状态、按角色分工的 agent，靠磁盘文件协调"（换来可审计/可断点续跑/角色隔离/并行）；CC 押"一个连续有状态的热上下文"。代价拆成**四条税**：
1. **冷启动重建税**——agent 无状态，每回合从磁盘重建认知，主要被 227KB 任务档案吃掉。
2. **append-only 棘轮（解释"为什么*现在*才慢"）**——系统里一切只增不减：任务档案版本内越滚越大、红线/SOP 每出一次事故加一条、`agents.md` 已 404 行、连"每个优化都要留记录"都被写进硬门槛。**每回合税随时间单调上涨——系统被设计成越用越慢。** 老板"现在比以前慢"的体感是机械事实，不是错觉。
3. **交接序列化税**——CC 的 bug→fix→test 在一个上下文里状态从不丢；lab 拆成菲菲→GG→迷糊→波比，**每一跳把认知序列化成交接卡、再由下一棒反序列化重读**，4 角色=4 次冷启动。免费的"在场知识"变成付费的"写盘+重读"。
4. **齐平仪式税**——1 行改动和 5 模块超级需求走**同一套**三方会审/门禁/交接卡，协调开销固定成本，任务越小占比越接近 100%。老板"直说改 bug 发测"的场景恰是协调需求为零却付了全套 fleet 协调费。

   └─ 大/多角色/高风险 ─▶ 【全套】菲菲→GG→迷糊→波比

- **A. 任务分级 / 快车道（最大杠杆·最接近 CC 手感）**：intake 判血缘半径，小/低风险任务**整条流水线塌缩成一个 agent 在一个热上下文里做完 fix+verify+publish**，只留轻量审计存根，不走全套门禁四件套；全套菲菲→GG→迷糊→波比只留给真多角色、高风险的活。**仪式随血缘半径伸缩，而不是恒定。**
- **B. 砍断 append-only 棘轮（改变"越用越慢"）**：任务档案拆**小而新的"当前态头"（状态+未决项，每回合只读它）+ 按需才读的时间线日志**；红线/SOP 加**退役纪律**（已被机器门禁覆盖的红线就下架），否则每回合税无上限增长。借 Superpowers 的**薄派发器**把"厚 SOP 全量注入"改成"按任务类型只加载相关片段"，顺手实现红线退役。
- **C. 共享热环境缓存**：服务活性、git 枚举、猪猪 base、仓库清单做成 **fleet 级、每任务刷一次**的事实卡，不再每个 agent 每回合各探一遍。
- **D. 常见路径减少跳数**：多数小任务不需要 4 个角色边界；少一跳=少一次冷启动。角色分工在大协调任务上值回票价，在小任务上是纯序列化税。

**（诚实边界·不是要砍治理）** 这些仪式没有一条凭空来（会审、人工预检、机器门禁、巡视续跑，每条红线背后都是一次真事故：stash 覆盖、BUG-002 前向合并回退、交接卡失实、QA reward-hacking、agent 空停）。**问题不在"该不该有治理"，而在它被施加的方式＝固定成本 + 只增不减 + 冷启动**——于是碾压小任务、且永远变重。真正的提速＝让 lab 学会**按任务大小决定要不要付协调费（A）**并**停止让状态与规则无限膨胀（B）**，而非删红线。

**（状态）** 本条为讨论底料 + 方向，**未拍板、未落地**；后续若做，**A 快车道分级**与 **B 档案拆分/薄派发器**是能从根上改变"手感"的两条主路。数据来源：本次对话、`tasks/2026-08-03-v5.16-纸样变更通知.md`、`tasks/2026-08-09-v5.17-示例项目工作台.md`、`tasks/2026-08-14-v5.17.1-*.md`、Web 检索（MetaGPT/ChatDev/Superpowers/OpenHands）。呼应 §5「与业界的差距 / 升级方向」——此为其**效率维度**的补充。

#### 续 · 同日延伸讨论（常驻内存 → 体积怀疑与自我订正 → 全员 online 裁定）

> 承上，老板顺着"冷启动税"连追三问，逐层把"该不该常驻、常驻什么、在哪层常驻"聊到底。**过程含我一次明确的自我订正**（把体积/常驻从"提速主路"降级为"次要成本-质量杠杆"），一并留痕，防复盘时重走。

**（round 3 · "能不能把一次迭代的数据常驻内存？"）**
- **先分清常驻谁的内存**：① Node 引擎进程内存（缓存文件）——**几乎没用**，瓶颈不是 `fs.readFile` 磁盘延迟，是 token 必须重新进 LLM 上下文窗口；② LLM 上下文窗口——**这才是 CC 快 lab 慢的真差别**，老板要的是这个。
- **引擎对 ② 已做到的部分（超出直觉）**：`server.js:5` 设计原则即"常驻流式 query：同一 run 多轮往同一 query 推消息 → prompt 缓存热；断连/idle 后 resume 冷起"。`IDLE_CLOSE_MS=180_000`（3min）收工后留窗等下轮、**特意卡在 prompt 缓存 5min TTL 内**；超窗 close、下次 `resume=sessionId` 重放 transcript 续接。`【交回】` resume 回委托者原会话保上下文；只有 `【下一棒】` 派活才新建 run。**结论：单角色内的"常驻"已是现状**（热 query + 缓存 + session 续接三件套）。
- **真没热、也就是税的来源（三处）**：① **跨角色交接**（`【下一棒】`=新员工新 run 真冷读，session 续接保的是"某员工自己的"上下文、非"迭代共享"）；② **人在环长间隔**（超 3min 窗 + 5min TTL，resume 必然缓存冷、整段重吞）；③ 再怎么缓存进 Node 也绕不开 token 要进窗口。
- **"常驻整条迭代成一个上下文"物理不可得**：多天全量 transcript 远超窗口（CC 自己也得 `/compact`）+ 4 角色塞一个 context 毁掉角色隔离（各自红线/工具权限=安全特性）。
- **正确形态（当时提出）**：引擎常驻一个 **IterationWorkingSet**（冻结需求快照 + facet 当前态 + 未决项/下一棒 + 环境事实卡），**memory=缓存、disk=真相、可从文件重建**，派工时注入成"当前态简报"，把跨角色冷启动从"重读原始档案+重探环境"变成"接收热简报"。

**（round 4 · 老板怀疑"减小注入体积的收益" → 我自我订正）**
- **量化（老板对，我认）**：一个 turn 墙钟 = prefill + 生成 + 工具往返。**注入体积只影响 prefill**：缓存命中≈瞬时，不命中也就几秒，且稳定前缀本就打 ~9 折。**墙钟大头是生成 + 工具循环（分钟级）**；**版本级墙钟大头是停顿 + 返工（小时/天级）**。粗算：一次冷启动"周边事务"≈30–90 秒（且主要是**工具调用**读档案/探环境，不是 token 预填），一版 10–20 次 ≈ 5–30 分钟 ≈ 5 天墙钟的 **0.1–0.5%**；缩体积只攻其中 token 预填一小块 → **实际 <0.1%**。
- **我上轮缝错的两件事**：① **注入体积（prompt 多大）**——弱杠杆，缓存已消化，是**成本（省重读的钱）+ 质量（大 context 稀释注意力→误判/返工，v5.17 多个坑是读错）**，不该当提速卖；② **员工前置行为（它去读/探/摸清）**——**这才是老板眼里看到的"慢"**，慢在它选择做一串准备性工具调用，工作集简报的真价值是让它**不必去读/探**（省工具循环墙钟），**不是把 prompt 变小**。
- **提速杠杆重排（按对墙钟实际影响）**：1️⃣ **减冷启动次数/跳数（快车道 A）——最大**，小任务 4 跳塌 1 跳=省掉整整 3 个 agent 启动到跑完的循环（分钟~十分钟级/个），量级碾压"省几 k token"；2️⃣ **砍机器门禁 + 人在环停顿**（小时/天级）；3️⃣ **减返工**（范围冻结/质量前移）；4️⃣ 不重探环境（共享环境事实卡，分钟级，modest）；5️⃣ **缩注入体积——最小，且大半是省钱/降误判非提速**。
- **明确订正**：拆档案/薄派发器（B）的真价值是"**稳定前缀利于缓存 + 降误判**"，**不是提速**；提速在 A（减跳数）。

**（round 5 · 老板提"以迭代为中心，全员各起一会话常驻、实时监听/广播同步，全员 online 感" → 裁定：状态层 yes、LLM 会话层 no）**
- **对的一半**：以迭代为中心的数据 + 事件同步 + 团队在场感——方向对，且**引擎已有事件总线**（SSE `tasks-changed`/`handoff`/`run-status`/`conversation`）。问题只在：**"监听/在场"的主体该是引擎，不是 4 个 LLM 会话。**
- **"4 个 LLM 会话常驻整迭代 + 互相监听"会崩的 6 点**：① **撞 5min 缓存 TTL**——常驻天级=99.9% 时间缓存冷，"常驻"只保住子进程、没保住缓存；要真热得每 <5min 给 4 个各 ping 刷缓存 ≈ 每小时数百万 token 全烧在怠速（`IDLE_CLOSE_MS=3min` 就是因为持有超 TTL 是纯浪费——此提案撞已调好的参数）；② **LLM 不"监听"**，两 turn 间惰性，要它反应广播=注入一个 turn 跑一次推理→每次状态变化最多 4 个员工各醒来空想一遍；③ **广播进 context=4× 污染 + 撑爆窗口**（服务订阅 O(1)/条，LLM 装进 context 是此后每 turn 重算、O(context) 永久 + 稀释注意力）；④ **缓存一致性**——4 个热会话各持自己 context 里的状态副本，一动手即与磁盘/彼此发散，把无状态设计免费换来的"读即一致"换成 cache-invalidation 难题；⑤ **角色隔离本是安全特性**，共享广播 context 助长"把别人半成品推理当事实"（v5.17 已有此类坑）；⑥ **就算全跑通，只削最小杠杆（跨角色冷读，几十秒~两分钟/次）却花最大钱与最大改造，ROI 倒挂**。
- **正确实现（裁定形态）**：**状态层常驻·实时·便宜**（引擎持有迭代中心态对象、磁盘=真相、引擎=监听者、已有 SSE 驱动看板实时）+ **推理层惰性·按需·贵**（员工只在"该他上"时醒来、被喂一份新鲜一致的"当前态热简报"IterationWorkingSet、干完释放不保温）。**"全员 online 的感觉"给的是你这个观察者**（看板/会话实时流动），每个 agent 只在自己 turn 醒——即**异步团队 + 共享文档 + @提及**模型，而非"把 4 个人锁会议室 24h 省简报"。

```
状态层（常驻·实时·便宜）          推理层（惰性·按需·贵）
┌────────────────────────┐      ┌──────────────────────────┐
│ 引擎持有 迭代中心态对象    │      │ 员工会话只在「该他上」时才醒 │
│ 磁盘=真相 · 引擎=监听者    │─@页→│ 醒来即被喂一份「当前态热简报」│
│ SSE 广播(已有)驱动看板实时 │      │ 干完即释放，不怠速保温        │
└────────────────────────┘      └──────────────────────────┘
       ↑「团队在动」的在场感来自这里，不需要 4 个 LLM 一直烧着
```
- **业界佐证**：多智能体行早期试过"全员常驻群聊持续辩论"（early AutoGen 一派），因 token 爆炸 + 状态漂移，集体转向"**结构化交接 + 共享记忆**"。此提案恰是这行趟坑后走回来的路。

1. **常驻 / 在场：状态层 yes（引擎+磁盘+SSE，多已具备）、LLM 会话层 no**（撞 TTL/撞窗口/缓存一致性/侵蚀隔离/削最小杠杆最贵）。
