### 3.13 企微渠道 + 菲菲主人格（2026-07-22）

菲菲的企业微信渠道迁入 office-lab。**最终架构**（经一次转向后定稿）：`企微 → app/wecom_sidecar（Python 长连接哑管道）→ office-lab 主人格端点 /api/wecom/persona-reply（菲菲 Agent 作答，按需调知识库/登记需求）→ 流式回企微`。代码见 `app/wecom_sidecar/README.md`。

**一次关键的架构转向（复盘核心）：** 初版把「企微消息无条件转 RAG `/api/ask`、人设在 RAG 服务端（`channel=wecom`）」当门面——用户当场否掉，纠出两条病根：① **每句话都检索**（连「你好」都答「正在检索知识库」，机器味、且浪费额度）；② **外部渠道等于能直接驱动员工**（谁在企微发消息都能触发答题/干活，绕开看板门禁）。用户据此确立三原则并拍板转向：

- **渠道 = 纯 I/O，不是开工信号**。企微/飞书只做「信息进出」；正式派工/开工只在望子成龙看板由用户发起。sidecar 退化为哑管道，不判断意图、不查库、不派工。
- **主人格在 office-lab**（唯一事实源）。收到企微消息的是 office-lab 的菲菲 Agent 本人，不是 RAG。
- **知识库(RAG)、飞书文档等 = 主人格按需调用的工具**，不是本体。闲聊直接答，只有需要业务事实才查库。

**几个机制取舍（复盘要点）：**

- **主人格运行时为什么独立于看板 run 机制**：现有 `startRun/createDispatchRun` 深绑任务语义（任务快照、`autoChain` 接棒、`appendLessons` 教训沉淀、`【下一棒】`解析）。企微对话明确不是正式工作，若复用会误触发派工/接棒。故另建精简的 `personaSessions` 运行时：每企微用户一个常驻轻量会话（`makeInputChannel`+消费流，但剥离全部看板语义），只做「消息进→（按需用工具）→文本出」，结构上碰不到 `runs` 注册表——企微对话永不进看板（已验证：跑三类消息，`/api/runs` 无新增）。
- **人格会话为什么轻**：`systemPrompt` 用纯字符串（精简菲菲身份+渠道规则）而非 `claude_code` 预设 → 没有 coding 工具；走轻档 Sonnet；`allowedTools` 只白名单两个 MCP 工具、外加 deny 写/Bash 兜底 → 企微人格碰不到文件系统。契合企微 5s 秒回窗口与「常驻轻量会话」的成本取舍（缓存热续、空闲 4min close 后 resume 冷起）。
- **扩展能力做成 in-process MCP 工具**：`createSdkMcpServer`+`tool`（zod schema）挂 `knowledge_base_query`（按需查 RAG，internal 受众，取事实供菲菲转述）与 `stage_requirement_intake`（需求只落 `runs/wecom-intake.jsonl`、**绝不 spawn run**）。按 uid 建工具工厂（闭包注入 userid），并发多用户不串味。飞书等后续以同样方式挂新工具。
- **为什么渠道做 Python sidecar，而不是 Node 重写**：官方 `wecom-aibot-python-sdk`（`aibot.WSClient`）是 Python 的，长连接协议（鉴权/心跳/重连/流式 `reply_stream`）由它封装。用 Node 重写等于把一套已验证的协议实现再造一遍、且失去官方跟进。取舍：office-lab server（Node）**看护**一个 Python 子进程，进程边界即语言边界，二者只通过 HTTP（office-lab 内部端点）解耦。代价是多一个 Python 运行时依赖（自带 venv + setup 脚本兜底）。
- **为什么凭证从 RAG API 迁到 office-lab**：迁移前 worker 向 RAG 的 `/api/wecom-bot/runtime` 要 BotID/Secret（渠道当时住在 RAG）。渠道归属变更后，凭证事实源改为 office-lab（`runs/wecom-config.json`），sidecar 轮询 office-lab 的 `GET /api/wecom-bot/runtime` 热拉——保留了「后台改配置即热重连/断开」这个原设计的好特性（`_decide` 决策矩阵：connect/reconnect/disconnect/noop），只是换了事实源。

- **为什么渠道做 Python sidecar，而不是 Node 重写**：官方 `wecom-aibot-python-sdk`（`aibot.WSClient`）是 Python 的，长连接协议（鉴权/心跳/重连/流式 `reply_stream`）由它封装。用 Node 重写等于把一套已验证的协议实现再造一遍、且失去官方跟进。取舍：office-lab server（Node）**看护**一个 Python 子进程，进程边界即语言边界，二者只通过 HTTP（office-lab 内部端点 + RAG `/api/ask`）解耦。代价是多一个 Python 运行时依赖（自带 venv + setup 脚本兜底）。
- **为什么答题人设留在 RAG 服务端、渠道 worker 不自拼 persona**：RAG 侧 `answer_generation.py` 按 `PERSONA_CHANNELS={"wecom"}` 生效菲菲口吻。渠道 worker 只要 POST 时带 `channel="wecom"` 就得到成品答案——人设逻辑、受众隔离、信任评估都在答题服务这一层内聚，渠道保持「哑管道」。好处：口吻/脱敏规则改动不必碰渠道；坏处：渠道对答案内容无控制权（符合职责划分）。
- **为什么凭证从 RAG API 迁到 office-lab**：迁移前 worker 向 RAG 的 `/api/wecom-bot/runtime` 要 BotID/Secret（渠道当时住在 RAG）。渠道归属变更后，凭证事实源改为 office-lab（`runs/wecom-config.json`），sidecar 轮询 office-lab 的 `GET /api/wecom-bot/runtime` 热拉——保留了「后台改配置即热重连/断开」这个原设计的好特性（`_decide` 决策矩阵：connect/reconnect/disconnect/noop），只是换了事实源。
- **secret 脱敏 + 内部 token**：`GET /api/wecom-config` 不回 `botSecret`/`internalToken` 明文（只回 `botSecretSet` 布尔）、POST 留空即保留原值；明文 secret **只**在 `X-Internal-Token` 守卫的 `/api/wecom-bot/runtime` 回给 sidecar。token 首跑随机生成并固定落盘（变了会导致 sidecar 401）。当前前提是「sidecar 与引擎同机 localhost」，token 是够用的轻鉴权；若将来跨机暴露需升级为共享密钥（对接契约里已警示）。
- **为什么由 server.js 看护而非 tray 独立拉起**：sidecar 生命周期应与 office-lab 引擎绑定（引擎在→渠道在；引擎退→渠道退），且配置改动要能即时重启。server.js 已有 `spawn` + 优雅退出基建，看护逻辑（按需拉起、指数退避重启封顶 `WECOM_MAX_RESTARTS`、`stopping` 标记区分人为停止与崩溃、`gracefulShutdown` 连带关停）内聚在引擎里最自然。tray 只管拉起引擎，无需感知 sidecar。缺 SDK/凭证时 sidecar 退出、引擎退避重试且**不崩**，`lastError` 经 `/api/wecom-status` 与 `/api/health` 可见。
- **懒导入保测试性**：沿用迁移源码的写法，`aibot`/`aiohttp` 均在函数内延迟导入，使 `config`/`format`/`office_client`/`_decide` 等纯逻辑无需装 SDK 即可 `py_compile` + 断言验证。主人格三类行为也已实测：「你好」直接寒暄不调工具、业务问题触发 `knowledge_base_query`、转发需求触发 `stage_requirement_intake` 并回「去看板派工」（`runs/wecom-intake.jsonl` 落盘、无新 dispatch run）。
- **两条链路各自可自检 + 连接态可观测**：RAG 连通测试（`/api/wecom-test`）只证明「答题服务在」；企微凭证是否有效必须真连企微，故加企微连通测试（`/api/wecom-connect-test`）。设计上「sidecar 在跑就读实时上报状态、没跑才起短命 `--probe` 探测」——避免同 BotID 起第二条连接把在服务的连接互踢下线。为此 sidecar 经 `report.py` 在 `authenticated`/`disconnected`/`error` 事件回报连接态到 `/api/wecom-bot/report`，把状态行从「进程 running」升级为真实「已连接企微/认证中/断开」，也修了「running ≠ 已连上企微」的表达歧义。

> 范围外（预留）：意图判断已交给主人格自身（不写死分类器，符合原则）；外部下游客户答疑（RAG 客户脱敏人设路径）本期搁置；转发聊天记录做结构化 intake 的真机验证（合并转发卡片能否拿到正文）待真机；UI 侧「待派工」建议行（读 `wecom-intake.jsonl` 提示用户去看板派工）留待后续。


### 3.14 飞书多维表格（示例项目需求分诊看板，2026-07-22）

老板把示例项目需求记在一张飞书多维表（人工分诊看板：待处理→处理中→已完成，**精选看板非全量 backlog**）。给菲菲读写维护能力，让她做分诊助手、但不接管分诊/优先级/挑单（红线）。表：`base=<your-base-token> / table=<your-table-id>`。

**机制取舍：**

- **两个接入路径、按上下文分**：① **看板 PM 菲菲**（重、agent 驱动、要做 list/sort/create/update 等多种操作）→ 挂官方 `@larksuiteoapi/lark-mcp`（`preset.base.default`），零编码、官方维护。② **企微主人格 intake**（轻、固定操作=建一行「待处理」）→ 用一个 in-process 轻量飞书客户端（tenant token 缓存 + create record）直连，**不给 bypass 的主人格挂原始 Feishu 写工具**（保持它最小安全工具面），也避免给每个企微会话起一个 lark-mcp 子进程的开销。
- **权限姿态：全权维护 = 自主写、砍需求/删行才设门（用户 2026-07-22 拍板）**：老板把表全权交给菲菲、只给「行为建议」。故飞书**读+写（create/update）都进 `PERM_ALLOW` 静默放行**，登记/去重/补全/状态流转不逐条审批（逐条审批与「全权」自相矛盾，且写台账是低风险可回滚操作）。真正需要人的是**否定性/破坏性**操作：`拒绝/砍需求` 靠 SOP 要求她「只提建议、老板拍板」（自律层），`删除记录` 进 `PERM_DENY` **引擎硬禁**（门禁层，落实红线「不删行」，即便 preset 含 delete 也拦死）。这是「门禁只拦不可逆/否定操作、其余靠角色自律」的一贯取向。
- **可视化配置**：base/table/字段映射/凭证都在「飞书需求表设置」卡片编辑（凭证 env 优先、否则落 `runs/lark-config.json` gitignore、secret 脱敏）；「拉取字段」调 `/api/lark/fields` introspect，避免手猜字段名（默认映射已对齐实际表：需求点/状态/提出人/提出时间）。
- **为什么 MCP 只挂给菲菲、且 env 门控**：其余员工（ggbond/mihu/bobby）不需要飞书表；`run.employee==='feifei' && LARK_APP_ID` 才挂，避免无谓扩大工具面；无凭证时整块不挂、不影响任何员工（对齐 sidecar「缺依赖不崩」的取向）。
- **为什么 tenant 而非 user token**：自建应用 + `app_id/secret` 默认以 `tenant_access_token` 调 API，无需 OAuth 刷新，最适合无人值守。凭证走 env（不入库）；base/table/字段映射走 `runs/lark-config.json`（可后配）。
- **企微 intake 汇合到飞书、避免平行台账**：老板真实分诊台账就是这张飞书表，故 `stage_requirement_intake` 直接建「待处理」行，而不是维护一份独立的本地 `wecom-intake.jsonl`（后者退为「飞书不可用时的兜底，不丢数据」）。
- **字段：从「静态映射」→「自动识别」→「菲菲自己决定」的两步收敛**（用户连续两轮加码：「菲菲该自己看表决定」→「连字段配置都不要了，她按现有字段和增删需要自己定」）。终态：
  - **看板 PM 菲菲（Lark MCP）= 表的完整负责人**：读现有字段、自己决定新需求填哪些、需要新维度时**自己加字段**（`appTableField_create` 放行）。不需要任何字段映射配置。
  - **企微快速登记**：仍用 `larkAutoDetectMap()`（`list fields` 后按名称/类型匹配 + 缓存 10min）把新需求落成「待处理」行——这是"系统看着表决定落位"的兜底，无需人配；识别不到则回落本地 jsonl 不丢数据。
  - **结构自主度边界**（用户 2026-07-23 定，且此表目前私用）：加字段/填内容/流转状态**自主**；**删字段 / 改字段名 / 删行**不可逆、动结构 → 只**提建议**。设置卡片撤掉字段映射输入框，只留凭证 + base/table。
  - **后续（同日）反转为彻底全自主**：① 原靠 `npx lark-mcp` 读表，本机 npx 拉不起来→菲菲根本没飞书工具（见 §3.20），改为**引擎内直连客户端**做全套工具（读/改/建/删记录 + 增删改字段）。② 用户改主意：私用表**去掉那道闸**，删记录/删字段/改名都交给菲菲自主，只留"不可逆操作做完要说清（透明）"+"维护≠开工"。直连的建/删记录已对真实表往返实测通过。*取舍：把结构决策权也交给菲菲更贴「全权」，但「不可逆/破坏性」操作用硬闸兜底（deny → 她自然变成"提建议"），这与「删行硬禁」「拒绝只提建议」是同一条一贯取向；私用表降低了协同风险，但不可逆性仍值一道闸。*


### 3.15 HTTP 连接超时调优（事故驱动，2026-07-22）

**事故**：为清理测试遗留的孤儿 server 进程，用了 `taskkill /F` 强杀 + 短时间反复重启。之后用户浏览器里点设置无反应、软刷新一直 loading。抓包看：`/api/events`(SSE) 200，但 `/api/wecom-config`/`/api/lark-config`/`/api/runs` 全部 `pending` 永不返回。

**根因**：从我这边用**新连接** curl 这些接口全部秒回 200、CPU 0%——服务端是健康的。`netstat` 显示浏览器进程对 `127.0.0.1:4700` 开了**整整 6 条 ESTABLISHED**，正好是 **HTTP/1.1 每域名 6 连接上限**：这些连接在强杀/重启churn 中卡成悬挂态、占满连接池，导致任何新 `fetch` 排不到连接 → 永久 pending；软刷新复用同一连接池，故「刷新也一直 loading」。

**对策与取舍**：
- **主力 = 连接超时调优**（`server.keepAliveTimeout=15s`/`headersTimeout=20s`/`requestTimeout=60s`）：服务端主动在 15–20s 内回收半开/空闲/卡住连接（默认拖 5min），浏览器池及时腾出。**平台无关**，是真正解决问题的一手。
- **辅助 = `closeAllConnections()` on shutdown**：仅 best-effort。**实测发现 Windows 下 windowless Node 收不到优雅信号**——`taskkill`（不带 `/F`）直接报「只能强制终止」，托盘 Stop-Server 首选的温和 `taskkill /T` 对它无效、3s 后必走 `/F` 强杀，故 `gracefulShutdown`（SIGTERM/SIGINT 处理器）在 Windows 托盘路径上**根本不跑**，此段只在前台 Ctrl+C / 非 Windows 生效。强杀时 OS 自会关 socket，所以「旧连接不释放」本不是问题，卡住连接靠上面的超时兜底。
- **为什么不上 HTTP/2**：H2 多路复用能免掉 6 连接上限，但**浏览器只支持 H2 over TLS**（无 h2c）——要上证书，砸掉 office-lab「`node server.js` 零配置、绑 0.0.0.0 给 Tailscale/局域网」的开箱即用；且 H2 单连接一旦被强杀反而全挂，治不了本次的强杀根因。本机单人场景性价比极低，故不上；将来若走多用户/公网再单独做 HTTPS+H2。
- **运维纪律沉淀**：重启走托盘优雅停/启，非必要不 `taskkill /F`（本次是我为清孤儿强杀引发，教训记于此）。


### 3.16 菲菲的对话记忆（2026-07-23）

需求：菲菲在企微跟别人聊完，用户要能在系统里跟她讨论那些对话、让她总结"今天聊了啥/有什么新需求"——像人一样有跨对话记忆。

**机制取舍：**
- **记忆 = 落盘日志，不是内存**：企微人格会话本身是内存态（重启即丢），不能当记忆。改为每轮把「来信 + 菲菲回复」写进 `conversations.jsonl`（复用会话看板的 `logConversation`，`kind='wecom'`、`threadRootId=wecom:<userid>`），日志即记忆、且顺带在会话看板可视。
- **一个菲菲、一份记忆**：看板上的完整 agent 菲菲 和 企微的轻量人格菲菲，都挂同一个只读 MCP `feifei-memory` 读**同一份** `conversations.jsonl`。菲菲本身无状态，"记得"完全来自查这份日志——所以两个入口天然一致，不需要同步。
- **pull 而非 push**：不把历史塞进 prompt（会 token 爆且"今天全部"可能很大），而是给工具 `recall_conversations`（按人/时间/关键词过滤）让她**按需查**。"今天有什么新需求"→ 她查对话 + `recall_staged_requirements`（或飞书查待处理）自己汇总。
- **userid→显示名映射**：企微机器人消息通常只给 userid，故用手配的 `wecomConfig.userAliases` 把 `wecom:xxx` 显示成"静安"，不引入通讯录 API 权限。落盘与回忆都经它翻译。
- **落点选择**：直接复用会话看板的 conversations.jsonl（而非另起 wecom-chat.jsonl），一份存储同时满足"可视回看"和"菲菲检索"，避免双台账（与"企微 intake 汇合到飞书、避免平行台账"同一取向）。


### 3.18 企微消息防抖攒批 vs 5s 窗口（2026-07-23）

问题：原来同一用户每条消息各触发一次菲菲（一次 LLM）——逐条转发/连打多条 = 每条各回、碎片化、费钱。做「防抖攒批」（sidecar 按 userid 攒 buffer、静默 1.5s 后合并成一次）。

取舍要点：
- **和企微 5s 首帧窗口的张力**：攒批会推迟回复，可能超过"收到消息 5s 内回首帧"。解法不是"每条都先垫开场"（那会让单条"你好"也蹦"稍候"、正是之前刚修掉的毛病），而是**分情形**：单条 → flush 里先给答案一个 2.5s 短窗口，秒答直发、慢才垫开场；一旦**成 burst（第 2 条到达）**才立刻秒回开场占窗口，之后合并处理。即"只有确实要等（burst/慢答）才占窗口"。
- **合并粒度**：以"最后一条消息"承载最终答复，这批中间消息不各自回。逐条转发的多条被 `\n` 拼成一段一起理解（发件人企微仍不给，但内容合成缓解了碎片化）。
- **防刷兜底**：超 20 条/8000 字立即 flush，避免有人狂刷把 LLM 调用堆爆或上下文超长。
- **无新增延迟给单条快答**：单条"你好"经 1.5s 防抖 + 秒答 → ~2-3s 直接答、不垫开场，仍在 5s 内。


### 3.19 企微图片 → 菲菲读图（2026-07-23）

进料三块的最后一块。企微能给 bot 发 image/mixed，让菲菲直接看图（面辅料/报价单截图）。

- **可行性（先查后做）**：官方 SDK `WSClient.download_file(url, aeskey)` 下载+AES-256-CBC 解密（下载是自包含 GET、无需额外 token）；图片帧带 `image.url`+`image.aeskey`。Agent SDK 输入是 Anthropic `MessageParam`、content 支持 image block，现有 `makeInputChannel.push` 推 content 数组即可；Claude 多模态。三点凑齐→可行。
- **图片并入防抖 buffer**：不给图片单开一条链路，而是塞进已有的按-userid 防抖 buffer（扩 `images`），让"文字+截图连发"在同一批合并成一次 query——一次调用、一并理解。
- **raw base64 不落 conversations.jsonl**：记忆/看板只标 `[图片×N]`，避免大 base64 撑爆日志；图内容只在那一次 query 的 content 里。
- **契约先行、真机后校**：企微图片帧的确切字段路径/真实 media 下载要真实凭证+真实图片消息才能坐实，故防御性取字段 + 下载失败兜底，先按 SDK docstring 契约写。**服务端视觉链路已用自制 PNG 端到端实测**（发红图→答"红色"），把不确定性收窄到"企微那一段"。
- 与系统 intake 读图（Read 工具）互补：系统里贴图走 Read、企微直接发图走 vision、多选复制丢图——三条路各自清楚。


### 3.20 事故：npx lark-mcp 不可靠 → 改直连 + KB 超时解耦（2026-07-23）

真机反馈两个失败，都是运行时/超时坑而非人格问题：

- **菲菲读不到飞书需求表**：飞书读走 `npx -y @larksuiteoapi/lark-mcp` 外部子进程——本机没装、npx 首次要联网下载、registry 慢 → 子进程起不来/超时，菲菲拿不到飞书工具（凭证 scope 其实都对）。会话里她只能拿 `knowledge_base_query`(RAG) 硬凑、还超时。**教训**：能力工具**优先 in-process**（引擎内直连），少依赖运行时 `npx`/外部子进程——后者在离线/慢网/未装的机器上是隐形炸弹，且每次 spawn 还拖慢启动。已把飞书读/改/建都换成引擎内直连客户端（`larkListRecords`/`larkUpdateRecord`/`larkCreateRecord`，同一 tenant token），弃用 lark-mcp。
- **RAG 慢把整轮拖炸**：`knowledge_base_query` 超时和 sidecar→office-lab 的 HTTP 超时都设 180s，撞一起——本地 RAG 一慢，KB 等满 180s 时 HTTP 也超时 → 用户看到"刚出了点岔子"。**教训**：**下游超时必须显著小于上游超时**（子调用 30s < 整轮 HTTP 180s），慢依赖要能"快速失败+降级"（返回"知识库暂不可用"而非拖垮整轮）。
- **工具选择要在提示里显式区分**：菲菲一度拿 RAG 查需求表（答非所问）。KB=产品业务知识、`lark_list_requirements`=需求表，两者用途在 prompt/SOP 里点明，避免她混用。


### 3.21 企微知识库查询按人限额（2026-07-23）

企微 `knowledge_base_query`（RAG）原对所有用户不设限。`defaultAudience=customer` 意味着外部人也可能在跟菲菲聊，两个真实风险：外部人无限量掏内部知识库（涉密）、RAG 调用成本不可控。给每个聊天对象一条策略记录（备注名 + 每日查询上限）+ 白名单开关。两处关键取舍：

- **硬控放工具代码、不放人设 prompt**。直觉会想「在 `buildPersonaPrompt` 里写一句『每人每天最多查 N 次』」——**错**：菲菲是 LLM，数不准也守不住，而且一条用户消息里她可能自主查库 0 到多次（`PERSONA_MAX_TURNS=12` 允许多轮工具往返）。所以计数与拦截落在 `knowledge_base_query` 工具入口（`makePersonaCaps(uid)` 已把 `uid` 闭包进来）：打 RAG 前 `consumeKbQuota(uid)`，超限直接返回文案、不触达 RAG。凡是「硬限制/配额/权限」都该在确定性代码里 enforce，prompt 只负责措辞。**推论**：限的是 KB 工具调用次数，不是消息条数——闲聊便宜又不敏感，该限的是「贵且涉密」的那个动作。
- **策略与用量分两个文件**。策略（谁、备注名、额度、白名单）进 `runs/wecom-config.json`（人低频改、要可读可编辑、`POST /api/wecom-config` 落盘）；用量计数（谁今天查了几次）进独立 `runs/wecom-kb-usage.json`（`{date,counts}`，机器高频写、按本地日期每日零点自然重置）。混一个文件会让「人编辑配置」和「机器写计数」互相打架，且计数天天变会污染配置的可读性。用量文件因每日重置恒定极小，无需清理任务。
- **额度用尽后仅停查库、不停聊**：返回给菲菲一段「今天额度用完了，我先按自己的理解答」的文本，她照常对话——比整个拒绝回复体验上不突兀。白名单开关默认关（所有人享全局默认额度 20/天），开启后仅名单内可查、其余 0 次；默认关=不破坏现有用户。
- **兼容迁移**：旧配置的一维 `userAliases`（`{userid:name}`）读盘时自动 seed 进新的 `users`（`{userid:{name,kbDailyQuota}}`），`wecomDisplayName` 优先读 `users` 备注名，老的显示名不丢。


### 3.22 批量投喂聊天记录（图片文件夹 / 压缩包，2026-07-23）

老板常把聊天记录以一堆截图交给菲菲提炼需求。原来企微一批最多 6 张、文件消息(zip)不支持；看板没有图片上传。需求：微信 + 看板两入口都能一次性把整批截图投喂进去。三处取舍：

- **四入口汇一个核心，而不是各写各的**。企微 zip 文件消息、企微多图放大、看板文件夹路径、看板 zip 上传——四条路看似不同，本质都是「拿到一批图片字节 → 交菲菲读图/登记」。所以只写一个服务端核心 `extractImages*` + `ingestChatImages`，**复用现成的 `personaReply(userid,text,images)`**（它早已支持 `images:[{media_type,data}]` 多模态 block + 菲菲人格 + `stage_requirement_intake`）。企微 sidecar 只负责把 zip 下载下来 base64 回传，抽取/解压/喂模型全在引擎里做一次。验证时用 3 张真实 PNG 走全链路，模型确实收到「3 张」——证明 ingest 抽出的 image block 形状与既有企微图片路径一致、可直接复用。
- **手写零依赖 zip 解析，不引三方库**。引擎的红线是「除 Agent SDK 外零依赖」。zip 不是 gzip，Node 内置 `zlib` 只能 inflate 单条 deflate 流、读不了 zip 容器结构。于是手写极简解析：从尾部扫 EOCD → 遍历中央目录取每项的方法/大小/本地偏移 → 图片项按 STORE(0) 直接切片、DEFLATE(8) 走 `zlib.inflateRawSync`。**关键细节**：压缩大小从**中央目录**读（不是本地头）——这样即使 Windows `Compress-Archive` 用了 data-descriptor（本地头 size=0）也拿得到正确长度。**已知边角**（不支持加密 / zip64 / bzip2 等其它方法）解析失败**优雅降级**为「改用文件夹路径入口」，不炸。用真实 `Compress-Archive` 产物验证通过。
- **护栏与顺序**：单批 ≤20 张、单图 ≤5MB、总量 ≤25MB（<`persona-reply` 的 30MB HTTP 上限，留余量），超量**截断/跳过并如实告知**张数——不静默丢。图片**按文件名数字序排序**（截图命名多含序号/时间，保对话顺序，避免模型读乱）。看板投喂经菲菲人格（同企微那颗大脑）而非另起 kanban run——复用现成 intake，最省接线。
- **真机不确定性**：企微「智能机器人」是否真会把用户发的文件投递成 `message.file` 事件、且带可下载的 url+aeskey，SDK 未文档化。代码以「取不到就走兜底话术、不崩」兜住，标注为待真机冒烟项。
- **看板侧回撤（同日）**：原计划里 office-lab 看板也做一个「投喂聊天记录」弹层（填路径/传 zip → 抽图 → personaReply）。落地后用户指出**方向错了**——看板聊天窗口本就有完整附件系统（回形针/粘贴/拖拽 → `/api/upload` → 注入文件路径、菲菲 Read 看），独立弹层是**冗余交互**。教训：**先摸清既有能力再加入口**——这次是我没先确认「聊天窗口已支持附件上传」就并行造了个平行入口。已删弹层；企微那套（zip 文件消息 + 抽图核心 + `/api/wecom/ingest-images`）保留（渠道侧确实没有等价能力）。看板侧真正的痛点转到 §3.23。


### 3.23 看板「聊天记录定制 block」——展示层问题不开后端通道（2026-07-23）

把一大段多方聊天记录（企微「多选复制」）直接粘进聊天输入框会刷屏、可读性极差。这本质是**展示层**问题，不是数据通道问题。取舍：

- **不开新后端通道、纯前端解决**。聊天记录随现有文本消息发送即可（菲菲 SOP 已会解析多方记录）。用**哨兵** `〘聊天记录〙…〘/聊天记录〙` 把原文包裹进 message：菲菲拿到完整原文，前端据哨兵把它渲染成可折叠 `.chatlog-block`。无需改 `/reply`、`/dispatch`、streaming input——沿用既有 `[附件…]` 尾注同款「文本里塞标记、前端渲染」约定。
- **显式按钮 + 独立粘贴框，而非自动识别**。用户明确要显式入口，因为**后期还会有其它形式的聊天记录**（不同平台/格式）。自动识别（粘贴时正则嗅探）看似顺滑，但会误判、且难扩展；显式入口给「多格式」留了缝（数据结构带 `format` 字段，默认 `wecom-multiselect`，解析不出则 `raw` 原样保留不丢）。复用 `pendingFiles`/`renderAttach` 的待发-chip 机制，让聊天记录像附件一样挂着、输入框保持干净。
- **一个踩过的坑（记着）**：验证正则时用 bash `here-doc` 造测试脚本，`\\s\\S` 被 shell 吞成 `[sS]`，误报「抽取 0 段」。**教训**：验证含大量反斜杠的正则，别用 shell here-doc 传脚本（转义层会污染），用 Write 落文件再跑——真实 app.js 字面量是对的，是测试脚手架骗了自己。


### 3.43 企微 Webhook 智能表格作飞书需求表的只读镜像：一次「越砍越对」的方案收敛（2026-08-01，用户需求驱动）

问题：老板要让**企微同事也能看到**示例项目需求表（他们没有飞书）。原话是「让菲菲**通过企微 bot** 维护需求表」。

**决策历程（从最重砍到最轻，每一步都由企微的坑逼出来）：**

1. **先想「企微直连 CRUD」**（对标飞书多维表格那套）。查证发现企微能读写表格的是 **WeDoc 智能表格 API**（`wedoc/smartsheet/*`），要**自建应用** + corpid/应用 secret 换 access_token。已按这套实现了一版（`WECOM_QYAPI` 客户端 + 6 个 `wecom_*` 工具 + 配置卡），冒烟到「假凭证真实打到 qyapi 拿 40013」链路已通。
2. **踩坑一：机器人≠自建应用。** 老板说「智能机器人就是我们的自建应用」——但企微里**群机器人 webhook 只能单向发消息**、**智能机器人（长连接 aibot）也只是聊天渠道**，它的 BotSecret 是长连接专用密钥、**喂不进 `gettoken`**；真正调 REST 要的是**自建应用的 secret**（两把不同的钥匙、同一个 corpid）。心智模型：**渠道（被搭话）≠ 能力（改表）**。
3. **踩坑二：手动建的表 API 接管不了。** 企微「客户端手动新建的智能表格拿不到可用 docid，只有 API 新建的才有」——这是最多人卡住的点。直连方案还得再加「API 建表」helper 才能落地。
4. **老板嫌烦，问 `path/101239`** → 那是智能表格「**接收外部数据**」**Webhook**：工作表菜单开一下得一个 URL，POST 就能写（`records` 新增 / `update_records`+record_id 更新），**不用自建应用、不用可信 IP、手动建的表也能用**。只能写、不能读/删/管字段。
5. **老板拍定最终架构**：**飞书＝唯一权威主表（菲菲照旧读写），企微＝只读镜像**，引擎单向把飞书投影过去。→ **直连那套整个删掉**，换成 Webhook 镜像引擎。

**为什么最终方案最优（约束反而变简单）：**
- 只读镜像 = **只写不读**，正好卡进 Webhook 的能力边界（读/删/管字段的缺失全都用不到）。
- **零凭证纠纷、零可信 IP、手动表可用**——企微那堆前置全绕开，配置就剩「粘一个 Webhook URL」。
- 单向投影 = **零一致性负担**（不是双写、没有「以谁为准」），也不用菲菲学任何企微工具——她只管飞书，镜像是纯引擎插管。

**实现要点**：`syncWecomMirror()` 读飞书→按 `record_id` 映射（`wecom-mirror-map.json`，`atomicWrite`）upsert 到企微；飞书删的行企微**标「作废」**（Webhook 删不了行）；**全推文本**（`larkCellText` 展平，企微建同名文本列即可，避开单选/日期字段类型限制）。三触发：定时（`armMirrorSync` 仿 `armPatrolSweep`）＋菲菲写飞书后去抖即时（`scheduleMirrorSync`）＋手动端点。定时全量兜住老板手动改飞书。

**通用教训**：① **「用 X 的 bot 做 Y」先分清 bot 是「渠道」还是「能力」**——平台的「机器人」常只是消息通道，真正的 CRUD 在另一套文档/数据 API 上；混为一谈会把「配个 webhook」错配成「自建应用+授权+可信IP」。② **能只写就别要能读的复杂度**——把需求收敛成「单向只读镜像」后，Webhook 这个受限但零门槛的通道刚好够用，砍掉了直连方案 90% 的前置。约束不是在「能力表」上比大小，而是看**你真正要用到的那几格**。③ **别怕推翻自己刚写的**：直连那版未联调未提交，识别到 Webhook 更贴需求就整体回退，比「既然写了就留着」省未来的维护与困惑（两张配置卡、死代码）。④ **凭证按「应用」隔离**：企微同一 corpid 下自建应用 secret ≠ 机器人 BotSecret，配置/env/脱敏都要分开。

**改动落点**：`app/server.js`（Webhook 镜像引擎 `syncWecomMirror`/`armMirrorSync`/`scheduleMirrorSync` + `wecom-mirror-config`/`-map` 持久化 + `larkCellText` 抽取 + `/api/wecom-mirror-config`、`/api/wecom-mirror/sync` 端点 + 三处菲菲写飞书触发 + 启停臂/清）、`app/public/{index.html,app.js}`（「企微镜像」设置分区）、`roles/feifei.md`（改一句「企微那张是只读镜像、你别碰」）。回退了直连版全部代码。引擎改动**需重启 server**；前端按 mtime 刷 `?v=`。Webhook URL 落 `runs/wecom-mirror-config.json`（gitignore、脱敏）。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.48 企微镜像逐行单发撞频率限制：一次「假成功 + 无反馈」的双层缺陷（2026-08-03，事故驱动）

问题：老板反馈企微文档镜像（§3.43）点「立即同步」**没有任何结果反馈，企微那边内容也没同步过去**。

复现与根因（服务端日志一眼定案）：`server.err.log` 里 30+ 行 `[wecom-mirror] 行同步失败 … webhook errcode=45009 Too many requests`，`server.out.log` 里每次 `webhook output` 都是 `{"errcode":45009,"errmsg":"Too many requests…"}`；`wecom-mirror-map.json` 至今为空 `{}`（一行都没落地）。两层缺陷叠加：

1. **功能层（主因）＝逐行单发撞「调用次数/分钟」限制**。旧 `syncWecomMirror` 对飞书 30+ 行 `for` 循环、**每行一个 webhook POST、背靠背零间隔**打出去。企微 webhook 有两类限流：记录数（3000 条/表·分钟）和**调用频率**——我们才 30 行、远不到记录数上限，卡的是**调用次数频率**（亚秒级连发 30+ 请求）。整批被 45009 拒。查证（WebSearch 企微开发者社区/文档）确认 45009=「接口调用超限」，官方建议正是「**批量减少请求数 + 批次间限速 + 退避重试**」。
2. **可观测层＝"假成功 + 无反馈"**。逐行失败被 `try{…}catch{console.warn}` 静默吞掉，`count` 只累加成功行（=0），**外层 try 正常走完 → `lastError` 被置空**，最后返回 `{ok:true, count:0}`。前端把它当成功、显示「已同步 0 行」，紧接着 `loadWecomMirrorConfig()` 又把结果条 `add('hidden')` 一闪隐掉——老板既看不到反馈、也不知道其实全失败了。**这是最阴的一类 bug：错误被逐条吞掉后，聚合层反而报成功。**

对策与取舍：
- **批量 > 单发**（治本）：`records[]`/`update_records[]` 本就支持一次请求写多行，旧代码却一行一发白白放大请求数。改 `wecomMirrorAddBatch/UpdateBatch`，每批 ≤100 行；~30 行从 30+ 次请求收敛到 **1 次**，直接绕开频率上限。新增回填 record_id 到映射（响应 `records[]` 与入参同序）、更新整批失败降级为逐批重建（目标行可能被人删）、已删行批量标「作废」。
- **限速 + 退避**（补稳）：批次间 400ms 间隔；`wecomWebhookPost` 对 45009 指数退避重试（1.5→3→6→12s，上限 20s、最多 4 次），退避耗尽才抛。批量已让请求数骤降，限速/退避是行数暴涨时的安全垫。
- **失败必须"响"**（治可观测）：返回加 `failed` 计数；**全失败明确 `{ok:false, error}`**（不再 `ok:true count:0`），`lastError` 写失败行数；前端改「**先 `await loadWecomMirrorConfig()` 再显示结果**」修掉一闪即隐，部分失败红字提示「已同步 N 行、M 行失败」。

通用教训：**① 对外部 API 循环调用，先问「有没有批量入口」——逐条发既慢又易撞频率限制，批量往往是官方首选；② 逐条 `catch` 吞错时，聚合层绝不能默认成功——失败要计数、要能让 `lastError`/返回值"响"，否则整批失败会伪装成"成功同步 0 行"这种最难察觉的状态；③ 排查"没反馈"先翻服务端日志，`errcode` 通常直接点名根因（这次 45009 一眼定案），不必从前端猜起。**

后续实测追修（同日）——**批量的反噬：一行坏拖垮整批（40058）**。重启后再点同步，45009 频率限制确实消失了，但整批（100+61=161 行）改报 **`errcode 40058 invalid Request Parameter`**：批量是原子的（整批成功或整批被拒），于是「某一行参数非法 / 单请求条数超上限」会让**整批 100 行连坐全失败**——这正是"批量"相对"逐行"的代价。老板一度想「加大阈值」，但 40058 不是频率问题，加大批只会让连坐范围更大、方向反了。对策＝**自适应二分降级**：`wecomMirrorAddAdaptive/UpdateAdaptive` 先整批发，失败就对半二分、递归到单行，把真正非法的那一行隔离成单行请求单独失败、其余好行照常落地；单行仍失败才计入 `failed` 并记下企微原话（`errSample`）回传前端。初始批大小顺势 100→200（happy path 一批发完，失败自有二分兜底）。**补充教训：批量写入必须自带"失败降级到更小粒度"的兜底**——否则一旦某行非法，批量就从"更快"变成"一个都进不去"；且错误文案别写死一种原因（先前写死"频率限制"，40058 出现后就误导了），要把下游 API 的原话如实带回。

真根因（同日第三修，一锤定音）——**新增用错了顶层键**。自适应二分把每一批都降到了单行，可**每一行仍报 40058**：这排除了"个别行数据坏"，指向系统性问题。核对企微 webhook「接收外部数据」的权威请求格式后真相大白：webhook 新增的顶层键是 **`add_records`**、更新是 `update_records`——而本功能**新增分支一直用的是 access_token 服务端 API 的 `records` 键**，企微当然一律 40058 拒收。这同时解释了最初那个诡异现象「`wecom-mirror-map.json` 从建起就恒空」：不是限流偶发，而是**新增自 2026-08-01 上线起就从没成功过一次**——巧的是更新分支用的 `update_records` 恰好是对的键，但因 map 一直空、根本没有行进入"更新"路径，所以错误 100% 集中暴露在新增上，前两修（限流→批量→二分）都在正确地治标、却没碰到这个键名错误。改 `wecomMirrorAddBatch`：`records`→`add_records`，返回体 record_id 也从 `data.add_records` 读。**这才是让内容真正同步过去的那一改**；前两修（批量/限速/退避/二分/errSample）仍有价值——它们把"限流"和"一行坏拖垮整批"这两个真实隐患提前治了，且正是二分降到单行、把 45009 与 40058 彻底分离，才让"系统性 vs 行级"一目了然、定位到键名。**最惨痛的一课：一个从没成功过的集成，"map 恒空"本该第一时间怀疑写入格式/契约，而不是先赖到运行期的限流/数据——空结果要区分"跑了但被拒" vs "跑了但没数据"，翻请求体比翻限流日志更快到根。**

**改动落点**：`app/server.js`（`wecomMirrorAddBatch` 顶层键 `records`→`add_records` + 返回解析【真根因】、`wecomWebhookPost` 加 45009 退避、`wecomMirrorAdd/Update`→`*Batch` + `*Adaptive` 二分降级、`syncWecomMirror` 分流分批 + `failed`/`errSample` + 全失败 `ok:false`）、`app/public/app.js`（`wecomMirrorSyncNow` 先刷状态再显结果、部分失败带回企微原话）。未改 HTTP 端点/SSE 事件/run 形状对外契约（`/api/wecom-mirror/sync` 返回仅**新增** `failed`/`error` 字段、`ok` 语义更严）。`node --check` 双通过；**待老板重启 server 后再点「立即同步」看反馈原话**：仍整表失败多半是企微镜像表列名/列类型对不上（按「同名文本列」在企微侧改），只剩个别行失败则是那几行数据被企微拒（反馈点名原因）。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.50 企微镜像终极真根因：整个请求体用错「方言」，且修好的代码从没重启生效（2026-08-04，事故驱动）

问题：§3.48 三修（限流→批量→二分→`records`→`add_records`）之后，老板反馈**镜像还是失败**，并顺手贴来企微工作表提供的「示例数据」。

复现与根因（服务端日志一眼定案，两件事叠加）：

1. **修好的代码从没跑过——server 一直没重启。** 翻 `app/runs/server.out.log`：今天（08-04 14:13）**最后一条** `webhook input` 的请求体顶层键**仍是旧的 `records`**（`grep -c '"records"'` = 6.9 万命中，`grep -c add_records` = **0**）。而 `server.js` 里 08-03 就已把键改成 `add_records`。结论：**上次改完 server 从未重启**，老板这些天一直在对着**旧进程**点「立即同步」，40058 自然一路不断——§3.48 末尾"待老板重启 server 后再点"的前置从没被满足。**「改了代码 ≠ 生效」，本仓库引擎改动一律需重启 server，日志请求体是判断「跑的是哪版代码」最快的证据。**
2. **即便重启也仍会 40058——整套请求体用错了「方言」。** 核对企微文档确认：**webhook「接收外部数据」** 与 **access_token 服务端 API** 是**两套不同方言**：
   - webhook：键用 **FIELD_ID**、**不带 `key_type`**、请求体须照抄工作表「示例数据」——`{ schema:{FIELD_ID:{title,type}}, add_records:[{values:{FIELD_ID: 纯文本}}] }`。
   - 服务端 API：键用**字段标题**、带 `key_type: CELL_VALUE_KEY_TYPE_FIELD_TITLE`、值是 `[{type:'text',text}]` 类型数组、顶层 `records`。
   本功能**从头到尾发的是服务端 API 那套方言**（`key_type=FIELD_TITLE` + 列名键 + 类型数组）打到 webhook 端点 → 每一行 invalid Request Parameter。§3.48 把 `records`→`add_records` 只改对了顶层键**这一格**，`key_type`/键形态/值形态**三格仍是错方言**，所以键改对了照样全崩。老板贴的「示例数据」正是权威模板：`field_example_one`=需求点 / `field_example_two`=状态 / `field_example_three`=提出人 / `field_example_four`=提出时间，schema + 纯文本值、无 key_type。

对策与取舍：
- **照抄示例数据的结构**（治本）：`wecomMirrorValues` 产出 `{FIELD_ID: 纯文本}`、新增 `wecomMirrorSchema()` 产出 `{FIELD_ID:{title,type:'text'}}`；`wecomMirrorAddBatch/UpdateBatch` 请求体改 `{schema, add_records/update_records}`、去掉 `key_type`。§3.48 的批量/限速/二分/errSample 全部保留（它们治的是限流与"一行坏拖垮整批"两个真实隐患，与方言正交）。
- **数据流改按 role 键、FIELD_ID 走配置**：`syncWecomMirror` 拍平的 `textMap` 从「飞书列名键」改成 **role 键**（summary/status/proposer/proposeTime），写入时经新增的 `wecomMirrorConfig.fields`（role→`{id,title}`）映射成企微 FIELD_ID。字段 ID 默认取自老板那张表的示例数据、落进配置——**换表/重建表后 FIELD_ID 会变，改 `runs/wecom-mirror-config.json` 即可，不动代码**。这样也把「读飞书用什么列名」与「写企微用什么字段 ID」彻底解耦。

通用教训：**① 「改了代码」和「代码在跑」是两回事——需重启的服务，验证第一步是翻日志看真实请求体/行为属于哪一版，而不是看源码；一个"从没重启"能让三轮正确修复全部白费。② 对接第三方，先分清「同名不同套」的方言——同是"写记录"，webhook 与 access_token API 的键名/键形态/值形态/有无 key_type 全不同，混用即 invalid parameter；权威模板不是文档里的通用示例，而是**目标资源自己给的「示例数据」**，照抄它最省事。③ 逐格排错要一次对齐所有格——§3.48 只改对顶层键一格、留着另外三格错方言，于是"改对了还是错"，误导了排查方向；契约类不一致最好整体比对示例、别一格一格试。④ FIELD_ID 这类"跟着目标表走、会变"的标识别硬编码进逻辑，抽到配置、给默认值 + 可覆盖。**

**改动落点**：`app/server.js`（`wecomMirrorConfig` 加 `fields` 映射；`wecomMirrorValues` 改纯文本值、新增 `wecomMirrorSchema`；`wecomMirrorAddBatch/UpdateBatch` 请求体换方言、去 `key_type`；`syncWecomMirror` textMap 改 role 键；标「作废」改 role 键 `{status:'作废'}`）。未改 HTTP 端点/SSE 事件/run 形状对外契约。`node --check server.js` 通过；请求体结构与老板贴的示例数据比对一致。**关键前置：必须重启 server**（旧进程从未加载 08-03 起任何镜像改动）；重启后点「立即同步」应见新增成功、`wecom-mirror-map.json` 落地、企微出现镜像行。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.52 企微镜像防重复：幂等映射「只在末尾落盘」留出中断→重复窗口（2026-08-04，用户提问驱动）

问题：老板问「我们系统定时写数据，不会重复吗？」——一个正中要害的提问。企微 webhook「接收外部数据」的 add 是**非幂等**的（每次都新建行、无按键 upsert），且 webhook **删不掉行**——所以「不重复」100% 靠我们自己的映射表兜。

分析：稳态**不会重复**。去重靠 `wecom-mirror-map.json`（飞书 record_id → 企微 record_id）：`syncWecomMirror` 把飞书行分成 `toAdd=不在 map` 与 `toUpdate=在 map`，定时轮只对已镜像行做**原地更新**、只对真正新行做 add；`_mirrorSyncing` 锁又保证定时 / 去抖即时 / 手动三个触发不会并发叠加去重复 add。**但有一个真实窗口**：`saveMirrorMap` 原本**只在整轮同步末尾落一次盘**，而 add 是分批发、回填的 record_id 先只存在**内存** map 里。若进程在「已写企微、尚未落盘 map」之间被杀 / 重启 / 崩溃，这批行在企微已存在、磁盘 map 却没记 → 下一轮定时把它们当「未镜像」**再 add 一遍 → 重复行**，且清不掉。此窗口在**首次全量**（map 空、一次性 add 30+ 行）时最大——恰是修完方言 bug 重启后即将发生的场景，也和本机「重启走托盘、别强杀」的运维纪律叠加（强杀正好落在这个窗口里）。

对策与取舍：**映射增量落盘**——`wecomMirrorAddAdaptive` 每次 `wecomMirrorAddBatch` 成功回填 record_id 后立即 `ctx.persist()`（=`saveMirrorMap`，`atomicWrite` 原子写、无torn write）。这把「中断→重复」的暴露面从「整轮同步」收敛到「**单次 webhook 调用与其后落盘之间**」——远程写和本地记录之间总有一个不可消除的最小间隙（任何「远程先写、本地后记」的幂等映射都有），做不到零窗口，但已是最小。代价＝多几次 atomicWrite（每批一次，首次全量约 1 次），可忽略。末尾整轮 `saveMirrorMap`（含标作废后的 map 删除）保留，覆盖 update/删除路径。

通用教训：**① 对「非幂等 + 不可删」的外部写入，去重全靠本地幂等映射，而这张映射的持久化时机就是可靠性的命门——「远程已写、本地未记」的中断窗口必然产生不可回收的重复，映射要「写一条记一条」而不是「整批完了再记」。② 幂等窗口消不掉、只能收敛：目标不是「零窗口」（远程与本地之间总有间隙），而是把窗口缩到单次远程调用。③ 运维纪律要和代码假设对齐——「重启走托盘别强杀」这条纪律，其价值之一正是避开这类「中途落盘前被杀」的窗口；反过来，代码也不该假设「永不中途被杀」。④ 好问题值钱：「会不会重复」这一问，直接逼出了一个平时不会触发、但首次全量必然经过的可靠性缺口。**

**改动落点**：`app/server.js`（`wecomMirrorAddAdaptive` 成功回填后 `ctx.persist()`；`syncWecomMirror` 的 ctx 加 `persist: () => saveMirrorMap(map)`）。未改对外契约。`node --check server.js` 通过；稳态去重（map + `_mirrorSyncing` 锁）走查无重复。**需重启 server 生效**。详见 CHANGELOG `[Unreleased]` 同名条目。


### 3.56 企微菲菲答「版本进度」答成飞书表：渠道人格被关在文件系统外、够不到唯一状态源（2026-08-06，用户提问驱动）

**现象**：老板在企微问菲菲「示例项目 5.16 到什么进度了？」，她回的是**飞书需求表**内容，没联合工作空间信息。

**为什么不「让菲菲找员工对话」**：老板一度想让企微菲菲去问其他员工。但员工脑子里**没有档案之外的私有知识**（设计即「任务档案=唯一状态源、指针不复制」），要「问 GG Bond 进度」他也只能回读同一份档案再复述——多绕一层、没多拿一个字，还要起一整个 Claude run（慢、贵，企微要秒回）。**查事实 → 读源；要判断/干活 → 那是 run = 开工 = 必须走看板**（企微≠开工信号，红线）。所以正解是给人格开一条**只读窄通道读源**，而不是「对话式驱动」员工。

**对策**：加只读 in-process MCP 工具 `query_version_progress`（handler 是 server 端 Node `fs.readFileSync`，**不放开 Claude 的文件系统权限**，与 `lark_*`/`buildTaskSnapshot` 同一模式）——按版本号定位主档案，聚成「条目逐条状态 + 发布态 + 时间线尾 + 同事近况」摘要。白名单准入（仅内部同事，进度不外泄）。派工红线不动：企微仍纯只读、不能开工。

**顺带坐实的坑（复用给未来读档案的人）**：**frontmatter 的 `status` 字段不可信**——v5.16 字面停在 `QA_PASSED`，但 `gates.released_test` 已 `true`（已发测）、还在做增量 REQ-0276。故进度**不能回读 `status`**，必须 `gates`（布尔位翻译发布态）+ 条目登记表逐条状态 + 时间线尾**三者交叉**。这与 §「条目按钮由条目状态驱动、与版本级 frontmatter status 无关」同源：**版本级 status 是叙事标签、会滞后，颗粒度真相在条目与 gates**。

**通用教训**：**渠道人格（企微/飞书 I/O 皮）与看板员工是两套能力边界，别默认它们信息互通。** 当一个入口「答得不对」时，先查它的**工具白名单里够不够得到那个事实源**，而不是怪它判断差——很多「答错」其实是「根本没通道」。补通道时优先**只读读源**（快、准、不破安全边界），别为了「更像人」去放开文件系统或让人格驱动真实 run（那会连累开工红线）。

**改动落点**：`app/server.js`（`findVersionArchive`/`extractTimelineTail`/`listActiveVersions`/`buildVersionProgress` 新解析器 + `makePersonaCaps` 注册 `query_version_progress` + `allowedTools` 白名单 + `buildPersonaPrompt` 引导）。需重启 server。详见 CHANGELOG `[Unreleased]` 同名条目。


### §3.59 飞书需求表读取：单页不翻页 = 静默截断（2026-08-07）

**现象**：菲菲反复反映读需求表（`lark_list_requirements`）老被 `limit` 截断，看不全。

**三层根因**（前两层是表象，第三层是真炸弹）：
1. **默认 `limit=60`**：工具入参不传 `limit` 时默认 60，日常裸调只回 60 条——这是菲菲直接感知到的截断。
2. **硬帽 200**：handler 与 `larkListRecords` 各有一处 `Math.min(200,…)`，传 `limit=500` 也封顶 200。
3. **★单页不翻页（静默截断）**：`larkListRecords` 只对飞书发一次 `GET …/records?page_size=N`，直接 `return data.data.items`，**没有 `page_token`/`has_more` 翻页循环**。表超过单页上限时，多出来的记录被**静默丢弃、不报错**。当时表约 132 条、未到单页上限，所以传 `limit=500` 恰好拉全，**掩盖**了这个 bug；REQ 编号已排到 0279，表越长越接近临界，届时菲菲会在「以为看到全表」的前提下漏判——这正是记忆条目「全量拉取才能全局判断、关键词搜漏新行」隐患的代码本体。

**对策**：`larkListRecords` 改成 `page_token`+`has_more` 翻页循环累加，`pageSize` 语义改为「期望的总条数上限」（默认 500），单页取 `min(500, 剩余额度)`（飞书 list records 单页上限 500），`has_more` 为假即停、`slice(0,cap)` 收口；工具 handler 去掉 200 硬帽、不传 `limit` 时默认拉 5000（实质=全表），describe 改「留空=全部（自动翻页拉全表）」。关键词过滤本就在拉取后跑，改成全表后过滤覆盖全量、顺带治「新登记行搜不到」。

**通用教训**：**凡是「一次请求 + 取 items」的分页 API 直连，只要目标集合会增长，就必须写全 `page_token`/`has_more` 翻页——否则就是一颗定时炸弹：小数据量下看着正常，越过单页上限后静默丢数据、无任何报错，最难发现。** 单元/手测阶段数据少恰恰最容易漏掉这类 bug。此坑与 `larkListRecords` 同形的任何直连列表（未来若接更多飞书表/外部列表 API）都要照此自检。

**改动落点**：`app/server.js`（`larkListRecords` 翻页 + `lark_list_requirements` handler 默认值/去帽）。需重启 server。详见 CHANGELOG `[Unreleased]` 同名条目。




### §3.82 企微智能表格接管需求表：一次撞在「能力分项授权」上的降级（2026-08-19 起，2026-08-21 降级定案）

> **结局先行**：主表反转**没做成**，已降级搁置，需求表仍以飞书为准、企微同事继续看 §3.43 那套 webhook 只读镜像。卡点不是技术实现（代码全通、表已建出、写入实测成功），而是**企微机器人的能力按项分授权，而「搜索与获取文档内容」要走领导审批、没批下来** → 表**写得进读不出** → 读不出就当不了主表。本节保留完整的调研与踩坑过程，因为其中两个判断错误、以及「授权项不对称」这个坑，比结论本身更值得记。

**缘起**：企业微信 2026-08 上线官方 AI 开放能力（`@wecom/cli`，Rust 二进制 + npm 分发、MIT 开源、14 个 Agent Skills，覆盖消息/邮件/文档/表格/待办/日程/会议/微盘/通讯录）。老板要在飞书表格能力之外加**企微文档维护能力**。范围经三轮澄清收敛：**只做需求表这一张**、**企微当主表**、飞书保留为手动同步副本、只给菲菲（看板 + 企微人格两个入口）、删改结构**全自主只要求透明**。

动机很实在：同事都在企微、没有飞书。§3.43 那套 webhook 只读镜像只能给他们看个**残缺投影**（只推 4 列、只写不读、删不掉行只能标「作废」、FIELD_ID 硬配）。有了真正的表 API，就该让企微那张变成能读能写能删的**主表**。

**第一堵墙（后被实测推翻一半）：企业模式 vs 小团队模式**

方案设计到一半，翻到一个官方文档没讲清、社区排查成本极高的坑（维护者在 [issue #64](https://github.com/WecomTeam/wecom-cli/issues/64) 确认、[#73](https://github.com/WecomTeam/wecom-cli/issues/73) 至今 open）：小团队模式（≤10 人）机器人以**授权用户身份**调用、继承授权人的既有文档权限（端点 `/mcp/bot/doc?uaKey`）；企业模式（>10 人）以**独立机器人身份**调用、**不继承**（端点 `/mcp/robot-doc?apikey`），只能访问「机器人自己创建的」或「被显式授予对象权限的」文档。本企业 >10 人，于是我据此判断「老板手动建的那张需求表，机器人读都读不了」，方案照「必须新建一张表 + 全量迁移」设计。

**⚠ 这个判断实测下来只对了一半。** `wecom-cli identity whoami` 的原文是：

> 机器人身份：菲菲 · 授权真人用户身份：项目负责人
> 「CLI 调用一定由你的机器人身份代用户执行，**真人授权用户创建或拥有的数据你可以进行读取、查询或下载，但你只能写入或修改机器人创建或拥有的数据**。如无法判断，以 CLI 实际执行结果为准。」

即这一版（8 月）**读已放宽、写仍受限**——issue #64（5 月、旧版 CLI、旧命令形态 `doc smartsheet_get_sheet`）描述的「读也不继承」已经不成立。**教训：拿三个月前的社区 issue 当当前平台行为的依据，会把方案往错的方向推**；真相在 `identity whoami` 这种「问平台自己」的接口里，比翻 issue 更权威、也更该先做。

另外两条实测坐实、且是真约束：新表**归属机器人**（老板在自己文档空间看不到源文件、只能存快捷方式）；智能表格**文件本身永久删不掉**（官方 `common.md` 明写「不支持删除智能表格文件」，#73 里确认机器人自己也删不了）——**建错了就永远留在那**。

**★ 真正拦下方案的第二堵墙：能力是「按项」授权的，读和写分属两项**

扫码授权（复用了菲菲那个在服务的长连接机器人 `aib50wGZ…W84`，省掉新申请；实测未踢掉 sidecar 的长连接，`connState` 全程 `authenticated`）之后，所有 `doc` 家族调用返回 `851008 partial no authorization`，并附一句官方要求逐字转达的提示：**「当前机器人未被授权『搜索与获取文档内容』能力，需向管理员申请使用。」**

注意 errmsg 里那个词：**partial**。老板去授权页开了一轮，回来实测得到一张极不对称的表：

| 调用 | 结果 |
|---|---|
| `smartsheet create` 建表 | ✅ `errcode 0`，拿到 `docid=s3_AOYAxngv…` |
| `smartsheet records add` 写一行 | ✅ `errcode 0`，`record_id=6a2hKW` |
| `smartsheet sheets list` 看子表 | ❌ `851008` |
| `smartsheet fields list` 看字段 | ❌ `851008` |
| `smartsheet records query` 读回 | ❌ `851008` |
| `doc search` 搜文档 | ❌ `851008` |
| `message aibot sessions list` | ✅ 通（说明授权本身生效，不是全局问题） |

**「创建/编辑文档」和「搜索与获取文档内容」是两个独立授权项**，前者批了、后者要走领导审批。于是能建表、能写行，就是**读不出来**。

**为什么「读不出」就必须降级、而不是先用起来**：① 菲菲答不了「需求表里有哪些/待处理有哪些」——那恰恰是这张表最高频的用途；② 迁移 206 行无法校验（写完读不回来，等于闭眼倒数据）；③ 最要紧的是，往一张读不出来的表里登记需求，会把台账劈成「飞书能查的」+「企微查不了的」两半，**比不写更糟**（本地 jsonl 至少 `recall_staged_requirements` 查得到）。所以 intake 落点也退回飞书优先，企微不做常规兜底。

**降级怎么落的（关键设计）**：把「启用」和「当主表」**拆成两个开关**（`enabled` / `isPrimary`）。只有 `isPrimary` 为真才 ① 让 `wecom_*` 六个工具真正干活（否则由 `wecomDegraded()` 闸住、只回一句降级说明，防止菲菲劈台账）、② 让旧 webhook 镜像自动退场。降级期两者皆假 → **旧镜像照常跑、同事的渠道零中断**，代码全保留、一行不删。读权限批下来后在设置里打开「作为主表」即全部生效。*取舍：多一个布尔位，换来「能力就绪但不可用」这个中间态可以被如实表达——比用 `enabled` 一个开关硬凑（要么全开要么全关）诚实得多。*

⑤ 直接改变了施工顺序：建表从「随手建一张试试」变成**一次性不可逆操作**，必须先 `--dry-run` 校验、字段一次定死。为此先只读探了飞书真表，结果和事前假设差得远：**206 行 / 19 列**（原以为 130+ 行 4 列），其中 4 个「图示案例*」文本列填充 0/1/0/0 是配图空占位、优先级里混进一个一次都没用过的脏选项 `JY2026A06247`、而「提出人」「提出时间」在飞书里**就是文本列**（有「晓娜、业务同事丙」这种多人写法、时间格式还不统一）——照搬成 user/date 类型会丢数据，所以企微侧照建文本列。**教训：不可逆操作之前，把目标数据的真实形状量出来，别拿印象施工。**

**机制取舍**

- **为什么破例引入外部二进制（与 §3.20「能力工具优先 in-process」的张力）**：§3.20 的真凶其实是 **npx**——每次调用现拉、离线/慢网/未装即炸。`wecom-cli` 是一次 `npm i -g` 装好的本地二进制，调用零网络前置，风险性质完全不同。且企微文档能力**没有**可直连的等价 REST 路径（自建应用那套已在 §3.43 试过并整体回退）。缓解：`wecomCliEntry()` 解析不到时整块能力优雅不可用、不影响任何员工（对齐 sidecar「缺依赖不崩」）。
- **Windows 上不要 execFile 那个 `.cmd` shim**：npm 全局 bin 在 Windows 是 `.cmd`，`execFile` 它必须开 `shell:true`，随之而来的是引号地狱 + 注入面（我们要传整坨 JSON 作参数）。改为**直接用当前 node 跑 `@wecom/cli/bin/wecom.js`**，`shell:false` + 参数数组，一次绕开两个问题。
- **写兜底保留 webhook，但和旧镜像彻底分家**：企业模式下 CLI 写入仍可能被拒，而 webhook 是**表自身**开的「接收外部数据」口子、与机器人身份无关，是可靠的第二条腿。但它属于**新表**，字段 ID 与旧镜像那张完全不同——故新起一份按「字段名→FIELD_ID」的映射，**不复用**旧镜像那份按 role 键、指向旧表的配置（§3.50 的方言坑教训：键名/键形态/值形态/有无 key_type 必须一次全对齐，混用即 40058）。**兜底删不了行**，所以删除工具无兜底、失败如实报错，且 SOP 要求菲菲「走了兜底必须说」——能力缺口不能被静默掩盖。
- **旧镜像「条件式退场」而非一刀切删**：主表反转后，飞书→企微的自动推送必须停（否则拿旧数据覆盖新改动）。但直接删掉会留空窗——老板还没扫码、还没建表的那段时间里，旧镜像仍是同事**唯一**能看到需求的渠道。故用闸 `mirrorAutoRetired() = wecomDocConfigured()`：企微主表一接通，自动推送自动退场；未接通照旧跑。**取舍：一个布尔闸换来「新旧交替期零空窗」，比「先删后建」稳。** 手动按钮与底层 webhook 函数全部保留。
- **读一律走 SQL 服务端过滤**：`records query --sql` 支持 `WHERE`/`LIMIT`，直接把 §3.59（分页静默截断）和性能规范（禁止先全量 load 再内存过滤）两条约束一次满足——这是相对飞书那套「拉回来再本地 filter」的净提升。
- **字段用名字寻址、不再硬配 FIELD_ID**：CLI 的 `records add/update` 用**字段名**做 key，这正是相对 webhook 方言（必须 FIELD_ID）的最大体验收益——换表/重建表不再需要改配置。

**通用教训**：

- **①「平台支持 X」要追问「以谁的身份、按哪几项授权支持」。** 官方 README 笼统写「可以读取文档、智能表格」，实际藏了两层分叉：身份模型（授权用户 vs 独立机器人，按企业人数分档）和**能力分项授权**（「创建/编辑」与「搜索与获取内容」是两项，后者要审批）。**权限模型比接口签名更值得先问清**——签名错了报参数错误一眼能懂，权限模型错了报的是一个看起来像「配错了」的码，然后你在分享链接、scode、重新授权、缓存之间反复打转。
- **② 别拿几个月前的社区 issue 当当前平台行为的依据。** 这次据 5 月的 issue #64 判定「企业模式读也不继承」，据此把方案设计成「必须新建表 + 全量迁移」；而 8 月这版实测是**读放宽、写受限**。issue 区适合快速理解「这个错误码大概是什么性质」（`851003` 那次就靠它省了几小时），但**当前行为要问平台自己**——`identity whoami` 这类自描述接口一句话就把权限边界讲清了，本该第一步就跑。
- **③「partial no authorization」这种词要当真。** errmsg 里一个 `partial` 就是在提示「按项授权、你只缺其中几项」。别把它当成「没授权」一把归零，也别当成「授权失败」——按项去探（我们最后是靠逐服务打一遍最轻的读调用，才看出 `message` 通、`doc` 不通、且 `create` 通而 `list` 不通这个不对称）。
- **④ 不可逆操作之前，先把目标数据的真实形状量出来。** 这次「以为 4 列 130 行、实际 19 列 206 行，且『提出人』『提出时间』两列的类型和想象相反（是文本不是人员/日期）」。若按印象建表，那张**永远删不掉**的表就永远错着。
- **⑤ 能力「就绪但不可用」要能被如实表达，别用一个开关硬凑。** 拆出 `enabled`（能力接通）/ `isPrimary`（是否当主表）两位，才让「代码全通、表已建好、但缺一项授权所以不启用」这个真实中间态既能落盘也能在 UI 说清；同时保证降级期旧通道零中断。一个开关的设计会逼你在「假装能用」和「假装没做」之间二选一。
- **⑥ 撞墙了要降级，不要硬上。** 「写得进读不出」时最大的诱惑是「先用起来，读的以后再说」——但那会把台账劈成两半，制造一个比现状更糟的状态。**降级的判据不是「能不能跑」，而是「跑起来会不会比现状更差」。**

**当前状态与解禁路径**：`runs/wecom-doc-config.json` 已存 `docid`（那张建出来删不掉的表，将来解禁直接复用、不必重建），`enabled=false / isPrimary=false`。等「搜索与获取文档内容」审批通过后：① 读回验证（表里那行 `REQ-TEST｜接通验证行（可删）` 就是第一个验证目标）；② 加成员权限 / 在新表上开「接收外部数据」拿兜底 webhook 与 FIELD_ID；③ 跑 `app/scripts/migrate-lark-to-wecom.mjs`（206 行 + 38 张图，进度落盘可中断重跑）；④ 设置里打开「作为主表」——这一刻旧镜像自动退场。**若审批一直批不下来**，那这次的净收益就只是「摸清了企微文档能力的真实边界 + 一套随时可启用的实现」，需求表维持飞书为准即可，没有任何回退动作要做。

### §3.94 需求表读取的第二次静默截断：每字段 60 字，把菲菲的 intake 判断建在碎片上（2026-08-21，老板观察驱动）

**现象**：老板看完守航冷启动首跑（run `20260821034335-b864a2`）的结论是「菲菲对需求了解的真的很少」。那轮她读了飞书「待处理」全量 30 条，逐条七项拷问，结论是 28 条不合格——理由多为「大需求／口径待确认／主观模糊」。流程上她做得对（挑 2 条、写需求说明 + 11 facet、建档案、seed 覆盖、回写飞书、交棒），但**判据薄**。

**根因（引擎，不是她）**：`larkFmtRecord` 里一句 `larkCellText(v).slice(0, 60)` —— **对每个字段一刀 60 字**。需求正文（需求点／详情／备注）普遍 100~400 字，于是她看到的是断在句中的碎片：

```
需求点:1. 增加买手环节
	任务创建成功后，买手备注要什么面料：文本+图片
2. 买手操作完成后可选指定运营和不指定
3. 其        ← 断在这里
```

REQ-0002/0004/0005/0006/0086 全部断句。**三层放大**：① 截断是**静默**的——她不知道被截了，只能凭碎片推断，「口径模糊」这个判断本身就是碎片的产物；② **无补救通路**——她在会话里确实试了「pull fuller detail」并重查 keyword，但 keyword 只在全量 JSON 上做客户端过滤、输出仍走同一格式化，**无论怎么查都拿不回全文**，而且当时**没有「读单条全文」的工具**；③ **附件不可读**——表里 `图示案例图片:image3.png` 这类附件对 UI 类需求就是需求本体，她只看到文件名，却没有任何提示告诉她"这里有你看不见的信息"。

**这是 §3.59 的同族第二例**：§3.59 是「单页不翻页 = 少了行」，本例是「每字段切 60 字 = 少了正文」。**同一张表、同一种病：把"压缩显示"当成了"数据接口"。**

**对策**：① 正文类字段（需求点/需求描述/详情/备注/说明/验收）额度放到 800 字，非正文 80 字，**截断处显式写出「本字段还有 N 字未显示，用 `lark_get_requirement` 读全文」**；② 新增 `lark_get_requirement(编号|record_id)` —— 单条、多行、零截断；③ `lark_list_requirements` 加 `full`（限 30 条）与 `status` 过滤（intake 传「待处理」，别整表拉 200+ 行）+ 总量护栏（>60k 字符自动降额度并明说，不静默丢）；④ 附件字段显式标注「引擎读不到图内容」，单条全文里进一步写明「关键信息在图里 → park，别猜」。

**同批 SOP 侧（`roles/feifei.md` §① 新增 1b/1c + 离开门禁 ④）**：这轮暴露的第二个问题与截断无关——**她压根没读需求语料库**。`docs/示例项目需求/<版本>/` 下每版都有《需求说明与验收标准》《需求确认文档》《实施记录》，而她只 `ls` 了目录拿版本号。最典型：REQ-0243 要复用已交付 REQ-0224 的「有纸样/无纸样」判定口径，她的做法是**派 Explore agent 去前端仓库 grep 代码反推**。故加两条硬要求：**1b「列表是摘要不是需求本体，进拷问前先读全文」**、**1c「判『口径模糊需老板拍板』之前，必须先证明语料库里也没定过」**（语料库＝历次需求文档 + 业务/IT 知识库 + 任务档案；已定过的直接沿用并注明来源，那不算替老板拍板），并明确**别用「grep 代码反推」代替读需求文档**（代码只说"现在怎么实现"，答不了"业务要什么"）。冷启动指令同步收窄了那句「禁用 `knowledge_base_query`」——它只该管**枚举底账**那一步，不该被读成"别查产品知识"。

**通用教训**：

- **① 给模型的「显示格式化」不能兼任「数据读取接口」。** 面向人眼的一行摘要（截断、省略、压缩）一旦成为 agent 的唯一输入，它的判断质量就被格式化参数悄悄封顶了。要么区分 list/detail 两个通路，要么让截断自己喊出来。
- **② 截断必须自证。** 静默 `slice()` 会让下游把碎片当全貌；一句「还有 N 字，用 X 读全文」就能把死路变成可走的路——**它省下的不是字符，是一次误判**。
- **③ 判「需求模糊」之前先问「我读全了吗、语料库查了吗」。** agent 的"严谨"会伪装成"这条有歧义、park 给老板"——而真实原因可能只是输入不全。所以门禁要求写清「查了哪儿、没定过」，把"证明模糊"的举证责任落到它自己头上。
- **④ 反推代码 ≠ 读需求。** 代码是"现在的实现"，需求文档是"业务要什么"；用前者替代后者时，已交付需求的口径就会被重新发明一遍（还可能发明错）。

**改动落点**：`app/server.js`（`larkFmtRecord` 分模式 + `LARK_BODY_FIELDS`/`LARK_ATTACH_FIELDS` + `larkFmtRecordFull` + `lark_get_requirement` 工具 + `lark_list_requirements` 的 `status`/`full`/预算护栏 + `guardedColdStartInstruction` 收窄禁令 + 企微人格 `allowedTools` 加新工具）、`roles/feifei.md`（§① 1b/1c、离开门禁 ④、工具段）。

### §3.97 需求表状态永远落后于现实：靠「某个角色记得翻表」的跨系统一致性必然漏（2026-08-21，老板日常观察驱动）

**现象**：v5.18 早已发线上（档案里 `released_prod: true`、`post_release_done: true`、`status: DONE`，波比 2026-08-20 收尾），飞书需求表里那几条 REQ 还挂在「待处理」。老板一句「菲菲总是忘记把任务档案的数据同步给飞书需求表格」。

**根因（结构性，不是态度）**：

1. **纪律只写在 SOP 里**：`roles/feifei.md` 让她在 PM_INTAKE 标「处理中」、PM_RELEASE_NOTES 标「已完成」+ 上线日期——**纯靠自觉，没有任何机器闸**。
2. **流水线最后一棒不是她**：发线上 + 上线后收尾都是波比。v5.18 的 `post_release_done` 注释原文就写着「待菲菲出版本发布说明/通知」——**她那一棒若没被再派一次，就没人去翻表**。忘记的窗口是流程结构造出来的，不是偶发。
3. **没有可挂的事件**：`released_prod` 这类 gate 是**员工手写 frontmatter**（v5.18 那几行带手写注释可证），引擎里根本没有「gate 翻转」回调。

**对策：对账（reconcile），不是回调**。新增 `syncLarkFromArchives()`——**任务档案＝事实源，需求表＝投影**：扫 `tasks/` 算出每条 REQ 的应有分诊态（`released_prod=true`→已完成 + 从 gate 行尾注释解析真实上线日；在登记表未上线→处理中；条目 `已跳过/已隔离`→回待处理），与表逐行对账后写回。三路触发：档案变动（挂现成的 `fs.watch(TASKS_DIR)`，debounce 5s + 全局最小间隔 2min）、30 分钟定时兜底（捞历史遗留，v5.18 就靠这一路）、手动 `POST /api/lark/sync`（支持 `dryRun`）。

**几个刻意的取舍**：

- **双向，不是单调前进**（老板当场纠正："可能要支持回退，不能一直往前推"）。第一版设计是"只往前推"（省心、零误降风险），但那样**发布回滚、条目被守航 park/隔离、需求被移出版本**都会让表停在一个已经不成立的「已完成」上。放开方向后护栏从"限方向"改成**限爆炸半径**：单轮降级超 3 条 → **整批降级不写、只报告 + 通知等人确认**（防某份档案被改坏/条目被误删而把整张表刷回去）。
- **多档案同 REQ 取 `fm.updated` 最新的那份**，不取"秩最高"。取最高秩看似安全，实则**等于禁止回退**（回滚就是在同一份档案上把 `released_prod` 改回 false；需求重开则是另一份更晚更新的档案）。
- **只碰三个字段**（状态/归属版本/上线日期），**「拒绝」行整行不碰**（那是分诊决定不是流程态），**表里没有的 REQ 只报告不新建**（新建要保真原始措辞，是菲菲的活）。
- **降级离开「已完成」时清空上线日期**——留一个已不成立的上线日比空着更糟。
- **幂等靠"归一化再比"**：日期字段（bitable type 5）存 epoch ms，**不能拿它的字面量跟 `YYYY-MM-DD` 比**——第一版正是这么写的，离线测试立刻照出「每轮都判不一致、每轮重写一遍」（白打 API + 审计日志全是噪声）。改成先把 ms 归一成本地日期串再比，复跑即 0 写入。写侧同理按字段 type 分流：type 5 写 epoch ms、文本字段写字符串。
- **失败不假装成功**：有活要干却一条没写成 → 明确 `ok:false`（§3.48 那次 `ok:true + count:0` 的教训），逐笔落 `runs/lark-sync.jsonl`，降级额外标 `direction:"down"`。

**通用教训**：

- **① 跨系统状态一致性只能靠对账，不能靠"某个角色记得住"。** 只要"同步"这件事的执行者不是状态变更的那一棒，忘记就是必然事件而非偶发失误。把它做成幂等对账（谁都不必记得，跑就是了）才是解。
- **② 事实源要唯一且可机读，投影侧就不该有人工改口。** 定了档案是事实源，表里的流程状态就必须"改了也会被推回"——这不是霸道，是避免两个都能改的写口互相覆盖（SOP 也据此改：要改状态去改档案）。
- **③ 自动化放开"回退"方向时，护栏要从"限方向"换成"限爆炸半径"。** 单调前进是最省心的安全，但它会把系统钉死在过期状态上；允许双向后，用**熔断 + 逐笔审计 + 通知**兜住误降级。
- **④ 幂等性要拿"复跑一次"验，不能只看"首跑对不对"。** 类型不一致（ms vs 日期串）这类 bug 首跑完全正常，只在第二轮暴露成"永远在写"。

**改动落点**：`app/server.js`（`parseReleaseDate` / `desiredLarkStates` / `larkSyncFieldMap` / `larkRankOfStatus` / `syncLarkFromArchives` / `scheduleLarkSync` + `fs.watch(TASKS_DIR)` 回调挂钩 + 30min 定时 + `POST|GET /api/lark/sync` + `larkConfig.autoSync` 总开关）、`roles/feifei.md`（「状态流转」改为引擎对账 + 她接 `missingRows`/`needsHuman`）、`.claude/agents/feifei.md`（速记同步）。
