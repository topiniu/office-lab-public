## 一、目标与形态
- **做什么**：把 TEMU 批量报活动从「运营在后台一页页手工点 + Excel 算利润」变成系统自动「查可报活动 → 拉候选商品 → 按公式算利润率 → 出报名清单 → 人工整批确认 → 完成报名」。
- **形态**：GYS 独立模块「批量管理」，与通知管理/示例项目并列；方向 C（直连 TEMU 开放平台）。
- **人工把关**：默认走**人工整批确认（分支 B）**后才提交；**自动报名（分支 A·免确认）能力后端保留、开关隐藏、不对用户暴露**——上线态一律人工确认。
- **★ 全模块设计原则（老板 2026-09-22 拍定·写死）**：**能自动就自动、能在系统里完成就不落地成 Excel/文件、人工只出现在"系统确实算不出 / 必须人拍板"处。** 落地体现：重量 TEMU 自动取；采购价公式自动派生 + 清单内高亮补（无外部表文件）；报名清单/结果都在系统页面 + 企微通知；人工只剩「分支 B 整批确认」+「补算不出的采购价行」，且同一张清单页一次做完。
  - **唯一的文件出口（老板 2026-09-24 追加）**：「**一键下载报名资料**」——导出 TEMU 后台批量报名可直接上传的表，给「API 报名还没上线」和「API 报错」两种情况兜底，让运营能拿着资料去后台手动报。它是**兜底出口、不是主流程**：系统内算、系统内审、系统内提交仍是默认路径（见 §四-bis）。
- **★ 交互形态：助理式、结论先行（老板 2026-09-24 定方向）**：终极目标是**程序自动判断哪些店的哪些商品该报哪些活动**，v1 只是在提交前加一道人工核对防误报。所以页面**不是「先选店 → 填参数 → 点查询 → 看表格」的表单流程**，而是**一进来就告诉你结论**：「你名下 N 家店、M 个活动，系统建议报 X 个商品」→ 看一眼报名数据 → 确认 → 再确认 → 提交。详见 §四。

## 二、已定业务口径（锁，来源：澄清单 v0.6 + 需求群 + 老板 2026-09-22）
| 项 | 口径 |
|---|---|
| 申报价 | **用平台建议价、不倒推、系统不做定价** |
| 利润率 | **只展示、不拦截、不设下限**（清仓类本就亏本清库存） |
| 成本公式 | 业务同事丙 v0.6 全套（采购价按 SKC 货号规则派生 / 总成本含头程尾程税广告售后 / 利润率=(申报价−总成本÷汇率因子)÷申报价）；**v1 固定、后期抽配置**；费率·汇率**按店铺**分设。克重改走 TEMU 真实重量（见 §五-bis）；TEMU 某 SKU 无重量时怎么兜底**未定**（原 444/550 规则是候选，进需求档时定） |
| 币种（2026-09-23 真实数据定） | **按候选接口返回的 `currency` 计算**（与澄清单「币种按店铺」一致，同店同币种；以返回值为准）：**CNY → 汇率因子=1**；**USD → 汇率因子=店铺汇率（默认 7）**。凡「售价×x%」类费用项（广告 10% 等）要先换回成本币种（人民币）：广告=售价×汇率因子×10%。单位：CNY 店实测为**人民币整元**（非分）。⚠ 业务同事丙原公式的 `÷7` 默认申报价是美元，CNY 店照搬会把成本缩小 7 倍、**利润率算高**——HTML 版 demo 早期即如此，GYS 临时 demo 页已按 currency 切换 |
| 采购成本来源 | **公式自动派生为主 + 清单内 inline 补价**（老板 2026-09-22 定板，取代早先「外部文档导入」通道）：从 TEMU `extCode`（≈后台导出表 SKC货号列）按业务同事丙规则派生；派生不出的行在报名清单里高亮「待补」，运营整批确认时顺手补一个采购价或勾「跳过不报」；**不产独立外部成本表文件**。真实采购成本（非前两位近似）属 v2 商品中心映射专项 |
| 运费补贴 | 做成开关、**默认不纳入**利润率 |
| 活动库存 | 按平台下限 + 业务设定值给出（非把 SPU 总量摊到 SKU）。**默认值（老板 2026-09-24 定，= 易用性评审 Q3）**：取「平台下限」与「活动类型设定值（配置页维护，默认 30，沿用报名表样例）」**两者较大者**；清单上**按 SPU 可改**、支持批量设。平台下限来源：`product.get` → `matchList[].suggestActivityStock`（建议活动库存）/ `targetActivityStock`（目标活动库存），均为 SPU 级；两者谁是「下限」**含义待官方文档确认**，进需求档前钉死取哪个 |
| 待补采购价的行 | **可以不补、按平台建议价直接报**（老板 2026-09-24 定，= Q2）：待补行**默认不勾**，运营可手动勾上直接报，该行利润率显示「**未算**」；补了价则按下方默认勾选规则自动重判 |
| 场次 | 需要选场次的活动，**默认报全部可报场次**，清单上可改（老板 2026-09-24 定，= Q4）。场次按商品取：`session.list.get` 必传商品 ID，`detail.get` 的 `activityInfo.sessionAssignType` 表示该活动的场次分配方式；量大时要控调用次数 |
| 重复报名 | **不做主动排重**——TEMU 对已报会报名失败、自动兜底 |
| 多活动 | 一个商品**可同时报多个活动**（不排他） |
| 利润率阈值 | **按活动类型/折扣分档配置**（不同折扣阈值可不同）。**阈值只决定默认勾不勾、不决定能不能报**（老板 2026-09-24 定，= Q1）：可算利润且 ≥ 该档阈值且未报 → 默认勾；可算但 < 阈值（含亏损）→ 默认不勾、可手动勾。折扣要求**没有独立字段**，判断依据用 `detail.get` 的 `requirements[]` + `canEnroll` |
| 活动优先级 | 85 折秒杀 > 9 折大促 > 85 折清仓（**可配**） |
| 活动周期 | **v1 只记录并展示活动周期**（结果页可见到期时间）；每天监控到期、自动重报**放 v2**（老板 2026-09-24 定） |
| 报名失败 | **不重试**，输出成功/失败 SKU 清单交业务（老板 2026-09-24 确认沿用澄清单口径） |
| 触发 | 运营手动 + 系统按天定时监控新活动；多店批量 |

## 三、技术方案（已坐实，2026-09-22）
- **凭证在店铺中心，走「代调」`/platform/api/call`，本模块不碰任何令牌/密钥/签名**（店铺中心代签）。
- 半托管店走 **`bg.marketing.activity.*` 六接口**（list.get 查活动 / detail.get / product.get 候选 / session.list.get 场次 / enroll.list.get 已报 / **enroll.submit 报名**）；**商品令牌够用**、我方 Temu 半托管店型支持——**已用真实店铺令牌实测 apiScopeList 全覆盖（含 enroll.submit 写）通过**。
- **P0 护栏**：① 报名 `enroll.submit` **只发一次 + 报完 enroll.list.get 回读确认 + 本模块自记报名流水对账**（代调层无重试/限流，防"读超时被当失败重发→重复报名"）；② 严禁盲报、报名不可撤销、报名截止跳过；③ 批量体积上限约 1MB，超了自动分批。
- **代签（代调）接线**：本仓到店铺中心的 Feign / TEMU 侧能力本仓空白，须新建——列为**开工第一个技术任务**单独打通验证（需店铺中心配合）。

## 四、入口界面（2026-09-24 改版：助理式、结论先行）

> 取代 09-24 上午版「三级选择器是流程起点」。三级选择器保留，但**从"第一步"降为"筛选条件"**：结论已经按当前登录人的店算好了，选择器只用来缩小范围，或者（持操作权限③时）切换去看别人的店。

### 4.1 能不能实现：能，关键是「提前算好」

- **为什么现在的 demo 做不到"一进来就有结论"**：demo 是点一下查一次、现场调 TEMU。一个员工名下几家店、每店几个活动、每个活动候选要分页拉全（真实店 1600~5900 个 SKU 行），再反查货号/重量、按商品查场次——现场算要几分钟，还会撞 TEMU 调用频率限制。
- **做法**：后端**按天定时 + 发现新活动时**，把「每家店 × 每个可报活动」的候选拉全、算好利润、按规则判好「建议报 / 不建议报 + 原因」，**存成一份"报名建议"**。用户打开页面读的是算好的结果，秒开；页面给「立即重新扫描」按钮，需要最新数据时手动触发（后台跑、跑完页面自动刷新）。**这一条本来就在已定口径里**（§二「触发：系统按天定时监控新活动」），改版只是把它从"后台功能"提到"页面的主角"。
- **代价（如实说）**：demo 是无状态的，正式版要**存数据**（报名建议 / 用户的勾选与补价草稿 / 报名流水），**要建表、有 DDL**——P4 报名流水本来就要建，这里提前到 P3。另外建议是某个时点算的，**提交前系统对要提交的那部分再实时复核一次**（申报价变没变、截止没有、是否已报），有变化的行提示用户，不静默提交。
- **"像 AI 助理"靠什么**：靠**主动算好 + 先给结论 + 每个判断都说得出原因**，**不引入大模型做报名决策**——报名不可撤销，判断必须是可复现、可解释的规则（利润率 / 阈值 / 待补 / 已报 / 截止）。助理式的"说人话"总结（如「今天新增 2 个活动，秒杀那个利润最好」）用规则拼文案就够，v2 再评估要不要接大模型润色。

### 4.2 页面长相（GYS 菜单「批量管理」）

**① 首页 = 今日报名建议**（进来即见，不用点查询）

```
┌──────────────────────────────────────────────────────────────┐
│ 👋 你负责的 3 家 Temu 店，当前有 5 个活动可报                     │
│    系统建议报名 412 个商品（SKC），另有 96 个需要你看一眼             │
│    数据更新于 今天 08:00 · [立即重新扫描]      范围：[本人 ▾][店铺 ▾] │
├──────────────────────────────────────────────────────────────┤
│ ⏰ 最急：XX 店 · 限时秒杀 · 还剩 6 小时截止                         │
├──────────────────────────────────────────────────────────────┤
│ 店铺 · 活动           截止       建议报   需看一眼   利润率中位  操作     │
│ XX店 · 限时秒杀        6小时后    120      8 待补     12%      [核对并报名] │
│ XX店 · 官方大促        3天后      260      30 亏损    6%       [核对并报名] │
│ YY店 · 清仓           5天后      32       58 待补     —       [核对并报名] │
│ ZZ店 · 官方大促        已报名 ✓  成功 250 / 驳回 4             [看结果]    │
└──────────────────────────────────────────────────────────────┘
```

- 一行 = 一张「**店 × 活动**」卡：截止倒计时、建议报几个、有几个需要人看（待补 / 亏损 / 数据异常）、利润率中位数。按截止时间排，最急的置顶。
- 「需要你看一眼」就是系统拿不准的部分：**待补采购价**（Q2：可不补直接报，但默认不勾）、**低于阈值 / 亏损**（Q1：默认不勾、可勾）、**数据异常**（利润率 < −100%）。
- 空态也要说人话：「你名下没有 Temu 半托管店」/「店铺授权不可用（状态 N）」/「今天没有新的可报活动，上次扫描 08:00」。

**② 核对页 = 点「核对并报名」进入某一张卡**

- 就是易用性评审 §2.3 那张清单：**按 SKC 一行、尺码折叠**；默认勾好系统建议的那些（Q1 规则）；顶部快捷筛选「只看需要我看的」一键把待补/亏损/异常挑出来；可补采购价、改活动库存（按 SPU）、取消勾选。
- 汇总条实时显示「将报名 X 个 SKC / Y 个 SKU，利润率中位 Z%」。
- 两个出口：**[确认报名]**（主按钮）/ **[下载报名资料]**（次按钮，见 §四-bis）。

**③ 确认 → 再确认 → 提交**（对应老板说的"点击确认再确认"）

- **第一次确认**：点「确认报名」→ 系统先对要提交的行做**实时复核**（价格/截止/已报），弹出摘要：「XX 店 · 限时秒杀：报名 120 个 SKC（520 个 SKU），活动库存合计 3600；有 3 个商品建议价刚变了，已按新价重算 [查看]」。
- **第二次确认**：摘要里要勾选「我已核对，知道报名提交后不能撤销」才能点「提交报名」。无操作权限②的人按钮置灰并说明原因。
- 支持**多张卡一起提交**（首页勾几张卡 → 批量确认），但摘要按「店 × 活动」逐张列清，不合并成一个模糊的总数。

**④ 结果 = 回到首页，那张卡变成结果卡**

- 成功 / 审核中 / 驳回（中文原因）/ 已报（不算失败）/ 查无 分类计数；驳回和失败的 SKU 可一键「**下载失败项报名资料**」去后台手动报（§四-bis）。企微同步推一句汇总。

**⑤ 配置页**（持操作权限①）：意向活动规则 / 商品排除规则 / 利润测算规则（按店铺）/ 各活动档位的阈值 / 活动库存默认值。店铺清单不在这里维护（自动取自 CRM 员工负责账户 + 店铺中心，见 §五）。

### 4.3 与已定口径的对齐

- 人工把关（分支 B）不变：系统只"建议 + 默认勾好"，**不会不经确认就提交**；自动报名开关仍隐藏。等 v1 跑一段、建议的准确度被验证了，再考虑对"高置信"部分放开自动（那是老板说的终极效果，不在 v1）。
- 店铺定位（§五）、权限四项（§七-2）、Q1~Q4（§二）全部沿用，只是呈现从"先选后查"变成"先给结论再筛"。

## 四-bis、一键下载报名资料（老板 2026-09-24 追加）

- **目的**：两种情况下让运营不被系统卡住——① **API 报名（P4）上线前**：系统已经把活动、候选、利润、默认勾选都算好了，下载下来直接去 TEMU 后台批量上传，**P3 做完就能用上**，不必等 P4；② **API 提交报错 / 被驳回时**：把失败那部分导出来，去后台手动补报。
- **文件格式 = TEMU 后台批量报名表的原样格式**（真实样例：`D:/Workspace/Projects/temu/ExampleProject/…/原始下载/…报名商品信息.xlsx`）：
  - sheet「活动申报价格」11 列：活动类型(活动主题) / SPU ID / SKC ID / SKC货号 / SKU ID / SKU货号 / 颜色属性 / 尺码属性 / 站点 / 活动申报价格 / 币种；
  - sheet「活动库存」3 列：活动类型(活动主题) / SPU ID / 活动库存。
  - 只包含用户**勾选要报**的行（与「确认报名」提交的是同一份数据），申报价 = 平台建议价，库存 = 清单上的值（含用户改过的）。
  - 业务同事丙 SOP 第⑤步是「删掉计算列再上传」——所以**默认下载的就是可直接上传的干净版**，不带采购价/成本/利润率列。另提供一个「带测算列」版本（多三列：采购价 / 总成本 / 利润率）给要留底或给老板看的人，两者文件名区分开。
  - 一店一活动一个文件（与 TEMU 后台按店按活动上传一致）；多张卡一起下载时打成一个压缩包，文件名「店铺名_活动名_站点_报名资料_日期」。
- **数据都有来源**：规格（颜色/尺码）取 `goods.list.get` 的 `productSkuSpecList`、SKC/SKU 货号取 `extCode`、活动类型取活动接口——已在调，零新增接口（见易用性评审 §3.5）。
- **下载后的状态**：系统不知道用户到底去后台报了没有。下一次扫描时用「已报名查询」（`enroll.list.get`）回读，报上的自动标「已报（手动）」，不会再被建议一遍。这一条依赖待确认 #12（TEMU 已报名查询能否查到后台人工报的），实测前先按"能查到"设计，查不到则退为用户手动标记「已手动报名」。
- **两个要先弄清的事**（进需求档前，见 §七-10、§七-11）：谁去后台上传；格式怎么验证。

## 五、店铺定位设计（2026-09-24 改写：老板定交互 + GG Bond 技术方案）

## 五-bis、利润率的地基：货号→采购价/重量 映射（P1 demo 硬证据 · 最高优先）
- **硬事实**（demo 2026-09-22）：TEMU 候选接口 `product.get` **只返回数字 `skuId/skcId`，不返回 SKC货号/SKU货号，也不返回重量**（货号只能当入参过滤）。而业务同事丙公式靠 **SKC货号派生采购价、SKU货号派生克重**——**仅凭 TEMU 接口算不出利润**，必须补一层「`skuId/skcId → 货号`（或直接 →采购价/重量）」映射。
- **三条路（v1 走哪条，待定 = 待确认 #9/#11 的收敛）**（⚠ 本段与下面「查证结论」是**探索过程留档**，已被下文「★ 真实令牌实测最终定论」+「接口与字段真名」取代——以那两段为准）：
  - **(a) 外部文档导入**：运营维护一张「skuId/货号 → 采购价/重量」表，系统读。可落地、但要人维护。
  - **(b) 商品中心直读**：TEMU SKU → 我方供应商变体 → 采购价/重量。跨系统、要商品中心配合建映射。
  - **(c) TEMU 商品接口反查（菲菲补充，最省，待 GG Bond 查证）**：该店 scope 已含 `bg.glo.goods.list.get/detail.get` 等商品接口——若它能按 `skcId` 反查到 **SKC货号 + 重量**，则**纯 TEMU 就能拿到公式所需，不必外部文档/商品中心**。**已派 GG Bond 查证。**
- **对"用户 0 参与"的影响**：(c) 成立 → 最接近 0 参与；(c) 不成立 → 退 (a) 外部文档（要人维护一张成本表）或 (b) 商品中心映射。
- **查证结论（GG Bond 2026-09-22，收口 #9/#11）**：
  - **货号（#9）走 (c) 纯 TEMU 反查**——SKC货号=`skcExtCode`、SKU货号=`skuExtCode`，都在 TEMU 商品域（`bg.glo.goods.detail.get` / `bg.glo.modelinfo.get`）；**商品中心给不了 SKC货号**（只有 `sync_platform_variant.sku` 疑似 SKU货号），而采购价公式靠 SKC货号前导数字，故必须走 TEMU 反查。
  - **重量（#11）走 (b) 商品中心直读为主**——店铺中心已把 TEMU 变体重量同步进 `sync_platform_variant.grams`（SKU 级·克），**在产接口 `/product/queryVariantRelations` 直接读、零新增 TEMU 调用**，且是**卖家真填值、比 demo 现用的 444/+50 兜底准得多**；TEMU 反查作兜底。⚠ `grams` 可空、覆盖率非 100%（该上线功能明写查不到就整单回退），**开工前须对目标店铺统计 grams 覆盖率**。
  - **唯一残口（前置）**：`skcExtCode/skuExtCode` 与 SKU 重量到底在商品接口**返回体**里、还是像 marketing 候选接口那样**只能当入参过滤**——文档强指示"在返回体"，但须一次真实令牌只读实调 `bg.glo.goods.detail.get` 收口（GG Bond 扩 demo 加一步，令牌到位即跑，届时 demo 可展示**真实利润率**）。
- **★ 真实令牌实测最终定论（GG Bond 2026-09-22，`bg.glo.goods.list.get` 调通·7549 SKC·非推测）**：
  - **重量 #11 = ✅ 走 TEMU 直取**：返回体 `productSkuSummaries[].productSkuWhExtAttr.productSkuWeight.value` 是**真实克重（毫克）**（实测 200000mg→200g），直接可用；**不必走商品中心、也不必 444 兜底**，比原派生规则准得多。
  - **采购价 #9 = ⚠ 取决于卖家填没填货号（大概率双通道，2026-09-22 老板质疑后修正）**：TEMU 的 `extCode` ≈ 后台导出表的「SKC货号」列（同一卖家自填编码字段）。业务同事丙采购价确从 SKC货号前两位数字派生，**能不能派生取决于该店卖家有没有把 SKC货号填成数字前导（如 `48-C01`）**：
    - **填了的店**（如报名表 ExampleProject 的 `48-C01`）→ API extCode 很可能返回该值 → 公式可派生 → **0 参与**；
    - **没填/乱填的店**（demo 测的 girl clothesss，extCode 大多空、或 `MYR-12` 非数字前导）→ 派生不出 → 需外部表兜底。
    - GG Bond「回外部表」结论基于**单店样本**（girl clothesss 没填），非普适；**真相大概率是双通道**。
    - **待钉死**：拿一个填了业务同事丙式货号的店（如 ExampleProject）在 demo 跑一次，看 API `extCode` 是否返回 `48-C01`。
  - **接口与字段真名（GG Bond 2026-09-23 真凭证实测，取代上文 `detail.get/modelinfo`、`skcExtCode/skuExtCode` 的推测名）**：反查走 **`bg.glo.goods.list.get`（不带 `.global` 后缀；带了返 7000016 type not exists——与 marketing 族、accesstoken 族必须带 `.global` 相反，别统一"顺手"加后缀）**；货号字段真名 **`extCode`**（SKC 层 / SKU 层各一份，按层级区分）；重量 `productSkuWhExtAttr.productSkuWeight.value`，**单位毫克**（÷1000 得克）。
  - **★ 采购价派生的假阳性风险（2026-09-23 真实货号暴露，写验收标准必须兜）**：真实 extCode 里有长数字（`604195447894`）、ISBN（`978…`）、占位（`skc-0`）等。HTML demo 早期「取全部前导数字」→ 上千亿采购价；GYS 临时 demo 已改为 L150 口径「取前两位」，但**前两位对非业务同事丙体系货号仍会产出看似合理、实则无意义的采购价**（ISBN→97、长数字→60），这类行**不会被标「待补」、会带着假利润率混进待确认清单**——比派生失败更危险（失败会高亮，假阳性不会）。
    - 业务同事丙 9/2 原规则其实是**格式白名单**，不是无条件 LEFT(2)：两位整数直用 / 两位数带小数取前两位 / 含字符如 `48-C01` 取前两位 / **不符的剔除**（L151 后「剔除」改为「待补」）。
    - **✅ 已定口径（老板 2026-09-24，= 待确认 #13）**：只有 extCode 形如「**恰好两位数字**，或**两位数字后紧跟非数字字符**」（`48` / `48.5` / `48-C01`）才派生采购价；其余一律「待补」——长数字（第 3 位是数字）、ISBN、前两位非数字、空都不派生。验收要有反例 facet：`604195447894`、`9787…`、`skc-0`、空 → 必须「待补」，不得出采购价。
  - **C1 v1 定板（✅ 老板 2026-09-22 认可）**：采购价 = **公式自动派生为主**（`extCode`/SKC货号前两位；实测填对率 8.31店=100%、ExampleProject=81%）+ **审阅清单内对"没解析出采购价的行"高亮"待补"、运营在整批确认时 inline 补一个采购价（即时算利润率）或勾选跳过不报**——**不产独立外部成本表文件**（把兜底从"另开一个 Excel"变成"清单里高亮+顺手补"）。重量走 TEMU 自动、无需进表。真实采购成本（非前两位近似）属 v2「商品中心 TEMU SKU→供应商变体映射」专项。残口(不阻断)：API `extCode` 对填对货号的店是否返回该货号，拿个填对的店跑 demo 即钉死（老板说不急）。
