# 对猪猪(Zhuzhu)平台的优化需求单 · QA 复盘驱动

> 读者：猪猪平台研发团队。产出人：office-lab（受项目负责人委托）。
> 口径：每条需求给「现状（带证据：`vision-e2e` 源码行号）＋ 诉求 ＋ 验收标准（facet，可断言）＋ 对应 QA 痛点」。验收标准写成猪猪自测可核对的可观测事实，不写实现方案。
> 缘起：项目负责人对 QA（迷糊老师）表现的四点复盘——① 测不出隐含 bug；② 版本迭代不做历史回归；③ QA 速度很慢很慢（只敢夜里排，早上回来常发现中止或质量差）；④ 偷懒（有造数 case 却直连库翻现成数据）。经 office-lab 查 35 个 QA run + 猪猪 `vision-e2e` 源码核准：**③④ 的一大半、④「夜里挂」的机械根因，源自猪猪执行底座的结构性约束**，故整理成本需求单。①「测不出隐含 bug」基本是 QA 方法论问题、已在 office-lab 侧改进 SOP，不在本单（仅末节列一条锦上添花项）。

## 一、现状基线（核准过的事实，别在这些上重复造轮子）

### 1.1 猪猪桌面端（`:32147`）当前暴露的 HTTP 路由（`vision-e2e/src/main/main.js`）

| 路由 | 方法 | 行为 | 证据 |
|------|------|------|------|
| `/app-runs/run-file` | POST | 跑一个测试文件；**同步阻塞到跑完才返回**；**单实例**，已有 run 在跑时第二个请求得 `409 busy` | `main.js:1249`（run-file）/ `main.js:1139-1152`（409 busy + activeExternalRunId）|
| `/app-runs/status` | GET | 查当前 activeExternalRunId | `main.js:1236` |
| `/external-activity/events` | POST | 活动事件通道（已存在） | `main.js:1206` |
| `/test-files*` | — | 读写测试文件 | — |
| `/external-integration-documents` | — | 拉当前版本对接文档 | `main.js:2158` |

**关键缺口**：桌面端 `:32147` **没有 `/validate-test-file`，也没有 headless 批量执行（test-sessions）**。=> 桌面 App 单开时，QA **被迫只能用最慢的 App-run**，预检退化到本地 `vision-e2e/src/shared/test-file-precheck.js` 脚本（且该脚本带 bug，见需求⑦）。

### 1.2 已具备、无需再做（避免重复提）

- **单 case 过滤已实现**：`scope=selected` + `caseId` + `case-not-found`（`main.js:1058-1084`）。历史说法「传单 case 仍跑全文件」已过时。（*待猪猪确认*：`caseIds` **数组**多选是否同样生效——`main.js:976` 读了数组，但外部 app-run 分支 `1058-1084` 只见单 `caseId` 处理，疑仍是单选。）
- **validate 步数告警已落地**：`case-many-steps` / `case-excessive-steps`（`test-file-precheck.js:794`）。文档「未实现」说法已过时。

## 二、需求清单

### Tier 1 · 直接决定「慢 + 夜里挂」，最高杠杆

#### REQ-Z01 · App-run 去单实例，支持并发/排队 【P0】
- **对应痛点**：③ 慢；使 ② 回归可行。
- **现状**：`run-file` 单实例，第二个请求 `409 busy`（`main.js:1139`）。QA 每个 run 30~72 次 curl + 15~26 次轮询全卡在这条串行链上；跑 L0/L1 全套回归慢到只能放弃 → 回归退化成「顺带路过」。
- **诉求**：支持一次提交一批文件/case 并行执行（多 worker）；若资源受限，至少服务端排队（提交即入队、按序消化、可查队列），不要直接 `409` 让调用方自己重试轮询。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z01-1 | 同时提交 N（≥3）个测试文件 | N 个并行/排队执行，全部有独立 runId 与结果，无一被 `409` 拒绝丢弃 |
| Z01-2 | 并行跑 vs 串行跑同一批 L0/L1 回归套件 | 并行总墙钟显著低于串行之和（给出并行度与实测耗时对比） |
| Z01-3 | 提交超过并发上限的任务 | 超出部分进队列、可 `GET` 查队列位置，不报错、不丢任务 |

#### REQ-Z02 · `run-file` 改异步 + 进度走事件流 【P0】
- **对应痛点**：③ 慢；④ 空转卡死。
- **现状**：POST `run-file` **同步阻塞到跑完才返回**（`main.js:1249`）——curl 超时响应就丢，只能去 `output/runs/.../summary.json` 捞；而事件通道 `/external-activity/events` **已经存在**（`main.js:1206`）却没用于把 run 进度推给外部调用方。
- **诉求**：POST `run-file` **立即返回 runId**（202 Accepted 语义），执行进度（每 case 开始/结束、step 级里程碑、最终 summary）通过事件流（复用 `/external-activity/events` 或新增 `GET /app-runs/:id/events` SSE）推送。让 office-lab 引擎「起了就走、完成事件到达自动接棒」，不用占着长连接空转轮询。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z02-1 | POST `run-file` | 立即返回含 runId 的响应（不阻塞到跑完），HTTP 不因执行时长超时 |
| Z02-2 | 订阅事件流 | 能按序收到该 runId 的「开始→逐 case 进度→完成(summary)」事件，含最终 pass/fail 明细 |
| Z02-3 | 客户端中途断开再重连 | 可凭 runId/游标补拉断开期间的进度事件，不丢关键的「完成」事件 |

#### REQ-Z03 · 桌面 App 单开时也提供 validate + headless 【P0】
- **对应痛点**：③ 慢；使 ② 回归可行。
- **现状**：`:32147` 桌面端只有 App-run（最慢），**没有** `/validate-test-file`、**没有** headless 批量执行。桌面一单开，QA 就没了快速迭代通道（headless），预检也退回本地带 bug 的脚本（需求⑦）。
- **诉求**：把 `/validate-test-file` 与 headless 批量执行（无可视化、并发、快）**挂到桌面 `:32147`**，或让原 runtime bridge（历史 `:32146`）随桌面 App 一起常驻可达。让「快速迭代→预检→headless 批跑→App-run 终验」四段链路在桌面单开时也完整。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z03-1 | 仅打开桌面 App（不额外起 runtime bridge） | `POST :32147/validate-test-file` 可用、返回同线上一致的 errors/warnings 结构 |
| Z03-2 | 仅打开桌面 App | headless 批量执行可用（可并发、比 App-run 快），产出可判定的逐 case 结果 |
| Z03-3 | 同一文件分别走 headless 与 App-run | 判定结论一致（headless 快速迭代、App-run 终验，不因通道不同得相反结论）|

### Tier 2 · 减少「抖挂」和无谓返工 —— 主要治 ④ 夜里挂

#### REQ-Z04 · 执行侧抖动自愈 + 幂等重试 【P1】
- **对应痛点**：④ 夜里挂。
- **现状**：`冻死(0 步无进度)`、`page.screenshot: waiting for fonts` 这类瞬时错误频发，QA 教训库反复记「retryable、重发即恢复」——但**平台不自愈，整轮 run 被判死**。夜间无人盯时，一个瞬时抖动＝一整晚白费。
- **诉求**：对已知 transient 失败（渲染冻结无进度、字体未就绪、截图瞬时失败等）平台内建**自动重试 + 幂等恢复**（step/case 级），并在结果里标注「重试过 N 次后成功/失败」，不把瞬时抖动直接计为用例失败。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z04-1 | 注入一次瞬时渲染冻结/字体未就绪 | 平台自动重试并恢复，该 case 最终判定不受这次瞬时错误影响 |
| Z04-2 | 结果报告 | 明示每 case 的重试次数/自愈情况，可区分「真失败」与「抖动后自愈」 |
| Z04-3 | 无人值守长批次（数十 case） | 单点瞬时抖动不会中止整批，其余 case 继续跑完 |

#### REQ-Z05 · 认证统一 + 持久化 【P1】
- **对应痛点**：③ 慢（试错）；④ 假红（登录步一挂后续全 skipped）。
- **现状**：headless 每 case 注入 storageState 恢复登录态（`authBootstrap=auto` 即可）；App-run 的 electron panel **不注入 storageState、也不跨 run 持久，还随日/环境漂移**——QA 只能靠 `includeRootSteps` true/false **反复试**，猜错一次登录步就挂、后续全 `skipped` 变假红。
- **诉求**：给一个**稳定一致、可查询的登录态注入口径**——App-run 与 headless 同源；用例不必猜「面板这次登没登」。要么 App-run 也支持注入 storageState，要么提供「当前面板是否已登录」的可查状态让用例条件化。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z05-1 | 同一登录态用例连跑多轮 App-run | 无需人工在 `includeRootSteps` true/false 间试错，行为确定可预期 |
| Z05-2 | 查询面板登录态 | 有明确接口/字段可判断「面板当前已登录/未登录」，用例据此条件化登录步 |
| Z05-3 | 同一登录 setup | headless 与 App-run 都能一致地进入已登录态，不出现「一个通道要登、另一个通道会因登录步而全 skipped」|

### Tier 3 · 降造数成本（间接治「翻库偷懒」）+ 预检准确

#### REQ-Z06 · macro 参数化 + teardown 按 id 清理 【P1】
- **对应痛点**：④ 偷懒（造数贵→翻库走捷径）；③ 慢（造数快）。
- **现状**：macro **只能静态展开、不支持参数化**（每个环节的「推进」各写各的，无法 DRY）；无 `saveAs` 跨步替换 → **造的数据无法按 id 定向清理**（teardown 缺位、造数留污染）。造数越贵，QA 越想直连库翻现成数据（项目负责人点名的偷懒），而翻库＝不可复现 + 空态假绿。
- **诉求**：① macro 支持**参数化**（同一流转 macro 传参复用，减少重复步骤）；② 支持 `saveAs`/运行时变量**跨步引用**，使 teardown 能按本 run 造出的 id 定向清理。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z06-1 | 用一个参数化 macro 造 3 条不同环节的数据 | 复用同一 macro 定义 + 不同入参即可，无需为每条各写一套步骤 |
| Z06-2 | case 造数后 teardown | 能引用本 run 造出记录的 id/标识做定向清理，跑完不留污染数据 |
| Z06-3 | case 失败时 | `teardown.alwaysRun` 仍执行清理，不因主体失败而漏清 |

#### REQ-Z07 · 本地 precheck 与线上 validate 对齐、修已知 bug 【P2】
- **对应痛点**：③ 慢（无谓返工/误导）。
- **现状**：桌面单开时 QA 只能用本地 `vision-e2e/src/shared/test-file-precheck.js`，它有两处已知问题误导用例：
  - `hasScopedExpectation is not defined` 崩溃（触发于「fill 值出现在自身 expectation」时）；
  - 对 `openUrl` 步**恒报** `target-missing` + `locatorScore 过低` 两条 blocking 假阳性（而 runtime `normalize.js` 里 `openUrl:{needsTarget:false}`，实为假阳性）。
- **诉求**：修上述两个 bug，并让本地 precheck 与线上 validate **判定口径一致**（同一文件两边 errors/warnings 结论相同）；若 REQ-Z03 让线上 validate 在桌面单开时也常驻，则本地脚本可退居备用，但仍需口径一致、不产生假阳性。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z07-1 | fill 值出现在自身 expectation 的用例过 precheck | 不再抛 `hasScopedExpectation is not defined`，正常给出校验结果 |
| Z07-2 | 含 `openUrl` 步的合法用例过 precheck | 不再对 `openUrl` 报 `target-missing`/`locatorScore` 假阳性 blocking |
| Z07-3 | 同一文件本地 precheck vs 线上 validate | errors/warnings 结论一致，不出现一边过一边挂 |

## 三、我方自担（非猪猪的锅，仅一条锦上添花）

- **①「测不出隐含 bug」是 QA 方法论问题**，office-lab 已在迷糊 SOP 加门禁（反事实关卡 + 每个写字段/写状态需求派生「回读」用例 + 强制回归真跑），**不要求猪猪承担**。
- **（可选·锦上添花）REQ-Z08 · 字段快照 + 前后 diff 断言原语 【P2】**：提供「读回某字段/某区块并做前后 diff」的断言能力，让「改 A 之后验 B 有没有被无声清掉」（如 v5.14「改款式条件→已录尺寸丢失」）这类**状态保留/回读**用例写起来更便宜。非阻塞，主战场仍在 QA 的用例设计。

## 四、优先级汇总

| 编号 | 需求 | 优先级 | 主治痛点 |
|------|------|:---:|------|
| REQ-Z01 | App-run 去单实例、并发/排队 | **P0** | ③ 慢 · ② 回归可行 |
| REQ-Z02 | run-file 异步 + 进度事件流 | **P0** | ③ 慢 · ④ 空转卡死 |
| REQ-Z03 | 桌面单开也提供 validate + headless | **P0** | ③ 慢 · ② 回归可行 |
| REQ-Z04 | 执行抖动自愈 + 幂等重试 | P1 | ④ 夜里挂 |
| REQ-Z05 | 认证统一 + 持久化 | P1 | ③ 慢 · ④ 假红 |
| REQ-Z06 | macro 参数化 + teardown 按 id | P1 | ④ 偷懒 · ③ 慢 |
| REQ-Z07 | 本地 precheck 修 bug、口径对齐 | P2 | ③ 无谓返工 |
| REQ-Z08 | 字段快照 + diff 断言原语（可选） | P2 | ①（锦上添花）|

> **一句话给猪猪团队**：P0 三条（去单实例并发、run-file 异步事件流、桌面单开也给 validate+headless）是把「QA 慢到只能夜里排」这件事从根上解决的总开关——并发让回归跑得起来、异步让引擎能自动接棒不空转、桌面 headless 让快速迭代通道回来。P1 三条治「夜里抖挂」和「造数贵到逼人翻库」。P2 收尾。
