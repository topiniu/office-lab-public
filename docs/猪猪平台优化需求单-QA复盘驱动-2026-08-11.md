## 二、需求清单

### REQ-Z09 · headless trace/report 增加 console + network 日志采集 【P1 · 可观测性】

> **⚠ 本条已按 2026-08-11 headless 实跑诊断重定位**（原拟的「headless 微应用可达性=代理/CORS 打通」前提**已过时、不成立**，见下）。

- **对应痛点**：③ 慢 —— 前端错误无法从猪猪产物取证，只能人工 curl 到网络层反推，慢且易误判根因。
- **诊断结论（2026-08-11 headless 实跑，证据 run 见本条末）**：
  - **原前提作废**：三个注册微应用源（`rms` / `zjk` / `commodity-zjk`）现均返 `Access-Control-Allow-Origin: *`，**headless 登录页正常渲染**（OCR 抓到「账号登陆」），**不再有 `loadMicroApp Failed to fetch`**。原报错对应"微应用源缺 CORS"的历史态，已在微应用服务端修好。且示例项目看板是**编进 master 包（umi.js）**的、非独立 remote-entry 微应用——"微应用可达性"本身就是误框。
  - **headless 进不了业务看板的真因 = 认证态没落在被测 origin**：gys-pre 的 `storageState` 把 `_TOKEN_` 绑在 `http://web.example.test` 源、且缺 `localhost` 会话 cookie；Playwright 按 origin 注入 → 被测 `baseUrl=http://localhost:8000` 拿不到 token → 前端守卫弹回 `/login`。App-run 因面板在 localhost:8000 **现场登录**故正常。**这属 office-lab 侧 auth-profile 配置、不是猪猪缺陷 → 已移出本单，由我方修**（重录以 localhost:8000 为源的 storageState，或 headless 走 `authBootstrap=run` 现场登录）。
  - **红鲱鱼**：`suppliers.example-company.offline.pre.cn` CORS/假证书确实坏，但它只是 `getSupplierAppUrl()` 拼"跳供应商端"深链的 base、dev 环境直返 `192.0.2.239`，**不 gate 看板/微应用渲染**。
- **本单唯一存留的猪猪侧诉求**：猪猪 headless（`test-sessions`）的 trace/report/diagnosis 目前**只存截图 + OCR + DOM，不采浏览器 console 日志、不采 network 请求日志**——qiankun 的 `Failed to fetch` 这类前端错误从猪猪产物根本无从取证（本次诊断即被迫人工 curl 到网络层反推、耗时）。**诉求：headless 执行时采集并随 report 落盘每步的 console（error/warning）+ network（至少失败请求的 URL / 状态码 / 失败类型），让前端错误可从猪猪产物直接取证。**

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z09-1 | headless 跑一个触发前端 fetch 失败 / JS 异常的用例 | report 里可查到该失败请求的 URL + 状态码 + 失败类型，及 console error 原文 |
| Z09-2 | 正常用例（无前端错误） | console/network 采集不显著拖慢执行、不撑爆报告体积（可配置：仅错误 / 采样）|

### REQ-Z10 · App-run 从「串行队列」升级到「并行多实例」 【P1】

- **对应痛点**：③ 慢；使 ② 历史回归跑得起来。
- **现状（证据）**：REQ-Z01 已把 `409 busy` 改成**入队不拒**（`GET /app-runs/queue` 可查），但交付的是**串行队列**——同一时刻仍**单实例执行**（教训库 #85、#90：App-run 单实例，队列逐个消化）。L0/L1 全套回归批次的墙钟 ≈ **各 case 串行之和**，回归仍慢到只敢夜里排。
- **诉求**：在排队之上支持**真正并行**（多 worker / 多面板同时执行），把长回归批次墙钟从「串行之和」降到「并行度分之一」；并发度可配置或按资源自适应，超出部分仍走队列不丢。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z10-1 | 提交一批 N（≥3）个用例文件 | 平台以并发度 K（K≥2）同时执行，总墙钟约 = 串行 / K，给出并行度与实测耗时对比 |
| Z10-2 | 多个 run 并行 | 各 run 的 runId / 登录态 / 造数互不串扰，结果各自独立可判 |
| Z10-3 | 提交超过并发上限 | 超出部分进队列、可查位置，不报错、不丢任务 |

---

### REQ-Z11 · App-run 造数链 checkpoint / 续跑 【P2】

- **对应痛点**：③ 慢 —— 长造数链每次为验最后一公里要**重放全链**。
- **现状（证据）**：App-run 每趟从头跑整条 macro 链；调试链尾断点时，链首每轮重放。本轮 run `20260811071357-67630f` 即典型：造数链 54 步，`idx29`（mode 切换假红）→ 修 → 重跑 → `idx32`（审价按钮 target-not-found）→ …… **每发现一个断点＝烧掉一整趟多分钟全链 App-run**，是长链调试的最大时间黑洞。
- **诉求**：支持在某 case/step 存**快照**（浏览器态 + 已造数据的 id 引用），后续从该快照**续跑**；调试链尾不必重放链首。与 REQ-Z06 的 `saveAs` teardown 配套，形成「造数一次、反复从中段调试」的能力。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z11-1 | 跑到第 N 步存 checkpoint，再从 N 续跑 | 不重放 1..N-1，续跑后最终态与全链跑一致 |
| Z11-2 | checkpoint 含已造数据引用 | 续跑复用这些 id、不重复造数 |
| Z11-3 | checkpoint 显式失效/清理 | 可主动作废，脏态不串到别的 run |

## 三、优先级汇总

| 编号 | 需求 | 优先级 | 主治痛点 | 依赖 |
|------|------|:---:|------|------|
| REQ-Z09 | headless trace/report 增加 console + network 采集 | P1（可观测性）| ③ 慢（前端错误可取证） | 诊断已完成（2026-08-11）|
| REQ-Z10 | App-run 串行队列 → 并行多实例 | **P1** | ③ 慢 · ② 回归可行 | — |
| REQ-Z11 | 造数链 checkpoint / 续跑 | P2 | ③ 慢（长链调试） | 与 Z06 saveAs 配套 |

> **一句话给猪猪团队**：v1.1 那批（桌面单开也有 headless / run-file 异步 / 自愈重试 / macro 参数化）已落地，谢谢。经 2026-08-11 实跑诊断，原以为的「headless 加载不了微应用」**不是猪猪的锅**——微应用 CORS 已服务端自愈、真正的 headless 进不去看板是我方 auth-profile 认证态没落被测 origin（我方自修）。所以留给猪猪的收敛为：**Z10 把已排队的 App-run 变成真并行（回归才跑得起来）**、**Z11 让长造数链能从中段续跑（长链调试不必每轮重放全链）**，外加 **Z09 一条可观测性小项（headless 采 console/network，好让前端错误能从产物取证、不必人工反推）**。Z10 是当前最高杠杆。
