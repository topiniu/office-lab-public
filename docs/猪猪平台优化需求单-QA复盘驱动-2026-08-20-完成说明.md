## 0. TL;DR（无人值守调用方最少需要知道的）

四件事，都能从 `GET <base>/app-runs/status` 自描述出来，**不要 hardcode**：

1. **单步不可能再无限 hang。** 到硬期限强制判失败（`error.code = "step-hard-timeout"`）、写 trace、run 继续跑到终态并产出 `summary.json`。要**精确**边界就在该步写 `hardTimeoutMs`（推荐给所有 `openUrl`/`reload`/`waitForNav`）。
2. **冻死 run 会自己释放槽位。** 已派发但 10 分钟（可调）无任何事件的 run 被看门狗判失败（`app-run-stalled`）、中断其在跑的 runtime、`activeCount` 归零、排队的立刻进来。**不需要人。**
3. **你们现在能自己清障。** `POST <base>/app-runs/{externalRunId}/cancel`（或 `DELETE <base>/app-runs/{externalRunId}`，或 MCP 工具 `cancel_run`），幂等。**不必 restart 猪猪，所以不会丢 HTTP 通道和面板登录态**——这正是你们上次选择 isolate 的原因。
4. **从列表捕获标量能用了。** `data.content[0].workflowId` 现在给你 `1152` 这个标量。`{{taskWfId}}` 直接插进下游 `callApi` body 不再是畸形值。

并行：`POST <base>/app-runs/batch`（MCP: `run_app_batch`）—— N 个文件在 **N 个各自独立的可视浏览器实例**里并行跑，并发度可配，超出排队不丢，一个卡死不影响其余。

## 1. REQ-Z12（P0 · 本轮 hard-block）—— 逐条对照

### 1.1 先说根因：你们那句「声明了 `timeoutMs`（20000）却未生效」的确切机制

需求单里那句判断是对的，而且指向了正确的位置。我们翻码定位到确切原因，值得完整写给你们，因为它解释了三个现象里的两个：

> **Playwright 的 `page.evaluate` 没有 timeout 选项**，也不受 `setDefaultTimeout` 约束。当渲染进程主线程被卡住（重型 SPA 重载 / 长同步任务 / 反复跳转）时，它返回的 promise **永不 settle、也永不 reject**。

而猪猪 runtime 的每一次可达性/快照/导航探测都建立在 `page.evaluate` 上，导航观察循环长这样：

```js
while (Date.now() - startedAt < timeoutMs) {
  await readPageMeta(page);   // page.evaluate —— 无界
  ...
}
```

截止时间只在**两次探测之间**被重新检查。所以**第一次探测被 park 住之后，循环再也回不到判定条件**——`timeoutMs=20000` 确实被读到了、确实传下去了，但那一层永远没有机会执行。这就是 step 停在 60、`steps/` 15 分钟无新 trace、`summary.json` 始终不产出的直接原因。

同一机制也解释了**为什么 `ZHUZHU_TRANSIENT_RETRY_BUDGET` 的自愈没触发**：自愈判定发生在一次 attempt **返回之后**，而这次 attempt 永远不返回。你们的判断「自愈只对瞬时崩溃生效、对步内永久 hang 不触发」在结论上完全正确，机制上是「自愈那段代码根本没被执行到」。

### 1.2 诉求 1 —— 步级硬超时

**做法（两层，分工明确）：**

- **步级硬超时（绝对保证）**：`executeWithRetries` 把每一次 attempt 套进 `withHardTimeout` —— 一个真实墙钟定时器，**不管被包住的操作在等什么都会触发**。到点后弃用原操作（吞掉它后续的 resolve/reject，不会变成 unhandled rejection、也不会再挟持 run），合成一个与正常输出**同形**的失败结果，尽力写出 trace，run 继续。
- **探测级硬期限（早失败 / 降级）**：给每步必经的四处无界 `page.evaluate` —— `readPageMeta`、`readPageReadiness`、`capturePageState`、`detectUiFrameworks` —— 以及 `page.screenshot` 各加 20s 上界。这一层的后果**按调用点不同**（我们逐点写了测试固定住）：
  - `settle` / **导航观察** / 框架探测 → 本来就有降级路径，超时 = 「这次探测放弃」，不影响该步判定（导航观察会把原因记进 `navigation.error`）。**你们那步卡住的正是导航观察这个循环**，现在它会带着 error 正常返回。
  - **证据快照**（`capturePageState`/`capturePageSnapshot`）→ 没有 catch-all，超时会向上冒、被步层归为 `step-hard-timeout`，**在 ~20s 触发，早于步级期限**。这是有意的：拿不到快照就没法继续该步的证据/diff 逻辑。

  两种后果都不是「无限等待」，而慢（但不卡）的页面不会被误判——探测本身很快返回就走正常路径。

**期限怎么取（请注意这里与验收字面值有个已知偏差，我们选择如实说明）：**

| 情况 | 期限 |
|---|---|
| 该步显式写了 `hardTimeoutMs` | **精确**用它 |
| 没写 | `max(该步声明的所有等待) × 2`，与下限 30s 取大，封顶 10 分钟 |

`timeoutMs=20000` 且没写 `hardTimeoutMs` → 硬期限 **40s**，不是 20s。原因：一步是「settle → 前置快照 → 定位 → 执行动作 → 导航观察 → 断言 → 证据采集」的复合体，其中好几个阶段**各自**都被允许用掉一次 `timeoutMs`；把整步硬卡在 `1 × timeoutMs` 会误伤大量合法的慢步。

**所以 Z12-1 要精确断言「≤ ~timeoutMs」，请在该步写 `hardTimeoutMs`：**

```json
{
  "id": "fg-nav-cost2",
  "type": "openUrl",
  "url": "http://localhost:8000/samplingCostOrder",
  "waitForNav": true,
  "timeoutMs": 20000,
  "hardTimeoutMs": 20000
}
```

也可以全局把倍数设成 1（`ZHUZHU_STEP_HARD_TIMEOUT_MULTIPLIER=1`）。我们建议**给所有导航步显式写 `hardTimeoutMs`**，已写进 `docs/test-case-generation-rules.md`。

**另外两点（超出诉求，但都是同一类坑，一起补了）：**

- 硬超时**不消耗**作者 `retries`，也**不吃**平台抖动自愈额度 —— 重试一个 hang 只会再烧一个完整期限。硬超时对该步是终局。
- `run()` 的收尾（`session.close()` / `storageState()` / OCR dispose）也加了 20s 上界。它们都要跟渲染器通信，在 wedged 页面上同样会 park —— 此前这会让一条**逻辑上已经跑完**的 run 仍然挂住调用方和队列槽位。

### 1.3 诉求 2 —— 冻死 run 自愈升级

按你们给的判定思路（「单步超 N×timeout 或整 run 超 M 分钟无新事件」）落了三层：

| 层 | 判定 | 结果 |
|---|---|---|
| 步级 | 单步超硬期限 | 该步判失败、写 trace、run 继续 |
| run 级 | 连续 N 步（默认 2）硬超时 | 页面已卡死 → 放弃剩余步（标 `stopped`）、发 `run-wedged` 事件、**收尾产出 summary**，不再 N × 期限地磨 |
| 队列级 | 已派发的 run 静默超过 `stallTimeoutMs`（默认 10 分钟） | 看门狗判失败（`app-run-stalled`、`retriable: true`）、中断其在跑的 runtime、**释放槽位**、`activeCount` 归零、`pump()` 放下一条进来 |

队列级看门狗是给「面板/进程层面彻底静默」这种步级机制也覆盖不到的情况兜底的，`.unref()` 的定时器每 30s 扫一次（`ZHUZHU_APP_RUN_STALL_SWEEP_MS`）。任何事件（包括逐步进度）都会刷新 `lastActivityAt`，所以正常的长 run 不会被误杀。

报告里 `telemetry.wedged` / `telemetry.hardTimeouts` 会标出来，读报告的人能区分「用例失败」和「浏览器卡死」。

**可观测性**：`GET /app-runs/queue` 与 `GET /app-runs/{id}` 现在每条 run 都带 `lastActivityAt` 和 `idleMs` —— 你们在做超时判定前可以先看它到底是"没动静"还是"在跑但慢"，不用猜。

### 1.4 诉求 3 —— 进程隔离

这一条我们要**如实分开讲清"做到了什么"和"没能证实什么"**：

**翻码结论：两条通道在代码层没有共享点。** headless `/test-sessions` 各自 `chromium.launch()` 自己的 Chromium、各自独立 context；`OcrService` 每个 run 一个实例；不存在模块级互斥锁、也不共用 App-run 队列槽位。所以**不存在"App-run 持有某个锁导致 headless 排队"这种串行依赖**。

**那你们观测到的 stall 是什么？** 我们的推断是叠加效应：卡死的渲染器把一个核打满，同时 **headless 自己的 `page.evaluate` 也是无界的** —— 同一个根因在 headless 侧同样成立。这是推断，不是证实（见 §7 已知限制）。

**所以我们的修法不依赖搞清上游原因**：给 headless 会话加上**自己独立的、绝对的**墙钟期限。

- `POST /test-sessions` 新增 `sessionTimeoutMs`（默认 40 分钟，`ZHUZHU_SESSION_HARD_TIMEOUT_MS`）。
- **双重强制**：① 作为 `runTimeoutMs` 下传给 `run()`（优雅路径：停步骤循环、自己写 summary）；② 外层再套一个 `withHardTimeout`（绝对路径：连"还没进步骤循环"都能触发，比如 `chromium.launch` 挂住 —— 这恰好对应你们看到的"只创建了 `session.json`"）。
- 任一触发都回到 round 层，**照常写出 `rounds/round-N/aggregate.json` + `diagnosis.json` + `report.md` 并正常返回 HTTP**（失败码 `session-hard-timeout`），而且**已经跑完的 case 结果不丢**。预算耗尽后剩余 case 直接跳过，不会每个再各给一份最小预算。

**净效果**：headless 通道**不可能再**出现"只创建 `session.json` 就永久静默、HTTP 永不返回"。这是可以断言的。至于"App-run hang 期间 headless 一切照常、速度不受影响"—— 需要真机复现才能确认，见 §7。

## 2. REQ-Z13（P1）—— App-run 取消端点

你们试的 `DELETE /app-runs/{externalRunId}` 现在**就是**取消端点。同时提供 POST 形式：

```bash
# 两个等价，/stop 与 /abort 亦为别名
curl -X POST "http://<host>:32147/app-runs/external-app-run-1787167096514-7eaf29/cancel?reason=stuck"
curl -X DELETE "http://<host>:32147/app-runs/external-app-run-1787167096514-7eaf29"
```

```json
{ "ok": true, "externalRunId": "external-app-run-...", "status": "cancelled",
  "cancelled": true, "wasRunning": true, "wasQueued": false,
  "activeCount": 0, "queuedCount": 0 }
```

**语义：**

- **running** → 中断进程内在跑的 runtime（abort 信号）+ 通知面板跳出逐 case 循环 + 标 `cancelled` + `activeCount` 归零，排队的立刻进来。
- **queued** → 直接从队列摘除，永不派发。
- **已结束** → `{ ok: true, cancelled: false, reason: "not-running", status: <原终态> }`，不报错、不改状态（幂等）。
- **未知 run** → `404` + `{ ok: false, status: "not-found" }`。

被取消的 run 在 SSE 上以终态事件 `cancelled` 收尾（`status` 枚举新增了 `cancelled`），`?wait=1` 的调用方也会拿到 `status: "cancelled"`。

**关键设计**：我们对 running 的 run 是**先拆掉真实工作、再 finalize**。否则会出现「槽位报空了，但 runtime 还在驱动浏览器」这种更糟的状态。而且**即使拆除失败（比如面板不响应），槽位依然释放**——把一条 run 永久留在 `running` 严格更糟。

**MCP 也有**：新增 `cancel_run` 工具（与 HTTP 同一实现的薄封装）。工具目录 9 → 11。

**这条正是为你们那个两难准备的**：不必 restart 猪猪桌面 App，所以不会丢 `:32148` HTTP 通道和面板登录态。

| # | 断言 | 状态 |
|---|---|---|
| Z13-1 | 对 running 的 run 调 cancel → 中止、`activeCount` 归零、标 cancelled，几秒内生效 | ✅ 单测覆盖（真机"几秒内"待验） |
| Z13-2 | 取消后立即提交新 run → 正常入队执行，无残留脏态/串扰 | ✅ 单测覆盖（断言 active/queued 集合无残留） |
| Z13-3 | 对已结束的 run 调 cancel → 幂等返回（not-running），不报错 | ✅ 单测覆盖（含连调两次、未知 run） |

## 3. REQ-Z14（P2）—— 列表响应捕获标量

`body[].path` 现在按「段 = `key` + 任意个访问符」解析，访问符支持 `[]`（展开）和 **`[N]`（下标，结果保持标量）**：

| 写法 | 结果 | 能否插进下游 callApi body |
|---|---|---|
| `data.content[0].workflowId` | 标量 `1152` | ✅ |
| `data.content[].workflowId` + `"first": true` | 标量 `1152` | ✅ |
| `data.content[].workflowId` | 数组 `[1152, 1153]` | ❌（原样保留旧语义） |
| `data.content[0].tags[1]` | 标量（下标可嵌套、可与取键混用） | ✅ |
| `[1].id` | 标量（顶层就是数组时直接下标） | ✅ |

`first: true`（别名 `saveAsScalar: true`）用于「断言路径必须保持 `[]` 展开形态、但捕获要标量」的场景，取首个非空成员。

**顺手修了一个你们没提但同源的坑**：下标越界**不再静默存 null** —— `saveAs` 取不到值时该断言直接判失败（`operator: "exists"`），错误里带完整 `body.<path>`。以前"路径写错"和"列表为空"都表现为 `null`，分不出来。

**旧语义零变化**：`[]` 的行为逐字保留（包括「作用于数组时丢 null、作用于对象时按位保留」这两种既有差异），`first` 缺省 `false`。所以你们**不必**为了 Z14 改任何已有用例；`createQuickTask` 那个"绕道从 `/create` 响应捕获"的改动可以回退，也可以留着（都能跑）。

| # | 断言 | 状态 |
|---|---|---|
| Z14-1 | `saveAs` 用 `data.content[0].workflowId` 捕获 → 标量、非 null、非数组 | ✅ 单测覆盖 |
| Z14-2 | 用捕获值拼下游 callApi body 的 `workflowId` → 合法标量、返 200 | ✅ 单测覆盖到"捕获值 JSON 序列化后是 `{"workflowId":1152}`"（真机 200 待验） |

## 5. REQ-Z10（P1，承上）—— 请重点看这条的口径

你们说得对，`GET /app-runs/queue` 之前一直是 `maxConcurrent: 1`，v1.2 的 Z10 只落在了 headless 批量上。这次给了**真正的并行多实例可视执行**，但**形态和你们可能预期的不同**，所以单独说明：

**做了什么**：`POST /app-runs/batch`（MCP: `run_app_batch`）—— N 个测试文件，**每个在自己独立的可视浏览器实例里执行**，并发度可配，超出的排队等槽（不丢）。这条通道**不走面板那个常驻单浏览器**，由主进程直驱，所以不受该面上 `maxConcurrent: 1` 的约束；各实例独立浏览器 + 独立会话期限，**一个实例卡死不影响其余**。

```bash
curl -X POST http://<host>:32147/app-runs/batch \
  -H 'content-type: application/json' \
  -d '{ "concurrency": 3, "authProfile": "gys-pre",
        "items": [ {"testFilePath":"v5.18/a.json"},
                   {"testFilePath":"v5.18/b.json"},
                   {"testFilePath":"v5.18/c.json","caseIds":["case-f1a"]} ] }'
```

请求体与 `/test-sessions/batch` 完全一致（同一个 worker 池、同一份共享默认值），差别只在这条强制 `headed: true`。结果读取与 headless 会话一致（`output/sessions/<id>/rounds/round-N/...`）。

**没做什么，以及为什么**：**面板那条交互式通道仍然是单常驻浏览器串行**（`maxConcurrent` 仍为 1）。面板的 `isRunning` + 单个 `runProgress` 模型与"一个常驻可视浏览器"是它作为**人工观测面**的固有结构 —— 把它改成 N 实例是一次横跨主进程 + 面板 + UI 的大改造，而且会动到 QA 每天在用的主路径。权衡后我们把并行落在了主进程直驱这条新通道上：它满足 Z10 的实质诉求（并行、并发度可配、超出排队不丢），而不拿单 run 路径的稳定性去换。

另外你们在需求单里说「Z10 和 Z12 是一对——并行了、单条冻死才不至于锁死全场」。这个因果这次被**反向解决**了：Z12 落地后，单条冻死**本身就不会**锁死全场（步级硬超时 + 队列看门狗 + cancel 端点三重保证），所以并行不再是冻死影响的解药。并行现在纯粹是回归墙钟的优化项 —— 这也是我们敢把面板通道保持串行的原因。

**注意**：每个并行实例是一个真实可视 Chromium，**并发度受机器资源约束**，默认只给 2。别盲目拉高。

## 7. 已知限制 / 请你们帮忙验的部分

我们不想把"机制已落"说成"现场已验"，所以分开列：

1. **Z12-3 的"拖垮"机制没能证实。** 翻码确认两条通道在**代码层没有共享点**（各自 Chromium、各自 context、无模块级锁、不共用队列槽位），所以不存在串行依赖。你们观测到的 stall 我们**推断**是「卡死渲染器打满 CPU」+「headless 自己的 `page.evaluate` 同样无界」的叠加，但这是推断。**本次的修法不依赖这个推断成立** —— 无论上游原因是什么，headless 现在都有独立绝对期限、永远终止、永远产出 aggregate。**如果真机复现后仍见两侧明显互相拖慢**，麻烦抓一下当时两侧的 CPU / 进程快照给我们，我们再定要不要把 headless 执行挪出 Electron 主进程做真正的进程级隔离。
2. **Z12-1 的期限与验收字面值有偏差**（40s vs ~20s）。原因和解法见 1.2 —— 写 `hardTimeoutMs` 即精确。这是我们主动选择的取舍（不误伤合法慢步优先），如果你们觉得默认倍数应该是 1，说一声我们改默认值。
3. **`page.evaluate` 只包了热路径 4 处。** locator-resolver / action-handlers / adapters 里按动作类型分支的 30 余处未逐个加探测级期限，靠步级硬超时兜底。**有界，但降级粒度是"整步失败"而非"这次探测放弃"**。如果后续发现某个具体动作分支（比如某个 AntD 组件的定位）经常卡，告诉我们是哪个，我们补上探测级期限。
4. **八条 facet 的真机验收待你们跑**（Z12-1/2/3、Z13-1/2/3、Z14-1/2）。我们这边是单测 + fake-page 复现，没有你们的被测环境。特别想请你们确认：Z13-1 的"几秒内生效"、Z12-2 的"`activeCount` 归零后排队的确实能进"、Z14-2 的"下游接口真的返 200"。
5. **`/app-runs/batch` 同步返回、无 SSE 逐条进度**（与 `/test-sessions/batch` 同限制）。要实时逐条我们再排。
6. **看门狗默认 10 分钟静默才回收** —— 一个**合法**但十几分钟不产生任何事件的步会被误判。默认可调、`0` 可关。你们的用例里如果有这种步，先跟我们说。
