# 对猪猪(Zhuzhu)平台的优化需求单 v3 · QA 复盘驱动

> 读者：猪猪平台研发团队。产出人：office-lab（受项目负责人委托）。
> 口径：每条给「现状（带证据）＋ 诉求 ＋ 验收标准（facet，可断言）＋ 对应 QA 痛点」；验收写成猪猪自测可核对的可观测事实，不写实现方案。
> 缘起：复盘迷糊 **v5.18 示例项目全量 QA**（守航态·无人值守）。本轮 QA 本身很顺——攻克了历史阻塞（制单页改 openUrl 直达绕 window.open、审版转正链补代提审、workflowId 标量捕获），机签了 5 个 facet GREEN+RED（REQ-0290-F3 转正唯一性、REQ-0299/0300 制单标识与保存时间）。**但后半程被猪猪平台一个 App-run 冻死 hard-block**：`sampling-5-18-req0290-costorder-merge.json` 的 f1a-f2 用例跑到 step60（両看板同值 ¥30 已命中）后，一个 `openUrl` 重载步**无限 hang**，连锁导致 **①整条 run 冻死不产 summary、②冻死 run 不自愈、卡住单并发队列 activeCount=1 十余分钟、③同进程的 headless `/test-sessions` 也被拖垮 stall**——最终 F1a/F2/F9 三个 facet 无法机签（守航无人、不敢 restart 猪猪怕丢通道），只能 isolate 留晨检。这是本单第一诉求。

## 二、需求清单

### REQ-Z12 · App-run 导航(openUrl/reload) hang 必须有硬超时中断，冻死 run 自愈释放槽位、不拖垮同进程 headless 【P0 · 本轮 hard-block】

- **对应痛点**：hard-block —— 直接导致 3 个 P0/P1 facet 无法机签。
- **现状（证据 · run `20260820-031817-514-panel-run-1787167096514-7eaf29`）**：
  - f1a-f2 用例跑到 `fg-assert-main-30`（step60，両看板 ¥30 已命中）后，下一步 `fg-nav-cost2`（`openUrl http://localhost:8000/samplingCostOrder`，`waitForNav:true`）**无限 hang**：step 停在 60、`steps/` 目录 15+ 分钟无新 trace、`summary.json` 始终不产出。
  - 该步**声明了 `timeoutMs`（20000）却未生效**——导航 hang 未被步级超时中断（疑 `waitForNav`/`waitUntil` 的等待未套 step timeout）。
  - **冻死 run 不自愈**：`GET /app-runs/queue` 十余分钟持续 `activeCount:1`、`active:[该 runId]`，`ZHUZHU_TRANSIENT_RETRY_BUDGET` 的自愈只对"冻死 0 步/字体错"这类**瞬时崩溃**生效，对"步内导航永久 hang"这类**卡死**不触发；单并发队列被这一条 run 锁死，后续 App-run 全部排不进。
  - **拖垮同进程 headless**：hang 期间新发的 headless `/test-sessions`（另起 context 本应独立）也 stall——只创建 `session.json`、始终不产 `rounds/aggregate.json`。即 App-run 面板 hang 会**污染整个 :32148 runtime 进程**，headless 逃生通道同时失效。
- **诉求**：
  1. **步级硬超时**：任何步（尤其 `openUrl`/导航/`waitForNav`）到 `timeoutMs` 必被强制中断、判失败、写 trace、继续/结束 run——绝不允许单步无限 hang 拖住整条 run。
  2. **冻死 run 自愈升级**：把"步内永久 hang"纳入自愈判定（如「单步超 N×timeoutMs 或整 run 超 M 分钟无新事件」→ 判该 run 失败、释放槽位、`activeCount` 归零），不只覆盖瞬时崩溃。
  3. **进程隔离**：App-run 面板卡死不得拖垮同进程的 headless 通道（headless 应能在 App-run hang 期间照常起 context 跑完）。
- **验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z12-1 | 用例含一个必然 hang 的导航步（如 openUrl 一个永不完成的 URL），设 `timeoutMs=20000` | 该步 ≤ ~timeoutMs 被判失败并写 trace，run 继续到结束并产出 summary（不无限 hang）|
| Z12-2 | 一个 run 卡死（模拟步内永久 hang） | 平台在有界时间内自动判该 run 失败、释放槽位，`GET /app-runs/queue` 的 activeCount 归零、后续 run 能进 |
| Z12-3 | App-run 面板 hang 期间提交 headless `/test-sessions` | headless 正常起 context 跑完并产 aggregate（不被 App-run hang 拖垮）|

### REQ-Z13 · 提供 App-run 取消/中止端点 【P1】

- **对应痛点**：hard-block 的兜底 —— 冻死 run 无法程序化清除。
- **现状（证据）**：本轮冻死 run 无任何接口可取消——试 `DELETE /app-runs/{externalRunId}` 返 `404 Route not found`；对接文档端点清单里也无 cancel/stop/abort。守航态（无人值守）下唯一出路是 restart 猪猪桌面 App，但那会**丢掉 :32148 HTTP 通道 + 面板登录态**，在无人环境风险极高（可能让整个会话再也跑不了 E2E），故我选择不 restart、直接 isolate——代价是本可机签的 F1a/F2/F9 只能留晨检。
- **诉求**：提供 `POST /app-runs/{id}/cancel`（或 `DELETE /app-runs/{id}`）**强制中止一个 running/queued 的 run** 并释放槽位；返回明确状态；被取消的 run 标 `cancelled`、不污染后续。这样即便 Z12 的自愈没兜住，调用方也能主动清障、继续跑别的用例，无需 restart 整个 App。
- **验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z13-1 | 对一个 running 的 run 调 cancel | run 被中止、`activeCount` 归零、状态标 cancelled，几秒内生效 |
| Z13-2 | 取消后立即提交新 run | 新 run 能正常入队执行，无残留脏态/串扰 |
| Z13-3 | 对已结束的 run 调 cancel | 幂等返回（not-running），不报错 |

### REQ-Z14 · assertResponse/networkResponse 的 body 路径支持数组下标取标量 【P2 · 造数效率】

- **对应痛点**：慢 —— 从列表接口捕获标量 workflowId 反复踩坑。
- **现状（证据 · runtime/assertions/index.js `readPath`）**：`readPath` 按 `.` 分段，只支持 `seg[]` 通配（flatMap 出**数组**）、**不支持 `seg[N]` 下标**。后果：想从 pageList 捕获单个 workflowId——
  - `data.content[0].workflowId` → `content[0]` 被当**字面 key**、取不到 → `saveAs` 存 null（本轮 probe 实证：捕获 null）；
  - `data.content[].workflowId` → 出**数组** `[1152]`，插进 callApi body `{"workflowId":"{{taskWfId}}"}` 后**畸形值 → 后端 400**（本轮 probe 实证）。
  - 唯一可靠标量来源只剩建单 `/create` 响应的 `data`（scalar）。凡"先查列表再拿某行 id 去调下游"的造数，都被迫绕道或改从 create 捕获——本轮为此改了共享 macro `createQuickTask` 补 create 响应捕获。
- **诉求**：`readPath` 支持数组**下标** `seg[N]`（如 `data.content[0].workflowId` 取第 0 行标量）；或提供等价的"取首个匹配标量"能力（如 `data.content[].workflowId` 配 `first:true` / `saveAsScalar`），让从列表捕获单值不再畸形。
- **验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z14-1 | `saveAs` 用 `data.content[0].workflowId` 捕获 | 存入的是标量（如 `1152`）、非 null、非数组 |
| Z14-2 | 用捕获值拼下游 callApi body 的 `workflowId` | 下游接口收到合法标量、返 200（非 400 畸形值）|
