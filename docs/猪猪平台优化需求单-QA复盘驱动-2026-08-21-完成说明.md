## 0. TL;DR（无人值守调用方最少需要知道的）

**五件事**，全部可从 `GET <base>/external-integration-documents` 的新 `headlessChannel` 块自描述出来，**不要 hardcode**：

1. **异步提交**：`run_headless({ testFilePath, wait: false })`（HTTP：`POST /test-sessions` 带 `"wait": false`）**约 1s** 返回 `{ sessionId, roundId, status: "running", terminal: false }`，会话在后台照常跑完落盘。**长造数链和"一次甩多个文件"都用它。**
2. **超时不再等于零信息**：阻塞模式现在由**服务端**设界（`waitTimeoutMs`，默认 **50s**，刻意小于 MCP SDK 默认的 60s 客户端超时）。到点**不报错**，返回**同一个句柄** + `waitTimedOut: true` + `partial: { sessionId, roundId }`，会话继续在后台跑。要旧的无限阻塞：`waitTimeoutMs: 0`。
3. **只看一个字段决定停不停**：所有会话响应都带 **`terminal`**。`get_run_summary({ runId: sessionId })` 轮询到 `terminal === true` 即止，终态里的 `status` / `firstFailure` / `reportPath` 与阻塞模式**逐字段同口径**（我们用同一个失败用例跑了同步/异步两遍逐字段比对）。
4. **句柄丢了有正规找回路径**：`list_sessions({ testFileId, limit })`（HTTP：`GET /test-sessions?testFileId=&limit=`）按测试文件倒序返回最近会话句柄。**请把 `sleep N && ls -1dt session-* | head -1` 从 SOP 里删掉**——你们说它取证不安全，我们同意，所以给了替代品（细节见 §1.4，包括为什么它不需要读 mtime）。
5. **headless 也能取消了**：`cancel_run({ runId: sessionId })`（HTTP：`POST /test-sessions/{id}/cancel`，别名 `/stop`、`/abort`，也支持 `DELETE /test-sessions/{id}`），幂等、有界进入 `cancelled` 终态、照常留证据。

**Z16-1 的答案（好消息，不用改姿势）**：`reuseBrowser` 一直只在**单个会话内部**复用一个 Chromium 进程；**会话之间从不共享浏览器 / context / cookie / storageState / runtime 变量**——每个会话自己 `chromium.launch` 一次。所以**多会话重叠是安全的，并发时不需要 `reuseBrowser: false`**。

MCP 工具目录 **11 → 12**（新增 `list_sessions`）；`run_headless` 新增 `wait` / `waitTimeoutMs` / `sessionTimeoutMs`；`cancel_run` 与 `get_run_summary` 现在**同时受理 headless 会话 id 与 App-run id**（id 决定通道，你们不用先判断它是哪种 run）。

## 1. REQ-Z15（P0）—— 逐条对照

### 1.0 先说缺口的确切位置（值得写给你们，因为它解释了"为什么会话都好、偏偏拿不到 id"）

你们观察到的两个事实同时成立：**磁盘上 17 个会话目录、结果齐全**（说明执行链没问题），但**超时响应零信息**。翻码定位到确切原因：

> `createTestSession` 只有「建会话文档 → 跑完一轮 → 返回响应」**一条同步路径**，而 `sessionId` **只出现在最后那个终态响应里**。

也就是说句柄的**产生时刻**被绑死在「跑完」这个事件上。于是：

- 客户端超时 → 连接死掉 → 句柄永远没机会送出 → `get_run_summary(runId)` 这条我们自己设计的回捞路径**无从调用**（你们的原话，完全准确）；
- 而且**这不是加个 try/catch 或改文案能修的**——服务端那边根本还没到"可以说出 id"的那一行。

所以修法是**把句柄的产生时刻提前到「会话文档创建完成」之后**（那一步只有一次文件读 + 两次小写，实测 26ms），跟"跑完"彻底解耦。这一改之后，三种提交模式（异步 / 有界阻塞 / 无限阻塞）自然都能拿到句柄，Z15-1 和 Z15-2 是同一个修复的两个出口。

### 1.1 诉求 1 —— `run_headless` 加 `wait` 参数 ✅

`wait` 默认 `true`（兼容），`false` 即异步提交。也接受 `async: true` 作为等价别名。

```jsonc
// POST <base>/test-sessions
{ "testFilePath": "sampling-5-19-xxx.json", "authProfile": "gys-pre", "wait": false }
```

**真实响应**（本机实测，26ms）：

```json
{
  "ok": true,
  "sessionId": "session-20260821-161729-95a78bb0",
  "roundId": "round-1",
  "status": "running",
  "terminal": false,
  "mode": "async",
  "partial": { "sessionId": "session-20260821-161729-95a78bb0", "roundId": "round-1" },
  "poll": {
    "tool": "get_run_summary",
    "args": { "runId": "session-20260821-161729-95a78bb0" },
    "endpoint": "/test-sessions/session-20260821-161729-95a78bb0"
  }
}
```

几个刻意的设计，请注意：

- **`roundId` 是提前算出来的**（新会话必然是 `round-1`），不是猜的——所以你们在提交那一刻就能拼出 `rounds/round-1/aggregate.json` 的路径。
- **`partial` 在异步响应里也给**（虽然此时不是"超时"），这样你们的解析代码**一套就够**：不管拿到哪种响应，读 `partial.sessionId` 恒定可用。
- 响应自带 `poll` 块（工具名 + 参数 + HTTP 端点），无人值守时不必回查文档。
- **提交那一刻会话状态就已经是 `running`**（不是 `pending`）——立刻轮询不会看到一个"其实在跑"的会话显示 `pending`。

> ⚠️ **一处语义变化请留意**：`wait:false` 时"预检 blocked"和"auth-missing"这两道门**移到了后台**（提交必须 ~1s 返回，不可能等预检+auth 走完）。它们会在你们轮询时以 `status: "blocked"` 呈现，证据照样落盘。想在提交那一刻就知道预检结论，先单独调 `validate_test_file`（这本来就是强制步骤）。

### 1.2 诉求 2 —— 无论如何超时都要先把句柄给出去 ✅

**这条我们按"服务端主动设界"来实现，而不是"在超时错误里补字段"**，理由是后者做不到：客户端超时发生在**你们那一侧**，服务端连"我超时了"这件事都不知道，没有机会往响应里塞任何东西。

所以：阻塞模式现在最多阻塞 `waitTimeoutMs`（**默认 50000**），到点**主动**返回句柄。默认值取 50s 是因为**你们说了 MCP SDK 默认 60s 且不是被测方可控的** —— 服务端先一步开口，你们那侧就永远不会走到"连接死掉"这个分支。

**真实响应**（本机实测，`waitTimeoutMs: 150` 触发）：

```json
{
  "ok": true,
  "sessionId": "session-20260821-161730-9295ef2b",
  "roundId": "round-1",
  "status": "running",
  "terminal": false,
  "mode": "wait-timeout",
  "waitTimedOut": true,
  "waitedMs": 150,
  "partial": { "sessionId": "session-20260821-161730-9295ef2b", "roundId": "round-1" },
  "poll": { "tool": "get_run_summary", "args": { "runId": "session-20260821-161730-9295ef2b" }, "endpoint": "…" },
  "message": "This session is still running after 150ms of blocking wait; the call returned a handle instead of timing out. It keeps executing in the background — poll get_run_summary(sessionId) … until `terminal` is true. Pass waitTimeoutMs:0 to block indefinitely, or wait:false to submit …"
}
```

注意 `"ok": true` —— **提交成功了、会话在正常跑**，这不是失败，所以我们没有把它塑造成 error（MCP 侧也不会置 `isError`）。判断"跑完了没"请看 `terminal`。

> ⚠️ **这是一处默认行为变更，请你们那侧确认一下**：一个「客户端超时设得很宽、且只认 `status === "passed"`」的老调用方，会从"一直等到结果"变成"需要轮询一次"。逃生口有两个：请求级 `waitTimeoutMs: 0`，或部署级 `ZHUZHU_SESSION_WAIT_TIMEOUT_MS=0`。批量通道（`/test-sessions/batch`、`/app-runs/batch`）我们**已强制豁免**（逐 item 强制无限阻塞），它们"跑完整批才响应"的契约不变。

### 1.3 诉求 3 —— `get_run_summary` 明确为 headless 的正规回捞路径 ✅

是的，你们实测到的"传 headless session id 能返回 `kind:"headless"` 的 pending 结果"是真的，而且现在**写进文档并给了示例**（对接文档 §MCP 接口 与 §Headless 测试会话接口）。同时做了两处加强，因为原来的返回口径其实**不够**你们直接用：

1. **headless 结果改为平铺**：原来是 `{ ok, kind, ok, data: { …整个会话文档… } }` 这种嵌套（你们得自己从 `data.rounds.at(-1)` 里挖状态）。现在 `status` / `terminal` / `ok` / `roundId` / `firstFailure` / `reportPath` / `diagnosisPath` / `repairContextPath` **直接在顶层**，与阻塞式 `run_headless` 的终态响应**同名同义**；原始文档仍保留在 `data`（不破坏你们已有的读法）。
2. **同口径不是"按约定"，是同一份代码**：按 id 读（`get_run_summary` / `GET /test-sessions/{id}`）和按文件列（`list_sessions`）共用同一个投影函数 `summarizeSessionDoc`。我们写了一条单测：**同一个会失败的用例**分别用同步模式和异步模式各跑一遍，逐字段比对 `status` / `roundId` / `firstFailure.stepId` / `firstFailure.caseId` / `firstFailure.code` / `reportPath` 一致。

**在途轮询**（实测）：

```json
{ "sessionId": "session-…", "status": "running", "terminal": false, "ok": null, "roundId": null, "roundCount": 0, "testFileId": "demo-file", "testFilePath": "f.json" }
```

**终态轮询**（实测）：

```json
{
  "sessionId": "session-…", "status": "passed", "terminal": true, "ok": true,
  "roundId": "round-1", "roundCount": 1,
  "firstFailure": null,
  "reportPath": "…/rounds/round-1/report.md",
  "diagnosisPath": "…/rounds/round-1/diagnosis.json",
  "repairContextPath": "…/rounds/round-1/repair-context.json"
}
```

**状态取值口径（请按 `terminal` 判断，不要自己维护白名单）**：终态 `passed` / `failed` / `blocked` / `cancelled`；在途 `pending` / `running` / `cancelling`。

> 顺便：终态里直接给了 `repairContextPath`，配合你们新写进迷糊 SOP 的「红了必须先读 repair-context」硬约束——**轮询到终态那一下就拿到路径了**，不用再多一跳。

### 1.4 诉求 4 —— 按 `testFileId` 反查最近会话的只读接口 ✅

MCP：`list_sessions({ testFileId, testFilePath, status, limit })`；HTTP：`GET <base>/test-sessions?testFileId=…&limit=5`。

**实测**（同一文件两个会话，倒序）：

```json
[
  { "sessionId": "session-20260821-161730-9295ef2b", "status": "passed", "terminal": true, "createdAt": 1787300250809 },
  { "sessionId": "session-20260821-161729-95a78bb0", "status": "passed", "terminal": true, "createdAt": 1787300249913 }
]
```

每条都带 `{ sessionId, status, terminal, ok, roundId, createdAt, updatedAt, testFileId, testFilePath, firstFailure, reportPath, diagnosisPath, repairContextPath }`——**找回句柄的同时就拿到了证据路径**。

**为什么它不需要读 mtime**（你们关心的取证安全）：会话 id 本身自带时间戳（`session-YYYYMMDD-HHMMSS-xxxxxxxx`），所以**目录名字典序倒排就是时间倒序**——我们既不 `stat` 也不看 mtime，而且**过滤发生在 `testFileId` 上**，所以并发的别人的会话**根本不会进入结果集**。这正是 `ls -1dt` 做不到的那件事。

三条实现细节，避免你们踩坑：

- 空结果**就是空数组**，不会"退化成最新那个"（`ls -1dt | head -1` 最危险的行为）。
- `limit` 默认 10、上限 100。
- 带过滤时最多扫最近 **500** 个会话目录（不带过滤时扫到够数即停）。按"反查最近句柄"的用途这是刻意的；要全量检索请直接读 `output/sessions/`。

## 2. REQ-Z16（P2 · 你们问的是语义，我们先直接回答）

### 2.1 「`reuseBrowser` 默认 true 时，多会话重叠会不会互相抢浏览器？」—— **不会，天然隔离**

我们翻了代码，逐层确认：

| 层 | 事实 |
|---|---|
| 浏览器进程 | **每个会话自己 `chromium.launch()` 一次**（`launchSharedBrowser`），会话之间**没有**任何共享的 browser 句柄、池或锁 |
| `reuseBrowser: true` 的真实作用域 | **单个会话内部**：root setup / 各 case / teardown 复用**这个会话自己的**那一个进程（把 `chromium.launch` 从 N+2 次降到 1 次，v1.2.1 的提速项） |
| context | 每个 `runSteps`（每个 case、每个 root 阶段）**各开独立 context** —— cookie / storageState / 页面状态互不可见 |
| runtime 变量 | 每会话一份（`createRuntimeVariables` 按 `sessionId-roundId` 建），不跨会话 |

所以：**`reuseBrowser: true` 与并发不冲突，你们并发时不需要改成 `false`**（改成 `false` 只会让每个 case 各自冷启浏览器、更慢）。你们本轮"17 个会话串行、结果全部正常"没踩到问题，不是运气——重叠也不会踩到。

为了让它**不再只是文档里的一句话**，我们做了三件事：

1. **写成明文**：对接文档的 `POST /test-sessions` 与 MCP `reuseBrowser` 参数说明都改为"scoped to one session"，并明确"并发不需要 `reuseBrowser:false`"。
2. **写成机器可发现的自描述**：`GET <base>/external-integration-documents` 新增 `headlessChannel` 块（`/app-runs/status` 也有精简版）：

```json
{
  "headlessChannel": {
    "submit": { "endpoint": "POST /test-sessions", "modes": ["sync","bounded-wait","async"], "asyncParam": "wait:false",
                "defaultWaitTimeoutMs": 50000, "timeoutAlwaysReturnsHandle": true,
                "handleFields": ["sessionId","roundId","partial.sessionId","partial.roundId"] },
    "poll":   { "endpoint": "GET /test-sessions/{sessionId}", "tool": "get_run_summary", "terminalField": "terminal" },
    "list":   { "endpoint": "GET /test-sessions?testFileId=&limit=", "tool": "list_sessions" },
    "cancel": { "endpoint": "POST /test-sessions/{sessionId}/cancel", "tool": "cancel_run", "graceMs": 20000, "idempotent": true },
    "isolation": {
      "browserPerSession": true, "reuseBrowserScope": "session", "contextScope": "case",
      "concurrentSubmitsIsolated": true, "reuseBrowserFalseRequiredForConcurrency": false,
      "note": "Each session launches its own Chromium process and a fresh browser context per case/root phase. reuseBrowser:true reuses that process inside one session only; overlapping sessions never share a browser, context, cookie jar, storageState or runtime variable scope."
    },
    "activeSessions": []
  }
}
```

3. **写成测试**：一条单测让两个会话时间上重叠、都用默认 `reuseBrowser: true`，断言 `launchBrowser` 被调 **2 次**、每个会话内部只用到 **1 个** browser 对象、且**两个会话用的不是同一个**。以后谁把浏览器改成跨会话共享，这条会先红。

### 2.2 「超时后的旧会话能不能取消？」—— **能了**

```bash
POST <base>/test-sessions/{sessionId}/cancel     # 别名 /stop、/abort
DELETE <base>/test-sessions/{sessionId}          # 等价
# MCP: cancel_run({ runId: "session-…" })        # 与 App-run 同一个工具，id 决定通道
# 请求体可选：{ "reason": "清障重来", "graceMs": 20000 }
```

两段式，因为"取消"要同时满足"干净"和"有界"：

1. **协作式（干净）**：中止信号下发到执行中的 run（引擎本来就支持 `options.signal`，逐步之间检查、每个 await 都 race），它收尾、**关掉自己的浏览器**，并**照常写出 `aggregate.json` / `diagnosis.json` / `report.md`**（`status: "cancelled"`、错误码 `session-cancelled`）。**已经跑完的 case 结果保留**，teardown 不再执行，不会再启新的 case。
2. **有界兜底（必然）**：若 `graceMs`（默认 20s，`ZHUZHU_SESSION_CANCEL_GRACE_MS`）内没进终态（真卡死了），**直接把会话文档判为 `cancelled`**，响应带 `forced: true`。**所以你们看到终态的时间一定是有界的。**

其他行为：

- **幂等**：取消已结束的会话 → `{ ok: true, cancelled: false, reason: "not-running" }`；未知 id → `404` + `code: "not-found"`。
- **诚实**：如果会话在"下发中止"和"grace 到点"之间**自己正常跑完了**，响应是 `{ cancelled: false, status: "passed", reason: "finished-before-cancel" }` —— 我们不会在 `status: "passed"` 旁边宣称 `cancelled: true`（这条是写完成说明时实测发现并改掉的，见 §5）。
- **孤儿回收**：猪猪重启后遗留的「文档写着 `running` 但其实没人在跑」的会话，取消时直接判终态（`orphaned: true`），不再永远挂在 `running`。

### 2.3 Z16 验收对照

| # | 断言 | 结果 |
|---|---|---|
| Z16-1 | 两会话重叠且均 `reuseBrowser:true`：文档给出明确语义；实测登录态/页面状态/runtime 变量互不污染 | ✅ **隔离由构造保证**（每会话独占 Chromium 进程 + 每 case 独立 context），已写成文档明文 + `headlessChannel.isolation` 自描述 + 单测。**结论：并发不需要 `reuseBrowser:false`** |
| Z16-2 | 对在跑会话调取消：有界进入 `cancelled` 终态、释放浏览器；`get_run_summary` 能读到该终态 | ✅ 协作式 + `graceMs` 强制兜底两条路径各有单测（含"无视中止信号的真卡死"）；`cancelled` 已纳入 `ok: false`（此前会算成 `ok: null` = 未知，对轮询方是错口径） |

// 1) 一次甩多个文件，各自约 1s 拿到句柄 —— 它们真并行
const handles = [];
for (const testFilePath of files) {
  const r = await callTool("run_headless", { testFilePath, wait: false });
  handles.push(r.structuredContent.sessionId);
}
// 2) 统一轮询到终态
for (const sessionId of handles) {
  let s;

    s = (await callTool("get_run_summary", { runId: sessionId })).structuredContent;

## 5. 自查时发现并修掉的三个缺陷（都是本次改动自己引入或暴露的，写给你们是因为其中一个会直接影响你们）

**① `wait:false` 的后台异常会让会话永久停在 `running`（严重，已修）。** 异步提交时**没有任何人 await 那个 promise**，所以后台路径里的意外抛错会被静默吞掉——会话文档永远停在 `running`、没有 round、没有产物。**这正是 v1.3 Z12-3 立誓消灭的「只创建 `session.json` 就永久静默」形态，被我这次的新代码从另一个入口又造了一遍。** 修法：任何 detached 执行都必须有"异常也要把状态推到终态"的兜底——先按正常路径 persist 一个终态 round；连 store 都坏了就退化为把会话状态写成 `failed`；两者都失败才 `console.error` 冒出来。**对你们的意义：轮询永远会收敛，不会出现"轮到天荒地老还是 `running`"。** 已有单测（注入一个必然抛错的 store，断言会话仍在 5s 内进入 `failed`）。

**② Windows 上会话文档的原子写会被轮询方顶掉（已修）。** 加了轮询之后，我把会话文档改成原子写（write-then-rename）以消除撕裂读；结果 Windows 上 `rename` 会因为**读方持有文件句柄**而 `EPERM`——而 v1.4 恰恰引入了"轮询期间反复读同一文档"。6 轮全量跑复现 1 次，表现就是 ①（会话永久 `running`，正是被 ① 藏住的）。修法：rename 重试阶梯（6 次、10ms 递增）→ 仍失败则**降级为就地写**（丢原子性也绝不丢进度）→ 读侧对撕裂解析重试一次兜底。

**③ 取消响应会在 `status: "passed"` 旁边宣称 `cancelled: true`（已修）。** 写这份说明、跑端到端 smoke 时发现的：会话在"下发中止"和"grace 到点"之间自己正常跑完了，而响应仍按"请求了取消"报 `cancelled: true`。这会让你们对响应里**其他所有字段**都失去信任。改为按实际结果报：`{ cancelled: false, status: "passed", reason: "finished-before-cancel" }`。

## 6. 已知限制 / 请你们帮忙验的部分

- **真机 facet 验收待你们跑**：本轮交付的是机制 + 单测（用 fake runImpl 模拟长会话、卡死、并发重叠）。七条 facet（Z15-1~5、Z16-1~2）需要在被测环境实跑确认。
- **⚠️ 最需要你们实测的是 Z15-4 的真实并行度**：单测里的"并发"是 fake runImpl 的时间重叠，**真机上 N 个 Chromium 的并行度受这台机器的 CPU/内存约束**。你们按 3 并发估算 68.3min → 22.8min，请实测一下这台机器上 2 / 3 / 4 并发的实际收益与稳定性（会不会因为资源争抢反而让单会话变慢、甚至触发步级硬超时），把结论回填给我们，我们写进对接文档（现在文档只写了"受机器资源约束"）。
- **异步提交没有 step 级实时进度**：轮询拿到的是会话级状态（`running` → 终态），不是逐步进度流。要 step 级实时进度目前只有可视 App-run 的 `/app-runs/{id}/events`（SSE）。给 headless 会话接 SSE 是后续项——**如果你们的守航看板需要"跑到第几步了"，请提，我们排上。**
- **在跑会话注册表是进程内的**：猪猪重启后，在跑会话的**协作式**取消能力随之消失（只剩"孤儿会话直接判终态"这条兜底）。与 App-run 队列现状一致。
- **cancel 之后被弃用的那次 run 可能还在后台收尾**：`forced: true` 只保证**你们**在有界时间内看到终态，不保证那个浏览器进程同一时刻就消失（它有自己的会话墙钟上限兜底）。要立刻回收资源需要进程级隔离（把 headless 挪出主进程），这是 v1.3 就记着的后续项。
- **`listSessions` 带过滤时扫最近 500 个会话目录**：会话目录累积到数千个后，很老的会话可能查不到。按"反查最近句柄"的用途是刻意的。

## 7. 给你们的建议动作（按优先级）

1. **把 SOP 里的 `sleep N && ls -1dt session-* | head -1` 换成**：`run_headless({wait:false})` → `get_run_summary` 轮询 `terminal` → 丢了用 `list_sessions({testFileId})`。这一步同时消掉你们本轮的 60.4min 前台 sleep 和"按 mtime 取证"这个安全隐患。
2. **改成并发甩批**（这才是 Z15 的主要收益，不是少猜几次目录）：一次 `wait:false` 提交 N 个文件再统一轮询。**先在真机上测出这台机器的合适并发度**（见 §6）。
3. **确认一下 §1.2 那个默认行为变更对你们无害**（阻塞模式 50s 后返回句柄）。如果你们某条链路确实要"一直等到结果"，用 `waitTimeoutMs: 0`。
4. `reuseBrowser` **保持默认 `true`**，不要为了并发改成 `false`（见 §2.1）。
5. 无人值守清障：headless 卡住用 `cancel_run({runId: sessionId})`，可视 run 卡住仍用 `cancel_run({runId: externalRunId})` —— **同一个工具，不必先判断 id 是哪种**。
