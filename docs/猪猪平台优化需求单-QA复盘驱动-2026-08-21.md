## 二、需求清单

### REQ-Z15 · `run_headless` 需要异步模式；且**超时也必须先吐 `sessionId`** 【P0 · 本轮最大时间漏损】

- **对应痛点**：③ 慢 —— 直接吃掉本轮 QA 墙钟的一大块，并且**堵死了 headless 的并发甩批**（下面第 3 点是这条需求的真正价值）。
- **现状（证据 · run `20260821041830-ad60b6`，墙钟 142.1min）**：
  - **17 次 `run_headless`，14 次返回字面量 `The operation timed out`（82%），仅 2 次正常返回 summary、1 次 `blocked`。** 你们 MCP 完成说明自述「`run_headless`：同步阻塞……若单文件很重，客户端侧设足够的调用超时即可」——但示例项目的用例是 60~90 步长造数链，实测**单会话时长中位 ~170s、最长 551s**，而 MCP 客户端超时（office-lab 走 SDK 默认，非被测方可控）远短于此。**对这类用例，超时是必然事件而不是例外。**
  - **超时响应里没有 `sessionId` / `roundId`**——于是 `get_run_summary({runId})` 这条你们设计的正规回捞路径**无从调用**（它需要 id，而 id 恰恰没返回）。会话其实**跑得很好**（磁盘上 17 个会话目录、结果齐全），只是调用方拿不到句柄。
  - **调用方被迫按文件系统 mtime 猜**：`sleep N && cd .../output/sessions && ls -1dt session-* | head -1` —— 本轮 `ls -1dt` 猜目录 **24 次**、前台 `sleep` **36 次共 60.4min**。这个姿势不只是慢，**它取证不安全**：按 mtime 挑「最新那个」会话，在有任何并发/他人会话时就会把别人的 run 当成自己的证据。
  - **同步阻塞语义还堵死了并发**：MCP 工具调用无法后台化（不是 Bash，没有 `run_in_background`），每发一个就阻塞到客户端超时。于是本轮 **17 个会话完全串行、零重叠**，各自时长之和 **68.3min = 墙钟的 48%**。**按 3 并发跑，这 68.3min 可压到约 22.8min。** 换句话说这条需求的杠杆不在「少猜几次目录」，而在**让 headless 的并发能力真正用得上**。
- **诉求**：
  1. **`run_headless` 加 `wait` 参数**（可默认 `true` 保持兼容）。`wait:false` 立即返回 `{ sessionId, roundId, status:"running"|"queued" }`，语义与 `run_app` 对齐。
  2. **无论如何超时，都要先把句柄给出去**：即使继续用同步模式、即使服务端自己超时，响应/错误体也必须带 `partial:{ sessionId, roundId }`。**"超时"不该等于"零信息"。**
  3. **`get_run_summary` 明确支持 headless `sessionId` 轮询到终态**（本轮实测传 headless session id 能返回 `kind:"headless"` 的 pending 结果，看起来已支持——请在文档里把它写成对 `run_headless` 的正式回捞路径并给示例）。
  4. **给一个按 `testFileId` 反查最近会话的只读接口**（如 `list_sessions({testFileId, limit})` 或 `GET /test-sessions?testFileId=&latest=1`），**目的是从协议上消灭「按 mtime 猜目录」这种取证不安全的姿势**——即便 1、2 都落地，断线/换 turn 后仍需要一条能重新找回句柄的正规路径。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z15-1 | `run_headless({..., wait:false})` 提交一个 60+ 步长链用例 | ≤2s 返回 `{sessionId, roundId, status}`；会话在后台照常跑完并落 `rounds/round-1/aggregate.json` |
| Z15-2 | 同步模式下让调用超时（或服务端超时） | 响应/错误体里带 `partial:{sessionId, roundId}`，调用方据此能继续回捞；**不允许零信息超时** |
| Z15-3 | 用 Z15-1 返回的 `sessionId` 轮询 `get_run_summary` | 能从 `pending`/`running` 轮询到终态，且终态结果与同步模式跑同一文件**一致**（passed/failed、firstFailure、reportPath 相同口径）|
| Z15-4 | 一次 `wait:false` 甩 3 个不同用例文件，再统一轮询 | 3 个会话**并发执行**（会话忙区间有重叠）、各自 `sessionId` 独立、结果互不串扰；总墙钟显著小于串行之和 |
| Z15-5 | `list_sessions({testFileId})`（或等价只读接口） | 返回该文件最近 N 次会话的 `{sessionId, status, createdAt}`，调用方**无需读文件系统 mtime** 即可找回句柄 |

### REQ-Z16 · 请确认 headless 的「超时后旧会话」语义：能不能取消？`reuseBrowser` 默认 true 时会不会互相抢浏览器？ 【P2 · 问句，不是 bug 报告】

- **对应痛点**：② 结论可信度（潜在的串数据风险）——**目前没有观测到它真的坏了，所以这条是请你们确认语义，不是报障。**
- **现状（观测）**：`run_headless` 客户端超时后，会话仍在服务端继续跑（磁盘证据齐全）。此时调用方通常会**直接再发一次** `run_headless`，而 `reuseBrowser` 默认 `true`。本轮 17 个会话经核对**完全串行、零重叠、结果全部正常**，所以没踩到问题；但我们无法从文档判断：两个会话在时间上重叠、且都 `reuseBrowser:true` 时，会不会共用同一个 Chromium/上下文而互相干扰（登录态、页面状态、runtime 变量）。
- **诉求**：
  1. 文档里明确 `reuseBrowser:true` 下**多会话重叠**时的隔离保证（各自独立 context？还是排队复用同一个？）。若不保证隔离，请在 Z15-4 的并发场景里给出正确用法（例如并发时须 `reuseBrowser:false`）。
  2. 给 headless 一个**取消**入口（对齐 v3 已交付的 App-run `cancel_run`）：超时后调用方想清障重来时，能先把旧会话停掉，而不是放任它在后台跑完再和新会话抢资源。

**验收标准（facet）**

| # | 场景 | 断言 |
|---|------|------|
| Z16-1 | 两个 headless 会话时间上重叠、均 `reuseBrowser:true` | 文档给出明确语义；实测两会话的登录态/页面状态/runtime 变量互不污染（或文档明写「并发须 reuseBrowser:false」并在越界时给出可读错误）|
| Z16-2 | 对一个在跑的 headless 会话调用取消 | 会话在有界时间内进入 `cancelled` 终态、释放浏览器资源；`get_run_summary` 能读到该终态 |
