### REQ-Z22 · 会话结果必须自带「登录/恢复到底发生了什么」【P0 · 本轮 14 小时损耗的正靶心】

**现状（证据）**：`common/sampling-base.json` 的 `recovery.login`（账号密码登录）在 `authBootstrap=run` 下**一直在成功执行**——次日 00:55 我们从 `steps/01-attempt-1-after.png` 看到的是完整登录态主看板。但当晚 10:45 那一轮，QA 拿到的信息只有：

- `status: failed`、`firstFailure.step = probe-nav-main`
- 98 条 page error（全部来自 `/login` 过渡期的第三方脚本）
- 一张 `01-attempt-3-after.png`（**重试第 3 次**的残态：二维码登录页）

于是她判定「登录未建立、wecom SSO 桌面端没起、**只有活人能登**」，写进阻塞报告、看板三条 entry、时间线，然后收工。**空转 14 小时。** 事实是：登录成功了，红是页面报错门在登录过渡期误杀。

**根因**：会话产物里**没有任何字段回答「登录成功了吗」**。`recovery` 是平台内部动作，对调用方完全不可见；调用方只能靠猜截图。而 `retries > 0` 时 per-attempt 截图会分叉——最后一次尝试的截图往往是退化态，恰恰最容易被当成「最终状态」。

**诉求**：
1. `summary.json` 与 `evidence-bundle.json` 增 `authTrace`：
   ```jsonc
   "authTrace": {
     "profile": "localhost-pre",
     "bootstrap": "run",
     "statusBefore": "expired",              // ready | expired | missing
     "recovery": { "triggered": true, "strategy": "account-password",
                   "attempts": 1, "succeeded": true,
                   "finalUrl": "http://localhost:8000/samplingWorkflow", "tookMs": 8421 },
     "authenticatedAt": 1787802100672
   }
   ```
2. `failureClass` 增一个取值 **`auth`**（登录未建立导致的红）。反过来同样重要：**`recovery.succeeded === true` 时，这一轮的红一律不得是 `auth`** —— 让「登录 OK、是别的原因」成为一个可被机器读到的**正面事实**，而不是需要人去推翻的默认怀疑。
3. `repair-context` 里，当 `authTrace.recovery.succeeded === true` 而 case 仍红时，显式给一句 `note: "登录已成功建立（见 authTrace），本次失败与登录态无关"`。

**验收 facet**：
| # | 场景 | 期望 |
|---|---|---|
| Z22-1 | 用一个凭据错误的 profile 跑 | `authTrace.recovery.succeeded=false` 且 `failureClass="auth"`，repair-context 指向凭据 |
| Z22-2 | 登录成功、后续值断言失败 | `authTrace.recovery.succeeded=true`、`failureClass="value-assertion"`、repair-context 带上面那句 note |
| Z22-3 | profile 本来就 fresh、未触发 recovery | `authTrace.statusBefore="ready"`、`recovery.triggered=false`（**不是省略字段**） |
| Z22-4 | `authTrace` 进 `evidence-bundle.json` 并纳入签名 | verify 能核出被篡改 |

**对应 QA 痛点**：本轮 14h 空转；以及历史上反复出现的「过夜失效 → 甩锅环境」（office-lab 复盘 §3.63）。

### REQ-Z23 · 页面报错门（Z-A）需要作用域、阶段、以及「一次把噪声给全」【P0 · 本轮第二大损耗，且正在侵蚀门禁本身】

Z-A 这道门**方向完全正确**，本轮它确实挡住了东西。问题出在 allowlist 的**形状**上，三个子问题，第三个已经开始造成质量损害：

**(a) 只能按 message 子串匹配，没有来源维度。** 本轮 40 条噪声**全部**发生在 `/login` 的登录过渡期：企微 SSO CDN 的 `SyntaxError`、`rms.example-company...` 微前端 bundle 的 `Failed to fetch`、wecom 桌面端 `checkLoginState` 的 `ERR_CONNECTION_CLOSED`、google translate、以及 AntD/React 的框架告警。它们和被测产品毫无关系，却只能靠**逐条文本**去捞。

**(b) 噪声非确定性 → 一轮补一条，补了 10 轮。** 这些报错只在特定组件渲染时才冒（AntD Table 的 `rowKey` 弃用告警要等 SKU 生成那一步才出现；React 重复 key 要等看板搜索才出现）。于是节奏变成：跑一轮（0.3–3.3min 全流程）→ 冒出一条新噪声 → 补一条 allowlist → 再跑。**光是为了让门闭嘴就烧掉 10 个来回。**

**(c) 逐条文本匹配把作者逼向过宽条目——门禁正在被削弱。** 最终沉淀进**共享库** `common/sampling-base.json` 的 24 条 allowlist 里，有 7 条危险条目，现在对**所有**示例项目用例生效：

```
"deprecated"                                   ← 裸通用词
"Failed to fetch"                              ← 任何产品 API fetch 失败都被吞
"Failed to load resource: net::ERR_CONNECTION_CLOSED / _REFUSED / _TIMED_OUT"
"api.example.test"            ← 这是被测产品自己的微前端宿主域
"Can't perform a React state update on an unmounted component"
```

QA 自己在会话里两次写下风险提示，然后还是提交了——因为在当前形状下，**没有别的写法能一次性关掉登录页噪声**。这不是她的纪律问题，是 API 形状把人推过去的。

**诉求**：
1. **allowlist 支持作用域字段**，`match` 变为可选：
   ```jsonc
   { "url": "**/login", "origin": "third-party", "phase": "auth-bootstrap",
     "match": "SyntaxError",            // 可选，进一步收窄
     "reason": "企微 SSO CDN 脚本在登录过渡期的噪声" }
   ```
   `origin` 至少支持 `same-origin` / `third-party`（相对被测 `baseUrl` 判定）。
2. **`pageErrorPolicy` 支持按阶段设**：`{"auth-bootstrap":"off","recovery":"off","under-test":"fail"}`。**建议默认就把登录/恢复阶段排除在门外**——用例作者不该为登录页第三方脚本的健康负责，这是平台比调用方更有资格做的判断。
3. **红件的 repair-context 一次给全 `suggestedAllowlist[]`**：把本轮**全部** distinct 噪声按 `(url × origin × message 首行)` 聚类，每条给建议的 `{url, origin, phase, match, reason 草稿, isThirdParty, count}`。**一轮给全，别让调用方一轮补一条。**
4. **预检新增「allowlist 过宽」告警码**（对齐你们 §Z-H 的弱 oracle 家族）：`match` 短于阈值 / 是通用词表命中 / 命中被测 baseUrl 同源 / 资源类匹配却没有 `url`+`origin` 限定 → warning + 指出它会吞掉什么。

**验收 facet**：
| # | 场景 | 期望 |
|---|---|---|
| Z23-1 | `phase:"auth-bootstrap"` 关门 | 登录过渡期 40 条噪声不致红，`summary.pageErrors[]` 仍全量记录并标 `suppressed:true` + phase |
| Z23-2 | 同一条 message 出现在 `under-test` 阶段 | **照样致红**（证明作用域真的生效，不是全局静音） |
| Z23-3 | 一个含 5 类不同噪声的红件 | repair-context 的 `suggestedAllowlist[]` **一次列全 5 类**（含 count 与 isThirdParty） |
| Z23-4 | 提交 `{"match":"deprecated"}` | 预检 warning，指出它会吞掉哪些类别 |
| Z23-5 | 提交 `{"match":"Failed to fetch"}` 且无 url/origin 限定 | 预检 warning（资源类匹配必须带来源限定） |

**对应 QA 痛点**：本轮 10 轮打地鼠；以及**已经发生的门禁削弱**（那 7 条过宽条目建议随本需求上线后由我方收窄，我们会同步回写）。

### REQ-Z24 · 把「状态没到」和「定位漂移」在**步级**分开【P1 · 承 §3.96 的 92/8】

**现状**：office-lab 复盘 §3.96 实测过——254 个定位类红趟里 **92% 其实是「元素当时不在页面上（状态/tab 没到）」**，只有 8% 是真 testid 漂移。本轮 REQ-0309 原样复现：11 轮红里有 6 轮是「该切的 tab 没切 / 该做的前置动作没做」，平台报出来的是 `target-not-found` / `DOM expectation was not met`，QA 只能**一张张翻截图**去判，每判一次就是一轮 2.5min 全流程重跑。

Z-D 的 `failureClass` 取值域里已经有 `reach` 了，但它是 **case 级**的；调用方在**步级** `firstFailure` 上看不到，也拿不到「那该去哪」。而你们已经有 `get_ui_contract`（Z-P）——**把它接到失败诊断上就行**。

**诉求**：`firstFailure` 增两个字段：
```jsonc
"failureClass": "reach",                 // 步级，与 case 级同一取值域
"reachDiagnosis": {
  "testidInContract": true,              // false = 真漂移，去改用例
  "requiredBoard": "sampleReview",
  "requiredTab": "待审核",
  "requiredStatusFields": { "sampleReviewStatus": 1 },
  "requiredAuthCodes": ["GYS-SAMPLING-SUPPLY-011"],
  "currentUrl": "...", "currentBoard": "supplyChain", "currentTab": "待处理"
}
```
并在 repair-context 里按这两类给**不同措辞的 `fix`**：`reach` → 「先把状态造到 X / 先切到 Y」；`target-drift` → 「testid 不在契约里，改用例」。

**验收 facet**：
| # | 场景 | 期望 |
|---|---|---|
| Z24-1 | 点一个当前 tab 下不存在、但契约里有的按钮 | `failureClass="reach"`，`reachDiagnosis.requiredTab` 指出该去哪 |
| Z24-2 | 点一个契约里根本没有的 testid | `testidInContract=false`，fix 措辞是「改用例」而非「造数」 |
| Z24-3 | 契约里查不到该 testid 的可见条件（覆盖率不足 13%） | 如实给 `reachDiagnosis: null` + 原因，**不猜** |

**对应 QA 痛点**：本轮 0309 的 11 轮往返；§3.96 全史 48% 定位类失败的误导性归因。

### REQ-Z25 · 能力自描述必须机器可核：请实现 `GET /capabilities`【P1 · 直接治本单〇节那场事故】

**现状**：`GET /capabilities` **在你们对接文档的端点表里列着**（我方从文档正文抽出 46 个端点声明，它是其中之一），但实测 **404**。而我方正是因为「文档说有能力、但没给 HTTP 路径」才去猜 `/verify-evidence`，猜错、404、误判「未上线」、把假事实印了两周。

**诉求**：
1. 实现 `GET /capabilities`，返回可直接用于接线的清单：
   ```jsonc
   { "version": "1.8.0",
     "capabilities": [
       { "id": "verify_evidence", "z": "Z-D", "status": "ga",
         "mcpTool": "verify_evidence",
         "http": { "method": "POST", "path": "/evidence/verify" },
         "since": "1.5.0", "readOnly": true } ] }
   ```
   `status` 至少区分 `ga | beta | planned` —— **让「还没做」和「做了但你打错门」在协议上可区分**，这是本单最核心的一条。
2. 对接文档正文里的端点表与 `/capabilities` **由同一份源生成**（今天这个 404 就是文档与实现漂移的产物）。
3. 顺带核一处易误读：`GET /auth/status` 不带 `profile` 时返 **404**（实测），语义上应是 400 —— 404 会让探活方误判「没这个端点」。带 `?profile=` 时 200 正常。

**验收 facet**：Z25-1 `/capabilities` 200，且逐条 `http.path` 实调都不返 404；Z25-2 文档端点表与 `/capabilities` 逐条一致（建议做成你们的自检用例）；Z25-3 `/auth/status` 无 profile 返 400 且 message 说明需要 profile。

### REQ-Z26 · 服务发现文件：别再让基地址漂【P2 · 但本轮吃掉 23 分钟 + 间接导致那 14 小时】

```jsonc
{ "appRunBaseUrl": "http://127.0.0.1:32147", "mcpUrl": "http://127.0.0.1:32147/mcp",
  "docPath": "/external-integration-documents", "version": "1.8.0",
  "pid": 35260, "startedAt": 1787801234567 }
```
消费方读文件、不记端口。

**验收 facet**：Z26-1 App 起后文件存在且字段可用；Z26-2 换端口重启后文件内容跟着变；Z26-3 App 退出后文件被清理或标 `stale`。
