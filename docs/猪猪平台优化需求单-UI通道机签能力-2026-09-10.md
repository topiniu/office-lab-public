# 猪猪平台优化需求单 · 让「UI 通道」拿得到机签绿灯（2026-09-10）

## 0. 先说清这单是怎么来的：一次真实的「制度把 QA 逼离界面」

项目跟踪 v0.1.0（GYS 新模块，4 个交付面）本地全量 QA 跑到 2026-09-10 的机器事实：

| 指标 | 数 |
|------|----|
| facet 全集 | 196 |
| COVERED_GREEN | 47 |
| **其中由 UI 通道（App-run 带 UI 断言）签出的** | **0** |
| UNCOVERED | 122（大批是渲染/存在性类） |
| HUMAN_INHERENT（挂人工视觉终验） | 20 |

**47 条绿全部是 callApi 打后端端点签出的。** 老板 2026-09-10 当场点名：「所有业务都 callApi 绕过去我还做 UI 界面前端干什么？」

**这不是 QA 偷懒，是激励倒置**，而倒置的那一端在我方门禁与你方能力的接缝上：

- 走**接口**：`callApi` ＋一条 value-assertion RED 校准 → 我方 `reconcile_coverage` **必得 COVERED_GREEN**。成本最低。
- 走**界面**：同一批 facet 的 UI 断言，被我方有效性 linter 成批拒签——
  - 「寄售单不出现在赶不上交期组」跑了 GREEN+RED 双证 → 判 `NO_ACTION`（纯只读属性断言、无被测写动作）；
  - 「现网 13 筛选 / 16 列 / 6 行操作原样保留」「两新列表头存在」→ 判 `PRESENCE_ONLY`（无值比较、正确与错误实现下都绿）；
  - 「点 tab 加载独立组件」→ 判 `TRACE_INVALID`（UI 交互无数据血缘）。

我方那三条 linter 判据**本身是对的**（它们防的是假绿灯），不打算放松。问题是：**当"验界面"这条路在机签上无路可走时，理性 agent 一定会去打接口**。代价当天兑现——`frontend/web-app/src/pages/stockUpManage/phaseConfig/index.tsx:352` 用 `moment(row.updateAt)` 漏了 `Number()`，后端全局 FastJSON 把 `Long` 序列化成字符串，于是模板列表**每一行**的「更新时间」都渲染成字面 `Invalid date`。这个 bug：

- `callApi` 打 `template/list` 一万次都是绿的（后端返的 `updateAt` 完全正确）；
- 最后是靠人眼扫截图偶然发现的，且因为没有机签路径，它只能以「cosmetic 观察」躺在 QA 报告里，两天没人接。

**我方已做的整改（2026-09-10 落地，机器硬判）**：覆盖矩阵加了「验证通道」维——facet 标期望通道（`ui`/`api`/`source`/`any`，`ui-visual`/视觉/渲染/存在性类自动归 `ui`），证据串由引擎从用例 `steps` 机读实际通道写成 `via=ui|api|mixed|unknown`；**期望 `ui` 的 facet 拿 `api` 通道的绿，覆盖闸门不计通过**。

> 实测覆盖（免得你们以为我方已经全查清了）：期望通道目前**没有一条是需求侧显式声明的**，全靠引擎从分类列/判据原文推断——196 条里推断出 48 条 UI 面，命中 10 条「拿接口绿冒充界面绿」的存量绿（`REQ-0338-F2/F6/F9/F41/F42`、`REQ-0339-F13/F38/F40/F89/F110`），剩下 148 条这道闸还管不着。我方正在推需求侧逐条声明 `通道` 列。

也就是说：**堵已经堵上了，但另一头的路得通**，否则结果只是把 122 条 UNCOVERED 变成 122 条「通道不符」——红得更诚实，可产品并没有被测得更好。下面 4 条就是那条路上缺的砖，按「卡住多少条 facet」排序。

> **前置说明**：`REQ-Z27`（validate 的 proof 模型不认识视觉断言 → 每条视觉断言必带一条清不掉的 warning）见 `docs/猪猪平台优化需求单-Z-E视觉验收接入实测-2026-09-07.md`，据我方 09-09/09-10 两轮实测**仍未闭环**。它与本单 REQ-Z33 是同一条链上的两段（Z27 让视觉断言过不了 validate，Z33 让视觉判定进不了证据），**建议合并排期**。

## REQ-Z32 · 列/表级「批量渲染断言」原语（P0，直接卡住 29 条渲染 facet）

**卡住的东西**：形如「某列每一行都渲染成合法的 `yyyy-MM-dd HH:mm`」「列表 16 列的表头与顺序原样保留」「进度列每行都出现流程节点条」这类判据。

**现在只能怎么写**：`assertDom` 一次断一个元素。想覆盖「每一行」，只能把 N 行展开成 N 个断言步（行数随数据漂移、写死行数必然脆），实际结果是 QA 退回去断「第一行」——而 `Invalid date` 那个 bug 恰恰是**每行都错**，断第一行本该抓到；但更常见的形态是「只有某几行错」（空值行、跨月行、边界数据行），断第一行必漏。而如果只断「这列存在」，我方 linter 判 `PRESENCE_ONLY` 不签。

**要什么**：一个能对「一列 / 一组同类元素」施加**格式判据**并返回逐行结果的断言原语。形态建议（不拘）：

```json
{
  "action": "assertColumn",
  "target": { "scope": "[data-testid=phase-template-table]", "column": "更新时间" },
  "expectation": {
    "rows": "all",
    "match": "^\\d{4}-\\d{2}-\\d{2}",
    "notMatch": "Invalid date|NaN|undefined|null",
    "minRows": 1
  }
}
```

**为什么这条是 P0**：它一次性把「渲染正确性」从**存在性**升级为**有区分度的值断言**——正确实现绿、错误实现红，正好满足我方 linter 的 G4（`PRESENCE_ONLY`）要求，且天然带反事实（`notMatch` 命中即红）。我方 196 条 facet 里 29 条 REQ-0338 渲染 facet、13 条 REQ-0341 列保留 facet 直接受益。

**附带请求**：`notMatch` 建议内置一组「渲染事故常量」默认值（`Invalid date` / `NaN` / `undefined` / `null` / `[object Object]` / `Infinity`），可 opt-out。这类字面量在任何页面上出现都是缺陷，**不需要审美判断，属确定性判据**——和你们 Z-E 里「截断/对比度/点击区」同一性质。

## REQ-Z33 · 视觉判定进 `evidence-bundle`，让 `assertVisual` 成为可机签证据（P0，卡住 20 条 HUMAN_INHERENT）

**现在的断点**：`assertVisual` / `assertVisualPeers` 跑第二趟能出很好的素材（我方 09-07 实测确认过，见 Z-E 单）。但素材只能**人读**——`visual-review.json` 里的 `diff.ratio` / token 差异表没有进 `evidence-bundle.json` 的结构化判定字段，我方 `reconcile_coverage` 拿不到「这条视觉断言的机器结论是 pass 还是 fail」，于是所有视觉 facet 只能标 `HUMAN_INHERENT`（20 条，全部挂着等老板晨间人工照点）。

对比一下你们 Z-D 做对的地方：`failureClass` 进了 `evidence-bundle`，我方 RED 校准就从「标题正则蒙」升级成了**结构判定**。视觉这条缺的是同一件东西。

**要什么**：
1. `evidence-bundle.json` 里给每条视觉断言一条结构化判定：`{key, kind: 'baseline'|'peers', verdict: 'pass'|'diff'|'defect'|'no-baseline'|'theme-mismatch', diffRatio, threshold, hardDefects: ['truncated'|'contrast'|'tinyHit']}`。
2. `verdict` 的口径由平台定、别让消费方各自解释阈值（我方现在自己在 `qa-report-card.js` 里维护「符合同族基线 / 与同族不一致 / 明显缺陷」三档，这属于消费方替平台定判据，早晚漂）。
3. 视觉断言能声明**绑定的 facet**（`coversFacets` 已在 case 级，希望能落到步骤级），这样一个 App-run case 里多条视觉断言可以分别签不同 facet，而不是整 case 一起绿。

**收益**：20 条 HUMAN_INHERENT 里至少 11 条（UX 增量 F112–F121 + REQ-0341-F48 的新旧双版渲染，已有真数据 App-run 截图见证）可以从「等人看」变成「机器签、人抽检」。

## REQ-Z34 · `paste` 原子动作（P1，卡住「粘贴上传」这类交互的机验）

> **先自我更正，免得你们白看**：我方 2026-09-10 报过「猪猪无 `press`/`paste` 原子动作」，**其中 `press` 是过期结论**——当轮对接文档的 step 通用字段表里已有 `press`（`key` 支持 `Enter`/`Escape`/`Meta+A` 这类组合），是我方工牌里的旧快照没跟上（已在 `docs/tech/QA门禁与角色演进.md` §3.132 纠正）。所以本条只剩 `paste`，且**提单前请我方再对一次当轮 `get_integration_doc`**，若 `paste` 也已存在，这条直接作废、责任在我方记账。

**现象（2026-09-10 实测）**：跟单看板全部弹窗按老板要求补齐了 `Ctrl/⌘+V` 粘贴图片上传（`usePasteImageUpload`：监听全局 paste、仅图片拦截、OSS 上传后追加受控列表）。这条我方机验不了——用例 DSL 里没有把「带 `clipboardData` 的 paste 事件」投给页面的原子动作。

结果只能是：源码照点（`SOURCE_ATTESTED`）＋ 开发自己用 Playwright 合成 `paste` 事件跑一趟人工见证。**QA 没有独立复现手段**——这正是「开发说改好了、QA 只能信」的形态，我方红线 6（无证据不判通过）在这里被架空。

**要什么**：`{action:'paste', target:..., payload:{kind:'image', file:'fixtures/x.png'} | {kind:'text', value:'...'}}` —— 合成带 `clipboardData` / `DataTransfer` 的 paste 事件（Playwright 侧那套你们比我们熟）。需要能区分「粘贴图片」与「粘贴文本」，因为被测代码的正确行为恰恰是**只拦图片、不影响文本粘贴**——负向那半边同样要能验。

**为什么不是 P0**：涉及的 facet 数量少（本模块 1~2 条）。但粘贴上传这类交互往后只会更多（老板本轮明确要求「都补齐」并对齐示例项目）。

## REQ-Z35 · `summary` 自带「本 case 走的哪条通道」（P2，但能防我方判错）

**现在我方怎么做的**：`reconcile_coverage` 读用例 JSON 的 `steps`，按动作名归类（`callApi`→api，`assertDom/assertVisible/assertVisual/capture`→ui 断言，`click/fill/navigate`→ui 动作），得出 `via=ui|api|mixed|unknown` 写进证据串。

**风险**：这是**消费方从用例源码反推运行事实**。动作名一改、或新增一种断言 kind，我方就会静默判错——而它现在是门禁判据，判错的后果是「该拦的没拦」或「不该拦的拦了」。这跟 Z28（`visualReview: null` 分不清"没挂断言"和"刚录基线"）是同一条道理：**运行时事实应该由平台给，不该让消费方猜。**

**要什么**（任一即可，越轻越好）：
- `summary.channel = { apiSteps: N, uiAssertSteps: M, uiActionSteps: K }`；或
- 每个 step 的 `actionType` 已有的基础上，在 summary 存根给一个 `channels: ['api','ui']` 数组。

我方会优先读平台给的，读不到再退回自己反推（和 `failureClass` 那条完全一样的兼容策略）。
