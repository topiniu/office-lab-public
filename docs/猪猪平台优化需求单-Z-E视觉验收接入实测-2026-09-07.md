# 猪猪平台优化需求单 · Z-E 视觉验收首次真接入的三处摩擦（2026-09-07）

## 0. 先说结论：Z-E 本身是好的，能用，而且当场就验出东西

今天是 **Z-E（v1.6 交付）第一次被真正接进 office-lab 的消费链路并跑起来**。此前 test-workflows 全库 208 份用例**一条视觉断言都没挂**（grep 坐实）——**这笔债欠在我方**，不是你们没交付；我们甚至去调了一个自己按命名习惯造出来的 `POST /visual-review`，把 404 读成「猪猪未实现」，挂了四个月人工债。这一点已在我方复盘里记清（office-lab `docs/tech/QA门禁与角色演进.md` §3.118），特此说明，避免你们背错账。

真跑记录（`sampling-visual-baseline-supply-chain.json`，供应链看板，4 个 case）：

| 趟次 | sessionId | 结果 |
|------|-----------|------|
| 首跑 | `session-20260907-183449-5122bdb9` | failed —— 4 条里 3 条 `visual-no-baseline`（录基线不算过），peers 那条直接 passed |

## REQ-Z27 · validate 的 proof 模型不认识视觉断言，导致每条视觉断言必然带 1 条 warning（P0，卡的是流程而非功能）

**现象**：任何 `assertVisual` / `assertVisualPeers` 步骤，validate 都固定给 `proofScore 30 / grade E` 且 `isCritical: true`，于是必然产出一条

```
search-global-assert-visible  warning  Step N: critical business step has proofScore 30, below C threshold.
evidence.proof.reasons: ["intent search-filter requires stronger business proof"]
```

`recommendation` 随之变成 `fix-before-run`、`quality.summary.overall = warning`。

**为什么这是 P0**：我方 SOP 是硬红线——**「生成后必过 validate，errors 和 warnings 都要清零」**。一条永远清不掉的 warning 会逼出两种坏行为，两种都是我们明令禁止的自欺：① 改标题绕过 intent 分类；② 放松/去掉断言。实测确认**改标题确实能绕**（`intent` 由 stepTitle 关键词决定：含「搜索」→ `search-filter`，换成中性词 → `generic`），但 warning 仍在（proofScore 恒 30），所以连"绕"都绕不干净——只能带着 warning 交付，或者不做视觉验收。

**建议**：把视觉断言纳入 proof 模型——`assertVisual` 的证明力就是「与基线的像素 diff + 阈值」，`assertVisualPeers` 的证明力是「设计 token 逐项比对 + mustMatch」，这两者都比 `assertDom presence` 强得多，不该是 E 档。至少：
- 认识这两个 kind，给出合理 proofGrade（有 `baseline` + `maxDiffRatio` 的应达 A/B；`assertVisualPeers` 有非空 `mustMatch` 的同理）；
- `intent` 分类别只看 stepTitle 关键词 —— 步骤 `type` 是 `assertVisual` 时，intent 显然不是 `search-filter`。**类型比标题可靠**（这跟你们 Z-D「别让判定挂在标题正则上」是同一条道理）。

## REQ-Z28 · `visual-no-baseline` / `visual-theme-mismatch` 那趟不产素材，消费方分不清「没挂断言」和「刚录基线」（P1）

**现象**：`evaluateVisualAssertion` 在缺基线与主题不符两个分支**提前 return**（`visual-baseline.js:386-404 / 420-434`），走不到 `collectVisualReview`。于是首跑的 `summary.visualReview` 是 `null` —— 与「这一轮压根没挂视觉断言」**完全同形**。

**代价**：我方消费层第一版据此把首跑判成「一条视觉断言都没挂」，**冤枉了用例**。现在只能靠反查 `steps[].expectation.type` 里有没有 `assertVisual` 才能区分（我们已这么修，但这属于消费方替平台补状态）。

**建议**（任一即可）：
- 这两个分支也 `collectVisualReview` 一条最小素材（带 `verdict: "no-baseline" | "theme-mismatch"` + 已录基线路径）；或
- `summary.visualReview` 存根里给 `attempted: <视觉断言步数>`，让「跑了但无素材」自带信号。

口径理由与你们一致：**「问不到」和「没有」必须可区分**，否则消费方只能猜——这正是 Z-D `pageErrors: null ≠ 0` 那条注释在讲的事。

## REQ-Z29 · `summary.visualReview` 的存根形状没写进对接文档（P1，文档缺口）

**现象**：文档写的是「每次跑到视觉断言都会产出 `visual-review.json`：截图 + 盒模型 + …」，读起来像 summary 里就有素材。实际 `summary.visualReview` 是**存根**：

```json
{ "items": 1, "artifactPath": "D:\\...\\runs\\<runDir>\\visual-review.json" }
```

`items` 是**数量（number）**，不是数组。我方第一版按 `Array.isArray(v.items)` 读 → 拿到 `1` → 判「素材为空」→ 又一次「有素材却说没做」。

**建议**：在对接文档的 Z-E 那节明写这个存根形状与字段语义（尤其 `items` 是计数），并写清「素材必须读 `artifactPath` 那个文件」。若体量允许，也可以考虑在 summary 内联 items（我方两种都支持，不强求）。

> 同族提醒：`pageErrors` 也是对象 `{policy, phasePolicy, total, failing, suppressed, dropped, allowlist[]}`，门要看的是 **`failing`**（实测样本 `total:200 / suppressed:200 / failing:0`）。这个我们已按实测接对，但文档里同样没写明形状——**建议把「消费方要读哪个字段」在文档里点名**，别让每个接入方各踩一次。
