# 猪猪平台优化需求单 · 只读透传展示类 facet 的机签路径（2026-09-19）

## ⚠ 更正声明（2026-09-19 晚·小呆呆巡视后迷糊实拼）——本单大幅收窄

**这单原本的头号诉求（「只读展示类 facet 没有能机签的合法路径」）经实拼后被证伪。** 巡视指出：我把「路径 A·跨身份造数」一次没试就定性为「需从零建 harness」推给老板，属空停。照指令老实拼了一次后发现：

- **造数链是现成积木纯拼装，不是新建 harness**：`buildTaskWithSu`（建单+物料诉求，与已机签的 REQ-0342 用例同一 macro）+ `case-f1` 关联规格步骤 + `flowSupplyDispatch`（派单宏本就指向 SH000322=example-user002）→ 切供应商身份查看。组好后 `lint_test_file` 实测 **1 case ✅ 无阻断项**——DB_FISHING/NO_ACTION/PRESENCE_ONLY 三连拒全消解。
- **跨端根本不需要新平台能力**：下方原「路径 A」主张平台缺一个 `switchAuth` 原子动作——**这是错的**。同一 browser context 多 origin 天然各持 cookie（gys :8000 走 `recovery.login` 自愈 + 供应商 :8001 走 `authProfile`），一个 case 里先 gys 造数、再供应商断言，**用当轮既有能力就能跑通**，无需任何新动作。

**所以：下方「REQ-Z36·路径 A」整条撤回**（platform gap 不成立，缺的是我方把 macro 拼起来、属 office-lab 自己的活）。**仅「路径 B·配对反事实区分度信号」作为可选优化保留**，且优先级从 P1 降为 P3——它只对「造数确实不成比例」的极少数 facet 有边际价值，不是这一类 facet 的必要条件。本单从「4 条 P0/P1 能力缺口」收窄为「1 条 P3 可选优化 + 一份实测记录」。

> 下文保留原始论证与 7 条案例证据（它们仍是真实的），但请以本更正声明为准阅读：原始诉求的强度已被我方自己的实拼推翻。

## ⚠ 二次更正（2026-09-19 晚·迷糊守航实跑收官）——路径 A 不止「可拼」，已「跑通并机签」

上面说「路径 A 是现成积木、缺的是我方把 macro 拼起来」——**现在这句话已由一次真跑证实到底**：起本地 partner-app@8001，把 crossend 用例真跑，连修 5 个 prior session 只 lint 没跑到的真堵点（① `buildTaskWithSu` 是各文件本地 macro、不在 shared 库 ② `run_e2e_batch` 不继承文件 `authProfile`，须批次级传 ③ 普通任务停买手态、要补 7 个流转 macro `flowBuyerToReview→…→flowGrading` 才到供应链看板 ④ 需要打样派单必填「样品审核人」且 radio 文案是「需要，仅上传样品实拍图」非「需要」 ⑤ 新派单任务落「待提审 pending」Tab 非「审核中」），最终 **REQ-0353-F2 全生命周期 35 步 GREEN(`session-20260919-044056-093a977f`) + 同 caseId RED 镜像(`session-20260919-044516-10e60b7b`·value-assertion) 经 `reconcile_coverage` 机签 COVERED_GREEN**。

**结论：只读透传展示类 facet 用「跨身份 in-session 造数」拿机签，当轮平台能力（同 context 多 origin 各持 cookie + `authProfile` + `authBootstrap=run`）完全够用，无需任何新平台动作。** 本单原头号诉求（含路径 A 的 `switchAuth` 平台缺口）**全部不成立**。缺的从来是我方把造数链拼全（含中间 7 个流转 + 需要打样派单变体），属 office-lab 自己的活，已完成一条（F2）作模板。余 facet 同模板可复制，纯我方工作量、非平台能力。路径 B（配对反事实信号）作为 P3 可选优化仍可保留，但已非必需。

## 0. 这单是怎么来的：12 条 facet「行为真测通过、机签 0 条」

示例项目 v5.24 · REQ-0353（供应商侧「生产打样」详情新增物料需求展示块，只透可外发字段、敏感字段接口层白名单）本地全量 QA 跑到 2026-09-19 的机器事实：

| 指标 | 数 |
|------|----|
| REQ-0353 facet 全集 | 12 |
| 行为已跑真 E2E（GREEN + RED 反事实双证） | 12 |
| 机签 COVERED_GREEN | **0** |
| 停在 BLOCKED_WITH_PROOF | 12 |

**这一次不是「QA 绕过 UI 去打接口」（那是 2026-09-10 那张单的故事）。** 这一次 12 条**全都从供应商界面真跑了 E2E**：从零搭通供应商侧通道（ERP 代登录铸 example-user002/example-user001 token → 本地起 partner-app@8001 代理 `/web-app-web`→本地 8041），GREEN run 四个 case 全 passed，并配了一趟**反事实 RED 校准**（同断言取反 → 全 failed，区分度已证）。

行为测到了、区分度证明了，**机签依然 0 条**——挡在中间的是 office-lab 侧的有效性 linter，而它这一次拦得「结构上正确、但对这一类 facet 无解」：

- REQ-0353 是**只读透传展示**功能：页面把上游（gys 建单 / 关联规格 / 派单）已经落库的物料需求，剔除敏感字段后展示给供应商看。**这个功能本身没有写动作、没有它自己产生的值**。
- 而 linter 的三条判据（`DB_FISHING` / `NO_ACTION` / `PRESENCE_ONLY`）**天生要求「有造数 Arrange + 有被测写动作 Act + 断产生的值」**。只读展示三样都给不出——不是因为测得不好，是因为这类功能结构上就不产生「自己的可断值」。

**我方 linter 判据本身是对的**（2026-09-10 那单已表态、这单继续不打算放松，它防的是假绿灯）。问题和上一单同构：**判据这头堵对了，可另一头的合法路得通**——否则每一个只读展示类需求撞上来，都是「行为真测通过、机签永远 0」。这一轮如果没人立这张单，天花板就永久留着。

## 3. 要什么：两条候选路径，任一到位即可解本类天花板

这类 facet 要拿到机签，缺口在两条路上，**平台侧只要给通任一条即可**（我方偏好路径 A，因为它连判据都不用动）：

### 路径 A（P0）· 跨身份「在同一 session 内造数」，把存量变成本测产出

**缺口**：只读展示的数据血缘**端到端是存在的**——上游 gys 建单 / 关联规格 / 印花 / 派单产生了数据，供应商侧只是下游读。断的就是「上游造的这条，下游显对了」。但这条血缘**跨两个身份 + 两个前端**（gys 管理员造 → 供应商视图看）。当轮 DSL 里 `authProfile` 是 **case 级 / 文件级**（`case.authProfile` / `settings.authMatrix`），**没有「一个 case 内先以身份 A 造数、再切身份 B 断言」的原子能力**（2026-09-19 对 `get_integration_doc` protocolVersion=1.8.0 的 26 项能力清单核对，未见 case 内切换鉴权的动作；若我方漏看、该动作已存在，本条降级为「我方去搭 macro」，责任在我方记账）。

**要的形态**（不拘）：允许一个 case 的 steps 内切换鉴权上下文，例如
```json
{ "action": "switchAuth", "profile": "gys-admin" }   // Arrange 段：以 gys 造数
// ... createQuickTask / 关联规格 / 派单 macro ...
{ "action": "switchAuth", "profile": "partner-app-lab002" }  // Assert 段：供应商侧读并断言
```
有了它，只读展示类 case 就有真实的 Arrange（gys 造数）→ Act（触发派单落到供应商可见）→ Assert（供应商视图显对），**linter 的 AAA 与同实体血缘天然满足、无需放松任何判据**，`DB_FISHING`/`NO_ACTION` 自动消解。

**验收口径**：一个 case 能以身份 A 完成造数、切身份 B 断言，且 `reconcile_coverage` 读到的 `qaTrace` 血缘链（provenance/operationId/entityRef）贯通两身份、置绿。

### 路径 B（P1）· evidence-bundle 里给「反事实配对的区分度证明」一个结构化字段

**给谁用**：对少数造数不成比例（如跨系统主数据、需真实存量态才能复现）的只读 facet，让「GREEN + 配对 RED 反事实」这对 run 本身成为可机读的区分度凭证。

**现状**：`verify_evidence` 已经在**单 case** 上返回 `discriminativePower` / `redCalibrated`（这做得对，和 Z-D 把 `failureClass` 进 bundle 同一思路）。缺的是**跨 case 的「配对」事实**——「case X（GREEN）与 case X'（同断言取反的 RED）是一对」这件事，现在只存在于我方用例命名约定里，平台不认，于是 reconcile 无法把「这对 run 已证区分度」当作只读 facet 的合法凭证。

**要的形态**：evidence-bundle（或 summary）给出配对断言的结构化判定，例如
```json
{ "facet": "REQ-0353-F2", "greenRun": "...-5c5e3c07", "redRun": "...-a797a799",
  "assertionKey": "spec-col-single", "counterfactual": true,
  "greenVerdict": "pass", "redVerdict": "fail", "discriminativePower": "high" }
```
口径由平台定、别让消费方各自解释（同 Z33 的教训）。有了它，我方可对**声明为只读透传类**的 facet，把「配对 GREEN+RED 已证区分度」作为 `NO_ACTION` 的合法例外收 COVERED_GREEN——**判据不放松，只是承认这类功能的「产生结果」发生在上游、其正确性由配对反事实证明**。

## 4. 优先级与建议排期

- **路径 A（P0）** 优先。它是「让只读展示类拿到机签」性价比最高的一条：不动任何判据、直接补齐 AAA 血缘，且这类跨端造数需求往后只会更多（凡「上游写、下游只读展示」的功能都撞同一墙）。
- **路径 B（P1）** 作为路径 A 覆盖不到的残余兜底（造数不成比例的真存量态 facet）。
- 与既有单的关系：与 2026-09-10「UI 通道机签能力」单（`docs/猪猪平台优化需求单-UI通道机签能力-2026-09-10.md`）的 REQ-Z32（列级批量渲染断言）**不冲突、互补**——Z32 解「把存在性升级成值断言」，本单解「只读展示的值不是本测产生的，血缘在上游」。建议同一条链上排期。
