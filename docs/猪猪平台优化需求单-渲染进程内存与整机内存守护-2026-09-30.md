# 猪猪平台优化需求单：渲染进程内存不释放 + 内存守护只看主进程（2026-09-30）

## 现场

- **2026-09-30 00:43:22**：猪猪 headless 通道的 `chrome-headless-shell.exe`（`ms-playwright\chromium_headless_shell-1208`）APPCRASH，异常码 `0xE0000008`（Chromium 的「分配不到内存」）。
- **00:43:25**：office-lab 引擎（同机 node 进程）退出码 `0xC0000409`，无日志——整机提交内存耗尽后被系统掐死。
- 当时同机负载：两个运行环境各一条 QA 会话、各甩一批并发 3 的 headless；两套 Java 后端；两个前端 dev server；**猪猪 Electron 渲染进程（`--type=renderer`，PID 5924）**。
- **事后空闲时实测**（02:26～02:28，三次采样、无任何测试在跑）：该渲染进程提交内存稳定在 **4.32 GB**，没有回落。
- 同一时刻 `GET /app-runs/status` 的 `memory` 块报 `rssMb: 150, growthMb: 1, rssWarnMb: 1024`——**只统计了主进程**，渲染进程的 4.3GB 完全不可见，守护判「正常」。

## 需求

1. **Z-MEM-1 渲染进程内存回收**：App-run / 可视化面板跑完后，释放 run 结果视图持有的大对象（截图、视频帧、DOM 快照、事件流缓冲）；或提供「空闲 N 分钟后重建渲染进程」的自愈。验收：连续跑 20 个 App-run 后空闲 10 分钟，渲染进程提交内存回到基线 ±300MB。
2. **Z-MEM-2 内存守护覆盖全部子进程**：`/app-runs/status.memory` 把 renderer / gpu / 由 headless 通道拉起的 `chrome-headless-shell` 一并计入（分项 + 合计），超阈值时告警字段置位。验收：本单现场复现时 `memory` 能报出 ≥4GB 并置 warn。
3. **Z-MEM-3 按整机余量自适应**：headless 与 `/app-runs/batch` 的并发在整机空闲内存 / 提交余量低于阈值时自动降档或排队，并在 `/app-runs/status` 暴露当前生效并发与降档原因（lab 侧已先做了全机槽位兜底：默认 3、空闲内存 <4GB 降到 1，但 lab 看不到猪猪自己拉起的浏览器）。
4. **Z-MEM-4 浏览器 OOM 可诊断**：headless 会话因浏览器崩溃终止时，session 结果给出明确的 `failureClass`（如 `browser-oom`），而不是一般性的 error——便于调用方区分「用例红」与「机器扛不住」。

## lab 侧已做（供对齐）

- 全机 headless 槽位（跨会话统一发号，默认 3，空闲物理内存 <4GB 降到 1；单项超时从真正开跑算起）。
- 引擎非正常退出后自动接回被打断的守航会话（每条最多 2 次）。
