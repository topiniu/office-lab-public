# 三方会审 · 开工前设计与实现会商（新功能版硬门禁 · 不碰代码）

> **是什么**：升级自业内 3 Amigos（George Dinwiddie / BDD / Specification by Example）——需求**开工前**，把 GG Bond（技术）、迷糊（测试）和菲菲（需求）拉到一起，**详细聊清「这个需求打算怎么设计、技术上打算怎么实现、怎么验」**，在写代码之前把设计与实现对齐。
> **为什么升级（从「各审一遍交清单」到「详细聊设计与实现」）**：旧口径是 review-only——两位各审菲菲草稿、各交一张问题清单、看不到彼此。实践发现光挑漏洞不够：新功能的技术实现路径、测试设计口径需要**三方真讨论、往返对齐**，否则菲菲一个人闭门想不清（v5.15 主线「工艺单导出」有 Excel 嵌图选型、字段是否存在、生成链路等真实技术未知数，恰是上一版会审挑出推迟来的——这类需求必须技术+测试一起会商）。所以：**开发要聊实现思路/技术选型/技术未知数，测试要聊测试设计/可测性/边界**，不再只是交一张清单。
> **仍然不做的（边界守死）**：会商是**开工前的设计对齐、不是开工**——开发**不建分支、不碰代码、不写正式《技术需求确认文档》**；测试**不写用例、不碰猪猪**。需求还没拍板，落正式方案/代码/用例会污染、且拍板后口径可能变。正式产物都在派工后。
> **机制说明**：office-lab 是方案 B 顺序交接，没有"三人同步圆桌"——**因为跨员工交接必须走 office-lab dispatch**（`app/hooks/block-employee-subagent.mjs` 只拦「用 `subagent_type=<员工>` 把别人的活嵌套进自己 run」，那样看板看不到、对方状态不亮）。
> ⚠ 2026-09-08 更正：这句原先写的是「一个 run 里 spawn 子代理被 hook 硬堵」——**那是把另一码事误当成了本机制的约束**。员工在自己那段活里 spawn `Explore`/`general-purpose` 子代理是**明确放行**的；当时真正拦下菲菲那 4 个子代理的是 DesktopTool 装在**用户级** `~/.claude/settings.json` 的 `itkb_gate.py`（CJ 开发坐席的「先查 it-kb」闸门，office-lab 无声继承），已于同日改成「office-lab 只提醒不阻断 + 材料阅读直接豁免」。**别再把"子代理用不了"当既定事实写进 SOP**——那次她正是因此没重试、改用降级读法交付，整版返工（复盘 §3.122）。工具被拦要么重试、要么换法、要么如实标降级，不许静默绕过。这里跑的是**异步/多轮版**：菲菲发冻结草稿 → 两位各在自己 run 读同一份文档、把设计/测试会商意见 `【交回】` 菲菲 → 有分歧或新盲区再往返一轮（可用 `cc_colleague` 让两方并行深聊，菲菲不停等）→ 收敛到三方对设计与实现对齐。看不到彼此实时发言，但多轮往返足以对齐。

## 什么时候用（★硬门禁，别当可跳过的软门禁）

卡在「**①.5 业务澄清（老板第一次介入）之后、② 会审结果拍板（老板第二次介入）之前**」——即菲菲的《需求说明》**已与老板聊清业务待澄清、业务口径已定稿、需求快照已冻结**之后跑。**为什么在业务澄清之后**：会审要在**清晰、不再变的需求**上评估设计与实现；带着没定的业务口径去会审，老板一改口径评估就作废（v5.14「会审刚回范围就被重塑、拍板碎成 5+ 轮」、v5.15 隐患的共同根因）。**两个介入点不合并**：业务该不该做由老板在 ①.5 先定，技术怎么做/能不能验的口径由会审暴露后老板在 ② 再定——旧的「合并成一次拍板省一轮」口径已废，压成一次反而必返工。（对应 SOP：`roles/feifei.md` §①.5/§①-plus/§②、`roles/ggbond.md`/`roles/mihu-teacher.md` §①-pre）

- **新功能 / 需求增强版（次版本位及以上）→ 必跑。** 不跑不算过 ①-plus，不得进拍板/派工。**不因「从聊天里起草版本」「PM 自己读代码查过了」「赶时间」而跳过**（聊天起草不豁免门禁，同「聊天起草也要先立卡」一个道理）。
- **插单 / 急修 / 纯修复版（补丁位）→ 可豁免**，但必须在任务档案时间线**显式写明「本版豁免会审 + 理由」**，不许静默省略。
- **降频也要显式**：连跑几版会审几乎挑不出设计/实现层面的东西（上游已够扎实），可降频，但在时间线写明「本版降频/略过 + 判据」。

> **前置门（必做）：①.5 已完成——需求已与老板聊清 + 冻结。** 发起会审的硬前提是业务待澄清全部有老板结论、业务口径定稿、需求快照已冻结（冻结门正文在菲菲 SOP §①.5）；冻结后到会审结束**不接业务方新的口径变更**（新增/改口径进下一轮或下一版）。**需求还带着业务待澄清就不许开会审**——否则会在还会变的需求上评估设计（v5.14「会审刚回、范围就被重塑、评估作废、拍板碎成多轮」实证）。**先澄清、后冻结、再会审，才是「少返工」的真解。**

## 怎么用（两种发起方式）

- **方式 A · 让菲菲发起**：在菲菲的 run 里对她说「按 `templates/三方会审-开工前体检.md` 走一轮开工前会审」。她依次发下面两段 `【下一棒】`（先 GG Bond、收到 `【交回】` 后再迷糊，或反之），收齐两方会商意见、往返到对齐，折进「待确认事项」，交回你拍板。
- **方式 B · 你手动派**：直接把下面两段贴进看板派给 GG Bond / 迷糊。各自 `【交回】` 的意见你转给菲菲汇总。

发起前把 `<需求文档路径>` 替换成本版《需求说明与验收标准》的实际路径。

## 派工文案（设计与实现会商，非 review-only）

### ① 派 GG Bond —— 技术设计与可行性会商
```text
【下一棒】GG Bond｜开工前技术会商，别开发、别建分支、别写正式技术方案文档、别改任何代码。
读 <需求文档路径>，和我详细聊清每条需求「打算怎么实现」：
① 实现思路 / 技术选型 / 链路方案——这条大概怎么做？关键技术选择有哪些、各自代价？
② 每条 N.2「数据来源」——(a) 这个数据我能不能真拿到（哪个系统/有没有现成接口或表/是否需要新建）？
   (b) 拿到的格式能不能程序化解析（附件是不是 OLE2 二进制 .xls / 扫描件 / 矢量轮廓 PDF 这类机读不出、需人工转写的）？
   拿不到、来源不明、或格式读不出的，逐个点名。
③ 技术未知数与成本权衡：哪条做不到 / 成本高到要重新权衡口径？哪条有隐藏大件风险（工作量可能主导整版）？
④ 我要动手但文档里还缺的信息（依赖、前置、口径盲区），列出来。
把上述设计意见 + 未知数清单【交回】菲菲；若我再往返一轮，继续聊到设计对齐。
※ 边界：可以聊实现方案与技术选型（这是你的价值），但不建分支、不碰代码、不落正式《技术需求确认文档》——那在拍板后正式开发第 ① 步。
※ 代码定位声明：凡涉及「根因在某文件/某组件/某行」的结论，一律标【假设·待验】——
  会商阶段没跑验证，实施第一步须先验证靶心再动手，别当既定事实写进 facet / 交接卡。
```

### ② 派迷糊 —— 测试设计与可测性会商
```text
【下一棒】迷糊｜开工前测试会商，别写测试用例、别碰猪猪。
读 <需求文档路径> 的验收标准（facet 表），和我详细聊清每条需求「打算怎么验」：
① 这条 facet 我打算怎么断言？能不能直接写成断言（有明确可观测结果）？
② 哪条是「体验良好 / 正常展示 / 符合预期」这类没法观测、没法断言的？点名，说该怎么改成可断言。
③ 缺哪些边界/异常场景（空数据 / 无权限 / 失败·超时 / 重复提交 / 并发）？
④ 要验这条得造什么数据、什么前置账号/权限/环境？
把测试设计意见 + 可测性清单【交回】菲菲；若我再往返一轮，继续聊到可测性对齐。
※ 边界：只聊测试设计与可测性，不落用例文档、不碰猪猪——那在拍板、派测之后。
```

## 菲菲收到两方会商意见后

1. 把开发、测试聊出的每一条（设计取舍 / 实现约束 / 可测性缺口），折进《需求说明与验收标准》第五节「待确认事项」（标注来源：技术会商 / 测试会商）。
2. 若三方在设计/实现上有分歧、或聊出新的口径盲区，**再往返一轮**（可 `cc_colleague` 让两方并行深聊，你不停等），直到「怎么设计、怎么实现、怎么验」三方对齐、无悬空未知数。
3. 对每条待确认给拟定口径 + 利弊，用 `decision`/`multiselect` 卡交回**用户拍板**（不自己定）——这就是 **② 会审结果拍板（老板第二次介入）**，只拍会审新暴露的设计/实现/可测性口径，**不把 ①.5 已定的业务口径拿回来重拍**。
4. 拍板结论回写文档与 N.2/N.4 对应处；**假设**转为**已知+来源**，**缺口**补齐；`【假设·待验】` 的代码定位类结论**不写死进 facet/交接卡**，留给 GG Bond 实施第一步验证靶心。**你仍不把实现细节写进《需求说明》**：实现设计留在会审记录里、喂给 GG Bond 派工后的技术确认文档；你的文档只吸收「设计/实现暴露出的业务口径/范围/facet 变化」。
5. **会审全过程记录默认落档**（不等用户开口）：把两段派工文案 + 两方会商意见 + 往返轮次 + 折入待确认的结论，整理进 `docs/示例项目需求/<版本>/三方会审记录.md`，供日后复盘。
6. 全部阻塞项有结论后，才走正式 `HANDOFF_TO_DEV`。

> 跑完这一轮，正式开发交接里"数据来源""facet 可测性""实现路径误判"三类返工应显著减少。判断是否降频（补丁版）＝会商还聊不聊得出设计/实现层面的新东西；但**新功能版一律必跑**，降频/豁免都要在时间线显式留痕，不许静默跳过。
